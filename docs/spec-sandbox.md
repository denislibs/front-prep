# Песочница и проверка ответов — спецификация

Документ фиксирует контракт между тремя частями работы: наборами тестов (`research/tests-*.js`), исполнителем кода в приложении и редактором.

## 1. Режимы исполнения

| Режим | Где выполняется | Для чего | Задач |
|---|---|---|---|
| `worker` | Web Worker | чистый JS: утилиты, данные, алгоритмы, асинхронность | 37 |
| `dom` | изолированный iframe | делегирование, focus trap, роутер, мини-Redux, VDOM | 8 |
| `react` | тот же iframe + React и ReactDOM | компоненты, хуки | 10 |

Воркер и iframe уничтожаются по таймауту (8 секунд плюс 5 секунд на каждую проверку, но не больше минуты), поэтому бесконечный цикл в коде пользователя не вешает приложение.

JSX транспайлится Sucrase перед исполнением — и в коде пользователя, и в телах тестов.

### Что пришлось учесть в браузере

Три особенности реального окружения, которых нет в Node:

- **Фокус.** Изолированный iframe получает opaque origin, и Chrome запрещает в нём программный `focus()`. Набор, для которого фокус и есть предмет проверки, объявляет `needsFocus: true` — тогда изоляция ослабляется точечно. Платой становится то, что зацикливание именно в такой задаче подвесит вкладку.
- **Кадры.** Скрытому фрейму браузер может не выдавать кадры, и тогда `requestAnimationFrame` не срабатывает вовсе. Внутри песочницы он продублирован таймером, поэтому решения, которые обновляют DOM из rAF, работают.
- **`act` из React.** В песочницу встроена production-сборка, где `act` не поддерживается и бросает исключение. Хелперы это распознают и переходят на ожидание применения рендера. В Node используется development-сборка, где `act` работает штатно.

## 2. Формат набора тестов

Файлы `research/tests-<batch>.js` объявляют один объект, ключ — id задачи:

```js
const TESTS_WORKER_A = {
  tx1: {
    env: 'worker',
    entry: 'deepEqual',
    starter: `function deepEqual(a, b) {
  // ваш код
}`,
    cases: [
      { name: 'считает одинаковыми вложенные структуры',
        body: `assert.equal(deepEqual({ a: [1, { b: 2 }] }, { a: [1, { b: 2 }] }), true);` },
      { name: 'различает разные значения',
        body: `assert.equal(deepEqual({ a: 1 }, { a: 2 }), false);` },
    ],
  },
};
```

Поля:

- `env` — один из режимов выше.
- `entry` — имя, которое обязан объявить пользователь. Если после исполнения кода такого идентификатора нет, все проверки помечаются как непройденные с понятным сообщением, а не падают с `ReferenceError`.
- `starter` — стартовый код в редакторе: сигнатура и комментарий, без решения.
- `cases` — от 4 до 10 проверок. `name` — по-русски, описывает поведение, а не механику (`сохраняет контекст вызова`, а не `apply работает`). `body` — тело функции, исполняется с кодом пользователя в области видимости.

Тела могут быть асинхронными: `await` разрешён, исполнитель всегда оборачивает их в async-функцию.

## 3. API проверок

Доступно во всех режимах:

- `assert.equal(actual, expected, message?)` — глубокое сравнение, отчёт показывает обе стороны.
- `assert.ok(value, message?)`
- `assert.throws(fn, message?)` — синхронное исключение.
- `assert.rejects(promise, message?)`
- `assert.close(actual, expected, epsilon?)` — для чисел с плавающей точкой.
- `sleep(ms)` — пауза.
- `spy()` — возвращает функцию с полями `calls` (массив массивов аргументов), `count`, `lastArgs`, `contexts`.
- `clock` — управление временем: `clock.tick(ms)` продвигает таймеры без реального ожидания. Обязателен в тестах на `debounce`, `throttle`, `retry`, иначе набор выполняется секундами.

Дополнительно в `dom` и `react`:

- `mount(html)` — создаёт фикстуру, возвращает корневой элемент, очищается между проверками.
- `render(element)` — монтирует React-элемент, возвращает контейнер.
- `click(el)`, `type(el, text)`, `press(el, key)` — события, обёрнутые в `act`.
- `getByText(root, text)`, `getByRole(root, role, options?)`, `queryAll(root, selector)`.
- `tick()` — дожидается применения эффектов и перерисовки.

## 4. Правила написания тестов

1. **Каждый набор обязан проходить против эталонного решения из `code`.** Тест, который валит правильный ответ, хуже отсутствия теста. Это проверяется автоматически при сборке.
2. Проверки идут от простого к сложному: первая — базовый happy path, дальше edge cases, последняя — самое каверзное (контекст вызова, отмена, повторный вызов).
3. Названия проверок — это подсказки. Провалившийся тест должен объяснять, что именно не реализовано.
4. Никаких проверок на внутреннюю реализацию: только наблюдаемое поведение.
5. Не полагаться на реальное время — только `clock.tick`.

## 5. Проверка ответов через Claude

На карточке появляется поле свободного ответа. Запрос уходит с вопросом, эталонным ответом карточки (`a` и `tip` без разметки) и текстом пользователя. Ответ возвращается структурой:

```json
{
  "score": 0,
  "verdict": "краткий вердикт одной фразой",
  "correct": ["что названо верно"],
  "missing": ["что упущено из существенного"],
  "wrong": ["где ошибка или неточная формулировка"],
  "phrasing": "как то же самое сформулировал бы сеньор"
}
```

Оценка от 0 до 5. В мок-интервью оценка 4 и выше проставляет карточке статус «знаю», ниже — «на повтор».

Если возможность недоступна (`claude.use('sample')` вернул `null`), блок свободного ответа не отображается, остальное приложение работает без изменений.

## 6. Развёртывание

Приложение остаётся одним самодостаточным HTML-файлом: библиотеки встроены, внешних запросов нет. Это делает его пригодным сразу для двух вариантов — публикации артефактом и выкладывания на GitHub Pages без изменений.
