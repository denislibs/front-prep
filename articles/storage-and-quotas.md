# Хранилища в браузере: что выбрать и сколько влезет

Вопрос «где хранить данные на клиенте» кажется простым, пока приложение маленькое. Потом выясняется, что `localStorage` блокирует главный поток, что браузер может однажды снести все данные пользователя разом, что две вкладки одного приложения дерутся за одну запись, а Safari удаляет всё через семь дней бездействия.

Эта статья — про то, какие хранилища есть, чем они на самом деле отличаются, как устроена IndexedDB (единственное серьёзное из них), сколько места реально даёт браузер и когда он его отбирает. И про то, как несколько вкладок договариваются между собой.

Про главный поток и почему его нельзя блокировать — в статье [как работает браузер](./browser-rendering-event-loop). Про кеширование сетевых ответов — в статье [Service Worker](./service-worker). Про доступ к хранилищам из фонового потока — в статье [Web Worker](./web-workers).

**Cookie** — единственное хранилище, которое браузер сам прикладывает к каждому запросу на домен. Отсюда назначение: то, что нужно серверу. Размер — около 4 КБ на куку, суммарно порядка 50 КБ на домен, и всё это едет по сети **в каждом запросе**, включая картинки. Держать в куках состояние интерфейса — значит платить трафиком за каждый файл. Флаги `HttpOnly` (недоступна из JavaScript), `Secure` (только по HTTPS) и `SameSite` (защита от подделки межсайтовых запросов) делают куку правильным местом для токена сессии — и единственным местом, где токен защищён от кражи через XSS.

**`localStorage`** — синхронное хранилище строк на origin, около 5 МБ, живёт вечно. Подробный разбор проблем — в части 2.

**`sessionStorage`** — то же самое, но своё у каждой вкладки и исчезает при её закрытии. Не разделяется между вкладками вообще: открыли ту же страницу в новой вкладке — там пусто. Это делает его удобным ровно для одного: состояние текущего сеанса работы во вкладке — шаг многошаговой формы, позиция скролла, откуда пользователь пришёл на страницу.

**IndexedDB** — асинхронная база данных с объектными хранилищами, индексами и транзакциями. Единственное хранилище, в котором можно держать серьёзные объёмы структурированных данных. Часть 3.

**Cache Storage** — хранилище пар «запрос — ответ», разобрано в статье про [Service Worker](./service-worker). Доступно и без воркера, прямо со страницы, — это иногда забывают.

**Origin Private File System (OPFS)** — файловая система, приватная для origin. Не то же самое, что File System Access API: пользователь её не видит, диалога выбора файла нет. Даёт настоящие файлы с посегментной записью и, что важнее всего, **синхронный доступ внутри воркера** (`createSyncAccessHandle`). Это единственный способ получить в браузере производительность, близкую к нативной, — на нём работает сборка SQLite для браузера. Обычному приложению не нужен; нужен видеоредакторам, инструментам работы с большими наборами данных и всему, что портирует на веб нативный код через WebAssembly.

Есть ещё исторические варианты, которые встретятся в старом коде: WebSQL (удалён из браузеров), AppCache (удалён), `document.cookie` как хранилище общего назначения (не надо).

## Часть 2. Почему `localStorage` — плохой выбор для данных

Он удобен: две строчки, работает везде. Именно поэтому в него кладут всё подряд. Разберём цену.

### Он синхронный

`localStorage.getItem` не возвращает промис. Значит, чтение с диска происходит **прямо на главном потоке**, и всё это время браузер не делает ничего другого — ни кадров, ни обработки кликов.

```js
// Каждая из этих строк блокирует главный поток на время работы с диском
const raw = localStorage.getItem('cart');       // чтение с диска
const cart = JSON.parse(raw);                   // плюс разбор
localStorage.setItem('cart', JSON.stringify(cart));  // сериализация плюс запись
```

На современных машинах данные обычно уже в памяти и операция быстрая. Но «обычно» — не гарантия: первое обращение после запуска вкладки читает файл с диска, а на медленном диске под нагрузкой это десятки миллисекунд. Хуже другое: **платит не только `localStorage`**, а `JSON.parse` и `JSON.stringify` вокруг него. Мегабайтный объект сериализуется десятки миллисекунд, и делается это синхронно.

Отсюда антипаттерн, который встречается в каждом втором проекте: хранилище состояния (Redux, Zustand, Pinia) целиком пишется в `localStorage` на каждое изменение. Каждое нажатие клавиши в форме превращается в сериализацию всего состояния приложения.

Если уж пишете туда — делайте это отложенно и только изменившуюся часть:

```js
// Не сериализуем всё на каждое действие; пишем не чаще раза в 500 мс
let pending = null;
let timer = null;

export function persist(key, value) {
  pending = value;
  if (timer) return;
  timer = setTimeout(() => {
    timer = null;
    try {
      localStorage.setItem(key, JSON.stringify(pending));
    } catch (err) {
      // QuotaExceededError или приватный режим — не роняем приложение
      if (err.name !== 'QuotaExceededError') throw err;
      console.warn('в localStorage не влезло, переходим на IndexedDB');
    }
    pending = null;
  }, 500);
}

// Отложенная запись рискует не успеть при уходе со страницы
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden' && pending !== null) {
    localStorage.setItem(/* ... */);
  }
});
```

Обработчик `visibilitychange` тут не украшение: `beforeunload` на мобильных срабатывает ненадёжно, а «скрытие» страницы — последний гарантированный момент для сохранения.

### Только строки

Всё превращается в строку. Числа, даты, `Map`, `undefined` — всё нужно сериализовать самому, обычно через JSON, а JSON теряет типы: дата станет строкой, `undefined` исчезнет, `NaN` превратится в `null`. Для сравнения, IndexedDB хранит значения структурным клонированием — дата остаётся датой, `Map` остаётся `Map` (об этом алгоритме — в статье про [Web Worker](./web-workers)).

### Около пяти мегабайт — и они кончаются молча

Лимит примерно 5 МБ на origin, причём считается в единицах UTF-16, то есть кириллический текст занимает вдвое больше байт, чем кажется. При переполнении `setItem` бросает `QuotaExceededError`. Если вы не оборачивали запись в `try`, приложение упадёт — и упадёт не там, где проблема, а в случайном месте.

### Недоступен из воркеров

`localStorage` синхронный, а синхронные хранилища в воркерах запрещены. Значит, данные, лежащие там, невидимы для [Service Worker](./service-worker) и обычных воркеров. Это отдельная причина не строить на нём ничего серьёзного.

### Когда он всё-таки уместен

Мало данных, они нужны **синхронно на старте**, и задержка недопустима. Классика — выбранная тема оформления: её надо применить до первой отрисовки, иначе пользователь увидит вспышку белого фона. Асинхронное чтение здесь проигрывает по определению.

```html
<script>
  // Встроенный скрипт до стилей: единственный законный случай синхронного чтения
  try {
    document.documentElement.dataset.theme = localStorage.getItem('theme') || 'light';
  } catch {}
</script>
```

Заворачивать в `try` обязательно: в приватном режиме и при отключённых хранилищах само обращение к `localStorage` бросает исключение.

## Часть 3. IndexedDB

### Модель данных

**База** принадлежит origin и имеет имя и целочисленную версию.

**Объектное хранилище** (object store) — аналог таблицы, но без схемы: в нём лежат произвольные значения, сохранённые структурным клонированием.

**Ключ** — по чему ищем. Три варианта:

- **встроенный** (`keyPath`) — поле самого объекта: `{ keyPath: 'id' }`;
- **автоинкремент** — база сама выдаёт номера: `{ autoIncrement: true }`;
- **внешний** — ключ передаётся отдельным аргументом при записи.

Ключами могут быть числа, строки, даты, массивы и типизированные массивы. Массив как ключ — способ сделать составной ключ: `['userId', 'createdAt']`.

**Индекс** — дополнительный способ поиска по полю значения. Без индекса поиск по не-ключевому полю означает перебор всего хранилища.

**Транзакция** — область, в которой происходят все операции. Она атомарна: либо применились все изменения, либо ни одного.

### Открытие и миграции

```js
function openDb() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open('app-db', 3);

    // Вызывается, только если версия в коде больше версии на диске.
    // Единственное место, где можно менять схему.
    request.onupgradeneeded = (event) => {
      const db = request.result;
      const tx = request.transaction;   // особая транзакция versionchange
      const from = event.oldVersion;    // 0 у нового пользователя

      // Миграции идут по нарастающей, без break — новичок пройдёт все шаги
      if (from < 1) {
        const notes = db.createObjectStore('notes', { keyPath: 'id' });
        notes.createIndex('by-updated', 'updatedAt');
      }
      if (from < 2) {
        db.createObjectStore('drafts', { keyPath: 'id', autoIncrement: true });
      }
      if (from < 3) {
        // Добавление индекса к существующему хранилищу — только через транзакцию апгрейда
        const notes = tx.objectStore('notes');
        notes.createIndex('by-folder-updated', ['folderId', 'updatedAt']);
      }
    };

    request.onsuccess = () => {
      const db = request.result;
      // Другая вкладка запросила новую версию — закрываемся, чтобы её не блокировать
      db.onversionchange = () => {
        db.close();
        location.reload();
      };
      resolve(db);
    };

    request.onerror = () => reject(request.error);

    // Открытие висит: другая вкладка держит старую версию открытой
    request.onblocked = () => console.warn('закройте другие вкладки приложения');
  });
}
```

Три вещи, которые обязательно спросят.

**Схема меняется только в `upgradeneeded`.** Создать хранилище или индекс в обычной транзакции нельзя. Значит, любое изменение структуры — это подъём версии и релиз.

**Миграции пишутся каскадом.** Пользователь мог не заходить полгода и приехать с версией 1 на версию 5. Проверки `if (from < N)` подряд, без `else`, проведут его через все шаги.

**`blocked` и `versionchange` — не экзотика.** Пользователь держит приложение открытым в трёх вкладках. Вы выкатили релиз, он обновил одну — она хочет версию 4, а две другие держат версию 3. Открытие заблокируется навсегда, если старые вкладки не закроют соединение. Обработчик `onversionchange` — обязательная часть, а не приятное дополнение.

Понижать версию нельзя: попытка открыть базу с версией меньше существующей завершается ошибкой. Соответственно, откат релиза назад ломает приложение у тех, кто успел мигрировать, — это надо учитывать в плане выката.

### Транзакции и почему они «умирают»

Транзакция создаётся с указанием хранилищ и режима:

```js
const tx = db.transaction(['notes', 'drafts'], 'readwrite');
const notes = tx.objectStore('notes');
notes.put({ id: 'n1', text: 'привет', updatedAt: Date.now() });
```

Ключевое свойство, из-за которого ломается больше всего кода: **транзакция автоматически закрывается, когда очередь микрозадач опустела, а новых запросов в ней не появилось**. Не по таймеру, не по вызову метода — именно так. Механику микрозадач разбираем в статье [как работает браузер](./browser-rendering-event-loop).

Отсюда знаменитая ловушка:

```js
// Ломается: TransactionInactiveError
const tx = db.transaction('notes', 'readwrite');
const store = tx.objectStore('notes');

const user = await fetch('/api/me').then((r) => r.json());  // ждём СЕТЬ
store.put({ id: user.id, name: user.name });                // транзакция уже мертва
```

`await` на сетевом запросе отдаёт управление, очередь микрозадач опустошается, транзакция закрывается сама. Когда ответ приходит, класть уже некуда.

А это работает:

```js
const user = await fetch('/api/me').then((r) => r.json());  // сначала всё внешнее

const tx = db.transaction('notes', 'readwrite');            // потом транзакция
tx.objectStore('notes').put({ id: user.id, name: user.name });
await new Promise((resolve, reject) => {
  tx.oncomplete = resolve;
  tx.onerror = () => reject(tx.error);
});
```

Правило формулируется просто: **внутри транзакции ждать можно только запросы к самой IndexedDB**. Всё остальное — сеть, `crypto.subtle`, таймеры, чтение файла — делается до открытия транзакции или после её завершения.

Отдельная тонкость: `await` на промисе от библиотеки-обёртки внутри транзакции обычно безопасен, потому что обёртка не выходит за пределы микрозадач. Но `await` на `Promise.resolve()` в некоторых браузерах уже достаточен, чтобы транзакция успела закрыться. Не рискуйте.

Ещё два свойства транзакций:

**Режимы.** `readonly` — несколько таких транзакций на одном хранилище идут параллельно. `readwrite` — эксклюзивна для своих хранилищ: другие транзакции ждут. Указывать `readwrite` там, где нужно только чтение, — способ на ровном месте выстроить очередь.

**Порядок.** Транзакции на пересекающихся хранилищах выполняются в порядке создания. Создали `readwrite` и не завершили — все следующие ждут её.

### Чтение и запись

```js
function toPromise(request) {
  return new Promise((resolve, reject) => {
    request.onsuccess = () => resolve(request.result);
    request.onerror = () => reject(request.error);
  });
}

// Точечное чтение по ключу
const note = await toPromise(
  db.transaction('notes').objectStore('notes').get('n1')
);

// Поиск по индексу: все заметки папки, отсортированные по времени
const range = IDBKeyRange.bound(
  ['folder-1', 0],
  ['folder-1', Number.MAX_SAFE_INTEGER]
);
const list = await toPromise(
  db.transaction('notes').objectStore('notes')
    .index('by-folder-updated').getAll(range)
);
```

`IDBKeyRange` — диапазон ключей: `only`, `bound`, `lowerBound`, `upperBound`, с флагами исключения границ. С составным индексом из части выше это даёт полноценную выборку «по папке, отсортировано по дате» без единого перебора.

`put` перезаписывает запись с тем же ключом, `add` бросает ошибку, если ключ занят. Разница важна для идемпотентной синхронизации: `put` можно повторять безопасно.

### Курсоры

`getAll` удобен, но кладёт результат в память целиком. На больших выборках это либо пик потребления памяти, либо длинная задача. Курсор идёт по записям по одной:

```js
// Суммируем размер вложений, не поднимая в память все записи
async function totalSize(db, folderId) {
  const tx = db.transaction('notes');
  const index = tx.objectStore('notes').index('by-folder-updated');
  const range = IDBKeyRange.bound([folderId, 0], [folderId, Infinity]);

  let total = 0;
  await new Promise((resolve, reject) => {
    const request = index.openCursor(range);
    request.onsuccess = () => {
      const cursor = request.result;
      if (!cursor) return resolve();   // записи кончились
      total += cursor.value.size || 0;
      cursor.continue();               // следующая запись — тот же onsuccess
    };
    request.onerror = () => reject(request.error);
  });
  return total;
}
```

Устройство неочевидное: один запрос, но `onsuccess` вызывается многократно — по разу на запись, после каждого `cursor.continue()`. Пока идёт этот цикл, транзакция жива, потому что запросы в ней не иссякают.

Полезные приёмы с курсорами:

- `openKeyCursor` — идти только по ключам, не поднимая значения. Дешевле, когда нужны идентификаторы.
- `cursor.advance(n)` — пропустить n записей. Так делают пагинацию, хотя для больших смещений это дорого; лучше запоминать последний ключ и открывать курсор от него.
- `cursor.delete()` и `cursor.update(value)` — изменить текущую запись, не открывая отдельный запрос.
- Второй аргумент `openCursor(range, 'prev')` — обход в обратном порядке. Так берут последние N записей.

### Почему сырая IndexedDB неудобна

Событийный API старше промисов: `onsuccess`, `onerror`, ручные обёртки. Код разбухает, ошибки теряются, транзакции закрываются в неожиданных местах.

Обёртки решают это по-разному:

**`idb`** (около 1 КБ) — тонкий слой промисов над тем же API. Понятия те же, синтаксис человеческий, поведение транзакций сохранено. Хороший выбор по умолчанию.

```js
import { openDB } from 'idb';

const db = await openDB('app-db', 3, {
  upgrade(db, oldVersion, newVersion, tx) {
    if (oldVersion < 1) db.createObjectStore('notes', { keyPath: 'id' });
  },
  blocked() { showToast('Закройте другие вкладки приложения'); },
  blocking() { db.close(); location.reload(); },
});

await db.put('notes', { id: 'n1', text: 'привет' });
const note = await db.get('notes', 'n1');
```

**Dexie** (около 25 КБ) — полноценная обёртка со своим языком запросов, декларативными миграциями, «живыми» запросами, которые сами перевычисляются при изменении данных. Берут, когда IndexedDB — основа приложения, а не побочное хранилище.

Цена обёрток одинаковая: размер бандла и ещё одна абстракция, чьи протечки придётся отлаживать. Выигрыш — код, который читается и не разваливается на транзакциях.

### Сколько дают

Точных цифр нет — квота вычисляется динамически. Ориентиры:

- **Chrome и родственники**: до 60% свободного места на диске на весь профиль, отдельному origin — примерно такой же потолок. На ноутбуке со 100 ГБ свободного места это десятки гигабайт. Раньше был лимит на группу сайтов (eTLD+1), сейчас счёт идёт по origin.
- **Firefox**: до 50% свободного места на группу сайтов, при этом отдельный origin ограничен 10 ГБ.
- **Safari**: исторически спрашивал разрешение после 750 МБ, сейчас даёт примерно до 60% диска — но с важными оговорками про удаление, см. ниже.

`localStorage` в эту квоту не входит: у него свои жёсткие 5 МБ.

### Как спросить

```js
async function reportStorage() {
  if (!navigator.storage?.estimate) return null;

  const { usage, quota, usageDetails } = await navigator.storage.estimate();
  const percent = ((usage / quota) * 100).toFixed(1);

  console.log(`занято ${(usage / 1e6).toFixed(1)} МБ из ${(quota / 1e6).toFixed(0)} МБ (${percent}%)`);
  // usageDetails есть не везде, но в Chrome показывает разбивку по хранилищам
  console.log(usageDetails);   // { indexedDB, caches, serviceWorkerRegistrations }

  return { usage, quota, percent: Number(percent) };
}
```

Цифры округлены намеренно — точное значение было бы способом опознать пользователя. Полагаться на них как на точные нельзя, как на ориентир — можно.

Разумная практика: перед большой записью проверять запас и заранее чистить своё. Ждать `QuotaExceededError` посреди транзакции — плохой сценарий: транзакция откатится целиком, и пользователь потеряет работу.

```js
async function ensureRoom(bytesNeeded) {
  const { usage, quota } = await navigator.storage.estimate();
  if (quota - usage > bytesNeeded * 1.5) return true;
  await evictOldCachedItems();          // чистим своё: старые кеши, вложения
  const after = await navigator.storage.estimate();
  return after.quota - after.usage > bytesNeeded;
}
```

### Устойчивое хранилище

По умолчанию данные считаются **лучшими из возможных** (best-effort): когда диску тесно, браузер выселяет данные редко посещаемых сайтов, чтобы освободить место. Выселение идёт **по origin целиком** — вместе исчезают IndexedDB, Cache Storage, localStorage и регистрация Service Worker. Частичного удаления не бывает.

```js
async function requestPersistence() {
  if (!navigator.storage?.persist) return false;

  if (await navigator.storage.persisted()) return true;

  // Просить стоит после того, как пользователь вложился в приложение:
  // создал документ, добавил данные. Тогда шанс получить «да» выше.
  const granted = await navigator.storage.persist();
  return granted;
}
```

Как браузеры отвечают:

- **Chrome** решает молча, по эвристикам: установлено ли приложение как PWA, разрешены ли уведомления, высок ли «уровень вовлечённости» сайта. Диалога пользователь не увидит.
- **Firefox** показывает запрос разрешения.
- **Safari** выдаёт устойчивость автоматически сайтам, добавленным на домашний экран, а API `persist` возвращает результат без диалога.

Что даёт `persisted: true`: данные не выселяются автоматически. Удалить их может только пользователь — через настройки браузера или очистку данных сайта.

Чего не даёт: бесконечной квоты. `QuotaExceededError` при переполнении никуда не денется.

### Политики Safari

Отдельная тема, о которую разбивается много офлайн-приложений. Intelligent Tracking Prevention в Safari удаляет **все** записываемые скриптом хранилища сайта, если пользователь не заходил на него **семь дней**. Под удаление попадают IndexedDB, Cache Storage, localStorage, куки, поставленные из JavaScript.

Что не удаляется: куки, установленные сервером заголовком `Set-Cookie` (для них правило мягче), и данные сайтов, добавленных на домашний экран.

Практические следствия:

1. **Клиентское хранилище в Safari — это кеш, а не архив.** Всё, что пользователь создал и не потеряет без боли, должно уезжать на сервер.
2. Приватный режим Safari отдельно урезает всё: Service Worker недоступен, IndexedDB работает в памяти и исчезает с закрытием вкладки, `localStorage` может бросать при записи.
3. Проверять доступность нужно кодом, а не по строке `userAgent`.

```js
async function storageAvailable() {
  try {
    const db = await openDb();      // IndexedDB в приватном Safari может отказать
    db.close();
    return true;
  } catch {
    return false;                   // работаем в памяти, предупреждаем пользователя
  }
}
```

## Часть 5. Что нельзя хранить на клиенте

Любое браузерное хранилище доступно JavaScript, работающему на странице. Значит, при XSS атакующий получает всё, что там лежит. Из этого:

**Токены доступа лучше держать в куке с `HttpOnly`.** Такая кука недоступна из JavaScript вообще, и украсть её через XSS нельзя. `localStorage` с токеном — популярная, но заведомо худшая схема: скрипт злоумышленника заберёт токен одной строкой. Куку дополняют `Secure`, `SameSite=Lax` или `Strict` и защитой от CSRF.

**Персональные данные — только по необходимости и с осознанным сроком жизни.** Если приложение показывает медицинские или платёжные данные, кешировать их «на всякий случай» — это создать копию на устройстве, которое могут потерять.

**Шифрование на клиенте не решает проблему, если ключ тоже на клиенте.** Зашифровали `crypto.subtle` и положили ключ рядом в IndexedDB — атакующий возьмёт оба. Схема имеет смысл, только когда ключ выводится из того, чего нет на устройстве: пароля, который пользователь вводит каждый раз, или ключа с сервера, живущего в памяти.

```js
// Ключ выводится из пароля пользователя и нигде не сохраняется
async function deriveKey(password, salt) {
  const material = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(password), 'PBKDF2', false, ['deriveKey']
  );
  return crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 250_000, hash: 'SHA-256' },
    material,
    { name: 'AES-GCM', length: 256 },
    false,                            // extractable: false — ключ нельзя выгрузить
    ['encrypt', 'decrypt']
  );
}
```

`CryptoKey` с `extractable: false` можно хранить прямо в IndexedDB: структурное клонирование его поддерживает, а вытащить сырые байты не получится даже своему коду. Это заметно лучше, чем хранить ключ строкой.

При выходе пользователя из аккаунта хранилища надо чистить явно — данные не исчезают сами:

```js
async function wipeLocalData() {
  for (const name of await caches.keys()) await caches.delete(name);
  const dbs = await indexedDB.databases?.() ?? [];
  for (const { name } of dbs) indexedDB.deleteDatabase(name);
  localStorage.clear();
  sessionStorage.clear();
}
```

## Часть 6. Согласованность между вкладками

Пользователь открыл приложение в трёх вкладках. В одной вышел из аккаунта — две другие продолжают показывать данные. В одной изменил заметку — две другие показывают старую. Хранилище общее, а состояние в памяти у каждой вкладки своё.

### `storage`-событие

Старый механизм: при изменении `localStorage` все **другие** вкладки того же origin получают событие.

```js
window.addEventListener('storage', (event) => {
  if (event.key === 'auth') {
    if (event.newValue === null) redirectToLogin();
  }
});
```

Особенности, из-за которых его часто применяют неправильно:

- Во вкладке, которая **сделала** изменение, событие не приходит. Свою реакцию вызывайте вручную.
- `event.key` равен `null` при `localStorage.clear()`.
- Событие даёт `oldValue` и `newValue` — уже строки, разбирать самому.
- Работает только с `localStorage` и `sessionStorage`, то есть тянет за собой все их недостатки.

Приём, который встречается в коде: писать в `localStorage` фиктивный ключ только ради оповещения других вкладок. Работает, но сегодня для этого есть нормальный инструмент.

### `BroadcastChannel`

Именованный канал сообщений между всеми контекстами одного origin — вкладками, iframe и воркерами, включая Service Worker.

```js
const channel = new BroadcastChannel('app-sync');

// Отправка. Данные проходят структурным клонированием — как в postMessage
channel.postMessage({ type: 'note-updated', id: 'n1', updatedAt: Date.now() });

channel.addEventListener('message', (event) => {
  const msg = event.data;
  if (msg.type === 'note-updated') store.invalidate(msg.id);
  if (msg.type === 'logged-out') location.assign('/login');
});

// Закрывать при размонтировании: канал держит ссылки на обработчики
// channel.close();
```

Отправитель своё сообщение не получает — как и в случае `storage`.

Практичный шаблон: **в канал шлём не данные, а уведомление об изменении**. Источником истины остаётся IndexedDB, а вкладки по сигналу перечитывают нужную запись. Так не бывает расхождений из-за порядка доставки сообщений, и не приходится гонять по каналу объёмные структуры.

### Web Locks

`BroadcastChannel` решает оповещение, но не решает вопрос «кто из вкладок делает работу». Синхронизация с сервером, запущенная из пяти вкладок одновременно, — это пять параллельных наборов запросов и гонки при записи.

```js
async function syncOnce() {
  // Пока держим блокировку, другие вкладки с тем же именем ждут своей очереди
  await navigator.locks.request('sync-notes', async (lock) => {
    const changes = await collectLocalChanges();
    await pushToServer(changes);
    await pullFromServer();
  });
  // Блокировка снимается автоматически, когда промис разрешился —
  // и при закрытии вкладки тоже, даже аварийном
}
```

Режимы и опции, которые пригодятся:

```js
// Не ждать очереди: если занято — просто выходим
await navigator.locks.request('sync-notes', { ifAvailable: true }, async (lock) => {
  if (!lock) return;      // кто-то уже синхронизируется, второй раз не надо
  await doSync();
});

// Разделяемая блокировка: много читателей, один писатель
await navigator.locks.request('db', { mode: 'shared' }, readData);
await navigator.locks.request('db', { mode: 'exclusive' }, writeData);

// Отмена ожидания по сигналу
const ac = new AbortController();
setTimeout(() => ac.abort(), 5000);
await navigator.locks.request('sync-notes', { signal: ac.signal }, doSync);
```

Главное достоинство — **блокировка снимается сама**, когда вкладка закрылась или упала. Самодельная блокировка через флаг в `localStorage` этого не умеет: закрыли вкладку в неудачный момент — флаг остался, и приложение заблокировано навсегда, пока пользователь не почистит данные.

Типичный набор для приложения с офлайном выглядит так: данные в IndexedDB, ответы сети в Cache Storage, оповещения через `BroadcastChannel`, единственность фоновой работы через Web Locks, а сама фоновая работа — в [Service Worker](./service-worker) или [Web Worker](./web-workers).

## Что спросят на интервью

**Чем `localStorage` плох для данных?** Синхронный — блокирует главный поток вместе с окружающими его `JSON.parse` и `JSON.stringify`; хранит только строки; около 5 МБ и `QuotaExceededError` при переполнении; недоступен из воркеров.

**Когда `localStorage` уместен?** Пара килобайт, нужных синхронно до первой отрисовки: тема оформления, язык. Обязательно в `try` — в приватном режиме обращение может бросить.

**Чем `sessionStorage` отличается от `localStorage`?** Своё у каждой вкладки, исчезает с её закрытием, между вкладками не разделяется.

**Что такое объектное хранилище, индекс и транзакция в IndexedDB?** Хранилище — набор значений с ключами, без схемы. Индекс — дополнительный порядок для поиска по полю значения. Транзакция — атомарная область операций, `readonly` или `readwrite`.

**Почему транзакция «умирает» при `await`?** Она закрывается автоматически, когда очередь микрозадач опустела и новых запросов в ней нет. `await` на сети или таймере отдаёт управление, транзакция закрывается, дальнейшие операции дают `TransactionInactiveError`. Внутри транзакции ждать можно только запросы к самой базе.

**Как делать миграции?** В `onupgradeneeded`, каскадом проверок `if (oldVersion < N)` без `else`, чтобы пользователь со старой версией прошёл все шаги. Обязательно обработать `blocked` и `versionchange`, иначе открытая старая вкладка заблокирует апгрейд.

**Зачем курсор, если есть `getAll`?** `getAll` поднимает всю выборку в память. Курсор идёт по записям по одной, позволяет обновлять и удалять на месте и не даёт пика памяти.

**Сколько места даёт браузер?** Динамически: в Chrome примерно до 60% свободного места на диске, в Firefox до 50% на группу сайтов и не более 10 ГБ на origin. Узнать — `navigator.storage.estimate()`, цифры округлены ради приватности.

**Что такое устойчивое хранилище?** `navigator.storage.persist()` — просьба не выселять данные автоматически. Chrome решает по эвристикам молча, Firefox спрашивает пользователя. Квоту не увеличивает.

**Как браузер выселяет данные?** Целиком по origin: разом уходят IndexedDB, Cache Storage, localStorage и регистрация Service Worker. Частичного удаления не бывает.

**Что особенного в Safari?** ITP удаляет записанные скриптом хранилища после семи дней без визитов. В приватном режиме Service Worker недоступен, IndexedDB живёт в памяти. Вывод: клиентское хранилище — кеш, а не архив.

**Где хранить токен?** В куке с `HttpOnly`, `Secure`, `SameSite`. В `localStorage` его заберут одной строкой при XSS.

**Как синхронизировать вкладки?** `BroadcastChannel` для оповещений, `storage`-событие как устаревший вариант. Полезный шаблон — слать уведомление об изменении, а данные перечитывать из IndexedDB.

**Зачем Web Locks?** Чтобы фоновую работу делала ровно одна вкладка. Блокировка снимается автоматически при закрытии вкладки — самодельный флаг в `localStorage` так не умеет и может залипнуть навсегда.

## Коротко, для повторения

1. Cookie — для сервера, едет в каждом запросе, 4 КБ. `sessionStorage` — на одну вкладку. `localStorage` — пара килобайт настроек. Cache Storage — ответы сети. IndexedDB — всё остальное. OPFS — гигабайты и почти нативная скорость в воркере.
2. `localStorage` синхронный, строковый, около 5 МБ и невидим для воркеров. Не место для состояния приложения.
3. IndexedDB — асинхронная, хранит значения структурным клонированием, умеет индексы, диапазоны ключей и составные ключи.
4. Схема меняется только в `onupgradeneeded`. Миграции — каскадом. Обрабатывайте `blocked` и `versionchange`, иначе апгрейд заблокируется другой вкладкой.
5. Транзакция закрывается сама, когда микрозадачи кончились. Внутри неё ждать можно только запросы к самой базе.
6. Курсор вместо `getAll`, когда выборка большая: нет пика памяти, можно менять и удалять на месте.
7. Сырой API событийный и неудобный — берите `idb` для тонкой обёртки или Dexie, когда база в основе приложения.
8. Квота считается динамически, порядка половины свободного диска. Спрашивайте `navigator.storage.estimate()` и чистите своё заранее, не дожидаясь `QuotaExceededError`.
9. `persist()` защищает от автоматического выселения, но не увеличивает квоту. Выселение идёт по origin целиком.
10. Safari удаляет клиентские хранилища после семи дней бездействия. Считайте их кешем: источник истины — сервер.
11. Токены — в куке `HttpOnly`. Шифрование на клиенте помогает, только если ключ не лежит рядом.
12. Между вкладками: `BroadcastChannel` для сигналов, Web Locks для единственности фоновой работы.
