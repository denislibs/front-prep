# Промисы изнутри

Промис умеют использовать все. Объяснить, почему `.catch` в середине цепочки её не обрывает, а продолжает — почти никто. Эта статья про механику: что за объект создаётся, какие у него состояния, что именно возвращает `.then` и почему из этого растут все правила работы с асинхронным кодом.

Порядок выполнения промисов относительно таймеров и отрисовки разобран в статье [как работает браузер](./browser-rendering-event-loop) — здесь мы на неё опираемся и не пересказываем. Достаточно помнить одно: колбэк промиса — это **микрозадача**, она выполняется после того, как стек опустел, но раньше любого `setTimeout`.

## Часть 1. Какую проблему решают промисы

### Колбэк и инверсия управления

До промисов асинхронный результат отдавали через **колбэк** — функцию, которую ты передаёшь чужому коду, чтобы он вызвал её, когда будет готов результат.

```js
getUser(1, function (err, user) {
  if (err) return handle(err);
  console.log(user.name);
});
```

Здесь есть скрытая проблема, которая называется **инверсия управления**: ты отдал свою функцию наружу и больше не контролируешь, как её вызовут. Библиотека может вызвать колбэк дважды. Может не вызвать ни разу. Может вызвать синхронно, хотя ты рассчитывал на асинхронность. Проверить это ты никак не можешь — ты просто надеешься, что автор написал аккуратно.

### Ад колбэков

Вторая проблема видна невооружённым глазом. Как только результаты нужны последовательно, код уезжает вправо:

```js
getUser(1, function (err, user) {
  if (err) return handle(err);
  getOrders(user.id, function (err, orders) {
    if (err) return handle(err);
    getItems(orders[0].id, function (err, items) {
      if (err) return handle(err);
      render(items);          // четыре уровня вложенности ради трёх запросов
    });
  });
});
```

Это называется **ад колбэков** (callback hell). Дело не в отступах — с ними можно смириться. Дело в том, что обработка ошибок повторяется на каждом уровне, а если забыть одну строку `if (err)`, ошибка исчезнет бесследно: она не всплывёт наверх, потому что каждый колбэк вызывается из своей задачи, где твоего кода на стеке уже нет.

### Ошибка не всплывает

Вот это стоит понять как следует, потому что вопрос любят на интервью.

```js
try {
  setTimeout(() => { throw new Error('бум'); }, 0);
} catch (e) {
  console.log('не поймает');    // сюда никогда не попадём
}
```

`try/catch` ловит ошибки только на **стеке вызовов** — цепочке функций, которые сейчас выполняются. Когда через ноль миллисекунд движок возьмёт колбэк таймера из очереди задач, стек будет пуст: ни `try`, ни окружающей функции на нём уже нет. Ошибка улетит в глобальный обработчик.

### Нечего скомпоновать

Третья проблема: колбэк — не значение. Его нельзя вернуть из функции, положить в массив, передать дальше. Нельзя написать «дождись этих пяти операций» — придётся руками считать счётчик завершившихся.

Промис решает все три проблемы одним ходом: **он превращает будущий результат в обычное значение, которое можно вернуть, передать и скомпоновать**. Функция вызовет твой колбэк ровно один раз и всегда асинхронно — за это отвечает спецификация, а не автор библиотеки.

## Часть 2. Три состояния и почему переход только один

**Промис** — объект-обёртка над результатом, которого пока нет. У него есть внутреннее состояние, три варианта:

- **pending** («ожидает») — результата ещё нет. Это стартовое состояние.
- **fulfilled** («выполнен») — есть значение.
- **rejected** («отклонён») — есть причина отказа.

Состояния fulfilled и rejected вместе называют **settled** («улажен»): промис определился, результат зафиксирован.

Правило жёсткое: **переход происходит один раз и он необратим**. Промис, ставший fulfilled, никогда не станет rejected. Второй вызов `resolve` или `reject` молча игнорируется — не бросает ошибку, просто ничего не делает.

```js
const p = new Promise((resolve, reject) => {
  resolve('первый');
  resolve('второй');       // проигнорировано
  reject(new Error('!'));  // тоже проигнорировано
});
p.then(v => console.log(v));   // «первый»
```

Зачем такая жёсткость. Промис — это обещание про **одно** событие. На него могут подписаться десять мест в разных частях приложения, причём в разное время: одни до того, как результат появился, другие — спустя минуту после. Если бы значение могло меняться, подписчики получали бы разное в зависимости от момента подписки, и рассуждать о таком коде стало бы невозможно. Неизменяемость результата — то, что делает промис безопасным для передачи куда угодно.

Отсюда же следует: **промис не для потока событий**. Для «пользователь кликает много раз» нужны обработчики событий или потоки (Observable), а не промисы.

### Подписка после завершения

Ещё одно следствие, которое часто удивляет: подписаться на уже завершённый промис можно, и колбэк вызовется.

```js
const p = Promise.resolve(42);

setTimeout(() => {
  p.then(v => console.log(v));   // 42 — сработает, хотя промис давно готов
}, 1000);
```

Промис хранит результат внутри. `.then` на завершённом промисе не вызывает колбэк немедленно и синхронно — он ставит его в очередь микрозадач. Это тоже часть контракта: **колбэк промиса никогда не выполняется синхронно**, даже если ответ уже лежит в кармане.

## Часть 3. Что на самом деле делает `.then`

Главная фраза всей статьи: **`.then` возвращает новый промис**. Не тот же самый, а новый, со своим состоянием, созданный в момент вызова `.then`.

```js
const p1 = Promise.resolve(1);
const p2 = p1.then(v => v + 1);
console.log(p1 === p2);   // false
```

Из этого одного факта следует вся механика цепочек. Каждый `.then` создаёт новое звено, у которого своё состояние pending, и это звено разрешается результатом колбэка. Цепочка — не «список подписчиков на один промис», а **последовательность промисов, где каждый следующий ждёт предыдущего**.

Разницу видно на контрасте:

```js
const p = Promise.resolve(1);

// Ветвление: три подписчика на ОДИН промис, все получат 1
p.then(v => console.log('a', v));   // a 1
p.then(v => console.log('b', v));   // b 1
p.then(v => console.log('c', v));   // c 1

// Цепочка: каждое звено ждёт предыдущее и получает его результат
Promise.resolve(1)
  .then(v => { console.log('a', v); return v + 1; })   // a 1
  .then(v => { console.log('b', v); return v + 1; })   // b 2
  .then(v => { console.log('c', v); });                // c 3
```

Первый вариант — три независимые ветки от общего корня. Второй — конвейер. Путать их — типичная ошибка: люди пишут `p.then(...)` три раза подряд отдельными выражениями и удивляются, что значение не накапливается.

## Часть 4. Три исхода колбэка

Что окажется в промисе, который вернул `.then`? Зависит от того, как завершился колбэк. Вариантов ровно три.

**Вернул обычное значение** — новый промис становится fulfilled с этим значением.

```js
Promise.resolve(1).then(v => v * 2);   // fulfilled со значением 2
```

Если колбэк не вернул ничего (нет `return`), значением станет `undefined`. Это источник ошибки «в следующем `.then` вдруг `undefined`» — потерянный `return`.

**Бросил исключение** — новый промис становится rejected с этой ошибкой.

```js
Promise.resolve(1).then(() => { throw new Error('бум'); });   // rejected
```

Обрати внимание: `throw` внутри колбэка промиса не «падает наружу», а превращается в отклонение следующего промиса. Именно это делает цепочку похожей на `try/catch` — ошибка не теряется, а едет дальше по цепочке.

**Вернул промис** — новый промис **ждёт** возвращённый и повторяет его судьбу.

```js
Promise.resolve(1)
  .then(() => fetch('/api/user'))          // вернули промис
  .then(res => res.json())                 // сюда придёт Response, а не промис
  .then(user => console.log(user.name));
```

Это свойство и называется **разворачиванием** (unwrapping, в спецификации — «усвоение», assimilation). Именно оно превращает вложенность в плоскую цепочку: вместо колбэка внутри колбэка ты просто возвращаешь промис и продолжаешь цепочку на том же уровне.

Разворачивание рекурсивное: промис, разрешённый промисом, который разрешён промисом, всё равно даст итоговое значение, а не матрёшку. Промиса, содержащего промис, в JavaScript не существует.

Точнее, движок проверяет не «это промис», а «у объекта есть метод `then`». Такой объект называется **thenable**. Поэтому промисы из старых библиотек прозрачно работают со встроенными.

### Цена разворачивания

Возврат промиса из `.then` стоит **две дополнительные микрозадачи** — движку нужно сначала подписаться на возвращённый промис, потом получить его результат. Это не влияет на архитектуру, но объясняет странные на первый взгляд порядки вывода в задачах на интервью:

```js
Promise.resolve()
  .then(() => Promise.resolve('A'))   // возвращаем промис
  .then(() => console.log('A финиш'));

Promise.resolve()
  .then(() => 'B')                    // возвращаем значение
  .then(() => console.log('B финиш'))
  .then(() => console.log('B ещё'))
  .then(() => console.log('B и ещё'));

// B финиш, B ещё, B и ещё, A финиш
```

Вторая цепочка успевает пройти три звена, пока первая разбирается с одним возвратом промиса. Помнить наизусть незачем — достаточно знать причину: возврат промиса добавляет два оборота очереди микрозадач.

## Часть 5. Как значение и ошибка едут по цепочке

У `.then` два аргумента: колбэк на успех и колбэк на ошибку.

```js
p.then(onFulfilled, onRejected);
```

Когда предыдущее звено завершилось успешно, вызывается первый. Когда отклонением — второй. **Ровно один из двух**, никогда оба.

А если нужного колбэка нет — результат едет дальше **насквозь**, не меняясь. Успех проходит мимо `.catch`, ошибка проходит мимо `.then` без второго аргумента. Это и есть механизм «ошибка всплывает до ближайшего обработчика».

### `.catch` — это просто `.then(null, fn)`

Буквально. В спецификации `.catch(fn)` определён как вызов `.then(undefined, fn)`. Отдельного механизма нет, это сокращение для читаемости.

Из этого сразу следуют два неочевидных вывода.

**Вывод первый: `.catch` в конце ловит ошибки всех предыдущих звеньев, а `.then` со вторым аргументом — нет.**

```js
// Ловит и ошибку сети, и ошибку в разборе JSON, и ошибку в render
fetch(url).then(r => r.json()).then(render).catch(handle);

// Ловит только ошибку fetch. Ошибка внутри render уйдёт в пустоту
fetch(url).then(r => r.json()).then(render, handle);
```

Причина: колбэк ошибки в `.then(onOk, onErr)` реагирует на **предыдущее** звено, а не на своё собственное. Ошибку, которую бросил `render`, ловить уже некому — `handle` находится в том же звене.

**Вывод второй: `.catch` в середине цепочки её не обрывает, а продолжает.**

```js
fetch('/api/user')
  .then(r => r.json())
  .catch(() => ({ name: 'Гость' }))   // подставляем запасное значение
  .then(user => render(user.name));   // выполнится в любом случае
```

`.catch` возвращает новый промис по тем же правилам, что и `.then`. Колбэк вернул объект — новый промис становится fulfilled с этим объектом, и цепочка едет дальше по дорожке успеха. Это не «выход из блока», это «преобразование ошибки в значение».

Ровно так же работает `try/catch`: после блока `catch` выполнение продолжается со следующей строки. Промисы просто повторяют знакомую семантику.

Если продолжать не надо, ошибку нужно **пробросить**:

```js
.catch(err => {
  logToServer(err);
  throw err;       // без этой строки цепочка поедет дальше как успешная
})
```

Забытый `throw` в промежуточном `.catch` — одна из самых дорогих ошибок на практике: приложение продолжает работать с `undefined` вместо данных и падает в другом месте, где причину уже не найти.

### `.finally` ничего не меняет

`.finally(fn)` вызывает колбэк при любом исходе и **пропускает результат насквозь**: и значение, и ошибку.

```js
showSpinner();
fetch(url)
  .then(r => r.json())
  .finally(() => hideSpinner())    // выполнится и при успехе, и при ошибке
  .then(data => render(data))      // data доедет нетронутым
  .catch(showError);               // ошибка тоже доедет
```

Колбэк `.finally` **не получает аргументов** — он не знает, чем всё кончилось, и это намеренно: его дело — уборка, а не решение.

Возврат из `.finally` игнорируется:

```js
Promise.resolve(1).finally(() => 999).then(v => console.log(v));   // 1, не 999
```

Но два исключения есть. Если `.finally` **бросит** ошибку, она заменит текущий результат. И если `.finally` вернёт промис, цепочка **дождётся** его, прежде чем ехать дальше — значение всё равно останется прежним, но пауза будет.

## Часть 6. Комбинаторы

Четыре статических метода, которые собирают несколько промисов в один. Разница между ними — только в том, когда итоговый промис завершается и что попадает в результат.

### `Promise.all` — «нужны все»

Ждёт все промисы. Успех — массив значений **в порядке аргументов**, а не в порядке завершения. Первая же ошибка мгновенно отклоняет общий промис.

```js
const [user, orders, settings] = await Promise.all([
  fetchUser(id), fetchOrders(id), fetchSettings(id)
]);
```

Когда: данные для одного экрана, без любого куска экран нечего показывать.

**Важнейший подводный камень: `Promise.all` при ошибке не отменяет остальные операции.** Он не может — у промиса нет отмены. Когда первый запрос упал, `Promise.all` отклонился, а два других продолжают идти, дойдут до конца, потратят трафик и, возможно, что-то запишут на сервере. Ты просто перестал слушать их результат.

Практическое следствие: если параллельные операции меняют состояние, `Promise.all` не даёт атомарности. «Либо все три записи, либо ни одной» промисами не выражается — нужна отмена (см. ниже) или откат на сервере.

Второе следствие: если один из промисов отклонится **после** того, как общий уже упал, его отклонение никто не обработает, и в консоли появится предупреждение о необработанном отклонении.

### `Promise.allSettled` — «хочу отчёт по всем»

Ждёт завершения всех, **никогда не отклоняется**. Результат — массив объектов с полем `status`.

```js
const results = await Promise.allSettled(ids.map(id => sendReport(id)));

const failed = results.filter(r => r.status === 'rejected');
console.log(`Отправлено ${results.length - failed.length} из ${results.length}`);
```

У успешных объектов есть поле `value`, у отклонённых — `reason`.

Когда: независимые операции, где частичный успех — нормальный исход. Загрузка десяти файлов, отправка пачки событий аналитики, прогрев нескольких кешей.

### `Promise.race` — «первый определившийся»

Завершается вместе с первым **улаженным** промисом — неважно, успехом или ошибкой.

```js
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Таймаут')), ms)
  );
  return Promise.race([promise, timeout]);
}
```

Классическое применение — таймаут. Помни ту же оговорку: проигравший гонку запрос продолжает выполняться, `race` его не отменяет.

### `Promise.any` — «первый успешный»

Ждёт первый **успех**, ошибки игнорирует. Отклоняется только если провалились все, и тогда причиной будет `AggregateError` с массивом всех ошибок в поле `errors`.

```js
try {
  const data = await Promise.any([fetchFrom(mirrorA), fetchFrom(mirrorB)]);
} catch (err) {
  console.log(err.errors);   // массив причин, если упали оба зеркала
}
```

Когда: несколько источников одних и тех же данных, годится любой ответивший.

Разница `race` и `any` в одном: `race` останавливается на первом улаженном, включая ошибку; `any` пропускает ошибки и ждёт успех.

### Сводка

| Метод | Завершается | Результат при успехе | При ошибке |
| --- | --- | --- | --- |
| `all` | все успешны | массив значений | первая ошибка |
| `allSettled` | все улажены | массив статусов | не отклоняется |
| `race` | первый улажен | значение первого | ошибка первого |
| `any` | первый успех | значение первого успешного | `AggregateError`, если упали все |

Все четыре принимают любой перебираемый объект, не только массив, и на пустом массиве ведут себя по-разному: `all` и `allSettled` немедленно успешны, `race` навсегда остаётся pending, `any` немедленно отклоняется.

## Часть 7. Отмена: почему промис нельзя отменить

**Промис отменить нельзя, и это не недоработка, а следствие устройства.** Промис — это подписка на результат. У него нет ссылки на операцию, которая его породила: `fetch` создал промис и ушёл, промис про `fetch` ничего не знает. Отменять надо **операцию**, а не обёртку над её результатом.

Для этого есть `AbortController` — отдельный объект-сигнал.

```js
const controller = new AbortController();

fetch('/api/data', { signal: controller.signal })
  .then(r => r.json())
  .then(render)
  .catch(err => {
    if (err.name === 'AbortError') return;   // отменили сами — это не ошибка
    showError(err);
  });

controller.abort();   // запрос реально прерывается
```

Что здесь происходит механически: `controller.signal` — объект события. `fetch` на него подписан, и когда вызывается `abort()`, `fetch` рвёт соединение и отклоняет свой промис ошибкой с `name === 'AbortError'`.

Промис не «отменился» — он **отклонился**. Правило трёх состояний не нарушено.

Ключевые моменты на практике:

- Отмену **должна поддерживать сама операция**. `AbortController` — просто сигнал; если функция его не слушает, ничего не произойдёт.
- Один контроллер можно отдать нескольким операциям — `abort()` прервёт все сразу. Это стандартный способ гасить пачку запросов при уходе со страницы.
- `AbortError` надо отличать от настоящей ошибки, иначе пользователь увидит «Ошибка загрузки» после того, как сам ушёл со страницы.
- В React такой контроллер вызывают в функции очистки эффекта, чтобы ответ на размонтированный компонент не приехал. Незакрытые подписки — типовой источник утечек, про них есть отдельная статья [память и утечки](./memory-and-leaks).
- `AbortSignal.timeout(5000)` даёт готовый сигнал, который срабатывает сам — короче, чем `race` с таймером, и в отличие от него действительно прерывает запрос.

## Часть 8. Необработанные отклонения

Если промис отклонился, а обработчика ошибок в цепочке нет, движок сообщает об этом отдельным событием.

```js
window.addEventListener('unhandledrejection', (event) => {
  event.preventDefault();          // подавить вывод в консоль
  sendToMonitoring(event.reason);  // reason — то, чем отклонили
});
```

Проверка отложенная: движок ждёт конца текущего оборота очереди микрозадач и только потом решает, что обработчика нет. Поэтому подписаться «поздно, но в том же обороте» можно:

```js
const p = Promise.reject(new Error('x'));
setTimeout(() => p.catch(handle), 0);   // поздно: предупреждение уже выдано

const q = Promise.reject(new Error('y'));
Promise.resolve().then(() => q.catch(handle));  // успели, предупреждения не будет
```

Событие `unhandledrejection` — единственный способ узнать о потерянных ошибках в проде. Без него отвалившийся запрос просто ничего не сделает, и пользователь увидит пустой экран без объяснений. Подробнее про глобальные ловушки — в статье [ошибки и отладка](./errors-and-debugging).

## Часть 9. Типичные ошибки

**Забытый `return` внутри `.then`.** Цепочка не дожидается вложенной операции.

```js
// Плохо: следующий then получит undefined и не дождётся save
.then(user => { save(user); })
// Хорошо
.then(user => save(user))
```

Стрелочная функция с фигурными скобками не возвращает ничего, и об этом забывают постоянно. Без скобок — возвращает.

**`.then` внутри `.then` вместо цепочки.** Вложенность возвращается, а вместе с ней ад колбэков.

```js
// Плохо: тот же ад, только в профиль
fetchUser(id).then(user => {
  fetchOrders(user.id).then(orders => {
    render(orders);
  });
});

// Хорошо: плоская цепочка
fetchUser(id)
  .then(user => fetchOrders(user.id))
  .then(render)
  .catch(showError);
```

В плохом варианте `.catch` снаружи не поймает ошибку из `fetchOrders`: вложенная цепочка живёт своей жизнью, наружная о ней не знает.

**Проглоченная ошибка.** Пустой или молчаливый `catch` — способ спрятать проблему на месяцы.

```js
.catch(() => {})            // так делать нельзя
.catch(() => null)          // почти так же плохо: дальше поедет null
```

Если ошибку действительно можно игнорировать, оставь комментарий, почему. Если нельзя — логируй и пробрасывай.

**Лишняя обёртка над промисом.**

```js
// Плохо: конструктор здесь не нужен, а ошибки fetch потеряются
function load(url) {
  return new Promise((resolve) => {
    fetch(url).then(r => r.json()).then(resolve);
  });
}
// Хорошо
function load(url) {
  return fetch(url).then(r => r.json());
}
```

Это называется **антипаттерн отложенного объекта** (deferred antipattern). `new Promise` нужен ровно в одном случае: когда ты оборачиваешь **не-промисный** источник — колбэк старого API, событие, таймер.

**Создание промиса раньше, чем нужно.** Промис начинает работу немедленно при создании, а не при первом `.then`. Он не «ленивый». Массив промисов — это массив уже запущенных операций.

```js
const promises = urls.map(u => fetch(u));   // все запросы УЖЕ пошли
await Promise.all(promises);                // просто ждём
```

Иногда это ровно то, что нужно, а иногда — сотня одновременных запросов, которых никто не просил.

## Что спросят на интервью

**Какие состояния у промиса и можно ли перейти из rejected в fulfilled?** Три: pending, fulfilled, rejected. Переход один и необратим; повторные вызовы `resolve`/`reject` игнорируются.

**Что возвращает `.then`?** Новый промис. Поэтому цепочки работают, и поэтому `p.then(a); p.then(b)` — это ветвление, а не цепочка.

**Что будет, если из колбэка `.then` вернуть промис?** Следующее звено дождётся его и получит развёрнутое значение. Промиса внутри промиса не бывает.

**Чем `.then(ok, err)` отличается от `.then(ok).catch(err)`?** Второй вариант ловит и ошибки самого `ok`, первый — нет.

**Прервёт ли `.catch` в середине цепочку?** Нет. Если колбэк не бросил ошибку, цепочка продолжится как успешная. Чтобы прервать, нужно пробросить ошибку через `throw`.

**Меняет ли `.finally` значение?** Нет, пропускает насквозь. Может только заменить результат на ошибку, если сам бросит, или задержать цепочку, если вернёт промис.

**Отменит ли `Promise.all` остальные запросы при ошибке?** Нет. Они продолжат выполняться, просто их результат никого не интересует. Для реальной отмены нужен `AbortController`.

**Разница `race` и `any`?** `race` реагирует на первый улаженный, включая ошибку. `any` ждёт первый успех и падает только когда провалились все, с `AggregateError`.

**Как отменить промис?** Никак. Отменяется операция — через `AbortController`; промис при этом отклонится ошибкой `AbortError`.

**Почему колбэк `.then` не выполняется синхронно, даже если промис уже готов?** Спецификация гарантирует асинхронность: колбэк всегда попадает в очередь микрозадач. Иначе порядок выполнения зависел бы от того, успел ли ответ прийти, и код был бы недетерминированным.

## Коротко, для повторения

1. Промис превращает будущий результат в значение: его можно вернуть, передать, скомпоновать. Колбэк вызовется ровно один раз и всегда асинхронно.
2. Состояния — pending, fulfilled, rejected. Переход один и необратим, повторные `resolve`/`reject` игнорируются.
3. `.then` возвращает **новый** промис. Отсюда цепочки и отсюда же разница между цепочкой и ветвлением.
4. Колбэк вернул значение — успех; бросил — отклонение; вернул промис — звено дожидается его и разворачивает.
5. Результат едет по цепочке насквозь мимо звеньев без подходящего обработчика. Так ошибка добирается до `.catch`.
6. `.catch(fn)` — это `.then(null, fn)`. В середине цепочки он не обрывает её, а возвращает на дорожку успеха; чтобы прервать — `throw`.
7. `.finally` не меняет значение и не получает аргументов. Исключение — если сам бросит или вернёт промис.
8. `all` — все или ошибка, `allSettled` — отчёт по всем, `race` — первый улаженный, `any` — первый успешный.
9. `Promise.all` при ошибке остальные операции **не отменяет** — они доработают до конца.
10. Промис отменить нельзя, отменяется операция через `AbortController`; промис отклоняется с `AbortError`.
11. Потерянные ошибки ловятся глобально через `unhandledrejection` — без этого в проде они невидимы.
