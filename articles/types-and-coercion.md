# Типы, приведение и сравнение

Половина «странностей JavaScript», которые показывают в твиттере, — это не странности, а следствия двух-трёх правил, записанных в спецификации. Если правила знать, поведение перестаёт быть загадочным и становится предсказуемым.

Эта статья про то, из чего состоят значения в JavaScript, чем примитив отличается от объекта на уровне памяти, как движок превращает объект в число, по каким шагам работает `==`, почему `0.1 + 0.2` не равно `0.3` и что теряется при копировании через JSON. Каждый термин объясняется на месте.

## Часть 1. Из чего состоят значения

### Семь примитивов и объекты

**Примитив** — это простое значение, у которого нет внутренней структуры и которое нельзя изменить. Их семь:

| Тип | Пример | Зачем |
| --- | --- | --- |
| `string` | `'привет'` | текст |
| `number` | `42`, `0.5`, `NaN`, `Infinity` | все обычные числа |
| `bigint` | `9007199254740993n` | целые произвольной длины |
| `boolean` | `true`, `false` | логика |
| `undefined` | `undefined` | «значения не присвоили» |
| `symbol` | `Symbol('id')` | уникальный ключ свойства |
| `null` | `null` | «значение осознанно пустое» |

Всё остальное — **объекты**: обычные объекты, массивы, функции, `Date`, `Map`, `RegExp`, DOM-узлы. Функция — это объект, который можно вызвать.

**Примитивы неизменяемы** (immutable). Это ключевое слово, и его часто понимают неправильно. Речь не про переменную, а про само значение:

```js
let s = 'привет';
s.toUpperCase();     // вернуло новую строку
console.log(s);      // 'привет' — исходная строка не изменилась

s[0] = 'П';          // молча ничего не делает (в strict mode — ошибка)
console.log(s);      // 'привет'

s = s.toUpperCase(); // а вот это работает: мы поменяли переменную, не строку
```

Строку изменить нельзя в принципе — можно только создать новую и положить в переменную. Поэтому у строк нет «мутирующих» методов: все они возвращают новую строку.

### Откуда у примитива методы

Если строка — это простое значение, почему у неё есть `.toUpperCase()`? Потому что при обращении к свойству движок временно оборачивает примитив в **объект-обёртку** (`String`, `Number`, `Boolean`, `Symbol`, `BigInt`), берёт метод из её прототипа, вызывает и обёртку выбрасывает.

```js
const s = 'привет';
s.custom = 1;        // обёртка создана, свойство записано, обёртка выброшена
console.log(s.custom); // undefined — новая обёртка ничего не помнит
```

У `null` и `undefined` обёрток нет — поэтому `null.foo` бросает `TypeError`. Именно от этого спасает опциональная цепочка `obj?.foo`.

### Почему `typeof null` возвращает `'object'`

Классический вопрос на интервью. Ответ — исторический баг, который не могут починить из-за обратной совместимости.

В первой реализации JavaScript значение хранилось как машинное слово, у которого младшие биты были **тегом типа**. Тег `000` означал «это объект, дальше идёт указатель». А `null` представлялся как нулевой указатель — то есть все биты нулевые, включая тег. Проверка типа смотрела на тег, видела `000` и честно отвечала «объект».

Починить это предлагали (`typeof null === 'null'`), но предложение отклонили: слишком много кода в интернете полагается на текущее поведение. Практический вывод:

```js
// Плохо: null пройдёт проверку
if (typeof x === 'object') { /* x может быть null */ }

// Хорошо
if (x !== null && typeof x === 'object') { /* точно объект */ }
```

## Часть 2. Значение против ссылки

Это то место, где ломается больше всего кода, и то место, которое чаще всего спрашивают, не называя прямо: «почему у меня стейт не обновился», «почему изменился массив, который я не трогал».

### Что лежит в переменной

**Примитив хранится в переменной целиком.** Присвоил переменную другой — скопировалось само значение, две переменные больше никак не связаны.

**Объект в переменной не лежит.** В переменной лежит **ссылка** — адрес места в памяти, где объект находится. Присвоил переменную другой — скопировался адрес. Объект остался один, а указывают на него теперь двое.

```js
let a = 10;
let b = a;
b = 20;
console.log(a);          // 10 — независимые копии

let o = { n: 1 };
let p = o;
p.n = 2;
console.log(o.n);        // 2 — один объект, две ссылки

console.log({} === {});  // false — разные адреса
console.log([] === []);  // false — тоже разные
```

Последние две строки объясняют, почему сравнение объектов «по содержимому» в JavaScript невозможно оператором: `===` для объектов означает «это буквально одно и то же место в памяти».

### Что это значит для аргументов функции

В JavaScript **всё передаётся по значению** — но для объекта «значением» является ссылка. Отсюда поведение, которое кажется противоречивым:

```js
function mutate(obj) {
  obj.n = 99;            // меняем объект по адресу — снаружи видно
}

function reassign(obj) {
  obj = { n: 99 };       // меняем локальную переменную — снаружи не видно
}

const x = { n: 1 };
mutate(x);   console.log(x.n);   // 99
reassign(x); console.log(x.n);   // 99, не изменилось вторым вызовом
```

Формулировка для интервью: **аргумент — это новая переменная, в которую скопировали ссылку.** Через неё можно дотянуться до объекта и изменить его. Присваивание самой переменной перенаправляет только локальную копию ссылки.

Тот же механизм — причина, по которой React не перерисовывает компонент:

```js
// Плохо: тот же адрес, React сравнил ссылки и решил, что ничего не изменилось
items.push(newItem);
setItems(items);

// Хорошо: новый массив — новый адрес
setItems([...items, newItem]);
```

Подробнее про это — в статье про [массивы, объекты и иммутабельность](./arrays-objects-immutability).

### Ссылка не значит «копия навсегда»

Ещё одна ловушка: `const` защищает переменную, а не объект.

```js
const cfg = { debug: false };
cfg.debug = true;    // работает: адрес не менялся
cfg = {};            // TypeError: присваивание переменной запрещено
```

`const` означает «в эту переменную больше нельзя положить другое значение». Для примитива это и есть неизменяемость. Для объекта — нет.

## Часть 3. Как определить тип

### `typeof`

Возвращает строку. Быстрый, работает с необъявленными переменными (не бросает `ReferenceError`), но грубый.

```js
typeof 1            // 'number'
typeof 'a'          // 'string'
typeof undefined    // 'undefined'
typeof Symbol()     // 'symbol'
typeof 1n           // 'bigint'
typeof null         // 'object'   ← баг
typeof []           // 'object'   ← массив неотличим
typeof new Date()   // 'object'
typeof function(){} // 'function' ← отдельный случай
```

Итог: `typeof` различает примитивы, но все объекты, кроме функций, для него одинаковы.

### `instanceof`

Проверяет, встречается ли `Constructor.prototype` в **цепочке прототипов** объекта. Прототип — это объект-«родитель», у которого ищутся свойства, если своих не нашлось; цепочка — последовательность таких родителей до `null`.

```js
class Animal {}
class Dog extends Animal {}
const d = new Dog();

d instanceof Dog      // true
d instanceof Animal   // true — работает по всей цепочке
d instanceof Object   // true
```

Два ограничения. Первое: с примитивами не работает вообще — `'a' instanceof String` это `false`, потому что примитив не объект.

Второе, важное на практике: **`instanceof` ломается через границу окружения**. Окружение (realm) — это отдельный набор встроенных объектов: у каждого `iframe`, у каждого воркера, у Node-модуля `vm` он свой. Массив, созданный в `iframe`, имеет прототип из **его** `Array`, а не из твоего:

```js
const iframeArray = iframe.contentWindow.eval('[1, 2]');
iframeArray instanceof Array   // false!
Array.isArray(iframeArray)     // true — работает всегда
```

### `Array.isArray` и «настоящая» проверка

`Array.isArray` смотрит на внутреннюю метку объекта, а не на прототип, поэтому границы окружений ему безразличны. Это единственный правильный способ проверить массив.

Для остальных встроенных типов есть приём с `Object.prototype.toString`:

```js
const kind = (v) => Object.prototype.toString.call(v).slice(8, -1);

kind(null)        // 'Null'
kind(undefined)   // 'Undefined'
kind([])          // 'Array'
kind(new Date())  // 'Date'
kind(/x/)         // 'RegExp'
kind(new Map())   // 'Map'
kind(Promise.resolve()) // 'Promise'
```

Практическое правило: примитив — `typeof`, массив — `Array.isArray`, свой класс — `instanceof`, встроенный тип — `Object.prototype.toString.call`.

## Часть 4. Приведение к примитиву

Когда объект попадает туда, где ожидается примитив (арифметика, склейка строк, сравнение), движок вызывает внутреннюю операцию **ToPrimitive**. У неё есть **подсказка** (hint) — какой примитив предпочтителен.

Подсказок три:

- `'number'` — арифметика (`-`, `*`, `/`), сравнения `<` и `>`, `Math.*`;
- `'string'` — когда объект используется как ключ или в шаблонной строке, `String(obj)`;
- `'default'` — `+` и `==`, где непонятно, чего хотят.

Порядок попыток:

1. Если у объекта есть метод `Symbol.toPrimitive` — вызвать его с подсказкой и взять результат. Всё, дальше не идём.
2. Иначе, при подсказке `'string'`: сначала `toString()`, если вернул не примитив — `valueOf()`.
3. Иначе (подсказки `'number'` и `'default'`): сначала `valueOf()`, если вернул не примитив — `toString()`.
4. Если оба вернули объект — `TypeError`.

Ключевая деталь: **`'default'` ведёт себя как `'number'`** для всех объектов, кроме `Date`, которая переопределяет это и ведёт себя как `'string'`. Отсюда:

```js
const d = new Date();
d + 1;    // строка: 'Mon Sep 01 2026 ... 1'  — hint 'default' → строка
d - 1;    // число: миллисекунды минус один    — hint 'number'
```

Разберём на своём объекте:

```js
const money = {
  amount: 100,
  valueOf() { return this.amount; },
  toString() { return this.amount + ' ₽'; },
};

money * 2          // 200      — hint 'number' → valueOf
`${money}`         // '100 ₽'  — hint 'string' → toString
money + 1          // 101      — hint 'default' → valueOf
String(money)      // '100 ₽'
```

А теперь с `Symbol.toPrimitive`, который перехватывает всё:

```js
const temp = {
  celsius: 20,
  [Symbol.toPrimitive](hint) {
    if (hint === 'number') return this.celsius;
    if (hint === 'string') return this.celsius + '°C';
    return `Температура: ${this.celsius}`;   // 'default'
  },
};

+temp        // 20
`${temp}`    // '20°C'
temp + ''    // 'Температура: 20'
```

Это объясняет знаменитое поведение массивов и объектов:

```js
[] + []        // ''   — у обоих toString() даёт ''
[] + {}        // '[object Object]'
[1,2] + [3]    // '1,23' — '1,2' + '3'
({}) + []      // '[object Object]'
```

У массива `valueOf` возвращает сам массив (не примитив), поэтому в дело идёт `toString`, а он у массива — это `join(',')`. У обычного объекта `toString` возвращает `'[object Object]'`.

## Часть 5. Нестрогое сравнение

### Что делает `===`

Строгое сравнение простое: разные типы — сразу `false`, одинаковые — сравниваем значения. Исключений два: `NaN` не равен ничему, включая себя, и `+0 === -0` истинно.

### Алгоритм `==` по шагам

Нестрогое сравнение сначала пытается привести операнды к общему типу. Полный алгоритм короче, чем кажется:

1. Типы совпадают → работает как `===`.
2. `null == undefined` → `true`. Друг с другом равны, **больше ни с чем** не равны.
3. Число и строка → строка приводится к числу.
4. Логическое значение с любой стороны → приводится к числу (`true` в `1`, `false` в `0`), сравнение начинается заново.
5. Объект и примитив (число, строка, символ, bigint) → объект приводится к примитиву через ToPrimitive с подсказкой `'default'`, сравнение начинается заново.
6. Всё остальное → `false`.

Обрати внимание на шаг 2: `null` не приводится к числу. Поэтому:

```js
null == 0        // false
null >= 0        // true!  сравнение > и < работает по другим правилам
null == false    // false
undefined == 0   // false
```

`null >= 0` истинно, потому что операторы `<`, `>`, `<=`, `>=` не имеют спецслучая для `null` — они честно приводят к числу, а `Number(null)` это `0`. Это разные алгоритмы, и это самая частая причина недоумения.

### Разбор `[] == ![]`

Каноничный вопрос. Разберём строго по шагам.

```js
[] == ![]   // true
```

1. Сначала вычисляется правая часть — `![]`. Оператор `!` приводит операнд к логическому значению по правилам truthy/falsy. **Любой объект истинный**, включая пустой массив. Значит `Boolean([])` это `true`, а `![]` это `false`.
2. Выражение стало `[] == false`.
3. Шаг 1 алгоритма: типы разные (объект и boolean).
4. Шаг 4: справа boolean → `Number(false)` это `0`. Выражение стало `[] == 0`, начинаем заново.
5. Шаг 5: слева объект, справа число → ToPrimitive для `[]` с подсказкой `'default'`. `valueOf` вернул сам массив (не примитив), поэтому `toString()` → `''` (пустая строка, потому что `[].join(',')` пустой).
6. Выражение стало `'' == 0`, начинаем заново.
7. Шаг 3: строка и число → `Number('')` это `0`.
8. `0 == 0` → `true`.

Мораль не «JavaScript сломан», а «объект в `==` превращается в строку, а строка в число, и по дороге теряется всё, что было». Ещё пара примеров, которые теперь очевидны:

```js
[] == false      // true  — как разобрали выше
[0] == false     // true  — '0' → 0
['0'] == false   // true
[1] == true      // true  — '1' → 1
[[]] == false    // true  — вложенный toString даёт ''
'' == 0          // true
'0' == false     // true
' \t\n' == 0     // true  — пробелы обрезаются при Number()
```

### Когда `==` уместен

Ровно один случай, и он полезный: **проверка «значение отсутствует»**.

```js
if (x == null) { /* x это null или undefined, больше ничего */ }
```

Это короче и надёжнее, чем `x === null || x === undefined`, и не путает с falsy-проверкой: `0`, `''` и `false` сюда не попадут. Многие стайлгайды (включая правило `eqeqeq` с опцией `smart`) разрешают `==` именно в этой форме.

Во всех остальных случаях — `===`. Не потому что «так принято», а потому что `==` может привести операнд дважды, и в код-ревью никто это в голове не прокрутит.

## Часть 6. Числа, `NaN` и правильное сравнение

### Почему `NaN !== NaN`

`NaN` («не число») — результат несостоявшегося вычисления: `0/0`, `Math.sqrt(-1)`, `Number('привет')`, `undefined + 1`.

Он не равен ничему, включая себя. Логика такая: `NaN` означает «результат неизвестен». Два неизвестных результата не обязаны быть одним и тем же значением, поэтому стандарт IEEE 754 (по которому устроены числа во всех языках) решил считать любое сравнение с `NaN` ложным. JavaScript просто следует стандарту.

Побочный эффект: `NaN` — единственное значение, для которого `x !== x` истинно. Это старый способ его обнаружить.

### `isNaN` против `Number.isNaN`

Глобальный `isNaN` сначала **приводит аргумент к числу**, и поэтому врёт:

```js
isNaN('привет')     // true  — Number('привет') это NaN
isNaN(undefined)    // true  — Number(undefined) это NaN
isNaN({})           // true
isNaN('')           // false — Number('') это 0
```

`Number.isNaN` ничего не приводит: он отвечает `true` только если аргумент буквально `NaN`.

```js
Number.isNaN('привет')  // false — это строка, а не NaN
Number.isNaN(NaN)       // true
```

Правило: **всегда `Number.isNaN`**. Тот же принцип у `Number.isFinite` против глобального `isFinite` и у `Number.isInteger`.

### `Object.is` и SameValueZero

В JavaScript четыре алгоритма равенства, и полезно держать в голове их различия.

| Алгоритм | `NaN` с `NaN` | `+0` с `-0` | Где используется |
| --- | --- | --- | --- |
| `==` | не равны | равны | нестрогое сравнение |
| `===` | не равны | равны | строгое сравнение |
| SameValueZero | **равны** | равны | `includes`, ключи `Map` и `Set` |
| SameValue (`Object.is`) | **равны** | **не равны** | `Object.is`, `Object.defineProperty` |

Отсюда практическая разница между `indexOf` и `includes`:

```js
[NaN].indexOf(NaN)    // -1   — indexOf сравнивает через ===
[NaN].includes(NaN)   // true — includes использует SameValueZero
```

`Object.is` пригождается редко — в основном там, где `-0` и `+0` надо различать (например, при вычислении направления). React использует SameValueZero-подобное сравнение в `Object.is` для проверки изменения состояния.

### Почему `0.1 + 0.2 !== 0.3`

Числа в JavaScript — это **числа с плавающей точкой двойной точности** (IEEE 754 double): 64 бита, из них 52 на мантиссу (значащие цифры), 11 на порядок, 1 на знак. Хранятся в двоичной системе.

Проблема в том, что `0.1` в двоичной системе — бесконечная периодическая дробь, ровно как `1/3` в десятичной. Её приходится обрезать. Обрезали `0.1`, обрезали `0.2`, сложили — ошибки сложились:

```js
0.1 + 0.2              // 0.30000000000000004
(0.1 + 0.2).toFixed(20) // '0.30000000000000004441'
0.3.toFixed(20)         // '0.29999999999999998890'
```

Это не баг JavaScript: то же самое в Python, Java и C. Просто в JavaScript чаще считают деньги в браузере.

Как сравнивать правильно — через допуск (epsilon):

```js
const equal = (a, b) => Math.abs(a - b) < Number.EPSILON;
equal(0.1 + 0.2, 0.3);   // true
```

`Number.EPSILON` — минимальная различимая разница около единицы (примерно `2.22e-16`). Для больших чисел абсолютный допуск не годится, нужен относительный:

```js
const close = (a, b, rel = 1e-9) =>
  Math.abs(a - b) <= rel * Math.max(Math.abs(a), Math.abs(b), 1);
```

Практический совет для денег: **не храни деньги в дробных числах**. Храни в минимальных единицах — копейках, центах — целыми числами, и форматируй при выводе через `Intl.NumberFormat`.

### Когда нужен `BigInt`

Целые числа точны только до `Number.MAX_SAFE_INTEGER` — это `2 ** 53 - 1`, около 9 квадриллионов. Дальше начинаются провалы:

```js
Number.MAX_SAFE_INTEGER          // 9007199254740991
9007199254740992 === 9007199254740993   // true! оба округлились одинаково
```

Это реальная боль: идентификаторы из бэкенда (Twitter-подобные snowflake ID, идентификаторы из PostgreSQL `bigint`) не влезают в `number`. `JSON.parse` их молча испортит.

`BigInt` — отдельный примитивный тип для целых произвольной длины:

```js
const id = 9007199254740993n;      // литерал с суффиксом n
BigInt('9007199254740993')         // из строки

id + 1n                            // 9007199254740994n
id + 1                             // TypeError: смешивать нельзя
Number(id)                         // можно явно, но потеряешь точность
10n == 10                          // true  — == приводит
10n === 10                         // false — типы разные
```

Правило: пришёл большой идентификатор — держи его строкой и не превращай в число вообще. `BigInt` нужен, когда с числом надо считать.

## Часть 7. Копирование объектов

### Поверхностная копия

**Поверхностная копия** (shallow copy) создаёт новый объект и переносит в него значения свойств верхнего уровня. Если значение — примитив, скопируется само значение. Если объект — скопируется ссылка, и вложенный объект останется общим.

```js
const orig = { name: 'Аня', address: { city: 'Москва' } };
const copy = { ...orig };

copy.name = 'Боря';
console.log(orig.name);           // 'Аня' — примитив скопировался

copy.address.city = 'Питер';
console.log(orig.address.city);   // 'Питер' — ссылка общая!
```

То же самое делают `Object.assign({}, orig)`, `arr.slice()`, `[...arr]`, `Array.from(arr)`.

### `structuredClone`

Встроенная глубокая копия, доступная в браузерах и Node. Умеет то, чего не умеет JSON:

```js
const deep = structuredClone(orig);
```

Что переживает клонирование: вложенные объекты и массивы, `Date`, `Map`, `Set`, `RegExp`, `ArrayBuffer`, типизированные массивы, `Blob`, `File`, и — важно — **циклические ссылки** (объект ссылается сам на себя).

Чего не умеет: функции, DOM-узлы и символы — бросает `DataCloneError`. Прототипы не сохраняются: экземпляр класса вернётся обычным объектом. Геттеры вычисляются и превращаются в обычные значения.

### Что теряет `JSON.parse(JSON.stringify(x))`

Старый трюк «глубокой копии» через сериализацию. Работает, но тихо ломает данные:

```js
const src = {
  date: new Date('2026-01-01'),
  undef: undefined,
  fn: () => 1,
  nan: NaN,
  inf: Infinity,
  map: new Map([['a', 1]]),
  set: new Set([1, 2]),
  sym: Symbol('x'),
  big: 10n,
};

JSON.parse(JSON.stringify(src));
// { date: '2026-01-01T00:00:00.000Z',  ← строка, а не Date
//   nan: null, inf: null,              ← превратились в null
//   map: {}, set: {} }                 ← опустели
// undef, fn, sym — пропали целиком
// big — бросит TypeError ещё на stringify
```

Плюс: циклические ссылки бросают `TypeError: Converting circular structure to JSON`, а `toJSON` у объекта незаметно подменяет результат.

Выбор такой: `structuredClone` по умолчанию, `lodash.cloneDeep` — если нужны функции, прототипы или тонкая настройка, `JSON` — только для заведомо простых данных, пришедших с сервера.

## Часть 8. Ложные значения и оператор `??`

**Ложных** (falsy) значений ровно восемь, и список стоит помнить наизусть:

```
false, 0, -0, 0n, '' (пустая строка), null, undefined, NaN
```

Всё остальное истинно. В том числе то, что интуиции противоречит: `'0'`, `'false'`, `[]`, `{}`, `function(){}` — все истинны.

### `||` против `??`

`||` возвращает правый операнд, если левый **ложный**. `??` (нулевое слияние, nullish coalescing) — только если левый `null` или `undefined`.

```js
const count = 0;
count || 10       // 10  ← ноль ложный, значение потерялось
count ?? 10       // 0   ← ноль сохранился

const name = '';
name || 'Гость'   // 'Гость'
name ?? 'Гость'   // ''
```

Классический баг: настройка «показывать подсказки» со значением `false` через `||` молча превращается в `true`. Или количество товаров `0` превращается в дефолт.

Правило: **`??` для значений по умолчанию, `||` для «любое пустое сойдёт за отсутствующее»**. Второе законно для строк, где пустая строка действительно означает «не заполнено».

Смешивать `??` с `||` и `&&` без скобок запрещено синтаксически — специально, чтобы не было споров о приоритете:

```js
a || b ?? c        // SyntaxError
(a || b) ?? c      // так можно
```

Есть и присваивающие формы:

```js
opts.retries ??= 3;   // присвоить, только если null или undefined
opts.name ||= 'без имени';
opts.flag &&= false;
```

## Что спросят на интервью

**Сколько примитивных типов и какие?** Семь: string, number, bigint, boolean, undefined, symbol, null. Всё остальное — объекты.

**Почему `typeof null` это `'object'`?** Баг первой реализации: `null` представлялся нулевым указателем, а тег типа «объект» был нулевым. Не чинят из-за обратной совместимости.

**В чём разница между передачей по значению и по ссылке?** В JavaScript всё передаётся по значению, но для объекта значением является ссылка. Поэтому изменение свойств объекта видно снаружи, а переприсваивание самого аргумента — нет.

**Чем `==` отличается от `===`?** `===` не приводит типы. `==` приводит по шагам: null/undefined, число со строкой, boolean в число, объект в примитив. Использовать `==` стоит только в форме `x == null`.

**Почему `[] == ![]` это `true`?** `![]` даёт `false`, `false` приводится к `0`, `[]` через `toString` даёт `''`, `''` приводится к `0`, `0 == 0`.

**Почему `null == 0` ложь, а `null >= 0` истина?** У `==` есть спецправило: `null` равен только `undefined`. У операторов сравнения такого правила нет, они приводят `null` к нулю.

**Чем `isNaN` отличается от `Number.isNaN`?** Глобальный сначала приводит аргумент к числу, поэтому `isNaN('abc')` истинно. `Number.isNaN` проверяет буквально.

**Почему `0.1 + 0.2 !== 0.3`?** Двоичное представление дробей конечной длины не может точно выразить эти десятичные дроби. Сравнивать через допуск, деньги хранить в целых копейках.

**Как проверить, что перед тобой массив?** `Array.isArray`. `typeof` даст `'object'`, `instanceof Array` сломается на массиве из другого окружения (iframe, worker).

**Что теряет копирование через JSON?** `undefined`, функции, символы — исчезают. `Date` становится строкой. `NaN` и `Infinity` становятся `null`. `Map` и `Set` пустеют. Циклические ссылки бросают ошибку.

**Когда `??` лучше `||`?** Когда `0`, `''` и `false` — законные значения, а не «отсутствие значения».

**Что вернёт `[1,2] + [3]`?** Строку `'1,23'`: оба массива приводятся к строке через `toString`, который делает `join(',')`.

## Коротко, для повторения

1. Семь примитивов, всё остальное — объекты. Примитивы неизменяемы, методы им даёт временная обёртка.
2. `typeof null === 'object'` — исторический баг, проверяй `x !== null && typeof x === 'object'`.
3. Примитив копируется целиком, объект — адресом. `===` для объектов сравнивает адреса, а не содержимое.
4. Аргумент функции — новая переменная с копией ссылки: свойства менять можно, переприсваивание наружу не видно. `const` защищает переменную, не объект.
5. Проверки типа: примитив — `typeof`, массив — `Array.isArray`, свой класс — `instanceof`, встроенный тип — `Object.prototype.toString.call`.
6. ToPrimitive: `Symbol.toPrimitive` → затем `valueOf`/`toString` (для подсказки `'string'` порядок обратный). `'default'` ведёт себя как `'number'`, кроме `Date`.
7. `==` может привести операнды дважды. Единственное оправданное применение — `x == null`.
8. `NaN` не равен себе. Проверять `Number.isNaN`. `includes` находит `NaN`, `indexOf` — нет.
9. Дроби неточны: сравнивай через `Number.EPSILON` или относительный допуск, деньги держи в целых. Большие идентификаторы — строкой или `BigInt`.
10. Спред и `Object.assign` копируют один уровень. Глубоко — `structuredClone`; через JSON теряются `Date`, `undefined`, функции, `Map`, `Set`.
11. Восемь ложных значений: `false`, `0`, `-0`, `0n`, `''`, `null`, `undefined`, `NaN`. Всё остальное истинно.
12. `??` срабатывает только на `null` и `undefined`, `||` — на любом ложном значении.
