# Область видимости и замыкания

Замыкание — тема, на которой валятся собеседования не потому, что она сложная, а потому что её обычно учат неправильно. Человек запоминает формулу «функция запоминает переменные снаружи», а потом не может объяснить, почему цикл с `var` печатает три тройки, почему колбэк в React видит старое состояние и почему один невинный обработчик держит в памяти мегабайт данных.

Всё это — следствия одного факта: **замыкание захватывает не значение, а саму переменную**. Ниже разберём, откуда этот факт берётся, начиная с того, как движок вообще ищет переменные.

Термины объясняются на месте, даже те, которые кажутся общеизвестными.

## Часть 1. Область видимости

### Что это такое

**Область видимости** (scope) — участок кода, внутри которого имя переменной что-то означает. Написал `count` — движок должен понять, какая именно ячейка памяти за этим именем стоит. Область видимости и есть правило, по которому он это решает.

Областей в JavaScript три вида:

- **Глобальная** — то, что объявлено вне всех функций и блоков. Живёт всё время работы страницы.
- **Функциональная** — создаётся при каждом вызове функции. Живёт, пока функция выполняется (и дольше, если её переменные кто-то удерживает — об этом вся вторая половина статьи).
- **Блочная** — фигурные скобки: тело `if`, тело цикла, просто `{ }` сами по себе. Работает только для `let`, `const` и `class`, но не для `var`.

### Лексическое окружение — то, что стоит за областью

Спецификация оперирует не «областью», а **лексическим окружением** (Lexical Environment). Это внутренняя структура, которую движок создаёт при входе в функцию или блок. У неё две части:

1. **Запись окружения** (Environment Record) — таблица «имя → ячейка со значением». Здесь лежат параметры функции и все объявленные внутри переменные.
2. **Ссылка на внешнее окружение** — указатель на то окружение, внутри которого этот кусок кода был **написан**.

Вторая часть — ключевая. Именно она превращает набор отдельных таблиц в **цепочку областей видимости** (scope chain).

### Как ищется переменная

Движок встретил имя. Дальше алгоритм тупой и предсказуемый:

1. Посмотреть в записи текущего окружения. Нашлось — взять оттуда, конец.
2. Не нашлось — перейти по ссылке на внешнее окружение и посмотреть там.
3. Повторять, пока не найдётся или пока не кончится цепочка.
4. Кончилась цепочка — `ReferenceError: x is not defined`.

```js
const userId = 7;                 // глобальная область

function outer() {
  const a = 'привет';             // область outer

  function inner() {
    const b = 1;                  // область inner
    console.log(b, a, userId);    // 1 'привет' 7
  }

  inner();
}
outer();
```

Из схемы видны два следствия, которые часто спрашивают:

- **Внутренняя функция видит внешние переменные, внешняя внутренние — нет.** Односторонность.
- **Ближняя переменная перекрывает дальнюю.** Если в `inner` объявить свою `a`, внешняя станет недоступна. Это называется **затенением** (shadowing).

### Лексическая область против динамической

**Лексическая** (она же статическая) область видимости означает: цепочка строится по тому, **где функция написана в тексте программы**. Не по тому, откуда её вызвали.

```js
const name = 'глобальное';

function say() {
  console.log(name);
}

function run() {
  const name = 'локальное';
  say();                // 'глобальное', а не 'локальное'
}
run();
```

`say` написана рядом с глобальной `name`, значит её внешнее окружение — глобальное. Откуда её позвали, роли не играет. Будь в JavaScript **динамическая** область видимости (как в старом bash или Emacs Lisp), вывод был бы `'локальное'`: функция смотрела бы в окружение вызывающего.

Это важно проговорить, потому что в JavaScript есть ровно одна вещь, которая ведёт себя динамически — `this`. Он определяется в момент вызова, а не в момент написания, и именно поэтому его так путают с областью видимости. Подробно про это — в статье [this и контекст вызова](./this-and-context).

## Часть 2. var, let, const и всплытие

### Что такое всплытие

**Всплытие** (hoisting) — не «объявления переезжают наверх», как пишут в туториалах. Реально происходит вот что: перед выполнением любого кода движок делает по нему проход и **создаёт в записи окружения ячейки для всех объявлений сразу**. Только потом начинает выполнять строки по порядку.

Разница между `var` и `let` — в том, что кладут в ячейку на этом первом проходе.

- `var`: ячейка создаётся и сразу получает значение `undefined`.
- `let` и `const`: ячейка создаётся, но остаётся **непроинициализированной**. Обращение к ней до строки объявления бросает ошибку.

```js
console.log(a);   // undefined — ячейка есть, значение уже положено
var a = 1;

console.log(b);   // ReferenceError: Cannot access 'b' before initialization
let b = 2;
```

Обрати внимание на текст ошибки: не «не определена», а «нельзя обратиться до инициализации». Движок **знает** про `b` — иначе сказал бы `b is not defined`. Он именно отказывается её отдать.

### Временная мёртвая зона

Промежуток от начала блока до строки с `let`/`const` называется **временная мёртвая зона** (Temporal Dead Zone, TDZ). Внутри неё переменная существует, но недоступна.

```js
{
  // TDZ для value начинается здесь
  typeof value;          // ReferenceError — даже typeof не спасает
  const value = 10;      // TDZ закончилась
  console.log(value);    // 10
}
```

Отдельно стоит запомнить: `typeof` для необъявленной переменной возвращает `'undefined'` и не падает, а для переменной в TDZ — падает. Это любимый вопрос-ловушка.

Зачем TDZ вообще нужна: чтобы `const` имел смысл. Если бы `const PI` до объявления возвращал `undefined`, то константа успевала бы побывать в двух состояниях — а это уже не константа. Заодно TDZ превращает опечатки и перепутанный порядок в громкую ошибку вместо тихого `undefined`.

### Функции всплывают целиком

**Объявление функции** (function declaration) на первом проходе не просто резервирует ячейку — оно создаёт функцию полностью. Поэтому её можно вызвать выше по тексту.

```js
greet();                      // работает
function greet() { console.log('привет'); }

hello();                      // TypeError: hello is not a function
var hello = function () {};   // ячейка есть, но в ней undefined
```

Во втором случае это **функциональное выражение** (function expression): всплывает только переменная `hello` со значением `undefined`, а функция попадает в неё лишь когда выполнение дойдёт до строки. Отсюда и ошибка: пытаемся вызвать `undefined`.

### Три отличия var от let

**1. Область.** `var` знает только функции, `let` знает блоки.

```js
function f() {
  if (true) {
    var x = 1;
    let y = 2;
  }
  console.log(x);   // 1 — var «вытек» из блока
  console.log(y);   // ReferenceError
}
```

**2. Повторное объявление.** `var x` дважды в одной области — молча работает. `let x` дважды — `SyntaxError` ещё до запуска.

**3. Глобальный `var` цепляется к объекту `window`.** `var g = 1` на верхнем уровне скрипта создаёт `window.g`. `let g = 1` — нет, он живёт в отдельной записи окружения скрипта. Практический эффект: `let` не может случайно перезаписать что-то встроенное.

Про `const` отдельно: он запрещает **переприсваивание переменной**, а не изменение объекта. `const arr = []` — `arr.push(1)` законно, `arr = []` нет. Константа — это ячейка, которую нельзя перенаправить на другое значение; на содержимое объекта, лежащего по ссылке, она никак не влияет.

## Часть 3. Замыкание

### Определение, которое реально работает

**Замыкание** (closure) — это функция вместе с тем лексическим окружением, в котором она была создана.

Формально в JavaScript замыкание — **каждая** функция: у любой из них есть внутреннее поле `[[Environment]]`, куда движок при создании записывает ссылку на текущее окружение. Говорить про замыкание становится интересно тогда, когда функция **пережила** окружение, в котором родилась.

```js
function makeCounter() {
  let count = 0;                 // локальная переменная makeCounter

  return function () {           // эта функция запомнила окружение makeCounter
    count += 1;
    return count;
  };
}

const next = makeCounter();
next();   // 1
next();   // 2
next();   // 3
```

`makeCounter` давно вернулась и снялась со стека вызовов. По обычной логике её локальные переменные должны были исчезнуть. Но возвращённая функция держит ссылку на окружение — значит **сборщик мусора не может его удалить**, и `count` продолжает жить.

**Сборщик мусора** (garbage collector) — часть движка, которая освобождает память под объектами, до которых больше нельзя добраться по ссылкам от корней (глобального объекта, стека вызовов). Пока на окружение есть живая ссылка, оно недостижимым не считается.

### Главное: захватывается переменная, а не значение

Вот утверждение, из которого выводятся почти все задачи на эту тему:

> Замыкание держит ссылку на **ячейку** переменной. Не снимок значения на момент создания функции, а саму живую ячейку. Изменилось значение в ячейке — замыкание увидит новое.

```js
let message = 'первое';

function show() {
  console.log(message);
}

show();               // 'первое'
message = 'второе';
show();               // 'второе' — функция не хранила копию
```

И обратное направление тоже работает: несколько функций, созданных в одном окружении, делят **одну и ту же** ячейку.

```js
function makePair() {
  let value = 0;
  return {
    get: () => value,
    inc: () => { value += 1; },
  };
}

const p = makePair();
p.inc();
p.inc();
p.get();   // 2 — обе функции работают с одной переменной value
```

А два разных вызова `makePair` создают два **разных** окружения — счётчики независимы. Окружение создаётся на каждый вызов, а не на каждую функцию в исходнике.

Отсюда правило для собеседования: **вопрос «какое значение увидит замыкание» всегда сводится к вопросу «сколько было создано окружений и что лежит в нужной ячейке в момент вызова».** Не в момент создания функции — в момент вызова.

## Часть 4. Классическая задача с циклом

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3 3 3
```

Почему не `0 1 2`. Разбор по шагам.

1. `var i` не имеет блочной области. Он принадлежит окружению функции (или глобальному). Ячейка `i` — **одна на весь цикл**.
2. Первая итерация: `i` равно `0`. `setTimeout` не вызывает колбэк, а ставит его задачей в очередь. Колбэк захватывает **ячейку** `i`, а не число `0`.
3. Вторая и третья итерации делают то же самое. В очереди теперь три колбэка, и все три ссылаются на одну ячейку.
4. Цикл проверяет условие в четвёртый раз: `i` равно `3`, условие ложно, цикл завершается. **В ячейке остаётся `3`.**
5. Синхронный код закончился, стек пуст. Событийный цикл начинает разбирать очередь задач (подробно про очереди — в статье [как работает браузер](./browser-rendering-event-loop)).
6. Первый колбэк читает ячейку `i` — там `3`. Печатает `3`. Второй и третий делают то же самое.

Заметь: даже без `setTimeout` эффект сохранится, если функции просто сложить в массив и вызвать после цикла. Асинхронность здесь не причина, а лишь удобный способ отложить чтение — причина в том, что ячейка одна.

### Починка 1: let

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0 1 2
```

Спецификация делает для `let` в заголовке цикла особую вещь: **на каждую итерацию создаётся новое окружение**, и значение из предыдущей итерации копируется в новую ячейку. Три итерации — три ячейки — три замыкания на три разных `i`. Ничего волшебного, просто цикл с `let` работает не так, как выглядит.

### Починка 2: немедленно вызываемая функция

Способ из эпохи до `let`. Оборачиваем тело итерации в функцию и сразу вызываем её — вызов создаёт новое окружение, а параметр получает **копию** текущего значения.

```js
for (var i = 0; i < 3; i++) {
  (function (j) {
    setTimeout(() => console.log(j), 0);
  })(i);            // i копируется в параметр j при вызове
}
// 0 1 2
```

Ключ в том, что аргументы передаются по значению: `j` — отдельная ячейка в отдельном окружении, и после вызова её никто не меняет.

### Починка 3: bind или дополнительный аргумент

```js
for (var i = 0; i < 3; i++) {
  setTimeout(console.log.bind(null, i), 0);   // i зафиксирован при создании
}
// 0 1 2
```

`bind` создаёт новую функцию с заранее подставленными аргументами — значение `i` считывается прямо сейчас. Тот же эффект даёт третий аргумент `setTimeout`, который передаётся в колбэк: `setTimeout(console.log, 0, i)`. Про `bind` подробнее в статье [this и контекст вызова](./this-and-context).

Все три починки делают одно и то же: превращают **одну общую ячейку** в **три отдельные**.

## Часть 5. Где замыкания работают каждый день

### Приватное состояние

До приватных полей класса это был единственный способ спрятать данные. Переменная в области функции недоступна снаружи в принципе — не «по соглашению с подчёркиванием», а физически.

```js
function createStore(initial) {
  let state = initial;                       // снаружи не достать
  const listeners = new Set();

  return {
    getState: () => state,
    setState(next) {
      state = next;
      listeners.forEach((fn) => fn(state));
    },
    subscribe(fn) {
      listeners.add(fn);
      return () => listeners.delete(fn);     // функция отписки — тоже замыкание
    },
  };
}
```

Это, по сути, скелет Redux. Обрати внимание на функцию отписки: она замкнулась и на `listeners`, и на `fn` — двух переменных из двух разных окружений.

### Фабрики функций

```js
const multiplier = (factor) => (n) => n * factor;

const double = multiplier(2);
const triple = multiplier(3);
double(5);   // 10
triple(5);   // 15
```

`double` и `triple` — одна и та же функция в исходнике, но два разных окружения с разными `factor`. Приём называется **каррирование** (currying), и вся его механика — замыкание на параметр.

### Обработчики событий

```js
function bindRow(row, id) {
  row.addEventListener('click', () => open(id));   // id живёт в замыкании
}
```

Обработчик вызовется через минуты после того, как `bindRow` завершилась. Он работает только потому, что окружение с `id` не было собрано мусорщиком.

### debounce

Классическая задача на живом кодировании — и она целиком про замыкание.

```js
function debounce(fn, delay) {
  let timer = null;                 // состояние между вызовами живёт здесь

  return function (...args) {
    clearTimeout(timer);            // читаем ячейку из замыкания
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const onInput = debounce((text) => search(text), 300);
```

`timer` — ровно та самая «переменная, а не значение»: каждая новая версия функции читает то, что записала предыдущая. Без замыкания пришлось бы держать таймер в глобальной переменной, и два разных `debounce` мешали бы друг другу.

## Часть 6. Утечки памяти через замыкания

**Утечка** — память, которую программа не может освободить, хотя данные уже не нужны. Замыкания — типичный источник, потому что удерживают окружение целиком.

### Один обработчик держит большой объект

```js
function init() {
  const hugeData = new Array(1_000_000).fill('...');   // мегабайты
  const id = hugeData.length;

  document.getElementById('btn').addEventListener('click', () => {
    console.log(id);        // нужен только id
  });
}
```

Здесь тонкость. Спецификация не требует хранить всё окружение — движки (V8 в том числе) при компиляции определяют, какие переменные реально используются внутри функции, и кладут в контекст замыкания только их. Так что в этом примере `hugeData`, скорее всего, будет освобождена.

Но полагаться на это опасно, потому что оптимизация ломается от мелочей: `eval` внутри, отладчик, а главное — **общий контекст**. Если в той же функции создаётся вторая замкнутая функция, которая использует `hugeData`, контекст будет общим, и первый обработчик продлит жизнь данных, которые ему не нужны.

```js
function init() {
  const hugeData = new Array(1_000_000).fill('...');

  const onClick = () => console.log('клик');           // hugeData не нужна
  const onDump = () => console.log(hugeData.length);   // а здесь нужна

  // обе функции разделяют один контекст: пока жива onClick, жива и hugeData
  document.getElementById('btn').addEventListener('click', onClick);
}
```

Практический вывод: если из большого объекта нужна одна цифра — **вытащи её и обнули ссылку**, не надеясь на оптимизатор.

### Не снятые обработчики и таймеры

Самая частая утечка вообще. Обработчик события ссылается на замыкание, DOM-узел ссылается на обработчик, а на узел ссылается живой документ. Удалил компонент, забыл `removeEventListener` — цепочка не рвётся.

То же с `setInterval`: пока интервал не остановлен, движок держит колбэк, а тот — всё своё окружение. Отсюда обязательная уборка в `useEffect` и в `disconnectedCallback`.

```js
useEffect(() => {
  const t = setInterval(tick, 1000);
  return () => clearInterval(t);     // без этого замыкание живёт вечно
}, []);
```

### Как ловить

DevTools → Memory → Heap snapshot. Сделай снимок, поработай со страницей, сделай второй, сравни в режиме Comparison. Раздел `Closure` в списке типов покажет, сколько памяти удерживается замыканиями; колонка Retainers — кто именно держит объект. Если после ухода со страницы её компоненты всё ещё в снимке, ищи не снятую подписку.

## Часть 7. Устаревшее замыкание в React

**Устаревшее замыкание** (stale closure) — ситуация, когда функция читает переменную из окружения, которое уже неактуально. В React это встречается чаще всего, потому что там каждый рендер — это **новый вызов функции компонента**, а значит новое окружение с новыми константами.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);        // всегда 0
      setCount(count + 1);       // всегда 0 + 1
    }, 1000);
    return () => clearInterval(id);
  }, []);                        // пустой массив зависимостей

  return <p>{count}</p>;
}
```

Разбор по шагам:

1. Первый рендер. Вызывается функция `Counter`, создаётся окружение, в нём `count` равен `0`.
2. `useEffect` с пустым массивом зависимостей запускается один раз. Колбэк интервала создан **в этом окружении** и замкнулся на его `count`.
3. Через секунду счётчик становится `1`, React рендерит компонент заново — вызывает `Counter` ещё раз. Создаётся **новое** окружение, где `count` равен `1`.
4. Но интервал не пересоздавался: он всё ещё держит колбэк из первого окружения. А там `count` — это `const`, и он навсегда `0`.
5. Каждую секунду выполняется `setCount(0 + 1)`. Значение не меняется, компонент застревает на единице.

Обрати внимание: это **не** противоречие с правилом «захватывается переменная, а не значение». Ячейка действительно захвачена — просто это ячейка первого окружения, и её значение никто не менял. `count` объявлен через `const` внутри функции компонента, а каждый рендер создаёт свежую пару «окружение + константа».

### Три способа починить

**1. Функциональное обновление.** Не читать `count` вообще.

```jsx
useEffect(() => {
  const id = setInterval(() => setCount((c) => c + 1), 1000);
  return () => clearInterval(id);
}, []);
```

`setCount` с функцией получает актуальное значение от самого React. Замыкание больше не участвует. Это лучший вариант, когда новое состояние выводится из старого.

**2. Честные зависимости.** Указать `count` в массиве — тогда эффект будет пересоздаваться на каждое изменение, и замыкание всегда свежее.

```jsx
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, [count]);   // интервал пересоздаётся каждую секунду
```

Работает, но интервал сбрасывается при каждом изменении — для таймера это плохо, для подписки на что-то обычно нормально.

**3. Ref как изменяемая ячейка.** `useRef` возвращает один и тот же объект на все рендеры. Замыкание захватывает объект, а читает поле `.current` в момент вызова — то есть свежее.

```jsx
const countRef = useRef(count);
countRef.current = count;              // обновляем на каждом рендере

useEffect(() => {
  const id = setInterval(() => console.log(countRef.current), 1000);
  return () => clearInterval(id);
}, []);
```

Тот же приём лечит устаревший колбэк в `useCallback` с пустыми зависимостями: сама функция стабильна, а внутрь смотрит через ref.

Правило, которое стоит запомнить: **массив зависимостей — это не оптимизация, а объявление того, какое окружение видит эффект.** Убрал из него переменную, которую читаешь, — получил устаревшее замыкание. Линтер `react-hooks/exhaustive-deps` ругается именно на это, и молча глушить его нельзя.

## Что спросят на интервью

**Что такое замыкание?** Функция вместе с лексическим окружением, в котором она создана. Практически: функция сохраняет доступ к переменным внешней области даже после того, как та завершилась.

**Что выведет цикл с `var` и `setTimeout`?** Три тройки. `var` даёт одну ячейку на весь цикл; все колбэки читают её после завершения цикла, когда там уже `3`.

**Как починить?** Заменить на `let` (новая ячейка на итерацию), обернуть в немедленно вызываемую функцию с параметром, либо зафиксировать значение через `bind` или третий аргумент `setTimeout`.

**Замыкание хранит значение или ссылку на переменную?** Ссылку на ячейку. Поэтому изменение переменной снаружи видно внутри замыкания, а несколько функций из одного окружения делят одно состояние.

**Чем `let` отличается от `var`?** Блочная область против функциональной; TDZ вместо `undefined` до объявления; запрет повторного объявления; глобальный `let` не попадает в `window`.

**Что такое TDZ?** Промежуток от начала блока до строки объявления `let`/`const`, где переменная уже существует, но обращение к ней даёт `ReferenceError`. Даже `typeof` падает.

**Всплывают ли функции?** Объявления функций — да, целиком, их можно вызывать выше по тексту. Функциональные выражения — нет, всплывает только переменная со значением `undefined`.

**Могут ли замыкания приводить к утечкам?** Да: удерживают окружение, пока жива функция. Классика — не снятый обработчик события или `setInterval`, продлевающие жизнь всему, что было в области.

**Почему колбэк в `useEffect` видит старое состояние?** Каждый рендер — новый вызов функции компонента и новое окружение. Эффект с пустыми зависимостями остался с окружением первого рендера. Чинится функциональным обновлением, честными зависимостями или ref.

**Зачем замыкания нужны на практике?** Приватное состояние, фабрики функций, каррирование, `debounce` и `throttle`, обработчики с параметром, модульный паттерн.

## Коротко, для повторения

1. Область видимости — правило, по которому имя связывается с ячейкой. Поиск идёт изнутри наружу по цепочке окружений и никогда наоборот.
2. Цепочка строится **лексически** — по месту написания кода, а не по месту вызова. Динамически ведёт себя только `this`.
3. Всплытие — это создание ячеек до выполнения кода. `var` сразу получает `undefined`, `let` и `const` остаются в TDZ до строки объявления.
4. Объявление функции всплывает целиком, функциональное выражение — нет.
5. Замыкание — функция плюс окружение её создания. Окружение живёт, пока жива функция.
6. Захватывается **переменная, а не значение**. Отсюда и три тройки в цикле, и общее состояние нескольких функций.
7. Одно окружение создаётся на **один вызов**. Разные вызовы фабрики — независимые состояния.
8. `let` в заголовке цикла создаёт новую ячейку на каждую итерацию — поэтому и чинит классическую задачу.
9. Замыкания — механизм приватности, каррирования, `debounce` и всех обработчиков с параметром.
10. Утечка возникает, когда живая функция удерживает уже ненужное окружение: снимай обработчики, чисти интервалы, не тащи большие объекты в общий контекст.
11. В React каждый рендер — новое окружение. Массив зависимостей объявляет, какое окружение видит эффект; неполный список даёт устаревшее замыкание.
