# Память, сборка мусора и утечки

В JavaScript память не выделяют и не освобождают руками — и именно поэтому про неё почти никто ничего не знает. Пока приложение маленькое, это не мешает. Потом приходит жалоба «вкладка через час работы ест полтора гигабайта и всё тормозит», и выясняется, что «сборщик мусора сам всё уберёт» — не заклинание, а утверждение с условиями. Условия надо знать.

Эта статья про то, где что лежит, по какому правилу сборщик решает удалить объект, почему циклические ссылки не проблема, а забытый `setInterval` — проблема, и как найти утечку в DevTools за двадцать минут вместо двух дней.

## Часть 1. Где лежат данные

### Стек

**Стек** (stack) — область памяти, устроенная как стопка тарелок: кладём сверху, снимаем сверху. Каждый вызов функции кладёт на стек **кадр** (frame): её аргументы, локальные переменные, адрес возврата. Функция закончилась — кадр снялся, память освободилась мгновенно и бесплатно, без всякого сборщика.

Стек быстрый, потому что «освободить» — это просто сдвинуть указатель вниз. И он маленький: обычно от нескольких сотен килобайт до пары мегабайт. Именно поэтому глубокая рекурсия падает с `Maximum call stack size exceeded` — кадры не поместились.

### Куча

**Куча** (heap) — большая неупорядоченная область, где живут объекты: массивы, функции, объекты, замыкания, узлы DOM. Размер объекта заранее неизвестен, живёт он произвольно долго, поэтому по принципу стопки его не разложишь.

### Что где

Правило, которое надо уметь сформулировать:

- **Примитивы** (число, строка, булево, `null`, `undefined`, символ, `bigint`) — небольшие значения, лежат прямо в переменной, то есть на стеке (движки оптимизируют по-разному, но модель именно такая).
- **Объекты** живут в куче. В переменной лежит **ссылка** — по сути адрес, где объект находится. Про то, как это проявляется при копировании и сравнении, есть статья [массивы, объекты и иммутабельность](./arrays-objects-immutability).

Отсюда поведение, которое все знают, но не все объясняют:

```js
let a = { n: 1 };
let b = a;        // скопировали ссылку, не объект
b.n = 2;
console.log(a.n); // 2 — это один и тот же объект в куче

let x = 1;
let y = x;        // скопировали значение
y = 2;
console.log(x);   // 1
```

Строки — примитивы, но большие: движок хранит их в куче, а семантику даёт как у примитива (изменить нельзя, только создать новую). Поэтому склейка строк в цикле на миллион итераций — это давление на кучу, а не «бесплатная операция со стеком».

## Часть 2. Достижимость

### Почему не счётчик ссылок

Первая идея, которая приходит в голову: считать, сколько ссылок указывает на объект, и удалять его при нуле. Такой сборщик называется **подсчётом ссылок** (reference counting), и он действительно был в старых браузерах.

Он ломается на **циклах**:

```js
function make() {
  const a = {};
  const b = {};
  a.pair = b;
  b.pair = a;   // ссылаются друг на друга
  return null;
}
make();
```

После выхода из функции `a` и `b` недостижимы: до них не добраться ни из какого работающего кода. Но у каждого счётчик равен единице — они держат друг друга. Такой сборщик их никогда не удалит. Именно из-за этого в IE до девятой версии текли обработчики событий: узел DOM и функция ссылались друг на друга через два разных механизма памяти.

### Как работает на самом деле

Современные движки используют **достижимость** (reachability). Правило:

> Объект жив, если до него можно добраться по цепочке ссылок, начав от одного из корней.

**Корни** (GC roots) — то, что живо по определению:

- глобальный объект (`window`, `globalThis`) и всё, что на нём висит;
- переменные и кадры функций, которые сейчас на стеке вызовов;
- активные замыкания;
- узлы, встроенные в живой документ DOM;
- отложенные колбэки: таймеры, обработчики событий, ожидающие промисы.

Алгоритм называется **пометить и подмести** (mark-and-sweep): сборщик стартует от корней, обходит все ссылки, помечает всё, до чего дошёл; всё непомеченное — мусор, его память освобождается.

## Часть 3. Сборщик поколений

Полный обход всей кучи стоит дорого: объектов миллионы. Поэтому движки (V8 в первую очередь) опираются на статистическое наблюдение, известное как **гипотеза поколений**: подавляющее большинство объектов умирает молодыми. Промежуточный массив внутри функции, объект события, временная строка — все они не переживают и десятка миллисекунд.

Значит, часто проверять надо только новые объекты.

### Молодое поколение

Новое пространство (**new space**, оно же nursery) — небольшая область, обычно единицы мегабайт, разделённая на две половины. Все новые объекты создаются здесь.

Сборка (**scavenge**, малая сборка) устроена так: живые объекты из активной половины копируются во вторую, половины меняются местами, а первая целиком считается пустой. Стоимость зависит **только от количества выживших**, а не от объёма мусора. Если из тысячи объектов выжил один — работы на один объект.

Объект, переживший две малые сборки, **повышается** (promoted) в старое поколение.

### Старое поколение

Старое пространство (**old space**) — большая область для долгоживущих объектов. Тут собирают редко и другим алгоритмом: пометить и подмести, плюс периодическая **компактификация** — сдвиг живых объектов вплотную друг к другу, чтобы убрать «дыры» (фрагментацию).

Полная сборка старого поколения дорогая, поэтому V8 делает её **инкрементально** (кусочками между задачами), **конкурентно** (в фоновых потоках) и **параллельно** (в нескольких потоках сразу). Всё для того, чтобы не остановить главный поток надолго — про то, чем грозит длинная задача на главном потоке, есть в статье [как работает браузер](./browser-rendering-event-loop).

Практические следствия:

1. **Короткоживущие объекты почти бесплатны.** Не надо «оптимизировать» создание временных объектов в цикле ради памяти — молодое поколение к этому и приспособлено. Переиспользование объектов ради экономии GC обычно преждевременная оптимизация.
2. **Дорого — держать объекты долго.** Объект, доживший до старого поколения, будет проверяться дорогим алгоритмом. Утечка страшна именно тем, что заполняет старое пространство.
3. **Пауза на сборку — редкая, но заметная.** Если в профиле производительности видны периодические «ступеньки» на графике памяти и всплески в главном потоке, помеченные как GC, — это оно.

## Часть 4. Что такое утечка в браузере

Определение, которое стоит запомнить дословно:

> **Утечка — это объект, который логически уже не нужен, но остаётся достижимым от корней, поэтому сборщик обязан его сохранить.**

Сборщик не ошибается. Он честно выполняет своё правило. Ошибается программа: она держит ссылку на то, что уже не должна держать.

Отсюда и метод поиска: искать надо не «где не освободили», а **кто держит ссылку**. Это принципиально другой вопрос, и DevTools отвечает именно на него.

Симптомы утечки:

- график памяти растёт при повторении одного и того же действия (открыл-закрыл модалку сто раз) и не возвращается к исходному уровню после принудительной сборки;
- страница со временем тормозит всё сильнее — сборщик работает всё чаще на всё большей куче;
- на слабых устройствах вкладка перезагружается сама (Out of memory).

Важный критерий: **утечка — это рост, который не откатывается.** Просто высокое потребление памяти — не утечка. Пила, которая возвращается к прежнему уровню, — нормальная работа сборщика.

## Часть 5. Шесть источников утечек

### 1. Неснятые слушатели событий

Самый частый случай. Слушатель — это ссылка от элемента к функции, а функция замыкает всё, что было рядом.

```js
function mountWidget(data) {
  const box = document.querySelector('#box');

  // Замыкание держит data. Слушатель на document держит замыкание.
  document.addEventListener('keydown', (e) => {
    if (e.key === 'Escape') hide(box, data);
  });
}
```

Виджет размонтировали, `box` удалили из документа — а слушатель на `document` жив, значит живо замыкание, значит живы и `box`, и `data`. Вызвали `mountWidget` двадцать раз — двадцать копий.

Лечится снятием: `removeEventListener` той же функцией и тем же флагом `capture`, либо `{ once: true }`, либо `AbortController` — подробно в статье [события DOM](./dom-events).

Тонкость: слушатель на элементе, который целиком удалён и больше нигде не упомянут, утечкой **не является** — узел и функция станут недостижимы вместе. Опасны слушатели на долгоживущих целях: `window`, `document`, `body`, глобальная шина событий.

### 2. Таймеры и интервалы

```js
setInterval(() => {
  chart.update(bigDataset);   // chart и bigDataset живут вечно
}, 1000);
```

`setInterval` — корень: браузер держит колбэк, чтобы вызывать его снова и снова. Пока интервал не очищен, живо всё, что колбэк замкнул. Компонент размонтировали, а интервал продолжает тикать и держать целый граф объектов.

`setTimeout` менее опасен — он снимается после срабатывания. Но таймаут на час держит замыкание час.

Правило: **у каждого `setInterval` должен быть свой `clearInterval` в коде очистки.** Если не можешь показать пальцем, где интервал останавливается, — у тебя утечка.

### 3. Подписки без отписки

Обобщение первых двух: любая подписка — на стор, на WebSocket, на `IntersectionObserver`, на `ResizeObserver`, на `MutationObserver`, на RxJS-поток — регистрирует твой колбэк в чужом списке.

```js
// Плохо
useEffect(() => {
  store.subscribe(onChange);
}, []);

// Хорошо: возвращаем функцию отписки
useEffect(() => store.subscribe(onChange), []);
```

Наблюдатели (`IntersectionObserver` и родня) требуют `disconnect()`. Они держат и колбэк, и наблюдаемые элементы.

### 4. Отсоединённые узлы DOM

Самая коварная категория, потому что визуально всё в порядке: элемент со страницы исчез.

**Отсоединённый узел** (detached node) — узел, удалённый из документа, но на который осталась ссылка из JavaScript. Пока ссылка жива, живо и **всё поддерево** этого узла: удалив контейнер с тысячей строк, ты не освободил ни одной, если где-то сохранил ссылку на контейнер.

```js
const cache = [];

function render(items) {
  const list = document.createElement('ul');
  for (const it of items) {
    const li = document.createElement('li');
    li.textContent = it.title;
    list.append(li);
  }
  cache.push(list);              // <- вот здесь утечка
  root.replaceChildren(list);    // старый список ушёл из документа,
}                                //    но остался в cache вместе со всеми li
```

### 5. Растущие кеши и логи

```js
const cache = new Map();

function getUser(id) {
  if (!cache.has(id)) cache.set(id, fetchUser(id));
  return cache.get(id);
}
```

Выглядит как разумная мемоизация. Но у этого кеша **нет выселения**: он растёт ровно столько, сколько разных `id` пройдёт через приложение. За рабочий день — десятки тысяч.

Кеш без ограничения размера — это утечка с отсрочкой. Минимум, что нужно: предел количества записей (LRU — выбрасываем давно не использованное), или срок жизни, или `WeakMap`, если ключ — объект. То же касается массивов логов, истории действий и очередей сообщений, из которых никто не вычитывает.

### 6. Замыкания, держащие лишнее

Функция замыкает **всё окружение**, в котором создана, а не только то, что использует — механику разбирает статья [область видимости и замыкания](./scope-and-closures). Движки умеют отбрасывать неиспользуемые переменные, но это оптимизация, а не гарантия — особенно если рядом есть `eval` или отладчик.

```js
function make() {
  const huge = new Array(1e6).fill('x');   // 1 млн элементов
  const id = huge.length;

  return () => id;   // используем только id, но окружение общее
}
```

Надёжнее вытащить нужное и явно оборвать связь:

```js
function make() {
  let huge = new Array(1e6).fill('x');
  const id = huge.length;
  huge = null;          // явно отпускаем
  return () => id;
}
```

Отдельный случай — **общее окружение двух замыканий**. Если из одной функции возвращаются две, они делят одно окружение: пока жива «лёгкая», жива и переменная, нужная только «тяжёлой».

Ещё одна классика — случайные глобальные переменные: присваивание без `let`/`const` в нестрогом режиме создаёт свойство `window`, то есть вешает объект прямо на корень. `'use strict'` и модули эту дыру закрывают.

## Часть 6. Слабые ссылки

### WeakMap и WeakSet

**Слабая ссылка** — ссылка, которую сборщик мусора не считает основанием сохранять объект. Если на объект остались только слабые ссылки, он будет собран.

`WeakMap` — коллекция «ключ-значение», где **ключом может быть только объект** и ключ удерживается слабо. Объект собрали — запись из `WeakMap` исчезла сама.

```js
const meta = new WeakMap();

function attach(el, data) {
  meta.set(el, data);   // el удерживается слабо
}
// Элемент удалили из DOM и отовсюду — запись в meta уходит сама
```

Это и есть штатный способ привязать данные к объекту, которым ты не владеешь: к узлу DOM, к экземпляру чужого класса, к аргументу функции.

`WeakSet` — то же самое для «набора объектов»: пометить «этот уже обработан», не мешая ему быть собранным.

**Почему они не итерируются.** У `WeakMap` нет ни `size`, ни `keys()`, ни `forEach`. Причина фундаментальная: содержимое зависит от того, когда именно отработал сборщик. Если бы можно было перечислить ключи, поведение программы стало бы зависеть от момента сборки — а это деталь реализации, недетерминированная и разная в разных движках. Такой канал наблюдения за сборщиком закрыли намеренно.

Отсюда практическое ограничение: `WeakMap` годится как **хранилище по ключу**, но не как кеш, который надо обойти или очистить целиком.

### WeakRef и FinalizationRegistry

`WeakRef` — слабая ссылка на объект в чистом виде:

```js
const ref = new WeakRef(bigObject);
// ...позже
const obj = ref.deref();   // либо объект, либо undefined, если его собрали
if (obj) use(obj);
```

`FinalizationRegistry` позволяет получить уведомление после того, как объект собран:

```js
const registry = new FinalizationRegistry((key) => {
  console.log('собран объект с ключом', key);
});
registry.register(obj, 'user:42');
```

Оба инструмента спецификация прямо помечает как «применять с осторожностью». Момент сборки не гарантирован: колбэк может вызваться через минуту, а может не вызваться никогда (например, при закрытии вкладки). Строить на них логику приложения нельзя — только необязательные вещи вроде очистки внешнего кеша или закрытия соединения «на всякий случай».

Реальная ниша: кеш больших объектов, которые не жалко потерять и легко пересоздать (разобранные картинки, распарсенные документы).

## Часть 7. Как искать утечку в DevTools

### Инструменты

На вкладке **Memory** есть три режима:

- **Heap snapshot** — полный снимок кучи: все объекты, их размеры и ссылки между ними. Главный инструмент.
- **Allocation instrumentation on timeline** — запись выделений во времени: видно, в какой момент и в какой строке кода родились объекты, которые дожили до конца записи.
- **Allocation sampling** — лёгкий статистический профиль по функциям, годится для долгих записей.

Ещё есть **Performance monitor** — живые графики JS heap size, количества узлов DOM и количества слушателей. С него удобно начинать: если растёт число узлов или слушателей при повторяющемся действии, диагноз уже почти есть.

### Два числа, которые надо различать

- **Shallow Size** — размер самого объекта, без того, на что он ссылается. У массива на миллион элементов shallow size маленький: сами элементы лежат отдельно.
- **Retained Size** — сколько памяти освободится, **если удалить этот объект**. То есть размер всего, что держится только через него.

**Смотреть надо на Retained Size.** Именно он отвечает на вопрос «кто виноват». Сортировка по нему сверху обычно сразу показывает виновника.

Связанное понятие — **доминатор**: объект, через который проходит любой путь от корня к данному. Вкладка Containment и колонка Retainers показывают цепочку удержания снизу вверх: «этот узел держится массивом, массив — свойством стора, стор — window».

### Метод трёх снимков

Это то, что нужно уметь описать на интервью.

1. Выполни целевое действие один раз «вхолостую» — чтобы прогрелись ленивые загрузки и разовые кеши.
2. Сделай **снимок 1**.
3. Повтори действие 5–10 раз (открыть-закрыть модалку, перейти на страницу и обратно).
4. Нажми кнопку принудительной сборки мусора (иконка корзины), затем сделай **снимок 2**.
5. Переключи режим сравнения на **Comparison** и выбери сравнение с первым снимком.

В колонке `#Delta` видно, сколько объектов каждого типа добавилось и не удалилось. Если после десяти открытий модалки прибавилось десять `Detached HTMLDivElement` — утечка найдена по типу, осталось найти держателя.

Принудительная сборка перед снимком обязательна: без неё в куче остаётся мусор, который просто не успели собрать, и вся картина зашумлена. Впрочем, DevTools и так запускает сборку перед снимком — но явная кнопка надёжнее.

### Фильтр Detached

В строке фильтра снимка набери `Detached`. Появятся все узлы DOM, оторванные от документа, но живые в памяти. Выбираешь самый жирный по Retained Size, смотришь панель Retainers внизу — там цепочка ссылок до корня. Обычно в ней сразу видно имя переменной или поля, которое держит узел.

### Разбор одного сценария

Жалоба: «SPA с таблицей заказов, к концу дня вкладка ест гигабайт».

**Шаг 1. Подтвердить, что это утечка.** Открываем Performance monitor, переключаемся между страницей списка и деталями двадцать раз. JS heap растёт со 40 до 180 МБ, после принудительной сборки падает только до 150. Не откатывается — утечка.

**Шаг 2. Понять масштаб.** Там же видно: DOM Nodes выросло с 3 тысяч до 40 тысяч и не падает. Значит текут узлы, а не просто данные.

**Шаг 3. Снимки.** Снимок, десять переходов туда-обратно, сборка, второй снимок, режим Comparison. В дельте: `Detached HTMLTableRowElement` — плюс 10 000, `Detached HTMLDivElement` — плюс 400. Ровно по тысяче строк на переход.

**Шаг 4. Найти держателя.** Фильтр `Detached`, сортировка по Retained Size, первая строка — `Detached HTMLTableElement` с ретейном 12 МБ. Смотрим Retainers:

```
Detached HTMLTableElement
  ← rows in Object (замыкание)
    ← context in ()=>{} (функция-обработчик)
      ← listener in ResizeObserver
        ← observers in Window
```

Читаем снизу вверх: `ResizeObserver`, созданный при монтировании таблицы, никто не отключил. Он держит колбэк, колбэк замкнул массив строк, массив держит все `tr`.

**Шаг 5. Проверить гипотезу в коде.** Ищем `new ResizeObserver` — действительно, `disconnect()` нигде нет.

**Шаг 6. Починить и перепроверить.** Добавляем `observer.disconnect()` в очистку, повторяем метод трёх снимков. `#Delta` по `Detached HTMLTableRowElement` стал нулём, куча возвращается к 45 МБ.

Порядок один и тот же всегда: **подтвердить рост → определить тип текущих объектов → найти держателя через Retainers → найти это место в коде → починить → перепроверить тем же измерением.**

### Что мешает при отладке

- Открытый DevTools сам держит ссылки на то, что ты вывел в консоль через `console.log`. Объект, залогированный один раз, будет жить, пока консоль не очищена. Перед снятием снимков консоль стоит очистить.
- Расширения браузера добавляют свои объекты в кучу. Отлаживать лучше в приватном окне без расширений.
- Development-сборки фреймворков хранят дополнительную отладочную информацию. Итоговое подтверждение лучше делать на production-сборке.

## Часть 8. Профилактика

Что реально снижает вероятность утечек:

1. **Симметрия подписок.** Подписался — в том же блоке кода напиши, где отпишешься. В React это `return` из `useEffect`, в классах — метод уничтожения.
2. **Один `AbortController` на компонент.** Все слушатели и запросы через один сигнал, очистка — один `abort()`.
3. **У каждого кеша есть предел.** Количество записей, срок жизни или слабые ключи. «Пока просто Map, потом разберёмся» — не разберутся.
4. **`WeakMap` для данных, привязанных к объектам.** Если ключ — узел DOM или чужой экземпляр, слабая коллекция избавляет от ручной очистки.
5. **Не хранить узлы DOM в долгоживущем состоянии.** Держи идентификатор и находи узел заново, а не сохраняй ссылку в глобальном сторе.
6. **Регулярное измерение.** Метод трёх снимков на ключевых сценариях раз в спринт находит утечку, пока она стоит десять минут, а не два дня.

## Что спросят на интервью

**Где хранятся примитивы, а где объекты?** Примитивы — по значению, в кадре стека; объекты — в куче, а в переменной лежит ссылка. Отсюда разница между копированием значения и копированием ссылки.

**Как работает сборщик мусора?** По достижимости: обходит граф от корней (глобальный объект, стек вызовов, замыкания, живой DOM, отложенные колбэки), помечает всё, до чего дошёл, освобождает остальное — алгоритм mark-and-sweep.

**Почему не подсчёт ссылок?** Он не собирает циклы: два объекта, ссылающиеся друг на друга, имеют ненулевые счётчики, но недостижимы. Достижимость эту проблему решает бесплатно.

**Что такое поколения?** Молодое пространство для новых объектов, собирается часто и дёшево копированием выживших; пережившие две сборки переезжают в старое пространство, где собирают редко, дорого и инкрементально. Основано на наблюдении, что большинство объектов умирает молодыми.

**Что такое утечка, если память освобождается автоматически?** Объект логически не нужен, но остаётся достижимым от корня — сборщик обязан его сохранить. Ошибка не в сборщике, а в лишней ссылке.

**Назови типичные утечки во фронтенде.** Неснятые слушатели на долгоживущих целях, незакрытые `setInterval`, подписки без отписки, отсоединённые узлы DOM, кеши без выселения, замыкания, держащие крупные структуры, случайные глобальные переменные.

**Что такое отсоединённый узел?** Узел, удалённый из документа, но удерживаемый ссылкой из JavaScript. Держит всё своё поддерево. Ищется в снимке кучи по фильтру `Detached`.

**Зачем `WeakMap` и почему он не итерируется?** Ключи удерживаются слабо и исчезают вместе с объектом — удобно для метаданных к чужим объектам. Не итерируется, потому что перечисление сделало бы поведение программы зависимым от момента работы сборщика.

**Чем `WeakRef` отличается от `WeakMap`?** `WeakRef` — слабая ссылка на один объект, читается через `deref()`, может вернуть `undefined`. Применять осторожно: момент сборки не определён. `FinalizationRegistry` даёт колбэк после сборки, но его вызов не гарантирован.

**Как найдёшь утечку?** Performance monitor для подтверждения роста, метод трёх снимков с Comparison для поиска типа текущих объектов, фильтр `Detached` и панель Retainers для поиска держателя, сортировка по Retained Size — по нему, а не по Shallow.

## Коротко, для повторения

1. Примитивы — на стеке по значению, объекты — в куче, в переменной ссылка. Стек освобождается сам при выходе из функции.
2. Сборщик работает по достижимости от корней, а не по счётчику ссылок, поэтому циклы для него не проблема.
3. Корни: глобальный объект, стек вызовов, замыкания, живой DOM, отложенные колбэки таймеров, слушателей и промисов.
4. Поколения: молодые объекты собираются часто и дёшево, пережившие две сборки переезжают в старое пространство, где сборка дорогая и инкрементальная.
5. Утечка — это достижимость без надобности. Искать надо держателя ссылки.
6. Шесть источников: слушатели, таймеры, подписки, отсоединённые узлы, безграничные кеши, тяжёлые замыкания.
7. Ссылка на корень отсоединённого поддерева держит все его узлы.
8. `WeakMap`/`WeakSet` — слабые ключи, не итерируются намеренно. `WeakRef`/`FinalizationRegistry` — только для необязательной логики.
9. Retained Size отвечает на вопрос «сколько освободится», Shallow Size — «сколько весит сам объект». Смотреть на первый.
10. Метод: подтвердить рост → три снимка и Comparison → фильтр `Detached` → Retainers → код → перепроверить.
