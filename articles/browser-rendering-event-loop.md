# Как на самом деле работает браузер

Эта статья про то, что происходит между «браузер получил HTML» и «пользователь увидел картинку и смог по ней кликнуть». И, главное, про то, как в эту картину встраивается событийный цикл — та самая штука, из-за которой `setTimeout(fn, 0)` выполняется позже промиса, а тяжёлый цикл подвешивает всю страницу.

Читать стоит подряд: каждая часть опирается на предыдущую. Все термины объясняются на месте, даже те, которые кажутся общеизвестными.

## Часть 1. Из чего состоит браузер

### Процессы и потоки — на пальцах

**Процесс** — это отдельная запущенная программа со своей памятью. Если процесс упал, остальные продолжают работать: у них своя память, они друг друга не видят.

**Поток** (тред) — это линия выполнения кода внутри процесса. Один процесс может иметь несколько потоков, и они делят общую память. Поток выполняет команды строго по очереди: пока не закончил одну, не начнёт следующую.

Современный браузер — это не одна программа, а несколько процессов:

- **Процесс браузера** — окно, адресная строка, вкладки, кнопка «назад».
- **Процесс рендерера** — по одному (обычно) на вкладку или на сайт. Именно он превращает HTML в пиксели и выполняет твой JavaScript.
- **Сетевой процесс** — качает файлы.
- **GPU-процесс** — общается с видеокартой.

Разделение нужно ради устойчивости и безопасности: зависшая вкладка не роняет браузер, а сайт из одной вкладки не может читать память другой.

Дальше нас интересует **процесс рендерера**, а в нём — один конкретный поток.

### Главный поток

Внутри рендерера есть несколько потоков, но ключевой один — **главный поток** (main thread). Он делает почти всё:

- разбирает HTML и CSS,
- выполняет твой JavaScript,
- считает, где какой элемент лежит,
- рисует содержимое,
- обрабатывает клики и нажатия клавиш.

**Всё это — по очереди, в один ряд.** Отсюда главное следствие, из которого растёт половина фронтенд-проблем: пока главный поток занят одним делом, он не делает ничего другого. Считаешь в цикле сумму миллиона чисел — в это время страница не реагирует на клики и не перерисовывается. Она не «тормозит» — она буквально стоит.

Рядом работают вспомогательные потоки: **компоновщик** (compositor) и **растеризаторы** (raster). Про них будет в части 3 — именно они позволяют части анимаций идти плавно, даже когда главный поток занят.

## Часть 2. От текста к дереву

### Парсинг HTML: получаем DOM

**Парсер** — программа, которая читает текст и строит из него структуру. HTML-парсер читает файл по кусочкам и превращает его в **DOM** (Document Object Model) — дерево объектов, где каждый тег стал узлом, а вложенность тегов стала вложенностью узлов.

```html
<body>
  <h1>Привет</h1>
  <p>Текст <em>с акцентом</em></p>
</body>
```

Важно: парсинг **потоковый**. Браузер не ждёт, пока скачается весь HTML: он строит дерево по мере поступления байтов и может показать верх страницы, пока низ ещё едет.

### Парсинг CSS: получаем CSSOM

Точно так же весь CSS — из внешних файлов, из тегов `<style>`, из атрибутов `style` — превращается в **CSSOM** (CSS Object Model): дерево правил, по которому можно быстро спросить «какие стили применяются к этому элементу».

CSSOM обязан быть **полным**, прежде чем можно что-то показать. Причина простая: последнее правило может перекрыть предыдущее. Если бы браузер рисовал по половине CSS, он сначала показал бы чёрный текст, а через мгновение перекрасил в красный — пользователь увидел бы мигание.

Отсюда правило: **CSS блокирует отрисовку**. Пока стили не загружены и не разобраны, браузер не покажет содержимое. Поэтому критически важный CSS выгодно встраивать прямо в страницу, а всё остальное грузить отдельно.

### Почему скрипт останавливает разбор HTML

Когда парсер натыкается на `<script>` без атрибутов, он **останавливается**: скачивает файл, выполняет его и только потом продолжает читать HTML.

Почему так: скрипт может вызвать `document.write` и дописать HTML прямо в текущее место. Браузер не знает заранее, будет он это делать или нет, поэтому вынужден подождать.

Отсюда два атрибута:

- `defer` — «скачивай параллельно, выполни, когда HTML разобран целиком, порядок скриптов сохрани». Это выбор по умолчанию для скриптов приложения.
- `async` — «скачивай параллельно, выполни сразу как скачался, порядок неважен». Годится для независимых счётчиков.

```html
<script src="app.js"></script>          <!-- останавливает разбор HTML -->
<script src="app.js" defer></script>    <!-- не останавливает, выполнится после разбора -->
<script src="counter.js" async></script><!-- не останавливает, выполнится когда угодно -->
```

Есть ещё нюанс: скрипт может спросить у элемента его стили (`getComputedStyle`). Поэтому выполнение скрипта ждёт, пока загрузится CSS, идущий выше по документу. Получается цепочка: медленный CSS задерживает JavaScript, а тот задерживает разбор HTML.

### Предзагрузчик

Пока главный парсер стоит на скрипте, браузер не бездельничает: параллельно работает **предзагрузчик** (preload scanner) — он бежит вперёд по тексту HTML и находит ссылки на картинки, стили и скрипты, чтобы начать их качать заранее.

Практический вывод: если ты вставляешь картинки и стили через JavaScript, предзагрузчик их не увидит и загрузка начнётся позже. Ссылки в разметке лучше, чем ссылки, появляющиеся из кода.

### Стадия 1. Стили

Браузер для каждого узла DOM вычисляет итоговый набор свойств: пробегает по правилам CSSOM, разбирается со специфичностью и наследованием и получает **вычисленный стиль** (computed style) — конкретные значения вроде `font-size: 16px`, `display: block`.

Здесь же выясняется, что часть узлов рисовать не нужно: элементы с `display: none` в дальнейший конвейер не попадают. Обрати внимание на разницу: `visibility: hidden` элемент оставляет — он невидим, но место занимает, значит участвует в макете.

### Стадия 2. Макет

**Макет** (layout, он же reflow — «перекомпоновка») — вычисление геометрии: где каждый элемент находится и какого он размера. Именно здесь `width: 50%` превращается в конкретные пиксели, а текст разбивается на строки.

Это самая дорогая стадия, потому что **каскадная**: изменил ширину одного блока — поехали соседи, потом их содержимое, потом всё, что ниже. Изменение геометрии одного элемента может заставить пересчитать половину страницы.

Что запускает макет: изменение `width`, `height`, `padding`, `margin`, `top`, `left`, `font-size`, добавление и удаление элементов, изменение текста.

### Стадия 3. Отрисовка

**Отрисовка** (paint) — заполнение пикселей: браузер записывает список команд рисования («здесь прямоугольник такого цвета, здесь текст таким шрифтом»), а потом выполняет его, превращая в растр — сетку пикселей. Этот шаг называется **растеризацией**.

Что запускает отрисовку без макета: изменение `color`, `background`, `box-shadow`, `border-radius`. Геометрия не поменялась, пересчитывать положение не нужно, но перекрасить — нужно.

### Стадия 4. Композиция

Страница рисуется не одной картинкой, а несколькими **слоями** — как прозрачные плёнки, наложенные друг на друга. Отдельный слой получают элементы с `transform`, `opacity`, `will-change`, видео, canvas и некоторые другие.

**Композиция** (compositing) — складывание готовых слоёв в финальную картинку с учётом их положения, прозрачности и порядка. Этим занимается **отдельный поток компоновщика**, а тяжёлую работу берёт на себя видеокарта.

Ключевое следствие: **если анимация меняет только `transform` и `opacity`, главный поток вообще не участвует**. Слой уже отрисован, надо лишь сдвинуть готовую плёнку. Поэтому анимация через `transform: translateX()` идёт плавно даже когда главный поток занят, а анимация через `left` — нет: она требует макета и отрисовки на каждом кадре.

```css
/* Плохо: каждый кадр — макет и отрисовка на главном потоке */
.box { transition: left .3s; left: 0; }
.box:hover { left: 100px; }

/* Хорошо: каждый кадр — только композиция */
.box { transition: transform .3s; }
.box:hover { transform: translateX(100px); }
```

### Частичные проходы

Конвейер не всегда идёт целиком. Браузер выполняет только то, что нужно:

- изменил `width` → стили, макет, отрисовка, композиция;
- изменил `background-color` → стили, отрисовка, композиция (макет пропущен);
- изменил `transform` → стили и композиция (макет и отрисовка пропущены).

Это и есть причина, по которой «анимируйте transform и opacity» — не суеверие, а прямое следствие устройства конвейера.

## Часть 4. Кадр

Экран обновляется с определённой частотой — обычно 60 раз в секунду (60 Гц), у современных устройств бывает 120 Гц. Браузер старается успевать выдавать новую картинку к каждому обновлению.

При 60 Гц на один **кадр** приходится `1000 / 60 ≈ 16.7` миллисекунды. За это время браузер должен успеть: выполнить накопившийся JavaScript, пересчитать стили и макет, отрисовать и скомпоновать. Реально на твой код остаётся около 10 мс — остальное браузер тратит на себя.

Не успел — кадр **пропущен**: экран показывает предыдущую картинку ещё раз. Пропустил несколько подряд — пользователь видит рывок.

Отсюда понятие **длинной задачи** (long task): любой непрерывный кусок работы на главном потоке дольше 50 мс. Пока он идёт, браузер не может ни отрисовать кадр, ни обработать клик.

## Часть 5. Событийный цикл

Теперь главное — как браузер решает, что делать в каждый момент.

### Стек вызовов

**Стек вызовов** (call stack) — список функций, которые сейчас выполняются. Вызвал функцию — она легла на стек, вернулась — снялась со стека. Пока стек не пуст, движок занят и ничего другого делать не может.

### Очередь задач

**Задача** (task, ещё говорят «макрозадача») — цельный кусок работы, который движок берёт и выполняет от начала до конца. Задачами являются:

- выполнение самого скрипта страницы,
- колбэк `setTimeout` и `setInterval`,
- обработчик события — клика, нажатия клавиши, ответа сети,
- разбор очередной порции HTML.

Задачи ждут своей очереди в **очереди задач**. Событийный цикл (event loop) — это простой бесконечный цикл: взять одну задачу, выполнить до конца, посмотреть, не пора ли отрисовать кадр, взять следующую.

### Очередь микрозадач

**Микрозадача** (microtask) — маленькая работа, которую надо выполнить как можно скорее, но не прерывая текущую задачу. Микрозадачами становятся:

- колбэки `.then`, `.catch`, `.finally` у промисов,
- продолжение функции после `await`,
- `queueMicrotask`,
- колбэки `MutationObserver`.

Правило: **когда текущая задача закончилась и стек опустел, движок выполняет всю очередь микрозадач целиком — и только потом берёт следующую задачу.**

«Целиком» здесь буквально: если микрозадача добавила новую микрозадачу, та тоже выполнится сейчас же, в этом же проходе. Очередь опустошается до дна.

### Классическая задача на порядок

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve()
  .then(() => console.log('C'))
  .then(() => console.log('D'));
queueMicrotask(() => console.log('E'));
console.log('F');
```

Вывод: **A F C E D B**. Разберём по шагам.

Выполнение самого скрипта — это уже задача. Внутри неё:

1. Печатается `A`.
2. `setTimeout` кладёт колбэк `B` в очередь задач. Ноль миллисекунд означает «как можно скорее», а не «сейчас».
3. Строится цепочка промисов. Промис уже разрешён, поэтому колбэк `C` немедленно попадает в очередь микрозадач. А вот `D` подписан на промис, который **вернёт** первый `.then` — этот промис ещё не разрешён, поэтому колбэка `D` в очереди нет вообще.
4. `queueMicrotask` кладёт `E` в очередь микрозадач — сразу за `C`.
5. Печатается `F`.

Скрипт закончился, стек пуст. Очередь микрозадач: `[C, E]`.

6. Выполняется `C`. В этот момент промис первого `.then` разрешается, и только теперь колбэк `D` встаёт **в конец** очереди микрозадач: `[E, D]`.
7. Выполняется `E`.
8. Выполняется `D`.
9. Очередь микрозадач пуста. Движок берёт следующую задачу — `B`.

Формулировка, ради которой этот вопрос и задают: **каждое звено цепочки `.then` — это отдельная микрозадача, и следующее звено попадает в очередь только после того, как выполнилось предыдущее.**

### Почему две очереди, а не одна

Микрозадачи нужны, чтобы реакция на уже готовые данные догнала код **до того, как пользователь увидит кадр**. Между задачей и микрозадачами отрисовки не бывает, значит промежуточное, несогласованное состояние интерфейса на экран не попадёт.

Цена — микрозадачи имеют безусловный приоритет над отрисовкой и вводом. Бесконечная цепочка микрозадач подвешивает страницу намертво: вкладка «живая», но кадр не нарисуется никогда. Это называется **голоданием** (starvation).

```js
// Так делать нельзя: очередь микрозадач не опустеет никогда
function loop() { queueMicrotask(loop); }
loop();
```

## Часть 6. requestAnimationFrame

`requestAnimationFrame` (сокращённо rAF) — способ сказать браузеру: «выполни эту функцию прямо перед тем, как рисовать следующий кадр».

### Где именно он вызывается

Смотри на схему выше: колбэки rAF выполняются **после** микрозадач и **перед** стадиями стилей, макета и отрисовки. Это идеальный момент, чтобы поменять что-то в DOM: изменения попадут в тот же кадр, лишнего прохода конвейера не будет.

### Чем он лучше `setTimeout` для анимаций

```js
// Плохо: интервал не синхронизирован с экраном
setInterval(() => { box.style.transform = 'translateX(' + (x += 2) + 'px)'; }, 16);

// Хорошо: ровно один вызов на кадр
function step() {
  box.style.transform = 'translateX(' + (x += 2) + 'px)';
  requestAnimationFrame(step);
}
requestAnimationFrame(step);
```

Три отличия:

1. **Синхронизация.** rAF вызывается ровно раз на кадр и точно перед отрисовкой. `setInterval(…, 16)` живёт своей жизнью: иногда два его срабатывания попадают в один кадр (лишняя работа впустую), иногда ни одного (рывок).
2. **Частота подстраивается.** На экране 120 Гц rAF вызовется 120 раз в секунду, на 60 Гц — 60. Анимация сама подстраивается под устройство.
3. **Экономия.** Во вкладке, которую не видно, rAF **не вызывается вообще**. `setInterval` продолжит работать и жечь батарею.

Колбэк rAF получает аргументом точное время кадра (`performance.now()` на момент начала кадра). Правильные анимации считают положение от времени, а не «прибавь два пикселя»: иначе на медленном устройстве анимация будет идти медленнее, а не пропускать кадры.

```js
let start = null;
function step(now) {
  if (start === null) start = now;
  const progress = Math.min((now - start) / 300, 1);   // 300 мс на всю анимацию
  box.style.transform = 'translateX(' + (progress * 100) + 'px)';
  if (progress < 1) requestAnimationFrame(step);
}
requestAnimationFrame(step);
```

### Соседи rAF в кадре

В том же месте кадра, рядом с rAF, браузер обрабатывает ещё несколько вещей:

- события `resize` и `scroll`,
- колбэки `IntersectionObserver` — «элемент появился во вьюпорте»,
- колбэки `ResizeObserver` — «элемент изменил размер»,
- анимации CSS и Web Animations API.

А `requestIdleCallback` — наоборот, вызывается **после** отрисовки, в остаток кадра, если он остался. Это место для необязательной работы: отправить аналитику, прогреть кеш. Если браузер занят, колбэк может не вызваться долго, поэтому у него есть таймаут.

### Ловушка: измерение внутри rAF

Самая частая ошибка с rAF — **принудительный синхронный макет** (forced synchronous layout, в народе «layout thrashing»).

Браузер откладывает пересчёт макета до последнего момента, накапливая изменения. Но если ты **читаешь** геометрию — `offsetHeight`, `getBoundingClientRect`, `scrollTop` — браузер обязан посчитать актуальное значение **прямо сейчас**, синхронно.

```js
// Плохо: на каждой итерации — принудительный пересчёт макета
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';   // читаем и тут же пишем
}

// Хорошо: сначала все чтения, потом все записи
const widths = items.map(el => el.offsetWidth);   // читаем
items.forEach((el, i) => {                        // пишем
  el.style.width = widths[i] + 10 + 'px';
});
```

В первом варианте на сто элементов приходится сто пересчётов макета вместо одного. Правило простое: **сгруппируй чтения, потом делай записи.**

## Часть 7. Что ломает плавность

Соберём вместе типичные причины «сайт тормозит»:

**Длинная задача на главном потоке.** Любой синхронный кусок дольше 50 мс: тяжёлый расчёт, разбор большого JSON, рендер огромного списка. Лечится разбиением на части, переносом в Web Worker (отдельный поток, где нет DOM, но есть вычисления) или уменьшением объёма работы.

**Анимация «дорогих» свойств.** Анимируешь `width` или `left` — каждый кадр требует макета и отрисовки на главном потоке. Переводи на `transform` и `opacity`.

**Принудительный синхронный макет.** Чтение геометрии вперемешку с записью стилей.

**Голодание микрозадачами.** Бесконечная цепочка промисов не даёт нарисовать кадр.

**Слишком много слоёв.** `will-change: transform` на сотне элементов съест память: каждый слой хранится отдельно. Это подсказка браузеру, а не бесплатная оптимизация.

**Огромный DOM.** Десятки тысяч узлов делают дорогими и стили, и макет. Отсюда виртуализация длинных списков: в DOM держат только видимое.

## Часть 8. Как это увидеть своими глазами

Открой панель Performance в DevTools, нажми запись, поработай со страницей, останови.

Что смотреть:

- **Полоса Main** — что делал главный поток. Задачи дольше 50 мс помечаются красным уголком: это и есть длинные задачи.
- **Цвета блоков**: жёлтый — выполнение JavaScript, фиолетовый — стили и макет, зелёный — отрисовка и композиция. Если много фиолетового — проблема в макете.
- **Полоса Frames** — сколько времени занял каждый кадр. Красные — пропущенные.
- **Предупреждение Forced reflow** — браузер прямо скажет, что ты заставил его пересчитать макет синхронно, и покажет строку кода.

Полезное упражнение: запиши профиль на своём проекте и найди самую длинную задачу. В 90% случаев это будет либо разбор данных, либо рендер большого списка.

## Что спросят на интервью

Тему любят, потому что она связывает всё сразу. Вероятные вопросы и краткие ответы:

**Что произойдёт, если поставить `<script>` в конце `<body>`?** Разбор HTML не будет заблокирован, элементы выше уже в DOM. Но сегодня лучше `defer` в `<head>`: скрипт начнёт качаться раньше, а выполнится всё равно после разбора.

**Чем `defer` отличается от `async`?** Оба качают параллельно и не блокируют парсер. `defer` выполняет после разбора HTML и сохраняет порядок скриптов, `async` — сразу после загрузки, в произвольном порядке.

**Почему `setTimeout(fn, 0)` не выполняется сразу?** Он ставит задачу в очередь. Перед ней выполнится текущий код и вся очередь микрозадач. Плюс браузер клэмпит вложенные таймеры до 4 мс, а в фоновой вкладке — примерно до секунды.

**Что выведет цепочка `.then` вперемешку с `queueMicrotask`?** Смотри разбор в части 5: каждое звено — отдельная микрозадача.

**Почему анимация через `transform` плавнее, чем через `left`?** `transform` обрабатывается на стадии композиции, в отдельном потоке и на видеокарте. `left` требует макета и отрисовки на главном потоке каждый кадр.

**Когда вызывается колбэк `requestAnimationFrame`?** После микрозадач, перед стадиями стилей, макета и отрисовки. Раз на кадр, не вызывается в невидимой вкладке.

**Что такое layout thrashing и как чинить?** Чередование чтения геометрии и записи стилей заставляет браузер пересчитывать макет синхронно на каждой итерации. Лечится группировкой чтений и записей.

## Коротко, для повторения перед выходом

1. Главный поток делает почти всё и делает по очереди. Занят — страница стоит.
2. HTML → DOM, CSS → CSSOM. CSS блокирует отрисовку, обычный `<script>` блокирует разбор HTML.
3. Конвейер: стили → макет → отрисовка → композиция. Композиция идёт мимо главного потока.
4. `transform` и `opacity` анимируются на композиции. Остальное дороже.
5. Один оборот цикла: одна задача → все микрозадачи до дна → возможно кадр (rAF → стили → макет → отрисовка).
6. Микрозадачи всегда раньше следующей задачи. Каждое звено `.then` — отдельная микрозадача.
7. rAF — раз на кадр, перед отрисовкой, не работает в скрытой вкладке.
8. Читай геометрию пачкой, пиши стили пачкой.
