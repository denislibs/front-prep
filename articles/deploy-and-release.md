# Выкладка и релиз фронтенда: атомарность, откат, постепенный раскат

У бэкенда выкладка устроена просто: остановили старые процессы, запустили новые, весь код теперь новый. У фронтенда так не выйдет, потому что код исполняется на чужих машинах, которых ты не контролируешь. Вкладка, открытая вчера, всё ещё выполняет вчерашний JavaScript и будет выполнять его столько, сколько пользователю вздумается её не закрывать. Отсюда растут все особенности фронтендовой выкладки: неизменяемые файлы, атомарное переключение, проблема устаревшей вкладки, откат переключением указателя.

Статья разбирает, что происходит после того, как конвейер выдал артефакт. Про то, что происходит до, — [конвейер сборки](./frontend-ci-cd).

## Часть 1. Хеш в имени файла — основа всего

### Проблема, которую он решает

Браузер кеширует ответы по **URL**. Если файл называется `app.js` и его содержимое поменялось, у браузера нет способа об этом узнать иначе как спросив сервер. Возникает вилка, где оба варианта плохи:

- Разрешить кешировать `app.js` надолго — часть пользователей неделями будет работать со старым кодом.
- Запретить кешировать — каждый заход по сети, даже когда ничего не менялось. Медленно и дорого.

**Хеш содержимого в имени файла** снимает вилку целиком. Сборщик считает хеш (короткую строку, однозначно зависящую от содержимого) и вставляет его в имя: `app-4f2c9a1b.js`. Дальше работает простое свойство: **изменилось содержимое — изменилось имя — изменился URL**. Старый URL навсегда соответствует старому содержимому, новый — новому. Кешу больше нечего путать.

Такие файлы называют **неизменяемыми** (immutable): по данному адресу всегда лежит одно и то же.

### Две политики кеширования

Раз файлы с хешем неизменяемы, их можно кешировать практически навсегда. А `index.html` — нельзя кешировать никогда, потому что именно он содержит ссылки на текущие хешированные файлы и является точкой входа.

Разница директив, которую спрашивают:

- `no-store` — не сохранять вообще. Нужен для страниц с приватными данными, для `index.html` избыточен.
- `no-cache` — сохранить можно, но перед использованием **обязательно спросить сервер**, не изменилось ли. Сервер отвечает `304 Not Modified` (пустой ответ, «бери из кеша»), если файл тот же. Это дёшево: один короткий запрос вместо скачивания.
- `max-age=31536000` — год в секундах, «можешь использовать без вопросов».
- `immutable` — «даже при обновлении страницы не переспрашивай». Без него браузер по нажатию «обновить» всё равно отправит проверочные запросы по всем файлам; с ним не отправит.

### Что ломается, если сделать наоборот

Обе ошибки встречаются в реальных проектах.

**`index.html` закеширован надолго.** Пользователь получает старую точку входа и застревает на предыдущей версии: он видит старый интерфейс, старые баги, не получает исправлений. Хуже того, отката для него не существует — переключение на сервере он просто не увидит. Лечится это только сбросом кеша у самого пользователя, до которого ты не дотянешься. Особенно неприятно, когда `index.html` закеширован промежуточным прокси или CDN, а не браузером: тогда «застревает» сразу целый оператор связи.

**Файлы с хешем отдаются без кеша.** Формально всё работает, но каждый переход по приложению тянет мегабайты по сети заново. Весь смысл разбиения на чанки исчезает: разбиение окупается только тем, что уже скачанные чанки лежат в кеше.

### Каскад хешей

Тонкость, которую полезно знать. Хеш файла зависит от его содержимого, а содержимое чанка включает ссылки на другие чанки. Значит, изменение общей библиотеки меняет её хеш, что меняет содержимое всех чанков, которые её импортируют, что меняет и их хеши. Один правленый файл может обновить половину бандла и обнулить кеш у пользователей.

Сборщики борются с этим, вынося таблицу соответствия «модуль — файл» в отдельный маленький файл (манифест или рантайм) и используя стабильные идентификаторы модулей вместо порядковых номеров. Подробности разбиения на чанки — в статье [модули и сборка](./modules-and-bundling).

## Часть 2. Атомарность выкладки

### Почему нельзя лить файлы по одному

Пользователь получает не один файл, а **связанный граф файлов**: `index.html` ссылается на чанки, чанки ссылаются друг на друга. Набор согласован только целиком.

Если выкладывать файлы по мере готовности, появляется **окно несогласованности** — промежуток, в котором на сервере лежит смесь версий. Сценарий:

1. Скрипт выкладки залил новый `index.html`.
2. Пользователь обновил страницу и получил новую точку входа со ссылкой на `main-9c4d.js`.
3. Скрипт до этого файла ещё не дошёл. Браузер получает 404.
4. Приложение не запускается. Белый экран.

Обратный порядок даёт не менее весёлый вариант: старый `index.html` продолжает отдаваться, но скрипт уже удалил старые файлы, чтобы освободить место.

Схема работает потому, что хеши в именах гарантируют отсутствие конфликтов: файлы двух версий спокойно лежат в одном каталоге. Старый `index.html` ссылается на старые имена, новый — на новые, и оба набора на месте.

**Атомарность** здесь означает, что момент переключения — одно неделимое действие. Способы это обеспечить:

- символическая ссылка `current` на каталог версии, переключаемая одной командой;
- переключение адреса источника у CDN;
- загрузка нового `index.html` последним файлом — не идеально атомарно, но одного файла достаточно, чтобы окно несогласованности схлопнулось до миллисекунд.

Отдельная тонкость: даже при правильном порядке `index.html` может быть закеширован на CDN. Значит, ему нужен либо `no-cache`, либо принудительный сброс кеша (инвалидация) сразу после выкладки. Инвалидация не мгновенна: на крупных сетях она расходится по узлам десятки секунд. В это время часть пользователей получает старую точку входа — что нормально ровно до тех пор, пока старые ассеты не удалены.

Классическая ошибка, которую стоит уметь назвать: `aws s3 sync dist/ s3://bucket/ --delete` одной командой. Флаг `--delete` удаляет всё, чего нет в новой сборке, — то есть ровно те чанки, которые прямо сейчас нужны открытым вкладкам.

## Часть 3. Проблема устаревшей вкладки

Это самый частый вопрос по теме, потому что он выявляет, понимает ли человек, что фронтенд исполняется на чужой машине.

### Сценарий

1. Пользователь открыл приложение утром. Браузер скачал `index.html` версии A и её чанки.
2. Вкладка остаётся открытой весь день. Пользователь не перезагружает страницу — одностраничное приложение переключает маршруты само, без обращения к `index.html`.
3. Днём выходит версия B. Скрипт выкладки заливает новые файлы и удаляет старые.
4. Вечером пользователь нажимает на раздел «Отчёты», который загружается лениво. Код вызывает динамический импорт: браузер идёт за `reports-3a91.js` — файлом версии A.
5. Файла нет. 404. Промис импорта отклоняется.

Почему страдают именно ленивые чанки: **динамический импорт** (`import('./Reports')`) не скачивает файл заранее. Он идёт за ним по сети в момент вызова — то есть через много часов после того, как страница загрузилась. Обычные чанки, скачанные при старте, лежат в памяти вкладки и от выкладки не зависят.

Что видит пользователь: в лучшем случае — пустая область вместо содержимого, в худшем — белый экран, если ошибка всплыла наверх. Ошибка приходит как отклонённый промис, и обычный обработчик ошибок компонента её не поймает, если импорт вызван не через механизм ленивой загрузки фреймворка, а руками в обработчике клика.

### Способ 1. Держать старые сборки

**Что делаем.** Не удаляем файлы предыдущих версий сразу. Держим последние N релизов или всё, чему меньше 30 дней.

**Почему работает.** Закрывает подавляющее большинство случаев: реальные вкладки живут часы, максимум несколько дней.

**Цена.** Хранилище — копейки, статика весит мегабайты. Реальная цена в другом:

- Старый фронтенд продолжает ходить в новый бэкенд. Значит, API должен оставаться совместимым назад на тот же срок, что и хранение сборок. Это ограничение на бэкенд, а не на фронтенд, и о нём надо договариваться.
- Каталог зарастает. Нужна автоматическая уборка по возрасту, иначе через год там тысячи файлов и никто не решается ничего удалить.
- Способ не защищает от вкладки, открытой месяц назад, и от аварийного случая, когда сборку удалили руками.

Это база, с которой начинают. Сам по себе способ не решает проблему полностью, но резко снижает её частоту.

### Способ 2. Ловить ошибку загрузки и перезагружать один раз

**Что делаем.** Перехватываем неудачный динамический импорт и вызываем `location.reload()`. Перезагрузка запросит `index.html`, который не кешируется, получит свежую версию со свежими именами чанков — и всё заработает.

**Почему нужен флаг.** Если файла нет по другой причине (сеть отвалилась, CDN лежит, у пользователя блокировщик), перезагрузка не поможет, ошибка повторится, и приложение уйдёт в бесконечный цикл перезагрузок. Это хуже исходной проблемы: страница мигает, пользователь ничего не может сделать. Поэтому перед перезагрузкой ставится отметка в `sessionStorage`, и вторая попытка не делается.

Почему именно `sessionStorage`, а не `localStorage`: он живёт в пределах одной вкладки и очищается при её закрытии. Отметка не должна пережить сессию и запретить полезную перезагрузку через неделю.

**Цена.** Пользователь теряет несохранённое состояние: заполненную форму, позицию скролла, открытые панели. Для приложения, где люди подолгу заполняют данные, это неприемлемо без предупреждения. Плюс на медленной сети способ иногда срабатывает ложно — импорт упал по таймауту, а не из-за релиза.

Код разобран в части 8.

### Способ 3. Уведомлять о новой версии

**Что делаем.** Приложение периодически спрашивает у сервера текущую версию и сравнивает с той, что вшита в его собственную сборку. Отличается — показывает ненавязчивое уведомление «доступна новая версия, обновить».

**Почему это лучший из трёх.** Он единственный обновляет пользователя **до** ошибки, а не после. И единственный, который отдаёт решение пользователю: он нажмёт «обновить», когда закончит писать письмо, а не посреди.

**Цена и нюансы.**

- Нужен опрос по сети. Раз в минуту — лишний трафик и лишняя нагрузка; раз в час — половина пользователей не узнает вовремя. Правильнее опрашивать по событию: когда вкладка снова стала видимой и когда пользователь переходит между маршрутами. Это дешевле и точнее, потому что совпадает с моментами, когда обновление уместно.
- Опрашиваемый файл сам не должен кешироваться, иначе версия будет вечно старой.
- Нужно решать, что делать при критическом исправлении: мягкое уведомление можно игнорировать сутками. Обычно вводят два уровня — «предложить» и «обновить принудительно через N минут».
- Нельзя перезагружать во время незавершённого действия. Уведомление должно уметь подождать.

На практике применяют все три вместе: старые сборки хранятся как страховка, уведомление ловит большинство пользователей заранее, а перехват ошибки остаётся последним рубежом.

### Отдельно: service worker

Если в приложении есть [service worker](./service-worker), картина меняется. Он может держать оболочку приложения в кеше и обновляться по контролируемому сценарию, снимая часть проблемы. Но добавляет свою: неправильно написанный воркер «залипает» и продолжает отдавать старую версию даже после выкладки — а он ещё и переживает закрытие вкладки. Отладка такого случая тяжелее, чем всё описанное выше.

### Тот же класс проблем на API

Устаревшая вкладка шлёт запросы кодом вчерашней версии: старые поля, старые пути, старые ожидания от ответа. Поэтому изменения API делают обратно совместимыми, а поля удаляют не тогда, когда фронтенд перестал их посылать, а когда перестали работать все вкладки, которые могут их послать.

## Часть 4. Откат

**Откат** у фронтенда — это переключение указателя на предыдущий артефакт. Не пересборка, не revert коммита, не «сейчас быстро поправим». Секунды вместо минут.

Почему пересборка при откате опасна:

- **Долго.** Пять минут сборки — это пять минут, которые пользователи проводят со сломанным приложением. Когда падает конверсия, это прямые деньги.
- **Результат может отличаться.** Сборка недетерминирована во времени: подтянулась новая транзитивная зависимость, обновился раннер, изменился внешний ресурс. Ты откатываешь код, но получаешь артефакт, который никогда не работал. Проверять его негде — уже прод.
- **Конвейер может быть красным.** Основная ветка сломалась по независимой причине, тесты не проходят, сборка не запускается. В этот момент возможность откатиться исчезает именно тогда, когда она нужнее всего.
- **Новые хеши.** Пересборка даёт другие имена файлов. Пользователи с уже загруженным новым `index.html` не получат ничего полезного, а количество разных версий в обращении вырастет ещё на одну.

Значит, требования к системе выкладки: хранить прошлые артефакты, уметь поставить любой из них по идентификатору, и делать это одной командой или одной кнопкой, доступной дежурному без прав на сборку.

**Чего откат не откатывает** — важная часть ответа на интервью:

- миграции базы данных;
- изменения в бэкенде, если выкладывали вместе;
- состояние фича-флагов;
- уже отправленные уведомления и письма;
- данные, которые новая версия успела записать в неверном формате;
- кеш CDN, если сброс не сделан явно.

Отсюда правило: изменения, которые нельзя отменить переключением указателя, выкатывают отдельным шагом и делают обратно совместимыми. Сначала бэкенд, который понимает оба формата, потом фронтенд.

## Часть 5. Постепенный раскат

**Канареечный релиз** — новая версия сначала показывается небольшой доле пользователей; если метрики в порядке, доля растёт. Название из шахтёрской практики: канарейка в клетке замечает газ раньше людей.

**Сине-зелёная схема** — два полных окружения. Одно обслуживает трафик, второе получает новую версию и прогревается. Переключение — целиком, откат — обратное переключение.

### Почему у фронтенда это сложнее, чем у сервера

- **У сервера один вход, у фронтенда — граф файлов.** Пользователь должен получить согласованный набор. Если `index.html` пришёл из синей версии, а чанк по случайности взялся из зелёной — приложение сломается. Спасают хеши: файлы разных версий не конфликтуют по именам, поэтому оба набора спокойно лежат рядом, а разводить надо только точку входа.
- **Сессия длинная.** Серверный откат мгновенно возвращает всех. Фронтендовый откат не влияет на тех, кто уже загрузил сломанную версию, — их вкладки продолжают её выполнять, пока не перезагрузятся. Раскат ошибочной версии на 5% пользователей значит, что эти 5% останутся с ней до перезагрузки.
- **Обратная связь запаздывает.** Серверные метрики видны за секунды. Клиентские ошибки надо сначала отправить с устройства пользователя, а часть браузеров этого не сделает вовсе. Метрики скорости загрузки собираются десятками минут, прежде чем станут статистически значимыми.
- **Липкость.** Пользователь не должен прыгать между версиями при переходах: сегодня зелёная, через минуту синяя. Иначе половина ошибок будет невоспроизводима.

### Как обычно решают

Разделение делают на уровне **CDN или пограничной функции** — маленького кода, который выполняется на узле сети рядом с пользователем и решает, какой `index.html` отдать:

1. Обе версии залиты в хранилище по разным префиксам: `releases/2026-09-02-a1b2/` и `releases/2026-09-03-c3d4/`.
2. Пограничная функция читает cookie с номером версии. Если её нет — бросает жребий по заданной доле и записывает cookie. Это и есть липкость.
3. Отдаётся `index.html` из соответствующего каталога. Ассеты обеих версий доступны всем — конфликта нет благодаря хешам.
4. Доля увеличивается ступенями с паузами на наблюдение: 1% — 5% — 25% — 100%.

## Часть 6. Фича-флаги

**Фича-флаг** — условие в коде, включающее ту или иную ветку поведения, причём значение приходит извне, а не из сборки.

Главное следствие: **«выложить» перестаёт означать «включить»**. Код едет в прод выключенным и лежит там сколько угодно. Включение — отдельное действие, обратимое за секунды и без новой выкладки. Релиз становится скучным техническим событием, а включение фичи — продуктовым решением.

Виды флагов, у которых разная судьба:

- **Релизные** — временные, живут до полного включения, потом удаляются вместе со старой веткой кода.
- **Операционные** — рубильники, отключающие тяжёлую функциональность при нагрузке. Живут долго осознанно.
- **Экспериментальные** — A/B-тесты, живут до конца эксперимента.
- **Доступ по подписке или роли** — формально не флаги, а бизнес-логика, живут всегда.

Смешивать их в одном списке — ошибка: у первых трёх должен быть срок, у последнего нет.

### Цена флагов

- **Ветвление кода.** Два пути существуют одновременно, оба надо поддерживать и тестировать. Каждый флаг удваивает число возможных состояний: десять флагов дают 1024 комбинации, а тестируют реально две-три. Значит, флаги обязаны быть независимыми, и любая их связка — источник багов, которые невозможно воспроизвести.
- **Мёртвые флаги.** Включён на 100% полгода назад, но код обеих веток жив, и никто не помнит, зачем он. Через год их сорок, и рефакторинг превращается в археологию.
- **Вес бандла.** Выключенный флаг не убирает код из бандла — обе ветки скачиваются пользователем. Ленивая загрузка помогает, но не бесплатно.
- **Неявное глобальное состояние.** Флаг, который читают в двадцати местах, ведёт себя как глобальная переменная со всеми вытекающими.

Гигиена простая: у каждого временного флага есть владелец и срок; задача на удаление создаётся в момент создания флага; раз в квартал список ревизуется; количество активных флагов ограничено и это ограничение соблюдается.

И важное: **флаг не заменяет откат**. Он спасает, только если поломка внутри той ветки, которую он выключает. Ошибка в общем коде, в конфигурации сборки или в самой системе флагов флагом не лечится.

## Часть 7. Общая ветка против длинных веток

**Trunk-based development** — все работают в одной основной ветке, вливаются маленькими порциями по несколько раз в день, ветки живут часы.

Длинные ветки — противоположность: фича живёт неделями, потом вливается одним куском.

Почему длинные ветки плохи:

- Конфликты слияния растут нелинейно: чем дольше ветка живёт, тем больше расхождение и тем выше шанс, что конфликт будет смысловым, а не текстовым.
- Ревью большого куска формальное. Тысячу строк внимательно не прочитают.
- Интеграция откладывается на самый конец, когда исправлять дороже всего.
- Релиз становится событием с большим объёмом изменений, а откат отменяет сразу десяток вещей, включая нужные.

**Почему trunk сочетается с флагами.** Незаконченная фича должна где-то жить. Либо в ветке (и тогда мы вернулись к длинным веткам), либо в основной ветке за выключенным флагом. Флаг — это то, что делает частые слияния возможными: неготовый код едет в прод, но пользователи его не видят.

Условие работоспособности схемы — быстрый и надёжный [конвейер](./frontend-ci-cd). Если проверки идут сорок минут и половина падений случайна, общая ветка будет постоянно красной, и все вернутся к длинным веткам естественным образом.

## Часть 8. Практика: рабочие конфиги и код

### Заголовки кеширования: nginx

Что делаем: разводим политику по типу файла. Почему именно так — разобрано в части 1: точка входа обязана быть свежей, хешированные файлы неизменяемы.

```nginx
server {
    root /var/www/app/current;   # символическая ссылка на каталог версии

    # 1. Файлы с хешем в имени. Шаблон ловит имена вида
    #    index-4f2c9a1b.js — дефис, 8+ шестнадцатеричных символов, расширение.
    #    Проверяем именно хеш, а не расширение: файл без хеша,
    #    попавший под правило, застрянет у пользователей на год.
    location ~* "-[0-9a-f]{8,}\.(js|css|woff2|png|svg|jpg|webp)$" {
        expires 1y;
        add_header Cache-Control "public, max-age=31536000, immutable";
        access_log off;
    }

    # 2. Точка входа. no-store был бы избыточен: пусть браузер хранит копию,
    #    но каждый раз переспрашивает. Совпало — вернём 304 без тела.
    location = /index.html {
        add_header Cache-Control "no-cache, must-revalidate";
        # Прокси и CDN тоже обязаны переспрашивать, иначе застрянет
        # целый оператор связи, а не один браузер.
        add_header Vary "Accept-Encoding";
        etag on;
    }

    # 3. Файл версии для проверки обновлений (см. ниже). Кешировать нельзя:
    #    закешированная версия всегда будет отвечать «обновлений нет».
    location = /version.json {
        add_header Cache-Control "no-store";
        default_type application/json;
    }

    # 4. Любой неизвестный путь отдаёт index.html — маршрутизация на клиенте.
    #    Обрати внимание: 404 для отсутствующего чанка сюда НЕ должен попадать,
    #    иначе браузер получит HTML вместо JavaScript и ошибка станет
    #    непонятной («unexpected token <»). Ассеты отдаём строго из /assets/.
    location /assets/ {
        try_files $uri =404;
    }
    location / {
        try_files $uri /index.html;
    }
}
```

Четвёртый пункт — частая и очень путаная ошибка. Если отсутствующий чанк отдаётся как `index.html`, браузер пытается выполнить HTML как модуль и падает с синтаксической ошибкой. В отчётах об ошибках это выглядит как загадочный сбой парсинга, а на деле это устаревшая вкладка из части 3.

### Заголовки кеширования: раздача через CDN

Для хранилища объектов заголовки задаются при загрузке файла, поэтому выкладка идёт в два прохода — сначала ассеты со своей политикой, потом точка входа со своей.

```bash
# Проход 1: неизменяемые файлы. Без --delete: старые версии остаются
# на месте, чтобы открытые вкладки могли дозагрузить свои чанки.
aws s3 sync dist/assets/ "s3://$BUCKET/assets/" \
  --cache-control "public, max-age=31536000, immutable" \
  --exclude "*.map"                                # карты исходников не публикуем

# Проход 2: точка входа и манифест версии — только после того,
# как все ассеты гарантированно на месте.
aws s3 cp dist/index.html "s3://$BUCKET/index.html" \
  --cache-control "no-cache, must-revalidate"
aws s3 cp dist/version.json "s3://$BUCKET/version.json" \
  --cache-control "no-store"
```

### Атомарная выкладка целиком

Что делаем: собираем последовательность в один скрипт с проверками. Почему по шагам — потому что порядок здесь и есть механизм атомарности.

```bash
#!/usr/bin/env bash
set -euo pipefail          # любая ошибка останавливает выкладку немедленно:
                           # половина выложенного релиза хуже, чем невыложенный

RELEASE="$(date +%Y%m%d-%H%M)-${GIT_SHA:0:8}"   # человекочитаемо + однозначно

# Шаг 0. Артефакт скачивается из конвейера, а не собирается здесь.
#        Тот же набор байтов, что проверяли на стенде.
aws s3 cp "s3://$ARTIFACTS/dist-$GIT_SHA.tar.gz" - | tar xz -C ./dist

# Шаг 1. Ассеты — первыми, рядом со старыми, ничего не удаляя.
aws s3 sync dist/assets/ "s3://$BUCKET/assets/" \
  --cache-control "public, max-age=31536000, immutable"

# Шаг 2. Полная копия релиза в свой каталог: именно она даст откат
#        одной командой и разные точки входа для канареечного раската.
aws s3 sync dist/ "s3://$BUCKET/releases/$RELEASE/" \
  --cache-control "public, max-age=31536000, immutable"

# Шаг 3. Проверка перед переключением: точка входа должна ссылаться
#        на файлы, которые реально доступны по сети.
for asset in $(grep -oE '/assets/[A-Za-z0-9._-]+' dist/index.html | sort -u); do
  curl -fsI "https://$CDN_HOST$asset" > /dev/null \
    || { echo "нет файла: $asset"; exit 1; }
done

# Шаг 4. Переключение — последнее и единственное неатомарное место.
#        Один файл, поэтому окно несогласованности — миллисекунды.
echo "{\"version\":\"$RELEASE\",\"sha\":\"$GIT_SHA\"}" > version.json
aws s3 cp dist/index.html "s3://$BUCKET/index.html" --cache-control "no-cache"
aws s3 cp version.json     "s3://$BUCKET/version.json" --cache-control "no-store"

# Шаг 5. Сброс кеша CDN — только для точки входа. Ассеты сбрасывать нельзя
#        и не нужно: они неизменяемы, а массовый сброс обнулит кеш узлам.
aws cloudfront create-invalidation --distribution-id "$CDN_ID" \
  --paths "/index.html" "/version.json"

# Шаг 6. Уборка отложена в отдельную задачу по расписанию:
#        удаляем каталоги релизов старше 30 дней, но не последние 10.
echo "Выложен $RELEASE"
```

Шаг 3 стоит отдельного внимания: это дешёвая проверка, которая ловит самый неприятный класс аварий — неполную заливку ассетов. Стоит десять секунд, экономит инцидент.

### Обработка ошибки загрузки чанка

Что делаем: оборачиваем динамический импорт, перезагружаем страницу один раз и защищаемся от цикла.

```ts
// lazyWithReload.ts
const RELOAD_FLAG = 'chunk-reload-attempted';

/**
 * Оборачивает динамический импорт. При провале загрузки чанка один раз
 * перезагружает страницу: index.html не кешируется, значит после
 * перезагрузки придут актуальные имена чанков.
 */
export function retryImport<T>(load: () => Promise<T>): Promise<T> {
  return load().catch((error: unknown) => {
    if (!isChunkLoadError(error)) throw error;   // сетевые и прочие ошибки не наши

    // Флаг живёт в пределах вкладки и стирается при её закрытии.
    // localStorage здесь был бы вреден: он запретил бы полезную
    // перезагрузку через неделю в другой сессии.
    if (sessionStorage.getItem(RELOAD_FLAG)) {
      throw error;   // вторая попытка не делается: показываем ошибку честно
    }
    sessionStorage.setItem(RELOAD_FLAG, '1');
    window.location.reload();

    // Промис, который никогда не разрешится: страница уже уходит,
    // и разрешать его нечем. Иначе интерфейс успеет мигнуть ошибкой.
    return new Promise<T>(() => {});
  });
}

function isChunkLoadError(error: unknown): boolean {
  const message = error instanceof Error ? error.message : String(error);
  // Формулировки различаются по браузерам и сборщикам, поэтому проверяем
  // набор признаков, а не одну строку.
  return /Loading chunk|Failed to fetch dynamically imported module|error loading dynamically imported module|Importing a module script failed/i
    .test(message);
}

// Флаг снимается после успешного старта приложения: значит,
// перезагрузка помогла и следующая проблема снова получит попытку.
export function clearReloadFlag() {
  sessionStorage.removeItem(RELOAD_FLAG);
}
```

Использование с ленивыми маршрутами:

```tsx
import { lazy } from 'react';
import { retryImport, clearReloadFlag } from './lazyWithReload';

const Reports = lazy(() => retryImport(() => import('./routes/Reports')));

// Вызывается один раз при монтировании корневого компонента.
clearReloadFlag();
```

Про сам вызов `reload`: у него нет параметра «загрузить с сервера» в современных браузерах — старый аргумент `true` давно игнорируется. Работает это только потому, что `index.html` отдаётся с `no-cache`. Если политика кеширования из части 1 нарушена, весь этот код бесполезен: перезагрузка вернёт ту же самую старую точку входа.

### Уведомление «доступна новая версия»

Что делаем: сравниваем версию, вшитую в сборку, с версией на сервере. Опрашиваем не по таймеру вслепую, а в моменты, когда это уместно.

Сборка кладёт свою версию в код через переменную окружения из конвейера (`VITE_BUILD_SHA`), а рядом с `index.html` лежит `version.json` с той же величиной.

```ts
// useAppVersion.ts
import { useEffect, useState } from 'react';

const CURRENT = import.meta.env.VITE_BUILD_SHA as string;
const POLL_MS = 5 * 60 * 1000;

export function useNewVersionAvailable(): boolean {
  const [stale, setStale] = useState(false);

  useEffect(() => {
    if (stale) return;   // узнали один раз — больше не спрашиваем
    let cancelled = false;

    async function check() {
      // Вкладка в фоне: опрашивать бессмысленно, пользователь всё равно не видит.
      if (document.visibilityState !== 'visible') return;
      try {
        // cache: 'no-store' обязателен: иначе браузер вернёт закешированный
        // ответ и версия навсегда останется «текущей».
        const res = await fetch('/version.json', { cache: 'no-store' });
        if (!res.ok) return;
        const { sha } = await res.json();
        if (!cancelled && sha && sha !== CURRENT) setStale(true);
      } catch {
        // Сеть могла отвалиться. Молча пропускаем: это не ошибка приложения.
      }
    }

    const timer = setInterval(check, POLL_MS);
    // Возврат к вкладке — самый частый момент, когда обновление уместно
    // и когда пользователь точно не в середине действия.
    document.addEventListener('visibilitychange', check);
    check();

    return () => {
      cancelled = true;
      clearInterval(timer);
      document.removeEventListener('visibilitychange', check);
    };
  }, [stale]);

  return stale;
}
```

Компонент-уведомление:

```tsx
export function UpdateBanner() {
  const stale = useNewVersionAvailable();
  if (!stale) return null;

  return (
    <div className="update-banner" role="status" aria-live="polite">
      {/* role="status" и aria-live: экранный диктор сообщит о плашке,
          но не перебьёт текущее действие пользователя */}
      <span>Доступна новая версия приложения.</span>
      {/* Никакого автоматического обновления: пользователь может
          заполнять форму. Решение за ним. */}
      <button onClick={() => window.location.reload()}>Обновить</button>
    </div>
  );
}
```

Для критического исправления схему расширяют полем в `version.json` вида `"minVersion"`. Если текущая сборка старше минимально допустимой, плашка становится модальной и обновление принудительно — но и тогда стоит дать время сохранить введённое.

### Фича-флаг: как выглядит в коде и где хранится

Что делаем: значения флагов приходят вместе с документом, чтобы не было мигания интерфейса, и читаются через один типизированный доступ.

Хранилище флагов — это отдельный сервис или таблица, где на флаг хранятся: ключ, значение по умолчанию, правила раскатки (доля, список пользователей, признак сотрудника), владелец и срок жизни.

```json
{
  "checkout-v2":        { "enabled": true,  "rollout": 25, "owner": "team-checkout", "expiresAt": "2026-11-01" },
  "search-suggestions": { "enabled": true,  "rollout": 100, "owner": "team-search",  "expiresAt": "2026-10-15" },
  "heavy-report-tab":   { "enabled": false, "rollout": 0,   "owner": "team-ops",     "kind": "kill-switch" }
}
```

Поля `owner` и `expiresAt` — не бюрократия. Именно они не дают списку превратиться в кладбище: без владельца никто не знает, можно ли удалять, а без срока никто и не вспомнит.

Значения вычисляются на сервере (он знает пользователя) и приходят вместе с документом:

```html
<!-- сервер подставляет это в index.html при отдаче -->
<script id="flags" type="application/json">
  {"checkout-v2": true, "search-suggestions": true, "heavy-report-tab": false}
</script>
```

Почему в документе, а не отдельным запросом: иначе первый кадр отрисуется со значениями по умолчанию, а через 200 мс интерфейс дёрнется. Это видно пользователю и портит метрики стабильности вёрстки.

```ts
// flags.ts
export type FlagKey = 'checkout-v2' | 'search-suggestions' | 'heavy-report-tab';
//                    ^ объединение строк, а не произвольная строка: опечатка
//                      в имени флага станет ошибкой компиляции, а не тихим false

const values: Record<string, boolean> = JSON.parse(
  document.getElementById('flags')?.textContent ?? '{}'
);

export const isEnabled = (key: FlagKey): boolean => values[key] === true;
```

Использование — и правило, которое стоит соблюдать:

```tsx
// Хорошо: развилка одна, на границе экрана. Ветки не переплетаются.
export function CheckoutRoute() {
  return isEnabled('checkout-v2') ? <CheckoutV2 /> : <CheckoutV1 />;
}

// Плохо: тот же флаг проверяется в восьми местах внутри одного экрана.
// Удалять такой флаг придётся вручную по всему файлу, а состояния
// «часть кода новая, часть старая» никто никогда не тестировал.
```

### Карты исходников в проде

**Карта исходников** (source map) — файл соответствия между собранным кодом и исходным. Без неё стек-трейс из прода выглядит как `t.a is not a function` в строке 1 столбце 48213 и бесполезен.

Проблема: карта содержит исходный код целиком. Выложить её рядом с бандлом — то же самое, что опубликовать репозиторий.

Что делаем: карты собираем, загружаем в сервис мониторинга ошибок и не публикуем.

```ts
// vite.config.ts
export default defineConfig({
  build: {
    // 'hidden' = карты создаются, но комментарий-ссылка
    // //# sourceMappingURL в конце бандла НЕ добавляется.
    // Браузер о картах не узнает, а сервис мониторинга получит их отдельно.
    sourcemap: 'hidden',
  },
});
```

```bash
# В конвейере, сразу после сборки и до выкладки.
# release должен совпадать с версией, которую приложение
# отправляет вместе с ошибками, иначе стек не развернётся.
npx sentry-cli sourcemaps upload ./dist \
  --release "$GIT_SHA" \
  --url-prefix "~/assets"

# И обязательно: карты не должны попасть в публичное хранилище.
find dist -name '*.map' -delete
aws s3 sync dist/ "s3://$BUCKET/" --exclude "*.map"
```

Альтернативы, если своего сервиса мониторинга нет:

- отдавать карты по отдельному адресу с проверкой доступа (по IP офиса или по авторизации) — тогда разработчик видит их в инструментах браузера, а посторонний нет;
- держать карты в приватном хранилище и разворачивать стек-трейсы вручную при разборе инцидента.

Чего делать не надо: класть `.map` рядом с бандлом «временно, для отладки». Такое временное живёт годами. Подробнее о работе со стеками — в статье [ошибки и отладка](./errors-and-debugging).

## Часть 9. Релиз сломал пользователей: что делать

### Как быстро понять

- **Отчёты об ошибках с версией сборки в теге.** Единственный надёжный сигнал: всплеск ошибок ровно на одной версии не спутаешь ни с чем. Для этого идентификатор релиза должен быть одинаковым в сборке, в картах исходников и в отчётах.
- **Метрика ключевого действия.** Ошибки видят не всё: белый экран без единого исключения бывает регулярно. Нужен счётчик вида «пользователь дошёл до оплаты», сравниваемый с обычным уровнем.
- **Метрики скорости по версиям.** Релиз может не ломать, а замедлять — это тоже поломка, просто медленная.
- **Алерты на долю, а не на количество.** «100 ошибок в минуту» ничего не значит без знания трафика. «Доля сессий с ошибкой выросла втрое относительно прошлой недели» — значит.

### Что нажать

1. **Остановить раскат.** Если шло постепенное включение — вернуть долю к нулю. Это самое быстрое действие и оно не требует ничьих подтверждений.
2. **Если фича за флагом — выключить флаг.** Секунды, без выкладки.
3. **Иначе — откатить указатель** на предыдущий релиз одной командой.
4. **Сбросить кеш точки входа** и убедиться, что откат реально доехал: открыть в приватном окне, проверить версию в манифесте, посмотреть, что доля ошибок падает.
5. **Сообщить.** Дежурному, поддержке, в канал команды. Поддержка должна знать, что отвечать пользователям, раньше, чем начнёт отвечать наугад.
6. **Только теперь разбираться в причине.**

Порядок именно такой. Диагностика на живых пользователях — самая дорогая диагностика из возможных: пока ты читаешь стек, люди уходят. Сначала вернуть работоспособность, потом искать, что случилось.

Разбор после инцидента ведётся без поиска виноватого. Вопрос не «кто это выложил», а «почему это прошло через все ворота» — и ответ должен превратиться в новую проверку в [конвейере](./frontend-ci-cd), иначе всё повторится.

## Что спросят на интервью

**Почему у файлов в имени хеш и какие заголовки кеширования им ставят?** Хеш зависит от содержимого, поэтому один URL всегда соответствует одному содержимому. Такие файлы кешируются на год с `immutable`. `index.html` — с `no-cache`: он и есть точка входа, которая должна быть свежей.

**Что будет, если закешировать `index.html` надолго?** Пользователь застрянет на старой версии и не получит ни исправлений, ни отката, потому что переключение на сервере он не увидит. Достучаться до него нельзя.

**Почему выкладку нельзя делать файл за файлом?** Появляется окно, в котором новый `index.html` уже отдаётся, а его чанков ещё нет, — пользователь получает 404 и белый экран. Правильный порядок: сначала все ассеты, не удаляя старые, потом одним действием переключить точку входа.

**Пользователь держал вкладку сутки, вышел релиз, он нажал на ленивый маршрут и получил ошибку загрузки чанка. Что делать?** Три меры вместе: хранить старые сборки несколько недель; перехватывать ошибку динамического импорта и один раз перезагружать страницу с флагом в `sessionStorage` от зацикливания; периодически сверять версию с сервером и предлагать обновиться до того, как ошибка случится.

**Почему при откате не пересобирают?** Долго, а результат может отличаться от того, что работало: сборка недетерминирована во времени. Плюс конвейер может быть красным именно тогда, когда откат нужен. Откат — переключение указателя на сохранённый артефакт.

**Чем канареечный релиз отличается от сине-зелёного и почему на фронте сложнее?** Канареечный даёт новую версию доле пользователей, сине-зелёный переключает всех разом между двумя окружениями. На фронте сложнее, потому что пользователь получает граф файлов, а не один ответ, сессия живёт часами и откат не догоняет уже загрузившихся. Решают разведением точек входа на уровне CDN с закреплением версии в cookie.

**Зачем фича-флаги, если есть постепенный раскат?** Они разделяют выкладку и включение: код едет выключенным, включается отдельным обратимым действием без сборки. Платишь ветвлением кода, комбинаторным ростом состояний и флагами, которые никто не удалил.

**Как отдавать карты исходников в проде?** Собирать в режиме `hidden`, загружать в сервис мониторинга с тем же идентификатором релиза, а сами файлы не публиковать. Карта содержит исходный код целиком.

## Коротко, для повторения

1. Хеш содержимого в имени файла делает URL неизменяемым — на этом держится вся схема кеширования.
2. `index.html` — `no-cache`, файлы с хешем — `max-age` на год плюс `immutable`. Перепутать местами нельзя: закешированная точка входа делает пользователя недостижимым.
3. Выкладка атомарна: сначала ассеты рядом со старыми, потом одним действием точка входа, уборка старого — отложенно.
4. `--delete` при заливке новой сборки удаляет чанки, которые прямо сейчас нужны открытым вкладкам.
5. Устаревшая вкладка ломается на ленивых маршрутах: динамический импорт идёт по сети спустя часы. Лечится тремя мерами вместе — хранением старых сборок, однократной перезагрузкой по ошибке и уведомлением о новой версии.
6. Флаг перезагрузки живёт в `sessionStorage`, иначе цикл перезагрузок при обычной сетевой ошибке.
7. Откат — переключение указателя на сохранённый артефакт, а не пересборка: пересборка долгая и может дать другой результат.
8. Откат не отменяет миграции, состояние флагов и изменения бэкенда — их делают обратно совместимыми.
9. Канареечный раскат на фронте делается разведением точек входа на CDN с закреплением версии в cookie; ассеты обеих версий лежат рядом и не конфликтуют благодаря хешам.
10. Флаги разделяют «выложить» и «включить», но стоят ветвлением кода и требуют владельца и срока жизни.
11. Карты исходников собираются скрытыми, загружаются в мониторинг по идентификатору релиза и не публикуются рядом с бандлом.
12. При инциденте порядок один: остановить раскат, выключить флаг или откатить, убедиться что доехало, сообщить — и только потом разбираться.
