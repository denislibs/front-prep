# Прототипы, наследование и классы

В JavaScript нет классов. То есть слово `class` есть с 2015 года, а вот классов в том смысле, в каком они существуют в Java или C#, — нет. Под `class` работает единственный механизм наследования, который был в языке с самого начала: **прототипы**.

Знать это нужно не ради эрудиции. Из прототипов напрямую следует, почему методы класса не копируются в каждый объект, почему `instanceof` иногда врёт, почему у стрелочной функции нельзя вызвать `new` и почему добавлять методы в `Array.prototype` — плохая идея.

Разберём механику снизу вверх: сначала прототип, потом `new`, и только потом `class`.

## Часть 1. Прототип простыми словами

**Прототип** — это другой объект, к которому идут за свойством, если своего такого свойства нет.

У почти каждого объекта есть скрытая ссылка на его прототип. В спецификации она называется внутренним полем `[[Prototype]]`, в отладчике отображается как `[[Prototype]]` или `__proto__`, а читается корректным способом через `Object.getPrototypeOf(obj)`.

```js
const animal = {
  eat() { return 'ем'; },
};

const dog = {
  bark() { return 'гав'; },
};

Object.setPrototypeOf(dog, animal);   // прототипом dog стал animal

dog.bark();   // 'гав' — своё свойство
dog.eat();    // 'ем'  — своего нет, нашлось в прототипе
```

### Как ищется свойство

Алгоритм короткий и его стоит запомнить дословно:

1. Есть ли у объекта **собственное** свойство с таким именем? Есть — вернуть его, конец.
2. Нет — взять `[[Prototype]]` и повторить шаг 1 для него.
3. Дошли до `null` — вернуть `undefined`.

Заметь: ошибки нет. Обращение к несуществующему свойству возвращает `undefined`, в отличие от обращения к необъявленной переменной, которое бросает `ReferenceError` (про это в статье [область видимости и замыкания](./scope-and-closures)).

**Собственное свойство** (own property) — то, что лежит физически в самом объекте, а не найдено по цепочке. Проверяется через `Object.hasOwn(obj, 'key')` (раньше — `obj.hasOwnProperty('key')`).

```js
'eat' in dog;                  // true  — оператор in ищет по всей цепочке
Object.hasOwn(dog, 'eat');     // false — собственного нет
Object.hasOwn(dog, 'bark');    // true
```

### Запись по цепочке не идёт

Важнейшая асимметрия: **чтение идёт по цепочке, запись — нет**. Присваивание всегда создаёт или меняет **собственное** свойство объекта.

```js
const proto = { count: 0 };
const a = Object.create(proto);   // прототип a — proto
const b = Object.create(proto);

a.count;        // 0 — прочитали из прототипа
a.count += 1;   // прочитали 0 из прототипа, записали 1 в собственное свойство a
a.count;        // 1
b.count;        // 0 — прототип не изменился
proto.count;    // 0
```

Из-за этого нельзя класть в прототип изменяемые данные: массив в прототипе будет один на всех (потому что `arr.push()` — не присваивание, а мутация общего объекта), а число будет вести себя как копия. Отсюда правило: **в прототипе — методы, в экземпляре — данные**. Классы это правило соблюдают автоматически.

Проверить цепочку можно руками:

```js
const obj = {};
Object.getPrototypeOf(obj) === Object.prototype;                    // true
Object.getPrototypeOf(Object.prototype);                            // null

const arr = [];
Object.getPrototypeOf(arr) === Array.prototype;                     // true
Object.getPrototypeOf(Array.prototype) === Object.prototype;        // true
```

Именно поэтому у пустого массива есть `map`, `filter` и `toString`: своих у него нет ни одного, всё найдено по цепочке. И поэтому же `[].hasOwnProperty` работает — оно приехало из `Object.prototype` через два звена.

Объект вообще без прототипа делается так:

```js
const dict = Object.create(null);
dict.toString;             // undefined — цепочки нет
```

Это стандартный приём для словарей: чистый объект нельзя случайно спутать с унаследованным свойством вроде `constructor`.

## Часть 3. `__proto__` против `prototype`

Самая частая путаница в теме, поэтому разберём медленно. Это **два разных свойства у двух разных сущностей**.

**`__proto__`** (правильнее — `Object.getPrototypeOf`) есть у **любого объекта**. Это ссылка на его прототип, то есть на объект, где будут искать недостающие свойства. Отвечает на вопрос: «а куда пойдут искать дальше?»

**`prototype`** есть **только у функций** — и то не у всех. Это обычное, видимое свойство функции, в котором лежит объект. Сама функция им не пользуется. Он нужен ровно для одного: **стать прототипом объектов, созданных через `new` от этой функции**.

```js
function Dog(name) {
  this.name = name;
}
Dog.prototype.bark = function () { return 'гав'; };

const rex = new Dog('Рекс');

Object.getPrototypeOf(rex) === Dog.prototype;   // true
rex.prototype;                                   // undefined — у экземпляра его нет
Dog.prototype.bark;                              // функция
```

Сведём в одну фразу, которую можно повторить на интервью:

> У функции `prototype` — это заготовка для будущих экземпляров. У объекта `__proto__` — это ссылка на его настоящий прототип. После `new` они указывают на один и тот же объект: `Object.getPrototypeOf(экземпляр) === Функция.prototype`.

Пара следствий, на которых ловят:

- У самой функции тоже есть `__proto__`, и он равен `Function.prototype` — оттуда берутся `call`, `apply` и `bind` (см. статью [this и контекст](./this-and-context)). Не путай `Dog.__proto__` (`Function.prototype`) и `Dog.prototype` (заготовка для собак).
- В объекте `Dog.prototype` есть свойство `constructor`, указывающее обратно на `Dog`. Поэтому `rex.constructor === Dog` — свойство найдено по цепочке. Если целиком заменить `Dog.prototype = { bark() {} }`, `constructor` потеряется, и это классический баг старого кода.
- `__proto__` — исторический геттер-сеттер из `Object.prototype`, оставленный в стандарте ради совместимости. В новом коде используй `Object.getPrototypeOf` и `Object.setPrototypeOf`. Менять прототип существующему объекту вообще не стоит: движок оптимизирует объекты по их «форме», и смена прототипа выбрасывает объект из всех оптимизаций.

Это можно написать вручную и убедиться, что никакой магии нет:

```js
function myNew(Fn, ...args) {
  const obj = Object.create(Fn.prototype);   // шаги 1 и 2 сразу
  const res = Fn.apply(obj, args);           // шаг 3
  return (typeof res === 'object' && res !== null) ? res : obj;   // шаг 4
}

const rex = myNew(Dog, 'Рекс');
rex.bark();   // 'гав'
```

Обрати внимание на шаг 4: если конструктор явно вернул объект, вернётся именно он. Возврат примитива (`return 42`) игнорируется. На этой особенности строится, например, паттерн «одиночка» через конструктор.

### Object.create

`Object.create(proto)` — прямой способ создать объект с заданным прототипом, без всякой функции-конструктора.

```js
const animal = { eat() { return 'ем'; } };
const dog = Object.create(animal);          // прототип задан сразу
dog.bark = function () { return 'гав'; };
```

Это самая честная демонстрация того, что прототипное наследование — про **связь объекта с объектом**, а не про классы. Классы поверх этого — уже синтаксис.

Второй аргумент `Object.create` принимает дескрипторы свойств — это редко нужно, но объясняет, почему `Object.create(proto, { x: { value: 1 } })` создаёт неперечисляемое свойство: по умолчанию все флаги дескриптора равны `false`.

## Часть 5. class — синтаксический сахар

```js
class Dog {
  constructor(name) {
    this.name = name;
  }
  bark() {
    return this.name + ': гав';
  }
}
```

Что реально создаётся:

1. Функция `Dog` — тело `constructor` становится её телом.
2. Объект `Dog.prototype`, в который кладётся метод `bark` и свойство `constructor`, указывающее на `Dog`.

Проверяется тривиально:

```js
typeof Dog;                              // 'function'
Object.hasOwn(Dog.prototype, 'bark');    // true
const rex = new Dog('Рекс');
Object.hasOwn(rex, 'bark');              // false — метод не в экземпляре
Object.hasOwn(rex, 'name');              // true  — а данные в экземпляре
```

Вот главный практический смысл прототипов: **методы существуют в одном экземпляре на весь класс**. Создай миллион собак — функция `bark` в памяти будет одна. Если бы методы копировались в каждый объект, миллион собак означал бы миллион функций.

Именно поэтому поле класса со стрелкой (`bark = () => {}`) — не бесплатная замена метода: оно кладёт **свою функцию каждому экземпляру**, зато навсегда привязывает `this`. Разбор компромисса — в статье [this и контекст](./this-and-context).

### Чем class всё-таки отличается от функции

Сахар не совсем прозрачный. Отличия есть, и их спрашивают:

- **Нельзя вызвать без `new`.** `Dog('Рекс')` бросает `TypeError`. У обычной функции-конструктора это молча ломалось бы.
- **Тело всегда в строгом режиме**, независимо от директив в файле.
- **Объявление класса не всплывает так, как функция.** Имя резервируется, но остаётся в временной мёртвой зоне до строки объявления — как у `let`. Обращение выше по коду даёт `ReferenceError`.
- **Методы неперечисляемы.** `for...in` по экземпляру их не покажет, а методы, положенные руками в `prototype` старым способом, покажет.
- **Внутреннее поле `[[HomeObject]]`.** У методов, записанных сокращённым синтаксисом, оно есть — благодаря ему работает `super`. У функции, присвоенной в `prototype` вручную, его нет, и `super` там невозможен.

## Часть 6. extends и super

```js
class Animal {
  constructor(name) { this.name = name; }
  eat() { return this.name + ' ест'; }
}

class Dog extends Animal {
  constructor(name, breed) {
    super(name);              // вызов конструктора родителя
    this.breed = breed;
  }
  eat() {
    return super.eat() + ' из миски';   // вызов метода родителя
  }
}
```

`extends` связывает **две цепочки сразу**:

- `Dog.prototype.__proto__ === Animal.prototype` — экземпляр найдёт методы родителя;
- `Dog.__proto__ === Animal` — сам класс унаследует **статические** члены родителя.

Второе часто упускают, а это ровно то, почему `Dog.create()` работает, если `Animal` объявил `static create()`.

### Почему нельзя трогать this до super()

В классе-наследнике объект создаёт не он сам, а **самый дальний предок в цепочке**. `super(...)` — это и есть тот момент, когда объект появляется и попадает в `this`. До вызова `super()` ячейка `this` находится в TDZ, и обращение к ней даёт `ReferenceError`.

```js
class Dog extends Animal {
  constructor(name) {
    // this.breed = 'корги';   // ReferenceError
    super(name);
    this.breed = 'корги';      // теперь можно
  }
}
```

Если конструктор в наследнике не написан вообще, движок подставляет `constructor(...args) { super(...args); }`.

### super — не «родительский объект»

`super.eat()` не равно `Animal.prototype.eat()` по смыслу вызова. Метод ищется в прототипе того объекта, где метод **был объявлен** (то самое `[[HomeObject]]`), а вызывается с текущим `this`. Поэтому внутри `super.eat()` значение `this.name` — это имя конкретной собаки, а не что-то родительское.

Разница видна на цепочке из трёх классов: если бы `super` означал «взять `this.__proto__.__proto__`», то при трёх уровнях наследования получилась бы бесконечная рекурсия. `[[HomeObject]]` эту проблему решает.

## Часть 7. Приватные поля

```js
class Counter {
  #count = 0;                 // приватное поле

  increment() {
    this.#count += 1;
    return this.#count;
  }

  static isCounter(obj) {
    return #count in obj;     // проверка без исключения
  }
}

const c = new Counter();
c.increment();   // 1
c.#count;        // SyntaxError ещё до запуска
```

Ключевые отличия от «приватности по соглашению» (`_count`) и от приватности через замыкание:

- Это **настоящая** приватность на уровне языка. Не достать ни через `Object.keys`, ни через `JSON.stringify`, ни через `Reflect.ownKeys`, ни через отладчик из чужого кода.
- Ошибка **синтаксическая**, а не времени выполнения: код с обращением к чужому приватному полю не запустится вовсе.
- Приватные поля не являются свойствами и не участвуют в прототипной цепочке — наследник к `#count` родителя не доберётся.
- Приватность привязана к классу, а не к экземпляру: метод одного объекта может читать `#count` другого объекта того же класса.

По сравнению с замыканием (`function makeCounter()` из статьи [область видимости и замыкания](./scope-and-closures)) выигрыш в памяти: методы остаются в прототипе, а не создаются на каждый объект.

## Часть 8. Статические члены

**Статический** член принадлежит самому классу, а не экземплярам.

```js
class Model {
  static registry = new Map();     // статическое поле

  static create(data) {            // статический метод
    return new this(data);         // this — сам класс
  }

  static { }                       // статический блок инициализации
}

Model.create({});      // работает
new Model({}).create;  // undefined — у экземпляра статики нет
```

Механически всё просто: статические члены кладутся **в саму функцию класса**, а не в её `prototype`. Поэтому экземпляр их не видит — его цепочка идёт через `Dog.prototype`, а не через `Dog`.

А наследник видит, потому что `extends` связал `Dog.__proto__ === Animal`. Отсюда же полезный приём: `new this()` в статическом методе создаёт объект правильного подкласса, потому что `this` в статическом методе — тот класс, через который метод вызвали.

## Часть 9. Почему у стрелок нет prototype

Обычная функция получает свойство `prototype` при создании, потому что её потенциально можно вызвать через `new`. У стрелочной функции внутреннего метода `[[Construct]]` нет — вызвать её через `new` нельзя в принципе, значит и заготовка для экземпляров не нужна.

```js
function f() {}
const g = () => {};

f.prototype;             // {} — объект-заготовка
g.prototype;             // undefined
new g();                 // TypeError: g is not a constructor
```

Та же логика распространяется дальше: `prototype` нет у методов, записанных сокращённым синтаксисом (`{ bark() {} }`), и у геттеров. Все они не предназначены для `new`. А вот у `class` `prototype` есть — и он неперезаписываем.

## Часть 10. instanceof

`obj instanceof Fn` отвечает на вопрос: **встречается ли `Fn.prototype` где-нибудь в цепочке прототипов `obj`**.

```js
const rex = new Dog('Рекс');
rex instanceof Dog;       // true  — Dog.prototype в цепочке
rex instanceof Animal;    // true  — Animal.prototype тоже
rex instanceof Object;    // true  — и Object.prototype
```

То есть `instanceof` проверяет не «кем был создан объект», а лишь форму цепочки. Отсюда три практических следствия.

**Первое: его можно обмануть.**

```js
const fake = Object.create(Dog.prototype);
fake instanceof Dog;      // true, хотя конструктор Dog не вызывался
```

**Второе: он ломается между «мирами».** Каждый iframe и каждый воркер имеет свои собственные встроенные объекты, включая свой `Array.prototype`. Массив из iframe не является `instanceof Array` в родительском окне — цепочки разные. Поэтому для проверки массива используют `Array.isArray(x)`, а для общей проверки типа — `Object.prototype.toString.call(x)`.

**Третье: поведение настраивается.** Оператор смотрит на символ `Symbol.hasInstance`, и класс может переопределить проверку.

```js
class Even {
  static [Symbol.hasInstance](n) { return n % 2 === 0; }
}
4 instanceof Even;   // true
```

Для полноты: `isPrototypeOf` делает то же самое, но принимает прототип напрямую — `Dog.prototype.isPrototypeOf(rex)`.

## Часть 11. Прототипы в реальном коде

### Когда работать с ними напрямую

Честный ответ: редко. В прикладном коде `class` покрывает практически всё, и лезть в `Object.setPrototypeOf` обычно означает, что задачу решают не тем инструментом.

Прототипы всё же нужны:

- **`Object.create(null)`** для словарей и любых объектов, ключи которых приходят снаружи. Нет цепочки — нет риска, что ключ `constructor` или `__proto__` совпадёт с унаследованным.
- **Полифилы.** Добавить недостающий метод в `Array.prototype` — единственный способ реализовать стандартную возможность в старом движке. Ключевое слово: **стандартную**, то есть ту, которая уже есть в спецификации.
- **Отладка и понимание чужого кода.** Библиотеки, написанные до 2015 года, целиком построены на явной работе с `prototype`.
- **Экономия памяти в горячем коде.** Если создаются сотни тысяч однотипных объектов, общий прототип с методами заметно дешевле, чем объекты с функциями-полями.

Ещё одна причина понимать механику — отладка. Когда в консоли видно, что у объекта нет метода, который «должен быть», ответ почти всегда в цепочке: где-то потерян прототип. Например, при `Object.assign({}, instance)` в новый объект скопируются только собственные свойства, а все методы останутся позади.

### Почему нельзя расширять встроенные прототипы

```js
// Так делать нельзя
Array.prototype.last = function () { return this[this.length - 1]; };
```

Причин несколько, и каждой достаточно:

**Столкновение со стандартом.** Ровно так браузеры не смогли добавить `Array.prototype.flatten`: популярная библиотека уже определила своё `flatten`, чужой код от нового метода ломался, и метод пришлось переименовать в `flat`. Твоё имя сегодня свободно, а через два года станет частью языка с другой семантикой.

**Столкновение с чужим кодом.** Две библиотеки определяют `last` по-разному — выигрывает та, что загрузилась позже. Отладка такого занимает часы.

**Ломается перебор.** Свойство, добавленное присваиванием, перечислимо, поэтому попадает в `for...in`:

```js
Array.prototype.last = function () {};
for (const key in [1, 2]) console.log(key);   // 0, 1, last
```

`Object.prototype` расширять ещё опаснее: испорченным окажется перебор **любого** объекта в программе.

**Падает производительность.** Движки держат быстрые пути для нетронутых встроенных прототипов. Изменил `Array.prototype` — часть оптимизаций отключается для всех массивов в программе.

Что делать вместо: обычные функции (`last(arr)`), классы-обёртки или, если очень хочется точечного синтаксиса, наследование от встроенного типа. Только помни, что `class MyArray extends Array` возвращает `MyArray` из `map` и `filter` — за это отвечает `Symbol.species`, и обычно это не то, чего ждут.

## Что спросят на интервью

**Что такое прототип?** Объект, к которому идут за свойством, если своего нет. Ссылка на него — внутреннее поле `[[Prototype]]`, доступное через `Object.getPrototypeOf`.

**Чем `__proto__` отличается от `prototype`?** `__proto__` есть у любого объекта и указывает на его прототип. `prototype` есть только у функций и служит заготовкой: он станет прототипом объектов, созданных через `new`. После `new` они совпадают.

**Что делает `new`?** Создаёт пустой объект, ставит ему прототипом `Fn.prototype`, вызывает `Fn` с этим объектом в качестве `this`, возвращает объект — если функция не вернула свой собственный объект.

**Как ищется свойство?** Собственное → прототип → прототип прототипа → `null` → `undefined`. Запись при этом по цепочке не идёт: присваивание всегда создаёт собственное свойство.

**`class` — это сахар над чем?** Над функцией-конструктором и её `prototype`. С отличиями: строгий режим, запрет вызова без `new`, TDZ вместо всплытия, неперечисляемые методы, поддержка `super`.

**Где живут методы класса?** В `Класс.prototype`, один экземпляр функции на все объекты. Поля класса — в самом объекте, свои у каждого.

**Что делает `extends`?** Связывает две цепочки: прототипы экземпляров и сами классы (для статических членов).

**Почему нельзя использовать `this` до `super()`?** Объект создаёт базовый класс, и `this` появляется только после вызова `super()`. До этого он в TDZ.

**Как работает `instanceof`?** Ищет `Fn.prototype` в цепочке прототипов объекта. Обманывается через `Object.create`, ломается между iframe, настраивается через `Symbol.hasInstance`.

**Почему у стрелочной функции нет `prototype`?** У неё нет внутреннего метода `[[Construct]]`, её нельзя вызвать через `new` — заготовка для экземпляров не нужна.

**Чем `#private` лучше `_private`?** Настоящая приватность на уровне языка, ошибка на этапе разбора кода, поле не видно ни в `Object.keys`, ни в `JSON.stringify`, ни наследникам.

**Почему нельзя дополнять `Array.prototype`?** Конфликты с будущим стандартом и чужим кодом, попадание в `for...in`, потеря оптимизаций движка. История с `flatten` — реальный прецедент.

## Коротко, для повторения

1. Прототип — объект, к которому идут за свойством, если своего нет. Цепочка заканчивается на `null`.
2. Чтение идёт по цепочке, запись — нет. Присваивание всегда создаёт собственное свойство.
3. Поэтому в прототипе держат методы, а данные — в экземпляре.
4. `prototype` — свойство функции, заготовка для будущих экземпляров. `__proto__` — ссылка объекта на его настоящий прототип.
5. `new`: пустой объект → прототип из `Fn.prototype` → вызов `Fn` с `this` → возврат объекта, если функция не вернула свой.
6. `Object.create(proto)` делает то же самое напрямую, без конструктора. `Object.create(null)` даёт объект вообще без цепочки.
7. `class` создаёт функцию плюс её `prototype` с методами. Отличия от функции: строгий режим, обязательный `new`, TDZ, неперечисляемые методы, `super`.
8. `extends` связывает и прототипы экземпляров, и сами классы — отсюда наследование статических членов.
9. `this` в наследнике доступен только после `super()`: объект создаёт базовый класс.
10. `#`-поля — настоящая приватность: синтаксическая ошибка при доступе снаружи, не видны наследникам и сериализации.
11. У стрелок нет `prototype` и `[[Construct]]`, поэтому `new` с ними невозможен.
12. `instanceof` проверяет наличие `Fn.prototype` в цепочке, а не факт вызова конструктора. Между iframe не работает — используй `Array.isArray`.
13. Встроенные прототипы не расширяют: конфликты имён, `for...in`, потеря оптимизаций.
