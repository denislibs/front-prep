# Производительность интерфейса: что тормозит и почему

«Приложение тормозит» — это не диагноз, а симптом. За ним стоят совершенно разные причины: слишком много перерисовок, одна тяжёлая перерисовка, долгое вычисление, огромный DOM, гигантский бандл, дёрганая анимация. Лечатся они по-разному, и приём, который спасает в одном случае, в другом только добавляет кода.

Поэтому статья начинается не с `React.memo`, а с измерения. Половина работы по производительности — это выяснить, что именно медленно. Вторая половина обычно оказывается однострочной.

Читать имеет смысл вместе со статьёй [как работает браузер](./browser-rendering-event-loop): там объяснено, почему главный поток один, что такое кадр и почему длинная задача подвешивает страницу. Здесь — что с этим делать на уровне приложения.

## Часть 1. Сначала измерь

### Три вопроса, на которые надо ответить

1. **Медленно при загрузке или при работе?** Первое — размер бандла и водопады запросов. Второе — перерисовки и вычисления.
2. **Одна операция медленная или всё подряд?** Одна — ищи конкретный обработчик. Всё — ищи то, что происходит при каждом обновлении.
3. **Медленно из-за количества или из-за одного тяжёлого куска?** Тысяча дешёвых компонентов и один дорогой лечатся противоположными способами.

### Профайлер React

Расширение React DevTools, вкладка Profiler. Нажимаешь запись, делаешь действие, останавливаешь. Что смотреть:

**Flamegraph** — дерево компонентов, ширина полосы равна времени. Серые компоненты не перерисовывались, цветные перерисовались. Первое, что ищешь: **широкие цветные полосы там, где ничего не должно было меняться**.

**Ranked** — те же данные, отсортированные по времени. Сразу видно топ дорогих компонентов за коммит.

**«Why did this render?»** — надо включить в настройках профайлера («Record why each component rendered»). После этого при выборе компонента будет написана причина: изменились пропсы (и какие именно), изменилось состояние, изменился контекст, перерисовался родитель. Это самый полезный переключатель во всём инструменте — он превращает догадки в факты.

Ещё одна настройка, «Highlight updates when components render», подсвечивает перерисовки рамкой прямо на странице. Напечатал букву в поле — вся страница вспыхнула рамками — диагноз поставлен за три секунды.

### Панель Performance

React-профайлер показывает время в компонентах. Он не покажет, что тормозит разбор JSON, дорогой CSS-селектор или принудительный пересчёт макета. Для этого — панель Performance в DevTools.

Что искать:

- **Длинные задачи** в полосе Main — блоки дольше 50 мс с красным уголком. Пока такая задача идёт, страница не реагирует ни на что.
- **Цвета**: жёлтый — JavaScript, фиолетовый — стили и макет, зелёный — отрисовка. Много фиолетового при вводе текста — проблема не в React, а в CSS и макете.
- **Предупреждение Forced reflow** — код прочитал геометрию и заставил браузер синхронно пересчитать макет.

Полезная привычка: включи в настройках замедление процессора (CPU throttling) в 4–6 раз. На машине разработчика всё быстро; проблемы пользователей воспроизводятся именно так.

### Правило

**Не оптимизируй то, что не измерил.** Мемоизация, которую добавили «на всякий случай», — это код, который надо читать, поддерживать и обновлять зависимости. Если она ничего не ускоряет, она чистый минус.

Важное уточнение, без которого начинается паника: **перерисовка сама по себе не страшна**. React вызвал функцию компонента, получил описание дерева, сравнил с предыдущим, увидел совпадение — DOM не тронул. Это дёшево.

Дорого становится в трёх случаях: перерисовок тысячи (большой список), внутри перерисовки идёт тяжёлое вычисление, или результат действительно меняет DOM и запускает макет.

Отсюда практическое следствие: **прежде чем бороться с количеством перерисовок, проверь, что дорого именно оно**. Часто настоящая проблема — один компонент, который на каждый рендер сортирует массив на десять тысяч элементов.

## Часть 3. Почему мемоизация часто не работает

`React.memo` оборачивает компонент и говорит: «если пропсы не изменились, не перерисовывай». Сравнение поверхностное — каждый проп сравнивается по `Object.is`, то есть объекты и функции сравниваются по ссылке, а не по содержимому.

Вот здесь и ломается.

```jsx
// Было: memo стоит, а толку нет
const Row = memo(function Row({ item, style, onSelect }) {
  return <div style={style} onClick={() => onSelect(item.id)}>{item.title}</div>;
});

function List({ items }) {
  const [query, setQuery] = useState('');

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      {items.map((item) => (
        <Row
          key={item.id}
          item={item}
          style={{ height: 40 }}                    // новый объект на каждый рендер
          onSelect={(id) => console.log(id)}        // новая функция на каждый рендер
        />
      ))}
    </>
  );
}
```

Каждая буква в поле перерисовывает `List`, а значит литерал `{ height: 40 }` создаётся заново. Новый объект — новая ссылка — `memo` видит изменившийся проп и перерисовывает строку. То же со стрелкой: она создаётся при каждом рендере и всегда не равна предыдущей.

`memo` здесь не просто бесполезен — он вреден: добавилось сравнение пропсов, которое всегда даёт «изменилось». Плата без выгоды.

```jsx
// Стало: ссылки стабильны
const ROW_STYLE = { height: 40 };     // константа вынесена из компонента

const Row = memo(function Row({ item, onSelect }) {
  return <div style={ROW_STYLE} onClick={() => onSelect(item.id)}>{item.title}</div>;
});

function List({ items }) {
  const [query, setQuery] = useState('');

  // функция создаётся один раз: она не зависит ни от чего изменяемого
  const handleSelect = useCallback((id) => {
    console.log(id);
  }, []);

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      {items.map((item) => (
        <Row key={item.id} item={item} onSelect={handleSelect} />
      ))}
    </>
  );
}
```

### Правило трёх

Мемоизация компонента работает, только если выполнены **все три** условия:

1. Компонент обёрнут в `memo`.
2. **Все** пропсы стабильны между рендерами: примитивы либо мемоизированные объекты и функции.
3. Компонент не читает контекст, который меняется.

Пропущено одно — не работает ничего. Именно поэтому `memo`, добавленный точечно «вот сюда», обычно не даёт эффекта: где-то среди восьми пропсов остался литерал.

### Ловушки

**Обработчик с аргументом.** Соблазн написать `onClick={() => onSelect(item.id)}` в родителе. Каждая такая стрелка уникальна. Решение — передавать идентификатор внутрь и вызывать там, или хранить его в атрибуте `data-`.

**`useCallback` с меняющейся зависимостью.** Обёртка есть, но в списке зависимостей лежит объект, который сам создаётся каждый рендер. Мемоизация формально выполнена, фактически бесполезна.

**Дети как пропс.** `<Card>{children}</Card>` — если `children` создаются в перерисовывающемся родителе, они новые каждый раз, и `memo` на `Card` не сработает. Это не баг, а особенность: спасает не `memo`, а перенос места создания, см. следующую часть.

**Значение контекста.** `memo` не защищает от контекста. Компонент внутри `memo`, читающий изменившийся контекст, перерисуется.

### А компилятор?

React Compiler автоматически расставляет мемоизацию за тебя, и в проектах, где он включён, ручные `useMemo` и `useCallback` в большинстве мест лишние. Но понимать механику всё равно нужно: во-первых, компилятор есть не везде, во-вторых, вопрос «почему memo не сработал» на собеседовании задают именно про ручной вариант.

## Часть 4. Композиция вместо мемоизации

Самый недооценённый приём. Он не требует ни `memo`, ни списков зависимостей.

```jsx
// Было: тяжёлое поддерево внутри компонента с частым состоянием
function Page() {
  const [tab, setTab] = useState('info');

  return (
    <div>
      <Tabs value={tab} onChange={setTab} />
      <HeavyChart data={chartData} />     {/* перерисовывается при смене вкладки */}
      <HeavyTable rows={rows} />          {/* и этот тоже */}
    </div>
  );
}
```

Смена вкладки перерисовывает график и таблицу, которым до вкладки нет никакого дела. Стандартная реакция — обернуть оба в `memo` и мемоизировать `chartData` и `rows`. Работает, но это три обёртки и три списка зависимостей, которые надо поддерживать.

```jsx
// Стало: состояние ушло вниз, тяжёлое поддерево пришло сверху
function Page() {
  return (
    <TabsShell>
      <HeavyChart data={chartData} />
      <HeavyTable rows={rows} />
    </TabsShell>
  );
}

function TabsShell({ children }) {
  const [tab, setTab] = useState('info');   // состояние живёт здесь

  return (
    <div>
      <Tabs value={tab} onChange={setTab} />
      {children}
    </div>
  );
}
```

## Часть 5. Опускание состояния вниз

Композиция работает, когда тяжёлое можно вынести наружу. Зеркальный приём — когда наружу выносится **состояние**.

```jsx
// Было: поле поиска перерисовывает весь экран
function ProductsPage({ products }) {
  const [search, setSearch] = useState('');
  const [sort, setSort] = useState('name');

  const visible = useMemo(
    () => products.filter((p) => p.name.includes(search)).sort(byField(sort)),
    [products, search, sort]
  );

  return (
    <div>
      <PageHeader />                                     {/* незачем */}
      <Filters sort={sort} onSortChange={setSort} />
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      <ProductGrid items={visible} />                    {/* 400 карточек */}
      <Sidebar />                                        {/* незачем */}
    </div>
  );
}
```

Что происходит на нажатие клавиши: перерисовывается `ProductsPage`, вместе с ним шапка, боковая панель, фильтры и все четыреста карточек. При этом карточки действительно должны обновиться — список фильтруется. А вот шапка и панель — нет.

Ощущение у пользователя: буквы появляются с задержкой, курсор «залипает». Особенно на слабых машинах и в мобильном браузере.

Лечение в два хода.

**Ход первый: то, что не зависит от состояния, не должно быть внутри перерисовки.** Здесь помогает композиция из предыдущей части.

**Ход второй: состояние ввода не должно жить выше, чем нужно.** Часто хватает разделить «то, что пользователь печатает» и «то, по чему фильтруем».

```jsx
// Стало: быстрое состояние внизу, наружу уходит только результат
function ProductsPage({ products }) {
  const [search, setSearch] = useState('');
  const [sort, setSort] = useState('name');

  const visible = useMemo(
    () => products.filter((p) => p.name.includes(search)).sort(byField(sort)),
    [products, search, sort]
  );

  return (
    <div>
      <PageHeader />
      <Filters sort={sort} onSortChange={setSort} />
      <SearchInput onSearch={setSearch} />     {/* буквы остаются внутри */}
      <ProductGrid items={visible} />
      <Sidebar />
    </div>
  );
}

function SearchInput({ onSearch }) {
  const [value, setValue] = useState('');

  // наружу отдаём не каждую букву, а установившееся значение
  useEffect(() => {
    const id = setTimeout(() => onSearch(value), 200);
    return () => clearTimeout(id);
  }, [value, onSearch]);

  return <input value={value} onChange={(e) => setValue(e.target.value)} />;
}
```

Теперь каждая буква перерисовывает один компонент с полем ввода. Страница просыпается раз в 200 мс, когда пользователь сделал паузу. Про то, как правильно устроить задержку и отменить устаревшие запросы, — в статье [поиск и автодополнение](./search-and-autocomplete), а про размещение состояния вообще — в статье [где должно жить состояние](./state-management-patterns).

Общий принцип: **держи быстро меняющееся состояние как можно ниже**. Это дешевле мемоизации, потому что не требует ни обёрток, ни зависимостей, ни памяти.

## Часть 6. `useTransition` и `useDeferredValue`

Иногда состояние опустить нельзя: фильтрация действительно меняет большой список, и обновить его надо. Тогда задача не «не перерисовывать», а **«не заставлять пользователя ждать перерисовки»**.

`useDeferredValue` даёт React разрешение отрисовать тяжёлую часть с отставанием.

```jsx
function Search({ items }) {
  const [query, setQuery] = useState('');
  const deferred = useDeferredValue(query);       // «отстающая» копия значения

  // тяжёлый список считается по отстающему значению
  const results = useMemo(
    () => items.filter((i) => i.name.includes(deferred)),
    [items, deferred]
  );

  return (
    <>
      {/* поле реагирует на query — мгновенно */}
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <div style={{ opacity: query !== deferred ? 0.6 : 1 }}>
        <Results items={results} />
      </div>
    </>
  );
}
```

Что происходит: React делает два рендера. Первый — срочный, с новым `query` и старым `deferred`: поле обновляется мгновенно, список остаётся прежним. Второй — несрочный, с новым `deferred`: пересчитывается список. Если за это время пользователь нажал ещё клавишу, несрочный рендер **выбрасывается** и начинается заново.

`useTransition` — то же самое, но помечается не значение, а обновление:

```jsx
const [isPending, startTransition] = useTransition();

function selectTab(next) {
  setActiveTab(next);                    // срочно: подсветка вкладки
  startTransition(() => {
    setContent(next);                    // несрочно: тяжёлое содержимое
  });
}
```

Разница на практике: `useTransition` берут, когда есть доступ к вызову `setState`; `useDeferredValue` — когда значение приходит пропсом и пометить его обновление нельзя.

Чего они **не** делают: не ускоряют вычисление. Если фильтрация занимает 500 мс, она и будет занимать 500 мс — просто главный поток сможет прерваться и обработать ввод. Это про отзывчивость, а не про скорость.

Ещё одна важная деталь: приём работает только тогда, когда тяжёлая работа идёт **в рендере**. Если ты вычисляешь в обработчике события синхронно, никакая транзакция не поможет: обработчик прервать нельзя.

## Часть 7. Виртуализация

Когда список большой, дело уже не в React, а в DOM. Десять тысяч узлов — это память, дорогой пересчёт стилей и макета, тормоза при прокрутке.

**Виртуализация** — держать в DOM только видимую часть списка, а остальному отдавать пустое место нужной высоты.

```jsx
// Было: рисуем всё
<div className="list">
  {rows.map((row) => <Row key={row.id} row={row} />)}   // 10 000 узлов
</div>

// Стало: рисуем видимое
import { useVirtualizer } from '@tanstack/react-virtual';

function List({ rows }) {
  const parentRef = useRef(null);
  const virtualizer = useVirtualizer({
    count: rows.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 48,
    overscan: 6,                       // запас сверху и снизу, чтобы не мигало
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: 'auto' }}>
      {/* распорка задаёт полную высоту, чтобы полоса прокрутки была честной */}
      <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
        {virtualizer.getVirtualItems().map((v) => (
          <div
            key={rows[v.index].id}
            style={{ position: 'absolute', top: 0, transform: `translateY(${v.start}px)`, height: v.size }}
          >
            <Row row={rows[v.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

Двадцать узлов вместо десяти тысяч — и прокрутка становится плавной независимо от длины списка.

Когда виртуализация **нужна**: сотни и тысячи элементов, каждый со своей разметкой. Порог примерный — от двух-трёх сотен строк со сложным содержимым, от тысячи для простых.

Что она **ломает**: поиск по странице (Ctrl+F найдёт только отрисованное), выделение и копирование всего списка, печать, простые якорные ссылки внутрь списка, доступность при неаккуратной реализации. Плюс появляется проблема элементов разной высоты, которую надо решать измерением.

Подробный разбор с прыгающей прокруткой, динамической высотой и подгрузкой — в статье [бесконечный список и виртуализация](./infinite-list-and-virtualization).

Перед виртуализацией всегда проверь более дешёвые варианты: пагинация, «показать ещё», CSS-свойство `content-visibility: auto`, которое позволяет браузеру пропускать отрисовку элементов вне экрана без единой строки JavaScript.

## Часть 8. Разделение кода и ленивая загрузка

Если медленно **при первом заходе**, а не при работе, дело в размере бандла: браузер должен скачать, разобрать и выполнить весь JavaScript, прежде чем покажет интерфейс.

```jsx
// Было: всё в одном файле
import AdminPanel from './AdminPanel';       // 300 КБ, нужны 2% пользователей
import ChartsPage from './ChartsPage';       // 200 КБ библиотеки графиков
import PdfExport from './PdfExport';         // 400 КБ, нужен по кнопке
```

**По маршрутам** — самое очевидное и самое выгодное разделение:

```jsx
// Стало: код маршрута грузится при переходе на него
const AdminPanel = lazy(() => import('./AdminPanel'));
const ChartsPage = lazy(() => import('./ChartsPage'));

<Suspense fallback={<PageSkeleton />}>
  <Routes>
    <Route path="/admin" element={<AdminPanel />} />
    <Route path="/charts" element={<ChartsPage />} />
  </Routes>
</Suspense>
```

**По действию пользователя** — для тяжёлых редких функций:

```jsx
function ExportButton({ data }) {
  const [busy, setBusy] = useState(false);

  async function handleClick() {
    setBusy(true);
    // библиотека приедет только сейчас, и только у тех, кто нажал
    const { exportToPdf } = await import('./pdf-export');
    await exportToPdf(data);
    setBusy(false);
  }

  return <button onClick={handleClick} disabled={busy}>Экспорт в PDF</button>;
}
```

Обязательная деталь: **предзагружай по намерению**. Ждать скачивания после клика — плохой опыт. Начинай загрузку при наведении курсора или при появлении кнопки во вьюпорте:

```jsx
<button
  onMouseEnter={() => import('./pdf-export')}   // модуль уже приедет к клику
  onClick={handleClick}
>
```

Что смотреть: анализатор бандла покажет, из чего он состоит. Типичные находки — библиотека дат со всеми локалями, библиотека графиков, притянутая в общий чанк ради одного экрана, две версии одной зависимости. Про то, как бандлер решает, что куда положить, — в статье [модули и сборка](./modules-and-bundling).

## Часть 9. Тяжёлые вычисления и воркер

`useMemo` не помогает, когда вычисление дорогое **при первом счёте**. Мемоизация избавляет от повторов, а не от самого вычисления. Разбор CSV на пять мегабайт, шифрование, обработка изображения, сложная выборка — всё это блокирует главный поток независимо от количества обёрток.

```js
// Было: 800 мс полной заморозки интерфейса
function handleFile(file) {
  const text = await file.text();
  const rows = parseHugeCsv(text);     // главный поток стоит, клики не проходят
  setRows(rows);
}
```

```js
// Стало: считаем в отдельном потоке
// worker.js
self.onmessage = (e) => {
  self.postMessage(parseHugeCsv(e.data));
};

// компонент
const worker = useMemo(() => new Worker(new URL('./worker.js', import.meta.url), { type: 'module' }), []);

useEffect(() => {
  worker.onmessage = (e) => setRows(e.data);
  return () => worker.terminate();
}, [worker]);

function handleFile(file) {
  file.text().then((text) => worker.postMessage(text));
}
```

Главный поток свободен: анимации идут, кнопки нажимаются, спиннер крутится по-настоящему.

Цена воркера: у него нет DOM, данные передаются копированием (для больших массивов используй `ArrayBuffer` с передачей владения, иначе копия сама займёт время), появляется асинхронность и обработка ошибок в двух местах. Полный разбор — в статье [веб-воркеры](./web-workers).

Дешёвая альтернатива для случаев попроще — **разбить работу на куски** и отдавать управление между ними, чтобы браузер успевал отрисовать кадр. Это не ускоряет, но убирает заморозку.

## Часть 10. Батчинг обновлений

**Батчинг** — объединение нескольких `setState` в одну перерисовку.

```jsx
function handleClick() {
  setCount((c) => c + 1);
  setName('Ася');
  setOpen(true);
  // React 18: один рендер, а не три
}
```

До React 18 автоматически батчились только обновления внутри обработчиков событий React. Всё, что после `await`, в `setTimeout` или в колбэке промиса, вызывало отдельный рендер на каждый `setState`:

```jsx
// React 17: три рендера
async function save() {
  await api.save();
  setLoading(false);      // рендер
  setSaved(true);         // рендер
  setError(null);         // рендер
}
```

В React 18 появился автоматический батчинг: обновления группируются везде, включая асинхронный код. Это одна из причин, почему при переходе на 18-ю версию иногда «ломаются» тесты, читавшие промежуточные состояния.

Обратная операция — `flushSync` — заставляет применить обновление немедленно и синхронно. Нужна редко: например, надо измерить DOM сразу после обновления или установить фокус в только что появившийся элемент. Каждый `flushSync` — это отказ от батчинга и лишний проход конвейера, поэтому в цикле он превращается в катастрофу.

Обрати внимание: батчинг — это про количество рендеров React. Браузер всё равно рисует не чаще раза в кадр, и как это устроено — в части про событийный цикл в статье [как работает браузер](./browser-rendering-event-loop).

## Когда не надо

**Не мемоизируй, не измерив.** `useMemo` вокруг `a + b` дороже сложения: обёртка тратит память на хранение значения и массива зависимостей и время на их сравнение. Мемоизация окупается на реальной работе — сортировке тысяч элементов, построении индекса, дорогом преобразовании.

**Не оборачивай всё в `memo` подряд.** Каждая обёртка — это сравнение пропсов при каждом рендере родителя и удержание предыдущего результата в памяти. Для листовых компонентов из трёх строк разметки сравнение восьми пропсов дороже, чем просто отрисовать заново.

**Не виртуализируй короткие списки.** До сотни элементов виртуализация вредна: код сложнее, поиск по странице ломается, а выигрыша нет.

**Не дроби бандл до бесконечности.** Пятьдесят маленьких чанков — это пятьдесят запросов и пятьдесят раундов ожидания. Ленивую загрузку применяют к крупным независимым кускам, а не к каждому компоненту.

**Не тащи воркер ради 20 мс.** Накладные расходы на создание воркера и передачу данных заметны. Смысл появляется на задачах от сотни миллисекунд.

**Не оптимизируй читаемость в ноль.** Компонент, где каждая переменная в `useMemo`, каждая функция в `useCallback`, а списки зависимостей по шесть элементов, — это код, в котором легко ошибиться: забытая зависимость даёт устаревшее замыкание, а такой баг ищется часами. Иногда быстрее сделать компонент проще, чем ускорять сложный.

**Не оптимизируй то, чего пользователь не заметит.** Перерисовка за 2 мс, происходящая раз в минуту, не стоит ни строчки кода. Ориентируйся на то, что видно: ввод текста, прокрутку, открытие экрана, перетаскивание.

**Помни про память.** Мемоизация — это обмен процессорного времени на память. Кеш на тысячу элементов в компоненте, живущем всё время работы приложения, — потенциальная утечка. Про то, как такое обнаруживать, — в статье [память и утечки](./memory-and-leaks).

## Что спросят на интервью

**Как вы будете искать причину тормозов?** Сначала измерение: профайлер React с включённой причиной рендера — для перерисовок, панель Performance — для длинных задач, макета и отрисовки, анализатор бандла — для медленной первой загрузки. Только потом приёмы.

**Назовите причины, по которым компонент перерисовывается.** Изменение своего состояния, перерисовка родителя, изменение контекста. Плюс уточнение, что перерисовка не равна изменению DOM.

**Почему `React.memo` не помог?** Скорее всего, среди пропсов есть объект или функция, создаваемые заново при каждом рендере родителя. Сравнение поверхностное, по ссылке. Либо компонент читает меняющийся контекст.

**Как не перерисовывать поддерево без `memo`?** Передать его через `children` из компонента, который сам не перерисовывается. Элемент создан выше, ссылка не меняется, React пропускает ветку.

**Пользователь печатает в поле, и тормозит весь экран. Что делать?** Опустить состояние поля в отдельный компонент, наружу отдавать установившееся значение. Для случая, когда тяжёлый список обязан обновляться, — `useDeferredValue` или `useTransition`.

**Чем `useTransition` отличается от `useDeferredValue`?** Первый помечает обновление несрочным, второй — значение. Оба не ускоряют вычисление, а позволяют прервать несрочный рендер ради отзывчивости. `useDeferredValue` выбирают, когда значение приходит пропсом.

**Когда нужна виртуализация и что она ломает?** Нужна на сотнях и тысячах узлов. Ломает поиск по странице, выделение всего списка, печать; требует решать вопрос элементов разной высоты.

**Что даёт автоматический батчинг в React 18?** Обновления группируются в один рендер везде, включая код после `await` и таймеры, а не только в обработчиках событий React.

**Мемоизация бесплатна?** Нет: память на хранение значения, время на сравнение зависимостей, сложность чтения и риск устаревшего замыкания при забытой зависимости.

## Коротко, для повторения

1. Сначала измерь. Профайлер React — про перерисовки, панель Performance — про длинные задачи и макет, анализатор бандла — про первую загрузку.
2. Включи «Record why each component rendered»: догадки заменяются фактами.
3. Причин перерисовки три: своё состояние, родитель, контекст. Перерисовка не равна изменению DOM.
4. `memo` работает, только если стабильны **все** пропсы. Литерал объекта или стрелка в пропсах убивают его целиком.
5. Композиция через `children` спасает поддерево без единой обёртки: элемент создан выше и не пересоздаётся.
6. Быстро меняющееся состояние держи как можно ниже. Это дешевле мемоизации.
7. `useTransition` и `useDeferredValue` не ускоряют, а делают отзывчивым: несрочный рендер можно прервать.
8. Виртуализация — когда узлов тысячи. Ломает поиск по странице и печать, порог начинается от сотен строк.
9. Разделение кода по маршрутам и по действиям плюс предзагрузка по наведению.
10. Тяжёлое вычисление лечится воркером или разбиением на куски, а не мемоизацией.
11. React 18 батчит обновления везде; `flushSync` — редкое исключение, а не инструмент.
12. У каждой оптимизации есть цена: память, читаемость, риск забытой зависимости. Оптимизируй то, что видит пользователь.
