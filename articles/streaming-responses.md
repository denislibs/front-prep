# Стриминг ответов: как работает печатающий ответ у ChatGPT

Модель генерирует ответ по одному кусочку за раз и делает это не мгновенно: длинный ответ рождается тридцать-сорок секунд. Если ждать, пока он закончится, и только потом показать — пользователь тридцать секунд смотрит на крутилку. Если показывать по мере генерации — первые слова появляются через полсекунды, и ожидание перестаёт ощущаться ожиданием.

Это не микрооптимизация. Общее время не изменилось ни на миллисекунду: ответ всё так же готов через тридцать секунд. Изменилось только то, когда пользователь увидел первый байт. И этот сдвиг меняет восприятие продукта сильнее, чем любое ускорение бэкенда, которое реально можно себе позволить.

Статья про то, как это устроено на клиенте: какие есть способы доставки, как читать поток через Streams API, как разбирать формат SSE, как не сломать интерфейс отрисовкой на каждый чанк и что делать, когда поток оборвался посередине.

Термин, который дальше будет постоянно: **чанк** (chunk) — очередной кусок данных, пришедший по сети. Он не совпадает ни со словом, ни с предложением, ни даже с символом: сеть режет байты как ей удобно.

## Часть 1. Почему стриминг вообще меняет ощущение

### Две метрики вместо одной

У любого ответа есть две разные характеристики времени:

- **Время до первого байта полезного содержимого** — когда пользователь увидел хоть что-то осмысленное.
- **Время до полного ответа** — когда всё закончилось.

Обычный запрос склеивает их в одно: первый байт содержимого = последний байт. Стриминг разводит: первое становится маленьким, второе не меняется.

### Что мы платим за стриминг

Честный список цены, который стоит проговорить на интервью, потому что кандидаты обычно называют только плюсы:

- **Соединение держится открытым весь ответ.** Тридцать секунд на пользователя вместо ста миллисекунд. Для сервера это не бесплатно: воркер занят, у прокси лимиты на число открытых соединений.
- **Нельзя закешировать по-обычному.** CDN не любит долгие ответы неизвестной длины, а `Content-Length` заранее неизвестен.
- **Ошибка может прийти после успешного статуса.** Заголовки уже ушли с кодом 200, а на десятой секунде упала модель. Кода ошибки уже не поставить — придётся передавать её внутри тела.
- **Клиент становится сложнее.** Буфер, разбор, батчинг, отмена, восстановление — это код, который надо написать и покрыть тестами.
- **Ретраи ломаются.** Автоматически повторить запрос, который наполовину доехал, нельзя: половина уже показана пользователю.

## Часть 2. Три способа доставить поток

### Способ 1. Обычный HTTP, читаемый по кускам

Самый простой вариант: обычный POST-запрос, обычный ответ, просто клиент не ждёт его целиком, а читает тело по мере поступления. Никакого специального протокола — сервер пишет байты в ответ и не закрывает соединение, пока не закончит.

Внутри это работает благодаря **chunked transfer encoding** в HTTP/1.1 (тело передаётся кусками, каждый со своей длиной, конец обозначен куском нулевой длины) или обычным DATA-кадрам в HTTP/2. Фронтенду разница не видна: `fetch` отдаёт `response.body` — поток, из которого можно читать.

Плюсы: работает везде, POST разрешён, заголовки любые, ничего лишнего в формате.
Минусы: всё, что сверх «просто байты», пишешь сам — разделители сообщений, идентификаторы, переподключение.

### Способ 2. Server-Sent Events

**SSE** (Server-Sent Events) — это соглашение поверх того же обычного HTTP-ответа. Сервер отдаёт `Content-Type: text/event-stream` и пишет туда сообщения в простом текстовом формате: строчки вида `data: ...`, сообщения разделены пустой строкой.

По сути это способ 1 плюс договорённость о разделителе. Ценность именно в договорённости: у сообщения есть чёткая граница, у него может быть тип и идентификатор, и это понимает не только твой код, но и встроенный в браузер `EventSource`.

Почти вся индустрия LLM-API остановилась на SSE: OpenAI, Anthropic и остальные отдают ответ модели именно так.

### Способ 3. WebSocket

**WebSocket** — полноценный двусторонний канал: после рукопожатия соединение перестаёт быть HTTP и превращается в трубу, где обе стороны шлют сообщения когда захотят.

Для ответа модели это почти всегда избыточно. Разбор — в статье [про реалтайм-транспорты](./realtime-transports), здесь коротко о том, почему сокет обычно проигрывает:

- **Данные текут в одну сторону.** Пользователь отправил вопрос, дальше сервер льёт токены. Двусторонность канала не используется.
- **Теряется вся инфраструктура HTTP.** Обычные заголовки, куки, кеш, привычные коды ошибок, метрики по URL, ретраи на балансировщике — со сокетом всё это надо придумывать заново.
- **Нет автопереподключения** — и это правильно, потому что переподключение к середине генерации всё равно требует логики на стороне сервера.
- **Прокси и корпоративные сети** заметно чаще ломают сокеты, чем обычные HTTP-ответы.

Сокет оправдан, когда во время генерации действительно нужен канал обратно: совместное редактирование, голос, интерактивная сессия с прерываниями. Для «спросил — печатается ответ» его берут либо потому, что сокет уже есть в приложении, либо по инерции.

### Сравнение

| | HTTP-поток | SSE | WebSocket |
|---|---|---|---|
| Метод запроса | любой | только GET у `EventSource`, любой у `fetch` | своё рукопожатие |
| Направление | сервер → клиент | сервер → клиент | в обе стороны |
| Границы сообщений | придумываешь сам | есть в формате | есть (кадры) |
| Переподключение | сам | бесплатно у `EventSource` | сам |
| Заголовки и куки | как обычно | как обычно у `fetch` | ограниченно |
| Кому подходит | простой поток текста | ответ модели, лента событий | чат, игры, совместная работа |

Практический вывод: **для ответа модели бери SSE поверх `fetch`.** Получаешь границы сообщений и типы событий даром, при этом сохраняешь POST, заголовки авторизации и нормальную обработку ошибок.

## Часть 3. Streams API: как читать тело по кускам

### Что такое ReadableStream

`fetch` возвращает `Response`, у которого есть `response.body` — объект **`ReadableStream`**. Это источник данных, из которого куски вытягивают по одному, а не забирают всё сразу.

Ключевая идея: поток **тянут** (pull), а не он тебя заваливает. Пока ты не попросил следующий кусок, поток не торопится. Это называется **обратное давление** (backpressure): медленный потребитель автоматически притормаживает источник, вместо того чтобы копить непрочитанное в памяти.

У потока просят **читателя**:

```js
const response = await fetch('/api/chat', { method: 'POST', body: JSON.stringify(payload) });
const reader = response.body.getReader();

while (true) {
  const { value, done } = await reader.read();
  if (done) break;          // поток закончился
  console.log(value);       // Uint8Array — сырые байты, не строка
}
```

Три вещи, которые тут важны:

1. `getReader()` **захватывает** поток. Пока читатель не отпущен (`reader.releaseLock()`), больше никто из потока читать не может. Это защита от двух читателей, растаскивающих куски вперемешку.
2. `value` — это `Uint8Array`, массив байтов. Не строка. Текст из него надо ещё достать.
3. `done: true` приходит **вместе с пустым `value`**, отдельным вызовом. Не забывай про `break`, иначе цикл будет крутиться вечно.

### Почему нельзя просто сделать String из байтов

Байты режутся сетью в произвольных местах. UTF-8 кодирует кириллическую букву двумя байтами, эмодзи — четырьмя. Ничто не мешает границе чанка пройти ровно посередине буквы: первый байт «п» попал в один чанк, второй — в следующий.

Если декодировать каждый чанк независимо, на границе получится мусор — символ замены. Поэтому декодер должен помнить хвост:

```js
const decoder = new TextDecoder();

// Плохо: каждый вызов декодирует независимо, разрезанный символ ломается
decoder.decode(chunk);

// Хорошо: декодер запоминает неполный символ и приклеит его к началу следующего чанка
decoder.decode(chunk, { stream: true });
```

Флаг `stream: true` означает «это не последний кусок, недоделанное придержи». В конце потока надо вызвать `decoder.decode()` без аргументов — это сбрасывает остаток.

На практике это одна из самых частых боевых ошибок в самописных клиентах: на английском тексте всё работает, а на русском или с эмодзи изредка появляются кракозябры. Изредка — потому что нужно точное совпадение границы чанка с серединой символа.

### TextDecoderStream: то же самое, но декларативно

Вместо ручного декодера можно пропустить поток через **преобразующий поток** (transform stream) — объект, который берёт поток на вход и отдаёт другой поток на выход:

```js
const stream = response.body.pipeThrough(new TextDecoderStream());
const reader = stream.getReader();
// теперь value — строка, склейка разрезанных символов уже сделана внутри
```

`pipeThrough` соединяет потоки в конвейер. `TextDecoderStream` внутри делает ровно то же самое, что `decode(chunk, { stream: true })`, просто ты об этом не думаешь.

Цена: чуть меньше контроля и чуть хуже поддержка в старых средах (в некоторых версиях Node и в старых мобильных браузерах `TextDecoderStream` появился позже). Если пишешь код, который поедет и в браузер, и в Node, ручной `TextDecoder` предсказуемее.

### Разбор потока на строки

Строка текста — не то же самое, что чанк. Один чанк может содержать три с половиной строки, а может — половину одной. Значит нужен **буфер**: копим пришедшее, отрезаем полные строки, остаток оставляем на потом.

```js
async function* readLines(response) {
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) break;

      buffer += decoder.decode(value, { stream: true });

      let index;
      // Отдаём только завершённые строки: те, у которых уже встретился перевод
      while ((index = buffer.indexOf('\n')) !== -1) {
        const line = buffer.slice(0, index);
        buffer = buffer.slice(index + 1);
        yield line.endsWith('\r') ? line.slice(0, -1) : line;  // CRLF от старых серверов
      }
    }

    buffer += decoder.decode();            // хвост недодекодированного
    if (buffer) yield buffer;              // последняя строка без перевода
  } finally {
    reader.releaseLock();
  }
}
```

Это **асинхронный генератор** — функция, из которой значения достают по одному через `for await`. Каждое значение приходит когда будет готово, а не все сразу. Подробнее про механику `await` — в статье [про асинхронность](./async-await).

Использование:

```js
for await (const line of readLines(response)) {
  console.log(line);
}
```

Обрати внимание на `finally`: если потребитель прервал `for await` через `break` или исключение, генератор получит команду завершиться, и читатель должен быть отпущен. Без этого поток останется захваченным.

## Часть 4. Формат SSE и как его разбирать руками

### Как выглядят байты

Тело ответа с `Content-Type: text/event-stream` выглядит так:

```
data: {"delta":"Привет"}

data: {"delta":", как"}

event: usage
data: {"tokens":42}

id: 17
data: {"delta":" дела?"}

data: [DONE]

```

Правила формата, которых достаточно знать:

- Одна строка — одно **поле**: `data`, `event`, `id`, `retry`. Формат `имя: значение`, пробел после двоеточия необязателен и съедается.
- **Пустая строка завершает сообщение.** Всё, что накопилось, отдаётся как одно событие.
- Несколько строк `data` подряд склеиваются через `\n`. Так передают многострочный текст.
- `event` задаёт тип события. Без него тип — `message`.
- `id` запоминается браузером и при переподключении уходит обратно в заголовке `Last-Event-ID`.
- `retry: 3000` говорит, через сколько миллисекунд переподключаться.
- Строка, начинающаяся с двоеточия, — комментарий. Её используют как **пинг**: сервер шлёт `: ping` раз в 15 секунд, чтобы прокси не убил «тихое» соединение.

`data: [DONE]` — не часть стандарта, а соглашение конкретных API. Не полагайся на него вслепую: считай поток законченным, когда пришёл `done` от читателя, а маркер используй как дополнительный сигнал.

### Полный разбор SSE поверх fetch

Собираем всё вместе. Этот код можно переносить в проект как есть.

```js
/**
 * Читает SSE-поток из fetch-ответа и отдаёт события по одному.
 * Возвращает объекты { event, data, id }, где data — сырая строка.
 */
async function* parseSSE(response) {
  if (!response.ok) {
    // Ошибку с нормальным статусом обрабатываем ДО того, как начали читать поток
    throw new Error('HTTP ' + response.status + ': ' + (await response.text()));
  }

  let event = 'message';
  let data = [];
  let id;

  for await (const line of readLines(response)) {
    if (line === '') {
      // Пустая строка — конец сообщения
      if (data.length) yield { event, data: data.join('\n'), id };
      event = 'message';
      data = [];
      continue;
    }
    if (line.startsWith(':')) continue;              // комментарий и пинг

    const colon = line.indexOf(':');
    const field = colon === -1 ? line : line.slice(0, colon);
    let value = colon === -1 ? '' : line.slice(colon + 1);
    if (value.startsWith(' ')) value = value.slice(1);

    if (field === 'event') event = value;
    else if (field === 'data') data.push(value);
    else if (field === 'id') id = value;
    // retry игнорируем: переподключением управляем сами
  }

  // Хвост без завершающей пустой строки — обрыв на середине сообщения.
  // Отдавать его нельзя: JSON почти наверняка неполный.
}
```

И слой поверх, который знает про формат конкретного API:

```js
async function* streamCompletion(payload, signal) {
  const response = await fetch('/api/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Accept: 'text/event-stream' },
    body: JSON.stringify(payload),
    signal,
  });

  for await (const message of parseSSE(response)) {
    if (message.data === '[DONE]') return;

    if (message.event === 'error') {
      throw new Error(JSON.parse(message.data).message);
    }

    let parsed;
    try {
      parsed = JSON.parse(message.data);
    } catch {
      continue;   // битое сообщение пропускаем, а не роняем весь ответ
    }

    if (parsed.delta) yield parsed.delta;
  }
}
```

Два решения тут стоят объяснения.

**Битый JSON пропускаем, а не бросаем.** Одно испорченное сообщение из тысячи не повод потерять весь ответ. Но если бы это был не текст, а, например, поток обновлений заказа, где пропуск меняет смысл, — наоборот, надо падать громко. Правило: пропускать можно то, потеря чего не создаёт неверного состояния.

**Ошибку внутри потока передаём отдельным типом события.** Статус ответа уже был 200 и изменить его нельзя. Единственный способ сообщить «модель упала на десятой секунде» — положить это в тело. Договоритесь с бэкендом о типе `error` заранее: без этого клиент увидит просто внезапно оборвавшийся поток и не отличит ошибку от нормального конца.

### EventSource: что даёт и почему его всё равно не берут

В браузере есть готовый клиент SSE:

```js
const source = new EventSource('/api/events');

source.addEventListener('message', (e) => console.log(e.data));
source.addEventListener('usage', (e) => console.log('служебное', e.data));
source.addEventListener('error', () => {
  // Сюда попадают и разрыв, и неудачная попытка переподключения.
  // Браузер уже сам запланировал следующую попытку — закрывать надо вручную.
  if (source.readyState === EventSource.CLOSED) console.log('всё, сдался');
});
```

Что достаётся бесплатно:

- **Разбор формата** — не надо писать буфер и парсер.
- **Автоматическое переподключение** при обрыве, с паузой из `retry`.
- **`Last-Event-ID`**: браузер запоминает последний `id` и при переподключении шлёт его заголовком. Сервер по нему может отдать пропущенное. Это готовая механика «продолжи с того места», которую при `fetch` пришлось бы писать самому.

Почему при этом почти все LLM-клиенты написаны на `fetch`:

- **Только GET.** Тело запроса передать нельзя. Промпт на несколько тысяч символов в query-строке — плохая идея: лимиты длины URL, промпт светится в логах прокси и в истории.
- **Нельзя задать заголовки.** `Authorization: Bearer ...` не поставить. Остаются куки, что не всегда подходит, особенно для кросс-доменных запросов.
- **Нет контроля над ошибками.** Отличить «сервер вернул 500» от «сеть моргнула» нельзя: и то и другое приходит одним безликим `error`.
- **Переподключение может быть вредным.** Если соединение оборвалось на середине генерации, `EventSource` радостно повторит **тот же GET** и начнёт генерацию заново — с нуля и за новые деньги.

Вывод: `EventSource` отлично подходит для того, для чего задумывался, — публичной ленты событий по GET (уведомления, счётчики, статусы). Для ответа модели — `fetch` плюс свой парсер.

## Часть 5. Отмена

### Почему кнопка «стоп» обязана прерывать запрос

Соблазн сделать кнопку «стоп» как «перестань показывать текст» велик: одна строчка, флаг `stopped = true`, отрисовка прекращается. Это неправильно по трём причинам:

1. **Сервер продолжает генерировать.** Модель домалывает ответ до конца, тратя вычисления и деньги.
2. **Соединение остаётся открытым.** Браузер держит лимит одновременных соединений к домену, следующий запрос может встать в очередь.
3. **Данные продолжают идти.** Трафик расходуется, на мобильном — заметно.

Прерывать надо по-настоящему, через `AbortController`.

```js
let controller = null;

async function send(payload, onDelta) {
  controller?.abort();                  // предыдущий запрос отменяем
  controller = new AbortController();

  try {
    for await (const delta of streamCompletion(payload, controller.signal)) {
      onDelta(delta);
    }
  } catch (error) {
    if (error.name === 'AbortError') return;   // это наша отмена, не ошибка
    throw error;
  }
}

stopButton.onclick = () => controller?.abort();
```

Механика: `controller.signal` передаётся в `fetch`, и при `abort()` браузер **закрывает соединение**. Читатель получает исключение, `for await` его пробрасывает, оно вылетает наружу с `name === 'AbortError'`.

Три вещи, на которых спотыкаются:

**`AbortError` — не ошибка приложения.** Его надо отличать и глотать. Иначе в мониторинге появится поток «ошибок», каждая из которых — нажатие кнопки «стоп».

**Абортить надо и при уходе со страницы.** Иначе в SPA переход на другой экран оставляет висящий поток, который продолжает дописывать в размонтированный компонент. В React это `useEffect` с очисткой, где `controller.abort()` вызывается в возвращаемой функции.

**Сервер должен реагировать на разрыв.** Закрытие соединения клиентом само по себе не останавливает генерацию: бэкенд должен слушать событие «клиент отвалился» и прерывать вызов модели. Это не фронтендовая часть, но именно её забывают, и потом удивляются счёту.

`AbortSignal.timeout(ms)` даёт готовый сигнал, который сработает сам. Для стриминга он опасен: он ограничивает **весь** ответ, а не паузу между чанками. Длинный ответ будет обрываться на середине. Правильный таймаут для потока — **по бездействию**: сбрасываемый таймер, который перезапускается на каждом чанке.

```js
function idleTimeout(ms) {
  const controller = new AbortController();
  let timer = setTimeout(() => controller.abort(), ms);
  return {
    signal: controller.signal,
    ping() { clearTimeout(timer); timer = setTimeout(() => controller.abort(), ms); },
    done() { clearTimeout(timer); },
  };
}
```

Вызываешь `ping()` на каждом чанке — и поток обрывается только если реально замолчал.

## Часть 6. Ошибка посреди потока

Ситуация, которой нет у обычных запросов: пятнадцать секунд текста уже на экране, и тут всё ломается. Стереть нельзя — пользователь это читал. Притвориться, что всё хорошо, тоже нельзя.

Рабочая схема:

1. **Оставить показанное.** То, что уже пришло, — валидный текст, он не стал неправильным от того, что продолжение не приехало.
2. **Явно пометить обрыв.** Строка под текстом: «Ответ прерван» с кнопкой «продолжить». Молчаливая остановка хуже всего: пользователь не понимает, всё это или ещё идёт.
3. **Не терять контекст.** Накопленный текст остаётся в состоянии сообщения, а не только в DOM.

```js
const message = { id, role: 'assistant', text: '', status: 'streaming' };

try {
  for await (const delta of streamCompletion(payload, signal)) {
    message.text += delta;              // копим в состоянии, а не только рисуем
    schedule(message);
  }
  message.status = 'done';
} catch (error) {
  message.status = error.name === 'AbortError' ? 'stopped' : 'failed';
  message.error = error.message;
} finally {
  flush(message);                       // дорисовать остаток в любом случае
}
```

Разделение `stopped` и `failed` важно для интерфейса: остановленное пользователем не нужно предлагать повторить теми же словами, а упавшее — нужно. Про то, как эти статусы живут в общей модели переписки, — в статье [про проектирование чата](./chat-system-design).

### Продолжение после обрыва

Полноценное «дописать с места обрыва» требует поддержки сервера: он должен уметь принять уже сгенерированный кусок и продолжить. Без этого честные варианты два:

- **Повторить целиком.** Просто, но пользователь получает другой текст, и первая половина, которую он читал, исчезает или дублируется.
- **Отправить новый запрос с накопленным текстом в контексте** и попросить продолжить. Работает, но склейка на стыке бывает кривой.

Если бэкенд умеет отдавать `id` каждого события, вариант лучше: при повторе передаёшь последний полученный `id`, сервер отдаёт всё, начиная со следующего. Ровно та механика, которую `EventSource` делает автоматически через `Last-Event-ID`, — просто реализованная вручную. Подробнее про восстановление пропущенного — в статье [про реалтайм-транспорты](./realtime-transports).

## Часть 7. Отрисовка: как не убить страницу

### Почему нельзя рисовать на каждый чанк

Чанки приходят часто — десятки в секунду. Если на каждый делать полную перерисовку сообщения, а тем более всего списка сообщений, получится сто перерисовок в секунду при экране в шестьдесят кадров. Большая часть работы буквально выбрасывается: пользователь физически не увидит промежуточные состояния между кадрами.

Хуже, если на каждом чанке ты ещё и парсишь markdown длинного текста заново. Тогда цена одного чанка растёт вместе с длиной ответа: последний чанк ответа на десять тысяч символов заставляет разобрать все десять тысяч. Получается квадратичная сложность, и к концу длинного ответа страница начинает ощутимо лагать.

### Батчинг по кадру

Решение: копить дельты в переменной, а отрисовку планировать один раз на кадр через `requestAnimationFrame`. Как устроен кадр и почему rAF — правильное место, разобрано в статье [про рендеринг и событийный цикл](./browser-rendering-event-loop).

```js
function createRenderer(render) {
  let pending = null;
  let frame = 0;

  return {
    push(state) {
      pending = state;
      if (frame) return;                       // кадр уже запланирован
      frame = requestAnimationFrame(() => {
        frame = 0;
        const snapshot = pending;
        pending = null;
        render(snapshot);                      // один раз на кадр
      });
    },
    flush(state) {                             // финальная отрисовка без задержки
      if (frame) cancelAnimationFrame(frame);
      frame = 0;
      pending = null;
      render(state);
    },
  };
}
```

Двадцать чанков между кадрами схлопываются в одну отрисовку. Пользователь не замечает разницы: он всё равно видит только кадры.

Цена: задержка до 16 мс. Для печатающегося текста это невидимо. Для чего-то, где важна каждая миллисекунда, батчинг не подойдёт — но такого в интерфейсе чата нет.

Во фреймворках это часто уже сделано: React с автоматическим батчингом объединяет обновления состояния внутри одного тика. Но если дельты приходят из `for await`, каждая итерация — своя микрозадача, и автоматический батчинг между ними не срабатывает. Проверяй профайлером, а не на веру.

### Обновлять текст, а не пересоздавать узлы

Если сообщение — один текстовый узел, самое дешёвое обновление такое:

```js
// Дорого: разбор HTML, создание узлов, потеря выделения текста мышью
node.innerHTML = escapeHtml(text);

// Дёшево: браузер меняет содержимое существующего узла
node.textContent = text;
```

`textContent` не пересоздаёт узлы, а значит не сбрасывает выделение пользователя. Мелочь, которую замечают: если человек выделил кусок ответа мышью, а перерисовка пересоздала узлы, выделение слетает — на каждом чанке.

### Автоскролл, который не мешает

Текст растёт вниз, и хочется прокручивать за ним. Но если человек отлистал вверх перечитать начало, а скрипт каждый чанк тащит его вниз, пользоваться этим невозможно.

Правило: **скроллить автоматически, только пока пользователь и так внизу.**

```js
let stick = true;
const NEAR = 64;   // считаем «внизу», если до конца меньше 64 пикселей

container.addEventListener('scroll', () => {
  const distance = container.scrollHeight - container.scrollTop - container.clientHeight;
  stick = distance < NEAR;
}, { passive: true });

function afterRender() {
  if (stick) container.scrollTop = container.scrollHeight;
}
```

Порог в несколько десятков пикселей нужен потому, что точное равенство почти никогда не выполняется: дробные высоты, зум, разные устройства.

Флаг `passive: true` говорит браузеру, что обработчик не будет отменять прокрутку, и тот не ждёт его выполнения перед скроллом. Подробнее про события — в статье [про DOM и события](./dom-events).

Когда `stick` стал `false`, покажи кнопку «вниз»: пользователь должен иметь способ вернуться к живому концу.

### Markdown на лету

Модель отдаёт markdown, и в любой момент времени он **неполный**. Типичные состояния середины:

- открыт блок кода тремя обратными кавычками, закрывающих ещё нет;
- открыта звёздочка жирного начертания, парной нет;
- начата таблица, шапка есть, разделителя ещё нет;
- ссылка открыта скобкой, URL ещё не приехал.

Наивный подход — парсить как есть — даёт мигание: половина ответа то становится жирной, то перестаёт, когда доехала вторая звёздочка.

Что работает:

**Достраивать незакрытое перед разбором.** Перед парсингом добавляем в конец копии текста закрывающие последовательности для того, что открыто. Незакрытый блок кода дописываем тремя кавычками — он сразу отрисуется как код, и по мере поступления просто будет расти.

```js
function closeOpen(text) {
  const fences = (text.match(/^```/gm) || []).length;
  if (fences % 2 === 1) text += '\n```';        // нечётное число — блок открыт
  return text;
}
```

**Разбивать по блокам и парсить только последний.** Всё до последнего пустого абзаца уже не изменится: markdown блочный, законченный абзац дальше не меняется от того, что придёт после. Значит готовые блоки можно распарсить один раз и закешировать, а перепарсивать — только незавершённый хвост. Это и убирает квадратичную сложность.

**Санитайзить результат.** Модель может вывести HTML, а он попадёт в разметку. Проверка обязательна и на потоке — иначе получится XSS из содержимого ответа.

Цена достраивания: короткие моменты, когда разметка выглядит не так, как будет в итоге. Незакрытая звёздочка успевает мигнуть. Это заметно меньшее зло, чем прыгающая вёрстка целого абзаца.

## Часть 8. Чек-лист боевого клиента

Что должно быть в коде, который идёт в продакшн:

1. `TextDecoder` со `stream: true` или `TextDecoderStream`.
2. Буфер строк с корректной обработкой хвоста и `\r\n`.
3. Проверка `response.ok` **до** начала чтения потока.
4. Тип события `error` внутри потока, согласованный с бэкендом.
5. `AbortController`, привязанный к кнопке «стоп» и к размонтированию.
6. Отдельная обработка `AbortError`, не попадающая в мониторинг ошибок.
7. Таймаут по бездействию, а не по общей длительности.
8. Накопление текста в состоянии, не только в DOM.
9. Батчинг отрисовки по кадру плюс финальный `flush`.
10. Автоскролл с проверкой «пользователь внизу».
11. Разбор markdown с достраиванием и кешированием готовых блоков.
12. `releaseLock()` или закрытие читателя в `finally`.

## Что спросят на интервью

**Зачем стримить ответ, если общее время не меняется?** Меняется время до первого видимого содержимого. Пользователь получает подтверждение, что система работает, и начинает читать сразу. Плюс он может остановить неподходящий ответ, не дожидаясь конца.

**SSE или WebSocket для ответа модели?** SSE. Данные идут в одну сторону, а сокет заставляет заново строить всё, что HTTP даёт бесплатно: заголовки, куки, коды ошибок, кеш, метрики. Сокет нужен, когда во время генерации реально идёт трафик обратно.

**Почему `TextDecoder` нужно вызывать со `stream: true`?** Границы чанков не совпадают с границами символов UTF-8. Многобайтовый символ может быть разрезан пополам. С флагом декодер придерживает неполный хвост и приклеивает его к началу следующего чанка.

**Как понять, где кончается одно сообщение в потоке?** По разделителю формата. В SSE это пустая строка. Байты чанка не совпадают с сообщением, поэтому нужен буфер: копим, отрезаем полные единицы, остаток храним.

**Почему не берут `EventSource`?** Только GET, нельзя задать заголовки, невнятные ошибки, а автопереподключение повторяет тот же GET — то есть перезапускает генерацию с нуля.

**Что делает кнопка «стоп»?** Вызывает `controller.abort()`, что закрывает соединение. Просто перестать рисовать нельзя: сервер продолжит генерировать и тратить ресурсы. Сервер, в свою очередь, должен прерывать работу при разрыве соединения.

**Ошибка пришла, когда половина текста уже на экране. Что делать?** Показанное оставить, статус сообщения перевести в «прервано», показать явную отметку и кнопку повтора. Накопленный текст должен жить в состоянии, чтобы не потеряться при перерисовке.

**Почему нельзя перерисовывать на каждый чанк?** Чанков десятки в секунду, кадров шестьдесят: лишние отрисовки выбрасываются. А если на каждом чанке ещё и парсить markdown целиком, сложность становится квадратичной по длине ответа.

**Как сделать автоскролл, который не бесит?** Прокручивать, только если пользователь уже у нижнего края (с запасом в несколько десятков пикселей). Отлистал вверх — прокрутку выключить и показать кнопку возврата.

## Коротко, для повторения

1. Стриминг не ускоряет ответ, он убирает пустое ожидание в начале. Цена: долгие соединения, сложный клиент, сломанные ретраи.
2. Три транспорта: HTTP-поток, SSE, WebSocket. Для ответа модели — SSE поверх `fetch`: POST, заголовки, границы сообщений.
3. `response.body` — `ReadableStream`, читается через `getReader()`. Чанк — это `Uint8Array`, а не строка.
4. `TextDecoder` со `stream: true` обязателен: иначе разрезанный многобайтовый символ превращается в мусор.
5. Границы сообщений собираются в буфере: копим текст, режем по `\n`, остаток храним до следующего чанка.
6. В SSE пустая строка завершает сообщение, `id` нужен для восстановления, строка с двоеточия — пинг против разрыва прокси.
7. `EventSource` даёт разбор, переподключение и `Last-Event-ID`, но только GET и без заголовков.
8. `AbortController` обязателен: кнопка «стоп» должна закрывать соединение, а не прятать текст. `AbortError` — не ошибка.
9. Таймаут для потока — по бездействию между чанками, не по общей длительности.
10. Ошибка после статуса 200 передаётся только внутри тела: договорись с бэкендом о типе события `error`.
11. Отрисовка батчится по кадру через rAF, текст копится в состоянии, финальный `flush` обязателен.
12. Markdown на лету: достраивай незакрытое, парси только последний блок, санитайзь результат.
