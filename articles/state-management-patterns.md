# Состояние: где оно должно жить

Почти каждый спор про «какой стейт-менеджер выбрать» на самом деле спор не о библиотеке. Библиотека — это последние пять процентов решения. Первые девяносто пять — это ответ на вопрос **где конкретно этот кусок данных должен лежать** и **кто имеет право его менять**.

Приложения, в которых больно, почти всегда болеют одинаково: все данные свалены в одно место, потому что «так проще найти». Ответ сервера лежит рядом с флагом «открыта ли шторка», значение поля ввода лежит в глобальном хранилище, а фильтры таблицы живут в памяти и исчезают при перезагрузке страницы.

Эта статья про то, как разложить состояние по местам. Без привязки к конкретной библиотеке: показываю на React, потому что на нём чаще всего спрашивают, но вся логика переносится на Vue, Svelte и что угодно ещё — там те же четыре вида состояния и те же ошибки.

**Состояние** — это любые данные, от которых зависит то, что видит пользователь, и которые могут поменяться за время жизни страницы. Всё остальное — константы, и про них разговора нет.

## Часть 1. Четыре вида состояния

Главная ошибка — считать, что состояние однородно. «Данные приложения». На самом деле есть минимум четыре сорта, и у каждого свои правила жизни.

### Состояние сервера

Данные, у которых **есть источник истины на бэкенде**: список заказов, профиль пользователя, содержимое корзины. Ты держишь у себя **копию**, и эта копия по определению может устареть в любой момент — потому что кто-то другой поменял данные, а тебе никто не сообщил.

Ключевые свойства: копия, устаревает, требует загрузки, может провалиться, может грузиться повторно. Для таких данных нужны понятия, которых нет у обычных переменных: «загружается», «ошибка», «устарело», «идёт фоновое обновление».

### Глобальное клиентское состояние

Данные, которые придумал сам клиент и которые нужны в нескольких несвязанных местах: тема оформления, текущая локаль, содержимое очереди уведомлений, «пользователь свернул левое меню».

Их мало. В нормальном приложении по-настоящему глобальных клиентских данных обычно наберётся на два экрана кода. Если их у тебя сотни — почти наверняка туда затесались серверные данные.

### Локальное состояние

Данные, которые нужны одному компоненту и его ближайшим детям: открыт ли выпадающий список, что сейчас набрано в поле, какая вкладка выбрана внутри карточки.

Их много, и это нормально. Локальное состояние — самое дешёвое: оно рождается вместе с компонентом, умирает вместе с ним, и никто снаружи о нём не знает.

### Состояние в URL

Данные, которые описывают **где сейчас находится пользователь**: какая страница, какой открыт элемент, какие применены фильтры, какая страница пагинации, какой поисковый запрос.

Признак простой: если пользователь скопирует адрес и пришлёт коллеге, тот должен увидеть то же самое. Если не увидит — состояние лежит не там.

### Почему их нельзя валить в кучу

Потому что у них разные жизненные циклы, и общее хранилище заставляет обслуживать самый строгий из них.

Серверные данные надо инвалидировать и перезапрашивать. Локальные — сбрасывать при смене сущности. URL-состояние — синхронизировать с историей браузера. Если всё это лежит в одном редьюсере, ты вручную пишешь код для всех четырёх сценариев, причём одинаковый в каждой фиче.

## Часть 3. Подъём состояния и когда он становится вредным

**Подъём состояния** (lifting state up) — базовый приём: если двум компонентам нужны одни данные, кладём их в ближайшего общего родителя и передаём вниз пропсами.

Приём правильный. Проблема начинается, когда его применяют механически и поднимают выше, чем нужно.

```jsx
// Было: состояние поднято на самый верх экрана
function OrderPage() {
  const [comment, setComment] = useState('');
  const [order, setOrder] = useState(null);

  return (
    <div>
      <OrderHeader order={order} />
      <OrderItems items={order?.items} />       {/* тяжёлый список на 200 строк */}
      <OrderTotals order={order} />
      <CommentField value={comment} onChange={setComment} />
    </div>
  );
}
```

Что здесь происходит на каждое нажатие клавиши в поле комментария: меняется `comment`, перерисовывается `OrderPage`, а значит и `OrderHeader`, и `OrderItems` с двумя сотнями строк, и `OrderTotals`. Ради одной буквы в текстовом поле.

Пользователь это чувствует как «печатаешь, а буквы отстают».

```jsx
// Стало: состояние опущено туда, где оно используется
function OrderPage() {
  const [order, setOrder] = useState(null);

  return (
    <div>
      <OrderHeader order={order} />
      <OrderItems items={order?.items} />
      <OrderTotals order={order} />
      <CommentField onSubmit={(text) => saveComment(order.id, text)} />
    </div>
  );
}

function CommentField({ onSubmit }) {
  // теперь буква меняет только этот компонент
  const [comment, setComment] = useState('');
  return (
    <form onSubmit={(e) => { e.preventDefault(); onSubmit(comment); }}>
      <textarea value={comment} onChange={(e) => setComment(e.target.value)} />
      <button>Сохранить</button>
    </form>
  );
}
```

Приём называется **опускание состояния** (state colocation): держи данные как можно ближе к месту использования. Родителю не нужен текст комментария — ему нужен факт «комментарий отправлен». Значит наверх идёт не значение, а событие.

Правило: **поднимай ровно до ближайшего общего предка тех, кому данные реально нужны.** Не до контейнера страницы, не до провайдера, не «на всякий случай в стор».

Подробнее про то, почему лишние перерисовки стоят дорого, — в статье [производительность интерфейса](./rendering-performance-patterns).

## Часть 4. Производное состояние и почему `useEffect` — не место для синхронизации

**Производное состояние** — то, что однозначно вычисляется из другого состояния. Полное имя из имени и фамилии. Отфильтрованный список из списка и строки поиска. Флаг «форма валидна» из значений полей.

Классическая ошибка выглядит так:

```jsx
// Было: второй источник истины плюс эффект для синхронизации
function UserList({ users }) {
  const [query, setQuery] = useState('');
  const [visible, setVisible] = useState(users);

  useEffect(() => {
    setVisible(users.filter((u) => u.name.includes(query)));
  }, [users, query]);

  return <List items={visible} />;
}
```

Что тут не так — не «неоптимально», а **сломано**:

1. Первый рендер отдаёт `visible === users`, то есть нефильтрованный список. Пользователь видит вспышку неправильных данных.
2. Эффект выполняется **после** отрисовки. Значит рендеров всегда два: сначала неверный, потом верный.
3. Появился второй источник истины. Если кто-то вызовет `setVisible` напрямую, данные разъедутся с `users` и `query`, и никакая проверка этого не поймает.

```jsx
// Стало: вычисляем при рендере, состояния хранится ровно одно
function UserList({ users }) {
  const [query, setQuery] = useState('');
  const visible = users.filter((u) => u.name.includes(query));

  return <List items={visible} />;
}
```

Один источник истины, один рендер, ноль эффектов, невозможно рассинхронизировать по построению.

### «А если фильтрация дорогая?»

Тогда мемоизация, а не отдельное состояние:

```jsx
const visible = useMemo(
  () => users.filter((u) => u.name.includes(query)),
  [users, query]
);
```

`useMemo` — это по-прежнему вычисление, а не хранение. Второго источника истины не появляется: если зависимости изменились, значение пересчитается. Но и злоупотреблять им не стоит — фильтрация массива на пару сотен элементов почти всегда дешевле, чем кажется. Мерь, прежде чем оборачивать.

### Когда эффект всё-таки нужен

Эффект нужен для **синхронизации с внешним миром**: подписка на сокет, слушатель на `window`, запись в `localStorage`, работа с элементом DOM напрямую. Признак: за пределами React есть что-то, что надо привести в соответствие.

Если и источник, и приёмник живут внутри React, эффект почти всегда лишний. Вопрос-детектор: «этот эффект только вызывает `setState` на основе других состояний и пропсов?» Если да — это вычисление, а не эффект.

## Часть 5. Дублирование состояния и как оно разъезжается

Дублирование — родственник производного состояния, но заметить его сложнее, потому что второй экземпляр выглядит осмысленно.

```jsx
// Было: выбранный элемент хранится копией
function Products() {
  const [items, setItems] = useState([]);
  const [selected, setSelected] = useState(null); // копия объекта из items

  function rename(id, name) {
    setItems(items.map((i) => (i.id === id ? { ...i, name } : i)));
    // selected остался со старым именем
  }

  return (
    <>
      <ItemList items={items} onSelect={setSelected} />
      <Details item={selected} />
    </>
  );
}
```

Переименовали товар в списке — в панели деталей осталось старое имя. Классический баг «в одном месте обновилось, в другом нет». Причём воспроизводится он только при конкретной последовательности действий, и в трекере живёт месяцами.

```jsx
// Стало: храним только идентификатор, объект находим
function Products() {
  const [items, setItems] = useState([]);
  const [selectedId, setSelectedId] = useState(null);

  const selected = items.find((i) => i.id === selectedId) ?? null;

  function rename(id, name) {
    setItems(items.map((i) => (i.id === id ? { ...i, name } : i)));
    // selected пересчитается сам, потому что он не хранится
  }

  return (
    <>
      <ItemList items={items} onSelect={(item) => setSelectedId(item.id)} />
      <Details item={selected} />
    </>
  );
}
```

Правило: **храни идентификатор, а не объект.** Объект — производная от списка и идентификатора. Тот же принцип работает и на уровне кеша серверных данных, где он называется нормализацией, — про это в статье [работа с данными](./data-fetching-patterns).

Бонусом решается вторая проблема: если элемент удалили, `find` вернёт `undefined`, и панель деталей честно покажет пустоту. В варианте с копией она показывала бы призрак удалённого товара.

## Часть 6. Машина состояний вместо набора булевых флагов

Это самая полезная часть статьи, и её же чаще всего спрашивают на собеседовании — обычно в формулировке «как бы вы описали состояние формы отправки».

Начинается всегда одинаково. Пишем форму, добавляем загрузку:

```jsx
const [isLoading, setIsLoading] = useState(false);
```

Потом появляется ошибка:

```jsx
const [isError, setIsError] = useState(false);
```

Потом экран успеха и подсветка изменённой формы:

```jsx
const [isSuccess, setIsSuccess] = useState(false);
const [isDirty, setIsDirty] = useState(false);
```

Четыре булевых значения — это **шестнадцать комбинаций** (два в четвёртой степени). Сколько из них осмысленны? Примерно четыре:

- всё `false` — форма покоится, ничего не трогали;
- `isDirty` — пользователь что-то ввёл;
- `isLoading` — идёт отправка;
- `isSuccess` — отправлено;
- `isError` — упало.

Пять, если считать точно. А остальные одиннадцать — это состояния вроде «одновременно загружается, успешно и с ошибкой». Твой код не запрещает им возникнуть: он лишь надеется, что ты нигде не забыл сбросить флаг. И однажды забудешь — например, в ветке с досрочным `return`.

Вот тот же код с флагами целиком — узнаваемый до боли:

```jsx
// Было
function SubmitForm() {
  const [isLoading, setIsLoading] = useState(false);
  const [isError, setIsError] = useState(false);
  const [isSuccess, setIsSuccess] = useState(false);
  const [error, setError] = useState(null);

  async function submit(data) {
    setIsLoading(true);
    setIsError(false);        // не забыть
    setIsSuccess(false);      // и это не забыть
    try {
      await api.send(data);
      setIsSuccess(true);
    } catch (e) {
      setIsError(true);
      setError(e);
      // а setIsSuccess(false) здесь уже не нужен... или нужен?
    } finally {
      setIsLoading(false);
    }
  }

  // и рендер, в котором порядок проверок задаёт приоритет
  if (isLoading) return <Spinner />;
  if (isError) return <Error error={error} onRetry={() => submit(last)} />;
  if (isSuccess) return <Done />;
  return <Form onSubmit={submit} />;
}
```

Проблемы, которые тут прячутся:

- Порядок `if` в рендере — это неявная и незадокументированная логика приоритета. Поменяй две строки местами — поведение изменится.
- Между `setIsLoading(true)` и сбросом флагов есть момент, когда состояние противоречиво. В React 18 обновления внутри обработчика батчатся, но в асинхронном коде после `await` — уже нет гарантии, что все `setState` попадут в один рендер во всех версиях и окружениях.
- Двойная отправка. Ничто не мешает вызвать `submit` пока `isLoading === true`.

```jsx
// Стало: одно поле состояния, значения перечислены явно
const IDLE = { status: 'idle' };

function SubmitForm() {
  const [state, setState] = useState(IDLE);

  async function submit(data) {
    if (state.status === 'submitting') return;   // двойная отправка невозможна
    setState({ status: 'submitting', data });
    try {
      const result = await api.send(data);
      setState({ status: 'done', result });
    } catch (error) {
      setState({ status: 'failed', error, data });
    }
  }

  switch (state.status) {
    case 'submitting':
      return <Spinner />;
    case 'failed':
      return <Error error={state.error} onRetry={() => submit(state.data)} />;
    case 'done':
      return <Done result={state.result} />;
    default:
      return <Form onSubmit={submit} />;
  }
}
```

Что изменилось по существу:

**Невалидное состояние стало невыразимым.** Нельзя оказаться одновременно в `submitting` и `done` — поле одно.

**Данные привязаны к состоянию.** `error` существует только внутри `failed`, `result` — только внутри `done`. В варианте с флагами `error` жил отдельно и мог остаться от прошлой попытки. В TypeScript это оформляется размеченным объединением, и компилятор перестаёт пускать в `state.error` вне ветки `failed`:

```ts
type FormState =
  | { status: 'idle' }
  | { status: 'editing'; data: FormData }
  | { status: 'submitting'; data: FormData }
  | { status: 'failed'; data: FormData; error: Error }
  | { status: 'done'; result: Result };
```

**Переходы стали явными.** Видно, что из `failed` можно вернуться в `submitting`, а из `done` — нет. Если переходов много, `useState` заменяется на `useReducer`, и все переходы собираются в одном месте:

```jsx
function reducer(state, action) {
  switch (state.status) {
    case 'idle':
    case 'editing':
      if (action.type === 'submit') return { status: 'submitting', data: action.data };
      return state;
    case 'submitting':
      if (action.type === 'ok') return { status: 'done', result: action.result };
      if (action.type === 'fail') return { status: 'failed', data: state.data, error: action.error };
      return state;                       // все прочие действия игнорируются
    case 'failed':
      if (action.type === 'submit') return { status: 'submitting', data: action.data };
      return state;
    default:
      return state;
  }
}
```

Заметь внешний `switch` по состоянию, а не по действию. Так редьюсер читается как таблица переходов: «в таком состоянии допустимо такое». Пришло действие `ok`, когда мы уже в `failed` — например, запоздал ответ от отменённой отправки — состояние не изменится. С флагами такой ответ спокойно поставил бы `isSuccess = true` поверх ошибки.

Отдельно про `isDirty`: в примере выше он превратился в состояние `editing`. Если тебе нужно и «идёт отправка», и «форма была изменена» одновременно, это признак, что у тебя два независимых измерения — тогда так и заведи два поля, но каждое с явным перечислением значений, а не булево. Подробнее про состояния формы — в статье [формы и валидация](./forms-and-validation).

## Часть 7. Состояние в URL

Фильтры таблицы, номер страницы, выбранная вкладка, поисковый запрос, идентификатор открытого элемента — всё это по природе своей **адрес**, а не данные.

```jsx
// Было: фильтры живут в памяти
function Orders() {
  const [status, setStatus] = useState('all');
  const [page, setPage] = useState(1);
  const { data } = useOrders({ status, page });
  // ...
}
```

Что пользователь получает: обновил страницу — фильтры сбросились. Нажал «назад» после открытия заказа — вернулся к первой странице без фильтров. Хочет прислать коллеге ссылку на «просроченные за март» — не может.

```jsx
// Стало: URL как хранилище
function Orders() {
  const [params, setParams] = useSearchParams();
  const status = params.get('status') ?? 'all';
  const page = Number(params.get('page') ?? 1);

  const { data } = useOrders({ status, page });

  function changeStatus(next) {
    setParams((prev) => {
      const p = new URLSearchParams(prev);
      p.set('status', next);
      p.delete('page');          // смена фильтра сбрасывает пагинацию
      return p;
    });
  }
  // ...
}
```

Что при этом бесплатно появляется: работают кнопки «назад» и «вперёд», состояние переживает перезагрузку, ссылка шарится, ошибка от пользователя воспроизводится по адресу из багрепорта.

Несколько практических деталей:

**`push` или `replace`.** Каждая буква в поле поиска не должна создавать запись в истории — иначе кнопка «назад» будет отматывать по букве. Для поиска используй замену текущей записи (`replace`), для смены вкладки или страницы — добавление (`push`).

**Значения по умолчанию не пишем в URL.** Если `status=all` — просто не кладём параметр. Иначе адрес превращается в простыню, а «чистое» состояние становится неотличимо от заданного.

**Валидация на чтении.** В URL может прийти что угодно: пользователь правил руками, ссылка старая, параметр переименовали. Читая, приводи к допустимому значению, а не доверяй строке.

```js
const ALLOWED = ['all', 'new', 'paid', 'overdue'];
const raw = params.get('status');
const status = ALLOWED.includes(raw) ? raw : 'all';
```

Что **не** надо класть в URL: текст в незавершённой форме, состояние аккордеона, позицию скролла, что угодно секретное. Адресная строка попадает в логи серверов, в историю браузера и в заголовок `Referer`. Разбор того, как браузер вообще обрабатывает адрес, — в статье [от адреса до страницы](./url-to-page).

## Часть 8. Серверные данные и почему им не место в Redux

Самый распространённый способ написать много лишнего кода — положить ответ сервера в глобальное хранилище руками.

```js
// Было: три экшена, три ветки редьюсера, санк — и так на каждый запрос
const FETCH_START = 'orders/fetchStart';
const FETCH_OK = 'orders/fetchOk';
const FETCH_FAIL = 'orders/fetchFail';

function ordersReducer(state = { items: [], loading: false, error: null }, action) {
  switch (action.type) {
    case FETCH_START: return { ...state, loading: true, error: null };
    case FETCH_OK:    return { items: action.payload, loading: false, error: null };
    case FETCH_FAIL:  return { ...state, loading: false, error: action.error };
    default:          return state;
  }
}

function fetchOrders() {
  return async (dispatch) => {
    dispatch({ type: FETCH_START });
    try {
      dispatch({ type: FETCH_OK, payload: await api.getOrders() });
    } catch (error) {
      dispatch({ type: FETCH_FAIL, error });
    }
  };
}
```

Тридцать строк ради одного запроса. И это ещё без отмены устаревшего ответа, без дедупликации одинаковых запросов из двух компонентов, без устаревания, без повтора при ошибке, без фонового обновления при возврате на вкладку.

```jsx
// Стало: кеш серверных данных отвечает за это сам
function Orders() {
  const { data, isPending, error } = useQuery({
    queryKey: ['orders'],
    queryFn: api.getOrders,
  });
  // ...
}
```

Дело не в том, что Redux плохой. Дело в том, что Redux решает другую задачу: он про **предсказуемые переходы синхронного клиентского состояния**. У серверных данных задача другая — это кеш с устареванием, и его надо решать инструментом для кеша. Механика подробно разобрана в статье [работа с данными](./data-fetching-patterns).

Практический признак, что ты используешь глобальный стор не по назначению: в нём есть поля `loading` и `error` рядом с данными, и таких троек больше пяти.

## Часть 9. Сброс состояния через `key`

Ситуация: компонент профиля с формой. Переключаемся с одного пользователя на другого — а в полях остались данные предыдущего.

```jsx
// Было: сбрасываем эффектом
function Profile({ userId }) {
  const [name, setName] = useState('');
  const [bio, setBio] = useState('');

  useEffect(() => {
    setName('');
    setBio('');
  }, [userId]);      // и так для каждого поля, и легко забыть новое
  // ...
}
```

Опять два рендера: сначала со старыми данными, потом с пустыми. Плюс список сбросов приходится поддерживать вручную.

```jsx
// Стало: другой пользователь — другой экземпляр компонента
<Profile key={userId} userId={userId} />
```

Механика: React сравнивает элементы по позиции и по `key`. Если `key` изменился, старый экземпляр размонтируется целиком, новый смонтируется с нуля. Всё локальное состояние внутри — включая состояние вложенных компонентов и неконтролируемых полей ввода — исчезает само.

Это самый недооценённый приём в React. Он же работает для сброса формы после успешной отправки (`key={submitCount}`), для перезапуска анимации, для полного пересоздания сложного виджета.

Цена: размонтирование настоящее. Уйдут подписки, обнулится позиция скролла внутри, потеряется фокус. Если состояние надо сбросить частично — `key` не подходит.

## Часть 10. Контекст и его цена

**Контекст** (context) — способ передать значение вниз по дереву, минуя промежуточные компоненты. Он решает проблему «прокидывания пропсов через десять уровней» (prop drilling).

Важно понимать, чем контекст не является: **это не хранилище состояния и не оптимизация**. Это транспорт. Состояние по-прежнему лежит в `useState` какого-то компонента, контекст лишь доставляет его вниз.

Отсюда главная его цена: **любой компонент, читающий контекст, перерисовывается при любом изменении значения** — даже если пользуется только одним полем из десяти.

```jsx
// Было: одно значение на всё
const AppContext = createContext(null);

function App() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('light');
  const [notifications, setNotifications] = useState([]);

  // новый объект на каждый рендер — потребители перерисуются даже
  // если ничего не изменилось
  return (
    <AppContext.Provider value={{ user, setUser, theme, setTheme, notifications }}>
      <Layout />
    </AppContext.Provider>
  );
}
```

Пришло уведомление — перерисовался каждый компонент, который читает контекст ради темы.

```jsx
// Стало: разные по частоте изменения данные разведены по разным контекстам
const UserContext = createContext(null);
const ThemeContext = createContext('light');
const NotificationsContext = createContext([]);

function App() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('light');
  const [notifications, setNotifications] = useState([]);

  const userValue = useMemo(() => ({ user, setUser }), [user]);

  return (
    <UserContext.Provider value={userValue}>
      <ThemeContext.Provider value={theme}>
        <NotificationsContext.Provider value={notifications}>
          <Layout />
        </NotificationsContext.Provider>
      </ThemeContext.Provider>
    </UserContext.Provider>
  );
}
```

Отдельный полезный приём — **разделить значение и функции его изменения**. Функции стабильны, значение меняется:

```jsx
const TodosContext = createContext([]);
const TodosApiContext = createContext(null);

function TodosProvider({ children }) {
  const [todos, setTodos] = useState([]);

  // объект с функциями создаётся один раз: обновление идёт
  // через функциональную форму, поэтому todos в зависимостях не нужен
  const api = useMemo(() => ({
    add: (text) => setTodos((prev) => [...prev, { id: crypto.randomUUID(), text }]),
    remove: (id) => setTodos((prev) => prev.filter((t) => t.id !== id)),
  }), []);

  return (
    <TodosApiContext.Provider value={api}>
      <TodosContext.Provider value={todos}>{children}</TodosContext.Provider>
    </TodosApiContext.Provider>
  );
}
```

Теперь кнопка «добавить», которая читает только `TodosApiContext`, не перерисовывается при изменении списка. А компонентам, которым нужен сам список, это и так нужно.

Если разведение по контекстам перестаёт помогать, значит задача уже про подписки на срез состояния — а это работа внешнего хранилища (Zustand, Jotai, Redux с селекторами), где компонент подписывается на конкретный кусок и просыпается только при его изменении.

Ещё один способ вообще не платить за контекст — передать поддерево через `children`, чтобы оно не перерисовывалось. Приём разобран в статье [композиция](./composition-patterns).

## Когда не надо

У каждого приёма есть цена, и есть ситуации, где приём делает хуже.

**Не выноси всё в URL.** Адрес — публичный интерфейс. Если положить туда десять параметров формы, ты зафиксируешь их имена: поменять станет ломающим изменением, старые ссылки перестанут работать. В URL идёт то, чем осмысленно поделиться.

**Не делай машину состояний из двух состояний.** Обычный `isOpen` для выпадашки — это нормально. Машина окупается, когда состояний три и больше и между ними есть запрещённые переходы. Форма с загрузкой и ошибкой — да, чекбокс — нет.

**Не тащи библиотеку кеша ради трёх запросов.** Если в приложении один экран, который что-то грузит, `useState` плюс `useEffect` с флагом отмены дешевле, чем зависимость на сорок килобайт. Понимать механику важнее, чем всегда её импортировать.

**Не нормализуй всё подряд.** Хранение по идентификаторам оправдано, когда одна сущность встречается в нескольких местах. Список настроек, показанный ровно один раз, нормализовать незачем — получишь косвенность без выгоды.

**Не дроби контексты до бесконечности.** Пять провайдеров вложенных друг в друга — уже сложно читать. Если их становится много, вопрос не в контекстах, а в том, что глобального состояния слишком много.

**Не опускай состояние вниз, если оно там дублируется.** Colocation хорош, пока данные нужны одному поддереву. Если ты опустил состояние в двух местах и теперь синхронизируешь их эффектом — стало хуже, чем было.

**Не начинай с `useReducer`.** Начинай с `useState`. Редьюсер окупается, когда переходов много и они связаны; для двух полей он лишняя церемония.

## Что спросят на интервью

**Какие виды состояния вы выделяете и зачем?** Серверное, глобальное клиентское, локальное, URL. Разные жизненные циклы: у серверного — устаревание и инвалидация, у URL — история браузера, у локального — привязка к жизни компонента. Единое хранилище заставляет вручную обслуживать все четыре режима.

**Почему серверные данные не стоит держать в Redux?** Redux решает задачу предсказуемых переходов клиентского состояния. Серверные данные — это кеш: нужны ключи, устаревание, дедупликация, повтор, фоновое обновление, отмена гонок. Всё это придётся написать руками, причём в каждой фиче.

**Что не так с `useEffect`, который делает `setState` на основе пропсов?** Это производное состояние, оформленное как хранимое. Лишний рендер, вспышка неверных данных, второй источник истины. Вычисляй при рендере, при дороговизне — `useMemo`.

**У вас четыре булевых флага состояния формы. Что скажете?** Шестнадцать комбинаций при пяти валидных. Невалидные состояния достижимы, приоритет задан порядком `if`, данные ошибки живут отдельно от состояния ошибки. Замена — одно поле `status` с перечислением, в TypeScript — размеченное объединение.

**Как сбросить состояние дочернего компонента при смене сущности?** Передать `key`. React размонтирует старый экземпляр и создаст новый. Альтернатива через эффект даёт лишний рендер и требует помнить про каждое поле.

**Почему компонент перерисовывается, хотя нужное ему поле контекста не менялось?** Контекст не умеет частичной подписки: значение изменилось — проснулись все потребители. Лечится разделением на несколько контекстов, мемоизацией значения провайдера или внешним хранилищем с селекторами.

**Когда подъём состояния — ошибка?** Когда подняли выше ближайшего общего предка. Тогда изменение частого состояния (ввод в поле) перерисовывает всё поддерево. Обратный приём — colocation, опустить состояние к месту использования.

**Как хранить выбранный элемент списка?** Идентификатором, а объект находить в списке. Копия объекта разъезжается с источником при любом обновлении списка.

## Коротко, для повторения

1. Четыре вида состояния: серверное, глобальное клиентское, локальное, URL. У каждого свой жизненный цикл.
2. Первый вопрос — не «куда положить», а «можно ли не хранить». Производное состояние вычисляй при рендере.
3. `useEffect`, который только зовёт `setState` от других состояний, — не эффект, а вычисление не на своём месте.
4. Храни идентификатор, а не копию объекта. Копии разъезжаются.
5. Четыре булевых флага — шестнадцать состояний, из которых валидны единицы. Одно поле `status` делает невалидное невыразимым.
6. Данные привязывай к состоянию: `error` живёт внутри `failed`, `result` — внутри `done`.
7. Фильтры, вкладки, пагинация и поиск живут в URL. Тогда работают «назад», перезагрузка и обмен ссылкой.
8. Серверные данные — это кеш, а не стор. Ключ, устаревание, инвалидация.
9. `key` — самый дешёвый способ полного сброса состояния поддерева.
10. Контекст — транспорт, а не хранилище. Изменение значения будит всех потребителей.
11. Поднимай состояние ровно до общего предка и опускай обратно, как только оно перестало быть общим.
