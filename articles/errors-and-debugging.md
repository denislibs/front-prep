# Ошибки: как их ловить, бросать и отлаживать

Обработку ошибок обычно пишут в последнюю очередь и по остаточному принципу: обернул в `try/catch`, вывел `console.log`, поехали дальше. Потом в проде появляется отчёт «Script error, строка 1, столбец 0», и выясняется, что о происходящем нельзя сказать вообще ничего.

Эта статья про механику: что такое объект ошибки, как он путешествует по стеку и по цепочке промисов, где стек теряется и что с этим делать. Плюс практика отладки — не «поставь брейкпоинт», а как ловить то, что руками не воспроизводится.

Опирается на [промисы изнутри](./promises) и [async/await](./async-await): оттуда нужно помнить, что отклонённый промис — это ошибка, едущая по цепочке, и что после `await` вызывающего кода на стеке уже нет.

## Часть 1. `throw` и почему бросать надо только `Error`

`throw` прерывает выполнение и начинает поиск ближайшего `catch` вверх по **стеку вызовов** — цепочке функций, которые сейчас выполняются. Не нашёл ни одного — ошибка вылетает в глобальный обработчик.

Бросить синтаксически можно что угодно:

```js
throw 'что-то пошло не так';   // строка
throw 404;                     // число
throw { code: 'E_AUTH' };      // обычный объект
```

И всё это — плохая идея. Причина одна: **у не-Error нет стека**. Объект `Error` при создании фиксирует, откуда его создали, в поле `stack`. Строка и число ничего не помнят, и в отчёте из прода ты увидишь текст без единого намёка на место.

Есть и вторая причина: инструменты рассчитывают на `Error`. Система мониторинга не сгруппирует брошенные строки в одну проблему. Браузер напечатает `Uncaught 404` без ссылки на строку. `err.message` окажется `undefined`, и вывод в интерфейсе сломается.

Что есть у любого `Error`:

- `name` — тип ошибки, по умолчанию `'Error'`;
- `message` — текст;
- `stack` — строка со списком вызовов на момент **создания** объекта (не броска — это разные моменты, если объект создали заранее).

`stack` не стандартизирован, но есть везде. Формат у движков разный, поэтому разбирать его регулярками — плохая идея; для этого есть готовые библиотеки.

### Встроенные типы

Все наследуются от `Error`:

- **`TypeError`** — значение не того типа или операция к нему неприменима. Самая частая ошибка вообще: `undefined is not a function`, обращение к свойству `null`.
- **`ReferenceError`** — обращение к несуществующей переменной. Сюда же попадает доступ к `let`/`const` до объявления — «временная мёртвая зона».
- **`SyntaxError`** — код не разобрался. Обычно на этапе разбора, но `JSON.parse` бросает её же во время выполнения.
- **`RangeError`** — значение вне допустимого диапазона: длина массива, слишком глубокая рекурсия (`Maximum call stack size exceeded`), неверная точность у `toFixed`.
- **`URIError`** — сломанный аргумент у `decodeURIComponent`.
- **`AggregateError`** — несколько ошибок сразу, о ней ниже.

Знать их наизусть не нужно, а вот различать полезно: `TypeError` почти всегда означает баг в коде, а не плохие входные данные. Если у тебя `TypeError` в обработке ответа сервера — скорее всего, ты не проверил, что данные пришли.

Отдельно стоит `DOMException` — ошибки браузерных API. Она не наследуется от `Error` в спецификации, но выглядит похоже и имеет `name`: `AbortError`, `NotAllowedError`, `QuotaExceededError`. Именно поэтому отменённый `fetch` проверяют по `err.name`, а не через `instanceof`.

## Часть 2. Свои классы ошибок

Смысл своего класса — дать вызывающему коду возможность **различать** ошибки и приложить к ним данные.

```js
class HttpError extends Error {
  constructor(response) {
    super(`HTTP ${response.status} ${response.url}`);
    this.name = 'HttpError';           // обязательно
    this.status = response.status;      // данные, а не текст
    this.url = response.url;
  }
}
```

**Зачем ставить `name` вручную.** По умолчанию `name` наследуется от `Error` и остаётся строкой `'Error'`. Имя класса туда не попадает автоматически. Без явного присваивания в консоли и в логах ты увидишь `Error: HTTP 500` вместо `HttpError: HTTP 500` — и потеряешь возможность отличить свою ошибку от чужой в тексте отчёта.

**Почему данные полями, а не в тексте.** Из `message` статус придётся выковыривать регуляркой, а поле `status` можно сравнить. Текст ошибки — для человека, поля — для кода.

Наследоваться лучше в один-два уровня. Глубокая иерархия классов ошибок красиво выглядит и никогда не используется: на практике проверяют два-три условия.

## Часть 3. `cause` — важнее, чем кажется

Классическая проблема: ошибка перехвачена на низком уровне, обёрнута в понятную и брошена дальше. Исходная при этом **исчезает** вместе со своим стеком.

```js
// Плохо: настоящая причина потеряна навсегда
try {
  return await api.getUser(id);
} catch (err) {
  throw new Error('Не удалось загрузить профиль');
}
```

В отчёте будет «Не удалось загрузить профиль» и стек до строки с `throw`. Что там случилось на самом деле — таймаут, 500-й ответ, сломанный JSON — узнать невозможно.

ES2022 добавил второй аргумент конструктора:

```js
// Хорошо: сохраняем исходную ошибку
try {
  return await api.getUser(id);
} catch (err) {
  throw new Error('Не удалось загрузить профиль', { cause: err });
}
```

`cause` — обычное поле, в нём лежит исходный объект ошибки целиком, с его типом, полями и стеком. DevTools печатает цепочку причин с отступами, системы мониторинга её разбирают.

Почему это важнее, чем кажется: в приложении с несколькими слоями ошибка проходит три-четыре обёртки. Без `cause` каждая обёртка **стирает** предыдущий контекст, и до отчёта доезжает самая внешняя и самая бесполезная формулировка вроде «Ошибка загрузки». С `cause` получается **цепочка причин**: «не отрисовался экран» ← «не удалось загрузить профиль» ← «HTTP 503» ← «сеть недоступна».

Правило: **перехватил и бросаешь новую — всегда прикладывай `cause`**.

Разворачивать цепочку тоже просто:

```js
function rootCause(err) {
  while (err.cause) err = err.cause;
  return err;
}
```

Свой класс тоже должен пробрасывать `cause` — для этого достаточно передать `options` в `super`:

```js
class AppError extends Error {
  constructor(message, options) {
    super(message, options);   // options.cause попадёт в this.cause
    this.name = 'AppError';
  }
}
```

### `AggregateError`

Когда ошибок сразу несколько, обёртка одной не подходит. `AggregateError` хранит массив в поле `errors`.

```js
try {
  await Promise.any([fetchFrom(a), fetchFrom(b)]);
} catch (err) {
  console.log(err.name);       // AggregateError
  console.log(err.errors);     // массив всех причин
}
```

Встроенно её бросает только `Promise.any`, когда провалились все, но конструктор доступен и своему коду — например, для валидации формы, где нужно вернуть все нарушения сразу, а не первое.

```js
const problems = validate(form);
if (problems.length) throw new AggregateError(problems, 'Форма заполнена неверно');
```

## Часть 4. `try/catch/finally` и его границы

```js
try {
  risky();
} catch (err) {
  handle(err);
} finally {
  cleanup();
}
```

`catch` можно писать без аргумента, если ошибка не нужна: `catch { ... }`.

**`finally` выполняется всегда** — при успехе, при ошибке и, что менее очевидно, при `return`, `break` и `continue` внутри `try`. Причина: `finally` создан для освобождения ресурсов, и он обязан отработать на любом пути выхода из блока.

```js
function f() {
  try {
    return 'из try';
  } finally {
    console.log('всё равно выполнюсь');   // напечатается ДО возврата
  }
}
```

Порядок здесь такой: значение `'из try'` вычисляется и запоминается, потом выполняется `finally`, потом происходит возврат.

А вот `return` **внутри** `finally` перезаписывает результат и — что хуже — **проглатывает ошибку**:

```js
function f() {
  try {
    throw new Error('бум');
  } finally {
    return 'ок';       // ошибка исчезает бесследно
  }
}
f();   // 'ок', никакой ошибки
```

Правило простое: **никогда не пиши `return` и `throw` внутри `finally`**. Линтер обычно ругается на это отдельным правилом.

### Чего `try/catch` не ловит

Он ловит только то, что произошло **на текущем стеке**, синхронно, внутри блока. Всё остальное — мимо.

**Колбэки таймеров и событий.** Их вызывает движок из своей задачи; твоего `try` на стеке в этот момент нет.

```js
try {
  setTimeout(() => { throw new Error('бум'); }, 0);
  button.addEventListener('click', () => { throw new Error('бум'); });
} catch (e) { /* не поймает ни одну */ }
```

**Отклонённые промисы без `await`.**

```js
try {
  loadData();          // async-функция без await
} catch (e) { /* не поймает */ }
```

Вызов вернул промис и мгновенно завершился. Отклонение произойдёт позже.

**Ошибки в других задачах вообще.** Обработчик `message` у воркера, колбэк `IntersectionObserver`, реакция на событие сети — везде свой стек. Про то, как браузер вызывает обработчики событий, — в статье [события DOM](./dom-events).

Что **ловит**: синхронный код, `await` внутри блока (потому что `await` бросает причину отклонения прямо в точке ожидания), и `throw` из функций, вызванных синхронно на любую глубину.

### Глобальные ловушки

Две последние линии обороны. В браузере:

```js
// Синхронные ошибки, не пойманные нигде
window.addEventListener('error', (event) => {
  report(event.error, { file: event.filename, line: event.lineno });
});

// Отклонённые промисы без обработчика
window.addEventListener('unhandledrejection', (event) => {
  event.preventDefault();     // подавить вывод в консоль
  report(event.reason);
});
```

Что важно знать про них:

- **Это два разных события.** Подписался только на `error` — потерял все асинхронные ошибки, а их сегодня большинство.
- **`error` ловит и ошибки загрузки ресурсов** (картинка, скрипт не скачались), но только в фазе перехвата: `window.addEventListener('error', fn, true)`. Обычная подписка их не увидит, потому что такие события не всплывают.
- **`Script error.` без подробностей** появляется, когда ошибка произошла в скрипте с другого домена (CDN). Браузер прячет детали из соображений безопасности. Лечится атрибутом `crossorigin` на теге скрипта и заголовком `Access-Control-Allow-Origin` на CDN.
- **`event.reason` может быть чем угодно** — тем, чем отклонили промис. Ещё одна причина отклонять только объектами `Error`.
- Старый вариант `window.onerror = fn` работает, но перезаписывается — один обработчик на всё приложение. Лучше `addEventListener`.

Глобальная ловушка — не замена локальной обработке. Её задача — узнать о том, что ты не предусмотрел, а не обрабатывать ожидаемые ошибки.

## Часть 6. Стек: почему в проде он нечитаем

### Что такое стек ошибки

`err.stack` — снимок цепочки вызовов на момент **создания** объекта `Error`. Читается сверху вниз: первая строка — где ошибка возникла, дальше — кто вызвал.

```
TypeError: Cannot read properties of undefined (reading 'name')
    at renderUser (app.js:42:18)
    at renderPage (app.js:80:3)
    at handleClick (app.js:120:5)
```

Из такого стека видно всю дорогу до проблемы. Ради этого и нужен `Error`.

### Где стек теряется

Стек **обрывается на границе задачи**. Функция, вызванная из очереди, не помнит, кто поставил её туда: тот код давно снялся со стека.

```
Error: HTTP 500
    at parseResponse (api.js:12:11)
    at async loadUser (api.js:30:3)
```

Кто вызвал `loadUser` — из этого стека не узнать. Кнопка? Роутер? Автообновление раз в минуту? Настоящего ответа в стеке нет.

Движки частично компенсируют: V8 умеет **асинхронные стеки** — искусственно сшивает кадры на границах `await` и промисов. В DevTools это видно как разделители «Async Call Stack». Но это реконструкция по внутренним записям движка, она ограничена по глубине и в отчётах из прода обычно отсутствует.

Практический вывод: **добавляй контекст сам**. Если стек не расскажет, откуда пришёл вызов, это должны рассказать поля ошибки.

```js
throw new HttpError(res, { context: { screen: 'profile', userId: id } });
```

### Исходные карты

В прод едет собранный код: минифицированный (имена сокращены до одной буквы, переносы убраны) и перемешанный сборщиком. Стек от него бесполезен:

```
    at t (main.a3f9.js:1:24817)
```

**Исходная карта** (source map) — файл `.map` рядом со сборкой, где записано соответствие «позиция в собранном файле — файл, строка, столбец и имя в исходнике». DevTools подхватывает её по комментарию в конце бандла и показывает нормальный стек и настоящий код в отладчике.

Три вещи, которые стоит знать:

1. **Выкладывать карты в публичный доступ не обязательно и обычно нежелательно** — это раздача исходников. Стандартная практика: собирать карты и загружать их в систему мониторинга приватно, а рядом с бандлом не публиковать.
2. **Карта должна соответствовать конкретной сборке.** Карта от предыдущей версии даст стек, указывающий на случайные строки. Отсюда привязка карт к версии сборки.
3. **Без карт отчёты из прода почти бесполезны.** Это первое, что нужно настроить, а не последнее.

## Часть 7. Проверять по `code`, а не по `instanceof`

Естественный способ различить ошибки — `instanceof`:

```js
if (err instanceof HttpError) { ... }
```

Работает, пока код живёт в одном месте. Ломается в трёх реальных ситуациях:

**Два экземпляра одного класса.** Если библиотека попала в сборку дважды (разные версии в зависимостях), классов `HttpError` тоже будет два. Объект создан первым, проверяешь вторым — `instanceof` даёт `false`, хотя ошибка «та самая».

**Другой контекст выполнения.** Объект из `iframe`, из воркера, из другого realm — у него своя цепочка прототипов. Ошибка из `iframe` не пройдёт проверку `err instanceof Error` в родительском окне.

**Ошибка пережила сериализацию.** Пришла с сервера в JSON, прошла через `postMessage`, восстановлена из хранилища — прототип потерян, остались только поля.

Надёжнее проверять признак, который переживает всё перечисленное:

```js
if (err.code === 'HTTP_ERROR') { ... }
if (err.name === 'AbortError') { ... }
```

Строка сравнивается одинаково в любом контексте и переживает сериализацию. Так устроены и встроенные API: отменённый `fetch` проверяют именно по `err.name === 'AbortError'`, потому что `DOMException` из `instanceof Error` не выводится.

Разумный компромисс: `instanceof` — внутри своего модуля, где классы гарантированно одни и те же; `code` или `name` — на любых границах: между пакетами, с сервером, между воркерами и окнами.

Полезная привычка — писать защищённо, потому что в `catch` может прилететь вообще что угодно:

```js
function toError(value) {
  if (value instanceof Error) return value;
  return new Error(typeof value === 'string' ? value : JSON.stringify(value));
}
```

В TypeScript тип пойманного значения — `unknown` именно по этой причине, и это правильно.

## Часть 8. Отладка

### Точки останова

`console.log` работает, пока не нужно посмотреть на пять переменных сразу или заглянуть в чужой код. Дальше — панель Sources в DevTools.

- **Обычная точка** — клик по номеру строки. Выполнение останавливается, видны все переменные в области видимости и стек вызовов.
- **Условная точка** — правый клик по номеру, «Add conditional breakpoint». Останавливается, только когда условие истинно: `id === 42`. Незаменима внутри цикла на тысячу итераций, где нужна одна конкретная.
- **Точка с логом** (logpoint) — печатает выражение и **не останавливает** выполнение. Это `console.log`, который не надо добавлять в код и потом убирать. Идеально для отладки анимаций и обработчиков, где остановка всё ломает.
- **Точка на исключении** — переключатель «Pause on exceptions», отдельно для пойманных и непойманных. Включаешь «на непойманных» и воспроизводишь баг: отладчик остановится ровно в месте броска, со всеми живыми переменными. Это самый быстрый способ найти источник неизвестной ошибки.
- **`debugger`** — оператор прямо в коде. Останавливает выполнение, когда DevTools открыт, и ничего не делает, когда закрыт. Удобен там, где строку трудно найти глазами — в сгенерированном коде, в динамически подключённом модуле. Главное — не забыть убрать; линтер за это ругается.

Отдельно есть точки на событиях DOM (сработает при любом `click`), на изменении узла DOM (кто удалил этот элемент?) и на сетевых запросах по маске URL.

### Отладка асинхронного кода

Здесь всё сложнее: между шагами `await` управление уходит наружу.

- **Шаг с заходом внутрь** (Step into) на строке с `await` не заходит в промис. Ставь точку в самом асинхронном колбэке.
- **Включи «Async stack traces»** в настройках DevTools — тогда в панели стека появятся кадры до `await`, отмеченные разделителями.
- **Точка останова внутри `catch`** и включённая пауза на исключениях экономят часы: вместо гадания сразу видно значение, вызвавшее проблему.
- **Проблемы «между кусками»** — состояние изменилось после `await` — точками останова ловятся плохо, потому что остановка меняет тайминг. Здесь надёжнее логировать с меткой времени и своим идентификатором операции.

### Что делать с отчётом, в котором ничего нет

Порядок действий, когда пришло «Script error» или голый стек:

1. Проверить исходные карты — загружаются ли, соответствуют ли версии.
2. Проверить `crossorigin` на скриптах с CDN: без него детали чужих ошибок скрыты.
3. Проверить, что подписка на `unhandledrejection` вообще есть.
4. Проверить, что в приложении не бросают строки — иначе стека не будет в принципе.
5. Добавить контекст: версия сборки, идентификатор пользователя и сессии, последние действия (хлебные крошки).

Пункты 1–4 закрываются один раз и навсегда. Именно они отличают отчёт, по которому баг чинится за десять минут, от отчёта, по которому его не найти вообще.

## Что спросят на интервью

**Почему нельзя бросать строку?** У неё нет стека и нет `message`. В отчёте будет текст без места возникновения, а мониторинг не сгруппирует такие ошибки.

**Зачем в своём классе ошибки писать `this.name`?** По умолчанию `name` остаётся `'Error'`; имя класса туда не попадает. Без него ошибка неотличима от любой другой в логах.

**Что такое `cause` и зачем он нужен?** Второй аргумент конструктора `Error`, хранящий исходную ошибку. Позволяет обернуть ошибку в понятную, не потеряв настоящую причину и её стек.

**Выполнится ли `finally`, если в `try` есть `return`?** Да, до фактического возврата. А `return` внутри `finally` перезапишет результат и проглотит ошибку — так делать нельзя.

**Что `try/catch` не поймает?** Всё, что выполняется на другом стеке: колбэки таймеров и событий, отклонённые промисы без `await`, ошибки в других задачах.

**Чем `error` отличается от `unhandledrejection`?** Первое — про непойманные синхронные ошибки, второе — про отклонённые промисы без обработчика. Нужны оба.

**Почему в проде стек нечитаем?** Код минифицирован. Нужны исходные карты, соответствующие конкретной сборке и загруженные в мониторинг.

**Почему стек обрывается в асинхронном коде?** Функция из очереди вызывается с пустого стека, вызвавшего кода на нём уже нет. Асинхронные стеки в DevTools — реконструкция движка, а не настоящий стек.

**Почему проверять `err.code` надёжнее, чем `instanceof`?** `instanceof` ломается при дублировании пакета, при переходе через `iframe` или воркер и после сериализации. Строковый признак переживает всё это.

**Что такое `AggregateError`?** Ошибка со списком ошибок в поле `errors`. Бросается `Promise.any`, когда провалились все, и годится для валидации, где нужно вернуть все нарушения сразу.

**Как отладить код, который падает раз в сто запусков?** Условная точка останова или пауза на исключениях плюс логирование контекста. Точечный `console.log` тут не помогает — нужен снимок состояния в момент броска.

## Коротко, для повторения

1. Бросать только `Error` и его потомков: у остального нет стека и `message`.
2. `TypeError` почти всегда означает баг в коде, а не плохие данные.
3. В своём классе обязательно ставь `name` и клади данные полями, а не в текст сообщения.
4. Перехватил и бросаешь новую — приложи `cause`, иначе исходная причина исчезнет навсегда.
5. `AggregateError` хранит список ошибок в `errors`; её бросает `Promise.any`.
6. `finally` выполняется всегда, включая путь через `return`. `return` и `throw` внутри `finally` писать нельзя.
7. `try/catch` ловит только текущий стек. Колбэки таймеров, обработчики событий и промисы без `await` — мимо.
8. Ошибка идёт вверх по стеку либо вперёд по цепочке промисов. Это разные маршруты.
9. Нужны обе глобальные ловушки: `error` и `unhandledrejection`.
10. Стек обрывается на границе задачи. Контекст добавляй сам полями ошибки.
11. Без исходных карт, привязанных к версии сборки, отчёты из прода бесполезны. Карты грузи в мониторинг, а не в публичный доступ.
12. На границах модулей и процессов проверяй `err.code` или `err.name`, а не `instanceof`.
13. Пауза на непойманных исключениях, условные точки и точки с логом экономят больше времени, чем любой `console.log`.
