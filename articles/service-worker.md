# Service Worker: офлайн, кеш и обновления

Service Worker — единственное место в браузере, где можно встать между страницей и сетью и ответить на запрос своими силами. Из этого растёт всё остальное: офлайн-режим, мгновенная загрузка с повторного захода, фоновая синхронизация, пуш-уведомления.

И из этого же растёт главный риск. Service Worker переживает перезагрузку страницы, живёт после закрытия вкладки и обновляется по своим правилам. Ошибка в нём — не «сломался экран», а «пользователи навсегда застряли на старой версии приложения, и вы не можете до них дотянуться». Такое случалось у больших команд.

Эта статья — про механику: как воркер устроен, почему обновляется именно так, что такое Cache Storage и чем он отличается от привычного HTTP-кеша, какие стратегии кеширования бывают и где какая уместна. Все примеры рабочие: их можно перенести в проект.

Предполагается, что вы понимаете, что такое главный поток и почему он один — это разобрано в статье [как работает браузер](./browser-rendering-event-loop). Service Worker — родственник [Web Worker](./web-workers): тоже отдельный поток без доступа к DOM. Разница в назначении, и она принципиальна, о ней ниже.

## Часть 1. Что это такое простыми словами

### Прокси, который вы пишете сами

**Прокси** — посредник, через которого идут запросы. Обычно прокси стоит на сервере, и вы им не управляете. Service Worker — прокси, который стоит **в браузере пользователя**, написан на JavaScript и целиком под вашим контролем.

Когда страница просит картинку, шрифт, JSON или даже сам HTML, запрос сначала попадает в воркер. Воркер решает: сходить в сеть, отдать из кеша, склеить ответ из кусочков или вернуть заглушку. Страница разницы не замечает — она просто получает `Response`.

```js
// sw.js — простейший осмысленный воркер
self.addEventListener('fetch', (event) => {
  // Перехватываем только картинки, остальное отдаём браузеру как есть
  if (event.request.destination !== 'image') return;

  event.respondWith(
    caches.match(event.request).then((cached) => {
      if (cached) return cached;              // мгновенно, без сети
      return fetch(event.request);            // промах — идём в сеть
    })
  );
});
```

Обратите внимание на устройство: если обработчик **не вызвал** `event.respondWith`, браузер обрабатывает запрос сам, обычным путём. Это важное свойство — воркер не обязан отвечать за всё.

### Чем он отличается от обычного воркера

[Web Worker](./web-workers) существует, пока жива создавшая его страница, и нужен для вычислений. Service Worker:

- **не привязан к странице**: одна копия воркера обслуживает все вкладки вашего сайта;
- **переживает закрытие вкладки**: может проснуться на пуш-уведомление или фоновую синхронизацию, когда открытых вкладок нет вообще;
- **засыпает**: браузер убивает воркер через несколько десятков секунд простоя и будит на следующее событие.

Из последнего следует правило, на котором спотыкаются все: **в Service Worker нельзя хранить состояние в переменных модуля**. Записали счётчик в глобальную переменную — через минуту воркер уснул, переменная исчезла, при следующем событии там снова ноль. Состояние живёт в IndexedDB или Cache Storage (см. [хранилища в браузере](./storage-and-quotas)).

### Что воркер может и чего не может

Есть: `fetch`, `caches`, `indexedDB`, `postMessage`, таймеры, `crypto`, `WebAssembly`, `importScripts`.

Нет: `window`, `document`, DOM, `localStorage` (он синхронный, а синхронные API в воркерах запрещены), прямого доступа к переменным страницы.

Работает только по HTTPS. Исключение — `localhost`, чтобы можно было разрабатывать. Причина очевидна: воркер способен подменять ответы, и по незащищённому соединению его смог бы подсунуть кто угодно, получив вечный контроль над сайтом.

### Шаг 1. Регистрация

```js
// main.js — регистрируем после загрузки, чтобы не конкурировать за сеть
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js', { scope: '/' })
      .then((reg) => console.info('SW зарегистрирован, scope:', reg.scope))
      .catch((err) => console.error('SW не встал:', err));
  });
}
```

`register` идемпотентен: вызвали десять раз с тем же URL — воркер один. Каждый вызов заставляет браузер проверить файл на изменения (об этом ниже), но новую копию не создаёт.

Регистрация после `load` — сознательное решение: во время первой загрузки сеть и главный поток заняты нужными пользователю ресурсами, воркер там только мешает. Цена — на самом первом визите воркер начнёт кешировать чуть позже; выигрыш — первая отрисовка не замедлится.

### Шаг 2. Установка

Браузер скачивает `sw.js`, разбирает его и запускает событие `install`. Это единственный момент, когда гарантированно можно наполнить кеш.

```js
const CACHE = 'app-shell-v7';
const SHELL = ['/', '/offline.html', '/assets/app.css', '/assets/app.js'];

self.addEventListener('install', (event) => {
  // waitUntil держит воркер живым и откладывает переход в waiting,
  // пока промис не разрешится
  event.waitUntil(
    caches.open(CACHE).then((cache) => cache.addAll(SHELL))
  );
});
```

`event.waitUntil(promise)` — способ сказать браузеру «я ещё не закончил». Без него воркер может уснуть посреди работы: он событийный, и браузер считает обработчик завершённым, как только тот вернул управление.

Важнейшее свойство: **если промис в `waitUntil` отклонился, установка провалилась целиком**. Воркер не активируется, старый продолжает работать. `cache.addAll` — атомарная операция: не скачался один файл из списка — не сохранится ни один. Это защита, но и мина: положили в `SHELL` ссылку на CDN, который в этот момент отдал 500, — новая версия не встанет, а вы об этом не узнаете без телеметрии.

### Шаг 3. Ожидание — и почему оно есть

Новый воркер установился и... встал в очередь. Он в состоянии `waiting` и **не контролирует ни одной страницы**, пока жив хотя бы один клиент, которым управляет старый воркер.

Причина — согласованность. Представьте, что новая версия приложения ждёт от API поля `total_cents` вместо `total`, а воркер новой версии переписывает запросы под новый формат. Если бы новый воркер захватил управление немедленно, открытая старая вкладка вдруг начала бы получать ответы в неизвестном ей формате и сломалась бы на ровном месте. Правило «одна версия воркера на все вкладки одновременно» это исключает.

Здесь же — самый частый источник недоумения: **обычная перезагрузка страницы не переключает воркер**. При reload новый документ начинает загружаться до того, как умер старый; момента, когда клиентов нет, не возникает. Нужно либо закрыть все вкладки сайта, либо явно попросить воркер пропустить очередь.

### Шаг 4. Активация и `skipWaiting`

```js
self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    // Удаляем все кеши, кроме текущего
    const names = await caches.keys();
    await Promise.all(
      names.filter((n) => n !== CACHE).map((n) => caches.delete(n))
    );
    // Включаем навигационный предзагрузчик: браузер начнёт грузить
    // документ параллельно со стартом воркера
    if (self.registration.navigationPreload) {
      await self.registration.navigationPreload.enable();
    }
    await self.clients.claim();
  })());
});
```

Два метода, о которых спросят на интервью:

**`self.skipWaiting()`** — «не жди, стань активным сразу». Вызывается обычно в `install`. Опасность: страница, загруженная старой версией, продолжает выполняться, но её запросы теперь обслуживает новый воркер. Если новая версия переименовала файлы (а сборщики делают это на каждом релизе, добавляя хеш в имя), старая страница попросит `app.a1b2.js` для ленивого чанка, а в новом кеше лежит `app.c3d4.js`. Результат — белый экран посреди работы. Поэтому `skipWaiting` без разговора с пользователем — плохая идея для приложений с ленивой загрузкой кода.

**`self.clients.claim()`** — «возьми под контроль уже открытые страницы, которые загрузились без воркера». Нужен в основном на самом первом визите: страница загрузилась раньше, чем воркер активировался, и без `claim` останется неуправляемой до следующей навигации. Опасность зеркальная: страница, начавшая жизнь без воркера, внезапно получает воркер посреди работы, и часть её запросов идёт по одному пути, часть — по другому.

Разумный вывод: `clients.claim()` в `activate` — почти всегда безопасно и полезно. `skipWaiting()` — только по явной команде пользователя (см. часть 8).

### Как браузер понимает, что воркер обновился

Браузер сравнивает **побайтово** скачанный `sw.js` с сохранённым. Отличается хоть на байт — начинается установка новой версии. Проверка происходит при навигации на страницу в области действия воркера, при вызове `register` и не реже раза в сутки.

Отсюда правило: **сам файл воркера нельзя кешировать надолго**. Если ваш CDN отдаёт `sw.js` с `Cache-Control: max-age=31536000`, браузер будет год сравнивать старый файл со старым и не увидит обновлений. Ставьте `Cache-Control: no-cache` (это значит «перепроверяй на сервере», а не «не храни»). Современные браузеры и так игнорируют кеш длиннее суток для файла воркера, но полагаться на это не стоит.

Важный нюанс: скрипты, подключённые через `importScripts`, по умолчанию тоже участвуют в сравнении только при первой установке. Если вся логика вынесена в отдельный файл, а `sw.js` — трёхстрочная обёртка, обновления могут не приезжать. Лечится сборкой: пусть сборщик впаивает хеш содержимого прямо в `sw.js`.

## Часть 3. Область действия

**Scope** — префикс URL, который воркер обслуживает. По умолчанию это каталог, где лежит файл воркера.

- `/sw.js` → scope `/` → контролирует весь сайт;
- `/js/sw.js` → scope `/js/` → контролирует только `/js/...`, а корень — нет.

Это самая частая ошибка новичка: положили воркер рядом со сборкой, в `/static/`, и удивляются, что `fetch` не срабатывает для главной страницы.

Расширить scope выше каталога файла нельзя — иначе на хостинге пользовательских страниц один пользователь захватил бы весь домен. Но есть легальный обход: сервер может отдать файл воркера с заголовком `Service-Worker-Allowed: /`, и тогда допустимо зарегистрировать его с более широким scope:

```js
navigator.serviceWorker.register('/static/sw.js', { scope: '/' });
// Сработает только если сервер прислал Service-Worker-Allowed: /
```

Проверить, кто вами управляет, можно так: `navigator.serviceWorker.controller` — либо объект воркера, либо `null`, если страница загружена без него (обычно на самом первом визите, до `clients.claim`).

## Часть 4. Событие `fetch`

Воркер видит **все** сетевые запросы своих страниц: навигацию, подресурсы, `fetch` из кода, XHR. Не видит: запросы других воркеров, `EventSource` в некоторых случаях, и, что важно, запросы, начатые до его активации.

```js
self.addEventListener('fetch', (event) => {
  const { request } = event;

  // Мутирующие запросы через воркер не гоняем — их нельзя переигрывать
  if (request.method !== 'GET') return;

  // Чужие домены оставляем браузеру: их ответы часто opaque (см. ниже)
  const url = new URL(request.url);
  if (url.origin !== self.location.origin) return;

  event.respondWith(handle(request));
});
```

`event.respondWith(promiseOfResponse)` обязателен **синхронно**, в том же тике обработчика. Нельзя дождаться промиса и вызвать `respondWith` внутри `.then` — браузер к тому моменту уже решит, что вы отказались, и пойдёт в сеть сам. Всю асинхронность прячьте внутрь передаваемого промиса, как в примере выше.

Если промис отклонится, пользователь увидит стандартную ошибку сети — причём для навигации это будет «нет соединения» даже при живой сети. Поэтому каждый обработчик обязан иметь запасной вариант.

### Три вида ответов

**Basic** — свой origin, читается полностью.

**CORS** — чужой origin, который прислал разрешающие заголовки. Читается.

**Opaque** — чужой origin без CORS-заголовков (обычный `<img src>` на CDN, запрос в режиме `no-cors`). Такой ответ можно положить в кеш и потом отдать браузеру, но **прочитать нельзя**: статус всегда `0`, тело недоступно. Две ловушки: во-первых, вы не отличите успешный ответ от 404 и закешируете ошибку навсегда; во-вторых, opaque-ответ занимает в квоте не свой реальный размер, а фиксированную «заполненную» оценку — в Chrome это порядка семи мегабайт на ответ. Десяток закешированных иконок с чужого CDN может незаметно съесть десятки мегабайт квоты.

```js
// Кешируем только то, что можно проверить
if (response.ok && response.type !== 'opaque') {
  cache.put(request, response.clone());
}
```

### `response.clone()` — не оптимизация, а необходимость

Тело ответа — **поток**, который читается ровно один раз. Отдали ответ странице и попытались положить тот же объект в кеш — получите ошибку «body already used». Клонировать нужно **до** первого чтения.

## Часть 5. Cache Storage

### Чем отличается от HTTP-кеша

HTTP-кеш браузера управляется заголовками сервера. Вы говорите `max-age`, браузер решает, что и когда хранить, когда выселять. Заглянуть внутрь, перечислить содержимое, гарантировать наличие файла — нельзя.

Cache Storage — программируемое хранилище пар «запрос → ответ». Вы решаете, что положить, под каким ключом, когда удалить. Заголовки `Cache-Control` на него **не влияют вообще**: положили — лежит, пока не удалите вы или пока браузер не выселит весь origin по квоте.

Из этого следует и главная опасность: у записей в Cache Storage **нет срока годности**. Никто не протухнет сам. Если вы не написали код удаления — данные лежат вечно.

### Основные операции

```js
// Открыть (создаётся при первом обращении)
const cache = await caches.open('api-v3');

// Положить свой ответ
await cache.put(request, response);

// Скачать и положить (сам делает fetch)
await cache.add('/logo.svg');
await cache.addAll(['/a.css', '/b.js']);   // атомарно: всё или ничего

// Достать. Ключом может быть Request или строка URL
const hit = await cache.match('/logo.svg');

// Поискать во всех кешах origin сразу
const anyHit = await caches.match(request);

// Удалить запись и весь кеш
await cache.delete(request);
await caches.delete('api-v2');

// Перечислить имена
const names = await caches.keys();
```

Ключом по умолчанию служит полный URL **вместе со строкой запроса**. Если ваши URL содержат метки аналитики (`?utm_source=...`), каждая метка создаст отдельную запись, и попаданий не будет. Лечится опциями поиска:

```js
// Игнорировать query-строку при поиске
const hit = await cache.match(request, { ignoreSearch: true });

// Игнорировать различие GET/HEAD и заголовок Vary
const hit2 = await cache.match(request, { ignoreMethod: true, ignoreVary: true });
```

Можно строить ключи вручную — это удобно для API, где кеш должен зависеть от пользователя:

```js
// Разделяем кеш ответов по пользователю, не трогая реальный URL
const key = new Request(`${request.url}#user=${userId}`);
await cache.put(key, response.clone());
```

### Версионирование

Главный приём — **имя кеша с версией**, а не удаление записей по одной.

```js
const VERSION = 'v12';
const SHELL_CACHE = `shell-${VERSION}`;
const RUNTIME_CACHE = `runtime-${VERSION}`;
const KEEP = new Set([SHELL_CACHE, RUNTIME_CACHE]);

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    for (const name of await caches.keys()) {
      // Удаляем только свои кеши, чужие (другой команды на том же origin) не трогаем
      if (name.startsWith('shell-') || name.startsWith('runtime-')) {
        if (!KEEP.has(name)) await caches.delete(name);
      }
    }
    await self.clients.claim();
  })());
});
```

Почему чистка именно в `activate`, а не в `install`: пока новый воркер ждёт, старый ещё обслуживает открытые вкладки и его кеш нужен живым. Удалили в `install` — сломали работающие страницы. `activate` наступает, когда старый воркер уже никого не обслуживает, — это единственный безопасный момент.

Цена подхода: при смене версии весь кеш скачивается заново, даже если поменялся один файл. Для оболочки приложения это обычно приемлемо (десятки, а не тысячи файлов); для runtime-кеша картинок версию лучше не менять при каждом релизе.

### Ограничение размера

Cache Storage не умеет вытеснять записи сам. Для растущих кешей — картинок, ответов API — пишите ограничитель:

```js
// Оставляем в кеше N самых свежих записей.
// keys() возвращает ключи в порядке добавления — этим и пользуемся.
async function trimCache(cacheName, maxEntries) {
  const cache = await caches.open(cacheName);
  const keys = await cache.keys();
  if (keys.length <= maxEntries) return;
  // Удаляем самые старые
  await Promise.all(
    keys.slice(0, keys.length - maxEntries).map((k) => cache.delete(k))
  );
}

// Вызывать после записи, но не блокируя ответ:
event.waitUntil(trimCache('images-v1', 60));
```

Это приближение: «порядок добавления» — не то же самое, что «давность последнего использования». Настоящий LRU требует хранить метки времени в IndexedDB рядом с записями; библиотека Workbox так и делает. Для большинства проектов приближения хватает, и цена — пара удалённых нужных картинок — невелика.

### Сначала кеш

```js
async function cacheFirst(request, cacheName) {
  const cache = await caches.open(cacheName);
  const hit = await cache.match(request);
  if (hit) return hit;

  const response = await fetch(request);
  if (response.ok) cache.put(request, response.clone());
  return response;
}
```

Мгновенный ответ, ноль сетевых запросов при попадании. Платим тем, что обновление не приедет никогда. Годится **только** для ресурсов, у которых URL меняется при изменении содержимого: файлы с хешем в имени (`app.7f3a2c.js`), версионированные шрифты, иконки.

### Сначала сеть

```js
async function networkFirst(request, cacheName, timeoutMs = 3000) {
  const cache = await caches.open(cacheName);

  try {
    // Не ждём вечно: медленная сеть хуже офлайна для UX
    const response = await Promise.race([
      fetch(request),
      new Promise((_, reject) =>
        setTimeout(() => reject(new Error('timeout')), timeoutMs)
      ),
    ]);
    if (response.ok) cache.put(request, response.clone());
    return response;
  } catch {
    const hit = await cache.match(request);
    if (hit) return hit;
    throw new Error('нет ни сети, ни кеша');
  }
}
```

Всегда свежие данные, кеш работает страховкой. Платим задержкой на каждый запрос. Для HTML и данных, где устаревшая информация вредна (баланс, статус заказа), — правильный выбор.

Обратите внимание на таймаут: `Promise.race` возвращает первый разрешившийся промис (подробнее в статье про [промисы](./promises)). Пять секунд ожидания в метро хуже, чем мгновенно показанная вчерашняя версия.

### Устаревшее с фоновым обновлением

```js
async function staleWhileRevalidate(request, cacheName, event) {
  const cache = await caches.open(cacheName);
  const hit = await cache.match(request);

  const fresh = fetch(request).then((response) => {
    if (response.ok) cache.put(request, response.clone());
    return response;
  }).catch(() => null);

  // Держим воркер живым, пока идёт фоновое обновление
  event.waitUntil(fresh);

  // Есть кеш — отдаём мгновенно, обновление приедет к следующему разу
  return hit || fresh.then((r) => r || Response.error());
}
```

Лучший компромисс для того, что меняется, но не критично: аватары, списки категорий, обложки, конфиг. Скорость как у «сначала кеш», свежесть отстаёт ровно на один заход.

Цена, о которой часто забывают: **пользователь видит старые данные и не знает об этом**. Если данные заметно изменились, интерфейс должен как-то отреагировать — хотя бы обновить список, когда придёт свежий ответ. Иначе получается «я нажал обновить, а всё по-старому».

### Только сеть с запасным ответом

```js
self.addEventListener('fetch', (event) => {
  if (event.request.mode !== 'navigate') return;

  event.respondWith((async () => {
    try {
      // Используем предзагруженный браузером ответ, если он есть
      const preloaded = await event.preloadResponse;
      if (preloaded) return preloaded;
      return await fetch(event.request);
    } catch {
      const cache = await caches.open(SHELL_CACHE);
      return (await cache.match('/offline.html')) || Response.error();
    }
  })());
});
```

`event.preloadResponse` — результат navigation preload, который мы включили в `activate`. Он решает реальную проблему: старт спящего воркера занимает десятки миллисекунд, и всё это время запрос документа ждёт. С предзагрузкой браузер отправляет запрос параллельно со стартом воркера.

## Часть 7. Предварительное кеширование оболочки

**Оболочка приложения** (app shell) — минимальный набор файлов, которого хватает, чтобы показать каркас интерфейса без сети: HTML, критический CSS, входной JS, логотип, шрифт.

Список нельзя писать руками — при каждой сборке меняются хеши в именах. Его генерирует сборщик:

```js
// vite.config.js — плагин сам соберёт манифест и подставит в воркер
import { VitePWA } from 'vite-plugin-pwa';

export default {
  plugins: [
    VitePWA({
      strategies: 'injectManifest',
      srcDir: 'src',
      filename: 'sw.js',
      injectManifest: {
        globPatterns: ['**/*.{js,css,html,woff2}'],
        maximumFileSizeToCacheInBytes: 3 * 1024 * 1024,
      },
    }),
  ],
};
```

```js
// src/sw.js — в это место плагин подставит массив
// вида [{ url: '/assets/app.7f3a.js', revision: null }, ...]
import { precacheAndRoute } from 'workbox-precaching';
precacheAndRoute(self.__WB_MANIFEST);
```

Что тут важно понимать, даже если пишете воркер руками: манифест содержит **ревизию** каждого файла. Файлы с хешем в имени её не требуют — само имя и есть версия. Для файлов без хеша (обычно `index.html`) ревизия считается по содержимому, и при изменении html воркер перекачает только его, а не весь кеш.

Практическое ограничение: в оболочку не кладут всё подряд. Мегабайты кода, которые нужны одному экрану из двадцати, скачиваются при установке воркера и жгут трафик пользователя. Разумный размер оболочки — сотни килобайт.

## Часть 8. Обновление без потери состояния

Самая недооценённая часть. Пользователь заполняет длинную форму, вы выкатываете релиз, воркер вызывает `skipWaiting`, страница перезагружается — данные потеряны. Так делать нельзя.

Правильный порядок: **обнаружить обновление → сказать пользователю → перезагрузить только по его команде**.

```js
// sw.js — сами не торопимся, ждём сигнала от страницы
self.addEventListener('message', (event) => {
  if (event.data && event.data.type === 'SKIP_WAITING') {
    self.skipWaiting();
  }
});
```

```js
// main.js — обнаружение и уведомление
let refreshing = false;

navigator.serviceWorker.addEventListener('controllerchange', () => {
  // Сработает после skipWaiting: управление перешло к новому воркеру
  if (refreshing) return;      // защита от двойной перезагрузки
  refreshing = true;
  window.location.reload();
});

navigator.serviceWorker.register('/sw.js').then((reg) => {
  // Случай 1: обновление уже ждёт — например, юзер вернулся на вкладку
  if (reg.waiting) promptUser(reg.waiting);

  // Случай 2: обновление найдено прямо сейчас
  reg.addEventListener('updatefound', () => {
    const incoming = reg.installing;
    incoming.addEventListener('statechange', () => {
      // installed + есть controller = это именно обновление, а не первый визит
      if (incoming.state === 'installed' && navigator.serviceWorker.controller) {
        promptUser(incoming);
      }
    });
  });

  // Проверяем обновления при возврате на вкладку — релиз мог выйти,
  // пока приложение висело открытым сутки
  document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'visible') reg.update();
  });
});

function promptUser(worker) {
  showToast('Вышла новая версия', 'Обновить', () => {
    worker.postMessage({ type: 'SKIP_WAITING' });
    // Перезагрузку сделает обработчик controllerchange выше
  });
}
```

Разберём по шагам, что произойдёт после клика:

1. Страница шлёт `SKIP_WAITING` ожидающему воркеру.
2. Воркер вызывает `skipWaiting()` и переходит в `activating`, затем `activated`.
3. Он забирает управление страницей — браузер выпускает событие `controllerchange`.
4. Обработчик перезагружает страницу; новый документ загружается уже под новым воркером.

Флаг `refreshing` не декоративный: при нескольких открытых вкладках `controllerchange` придёт в каждую, и без защиты можно поймать цикл перезагрузок.

Проверка `navigator.serviceWorker.controller` в `statechange` тоже обязательна. Без неё вы покажете «вышла новая версия» на самом первом визите пользователя, когда воркер просто установился впервые.

Если приложение умеет сохранять черновик, лучший вариант — не перезагружать вовсе: сохранить состояние в IndexedDB, перезагрузиться, восстановить. Но минимально приличное поведение — спросить.

## Часть 9. Типичные грабли

**Закешированный HTML — вечный старый сайт.** Самая опасная ошибка. Положили `index.html` в кеш по стратегии «сначала кеш» — пользователь получает старую разметку со ссылками на старые файлы всегда. Даже если вы почините воркер, старый воркер уже установлен у пользователя и отдаёт старый HTML, где нет кода регистрации нового.

Профилактика: HTML — только «сначала сеть». Лечение, если уже случилось, — «воркер-убийца»: выкатить по адресу `sw.js` файл, который сносит сам себя.

```js
// sw.js — аварийный вариант: снимает регистрацию и чистит кеши
self.addEventListener('install', () => self.skipWaiting());

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    for (const name of await caches.keys()) await caches.delete(name);
    await self.registration.unregister();
    const clients = await self.clients.matchAll({ type: 'window' });
    for (const client of clients) client.navigate(client.url);
  })());
});
```

Он сработает только у тех, чей браузер дойдёт до проверки `sw.js`, — поэтому и говорят «навсегда застряли»: часть аудитории вернётся, часть нет.

**Кеш растёт и съедает квоту.** Runtime-кеш картинок без ограничителя за месяц активного использования наберёт сотни мегабайт. Когда квота кончается, браузер выселяет данные origin — и уносит с собой IndexedDB, где лежат черновики пользователя. Ставьте `trimCache`, следите за `navigator.storage.estimate()` (см. [хранилища и квоты](./storage-and-quotas)).

**Разработка с включённым воркером.** Правите код, обновляете — ничего не меняется. Включите в DevTools галочки «Update on reload» и «Bypass for network» на вкладке Application. Ещё лучше — вообще не регистрировать воркер в дев-режиме:

```js
if (import.meta.env.PROD && 'serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}
```

**Кеширование ответов с ошибкой.** `fetch` не отклоняется на 404 и 500 — он отклоняется только при сетевом сбое. Без проверки `response.ok` вы закешируете страницу ошибки и будете отдавать её вечно.

**Ответы с `Vary`.** Если сервер варьирует ответ по `Accept-Language` или `Accept-Encoding`, `cache.match` может не найти запись, которая физически там лежит. Разбирайтесь с `ignoreVary` осознанно: игнорировать заголовок легко, но так вы можете отдать французу английскую версию.

**Диапазонные запросы.** Видео и аудио запрашиваются по кускам через заголовок `Range`. Наивный воркер отдаст на такой запрос полный файл со статусом 200, и `<video>` в Safari сломается. Либо пропускайте такие запросы мимо воркера, либо используйте готовый обработчик из Workbox.

## Часть 10. Отладка

Панель **Application → Service Workers** в DevTools:

- список воркеров с состояниями; кнопки `skipWaiting`, `Unregister`, `Update`;
- **Update on reload** — при каждой перезагрузке принудительно ставит новый воркер, минуя `waiting`. Только для разработки;
- **Bypass for network** — запросы идут мимо воркера. Способ проверить, воркер ли виноват;
- **Offline** в панели Network — проверка офлайн-сценария по-настоящему;
- ссылка на консоль воркера: у него **своя** консоль, `console.log` из `sw.js` в консоли страницы не появится. Это регулярно сбивает с толку.

**Application → Cache Storage** показывает все кеши и записи с заголовками. Здесь видно, не сложилось ли у вас пять версий одного кеша.

Служебная страница `chrome://serviceworker-internals` показывает воркеры всех сайтов и позволяет их принудительно останавливать — полезно, когда воркер «завис» в непонятном состоянии.

## Часть 11. Когда воркера нет

Service Worker недоступен: в приватном режиме Safari, в некоторых корпоративных сборках браузеров, при отключённых куках и хранилищах, на HTTP, в старых WebView.

Из этого следует железное правило: **воркер — это улучшение, а не фундамент**. Приложение обязано полностью работать без него. Практически:

- не переносите в воркер логику, от которой зависит корректность (авторизация, подпись запросов, преобразование данных);
- всегда проверяйте `'serviceWorker' in navigator` перед регистрацией;
- не считайте наличие кеша гарантией — `caches.match` вернёт `undefined`, и код должен это пережить;
- офлайн-функции интерфейса включайте по факту: `navigator.onLine` плюс реальная проверка запросом, потому что `onLine` лишь говорит, что есть сетевой интерфейс, а не что интернет работает.

## Что спросят на интервью

**Что такое Service Worker простыми словами?** Скрипт-прокси, работающий в отдельном потоке между страницами сайта и сетью. Может отвечать на запросы из кеша, живёт независимо от вкладок, засыпает и просыпается на события.

**Опишите жизненный цикл.** Регистрация → `installing` (событие `install`, наполняем кеш) → `waiting` (пока жив хоть один клиент старого воркера) → `activating` (событие `activate`, чистим старые кеши) → `activated`.

**Почему новый воркер ждёт?** Чтобы все открытые вкладки одновременно обслуживались одной версией воркера. Иначе старая страница получала бы ответы, сформированные логикой новой версии.

**Что делают `skipWaiting` и `clients.claim` и чем опасны?** `skipWaiting` пропускает очередь и активирует воркер немедленно; опасен тем, что работающая старая страница внезапно начинает получать ресурсы новой версии — ленивые чанки могут не найтись. `clients.claim` подчиняет уже открытые незахваченные страницы; опасен несогласованностью на первом визите. `claim` в `activate` обычно безопасен, `skipWaiting` — по команде пользователя.

**Обычная перезагрузка активирует новый воркер?** Нет. Новый документ начинает грузиться до смерти старого, момента без клиентов не возникает. Нужно закрыть все вкладки или вызвать `skipWaiting`.

**Чем Cache Storage отличается от HTTP-кеша?** HTTP-кешем управляют заголовки сервера, содержимое непрозрачно, срок жизни задаёт `Cache-Control`. Cache Storage полностью программируемый, заголовки на него не влияют, срока годности нет — чистить обязаны вы.

**Где чистить старые кеши и почему именно там?** В `activate`. В этот момент старый воркер уже никого не обслуживает; чистка в `install` сломала бы работающие вкладки, потому что старый воркер ещё жив.

**Назовите стратегии и когда какая.** Сначала кеш — файлы с хешем в имени. Сначала сеть — HTML и критичные данные. Устаревшее с фоновым обновлением — аватары, справочники. Только сеть с запасным ответом — навигация с офлайн-страницей.

**Почему воркер в `/js/sw.js` не контролирует корень?** Scope по умолчанию — каталог файла. Расширить можно только заголовком `Service-Worker-Allowed` от сервера.

**Что такое opaque-ответ и чем он опасен в кеше?** Ответ с чужого origin без CORS-заголовков: статус 0, тело не читается. Нельзя отличить успех от ошибки, и в квоте он занимает завышенную фиксированную оценку.

**Как сообщить пользователю о новой версии?** Слушать `updatefound` и `statechange`, при `installed` вместе с существующим `controller` показать уведомление; по клику отправить воркеру сообщение, тот вызывает `skipWaiting`, страница перезагружается по `controllerchange` с защитой от цикла.

**Зачем `response.clone()`?** Тело ответа — поток, читается один раз. Один экземпляр отдаём странице, клон кладём в кеш.

## Коротко, для повторения

1. Service Worker — программируемый прокси между страницами и сетью. Один на весь scope, работает без вкладок, засыпает — состояние в переменных не хранить.
2. Жизненный цикл: register → install → waiting → activate → activated. Ожидание гарантирует, что все вкладки под одной версией.
3. Reload не переключает воркер. Переключают закрытие всех вкладок или `skipWaiting`.
4. `skipWaiting` — только по команде пользователя. `clients.claim` в `activate` — обычно безопасно.
5. Scope = каталог файла воркера. Шире — только с заголовком `Service-Worker-Allowed`.
6. `event.respondWith` вызывается синхронно; вся асинхронность внутри промиса. `response.clone()` перед записью в кеш.
7. Cache Storage не подчиняется `Cache-Control` и ничего не удаляет сам. Версионируйте имена кешей и чистите в `activate`.
8. HTML кешируйте только «сначала сеть», иначе рискуете навечно запереть пользователя на старой версии.
9. Проверяйте `response.ok` и тип ответа: opaque и ошибки в кеш не кладём.
10. Воркер — улучшение поверх работающего приложения, а не его фундамент. Без воркера всё должно работать.
