# Поиск и подсказки: гонки, кеш и клавиатура

Поле поиска с выпадающими подсказками — задача, которую дают почти на каждом интервью и почти в каждом продукте пишут заново. Выглядит она на пять минут: слушаем ввод, дёргаем ручку, рисуем список. На деле в ней сходятся асинхронность, гонки, кеширование, машина состояний, клавиатурная навигация и доступность — то есть примерно всё, чем отличается сеньор от джуна.

Разберём её целиком: от задержки перед запросом до `aria-activedescendant` и морфологии русского языка. Соседние разборы: [бесконечные списки](./infinite-list-and-virtualization) — что делать, когда найденного слишком много, и [формы](./forms-and-validation) — где те же гонки всплывают в асинхронной валидации.

## Часть 1. Из чего на самом деле состоит задача

Наивный код умещается в шесть строк:

```js
input.addEventListener('input', async e => {
  const response = await fetch('/api/suggest?q=' + e.target.value);
  render(await response.json());
});
```

Что здесь сломано:

1. **Запрос на каждый символ.** Человек печатает 5–7 символов в секунду — это 5–7 запросов в секунду с одного поля.
2. **Гонка.** Ответы приходят в произвольном порядке, поздний ответ на старый запрос затирает актуальный.
3. **Нет состояний.** Пользователь не понимает, идёт загрузка, ничего не нашлось или всё упало.
4. **Значение не экранировано.** Символы `&` и `#` в запросе поломают URL.
5. **Клавиатуры нет.** По подсказкам нельзя ходить стрелками, нельзя закрыть список, скринридер о списке не знает.
6. **Кеша нет.** Пользователь стёр символ — снова идём в сеть за тем, что уже показывали секунду назад.

Дальше — по пунктам, с ценой каждого решения.

## Часть 2. Дебаунс, троттлинг и минимальная длина

**Дебаунс** (debounce, «устранение дребезга») — приём, при котором функция вызывается не сразу, а через паузу после последнего обращения. Каждый новый вызов сбрасывает таймер. Смысл: «сделай, когда человек перестанет печатать».

**Троттлинг** (throttle, «ограничение частоты») — вызывать не чаще, чем раз в N миллисекунд, равномерно.

Для поиска нужен именно дебаунс, и причина не в экономии, а в смысле. Промежуточные значения поля бесполезны: «мос», «моск», «москв» не нужны никому, нужна «москва». Троттлинг же гарантированно отправит часть промежуточных запросов — он выбирает моменты по времени, а не по смыслу. Троттлинг уместен там, где промежуточные значения содержательны: скролл, изменение размера окна, перетаскивание.

### Как выбрать задержку

Разумный диапазон — от 150 до 300 миллисекунд. Границы задаются двумя вещами.

**Снизу — скоростью печати.** Интервал между символами у уверенно печатающего человека — 100–150 мс. Задержка меньше 150 мс не склеит соседние нажатия и не сэкономит почти ничего.

**Сверху — восприятием.** Примерно со 100 мс задержка перестаёт быть незаметной, а после 300 мс интерфейс ощущается вялым. Если ответ сервера сам по себе занимает 200 мс, то дебаунс в 300 даёт полсекунды до первой подсказки — это уже много.

Практический ориентир: 200 мс при быстром бэкенде, 250–300 при медленном или дорогом. И честный ответ на интервью — «замерить: посмотреть распределение интервалов между нажатиями у реальных пользователей и долю запросов, которые дебаунс успевает отменить».

Отдельный приём — **срабатывание по переднему фронту** (leading edge) для первого символа: первый запрос уходит немедленно, остальные — с задержкой. Пользователь видит реакцию сразу, а поток запросов всё равно ограничен.

### Минимальная длина запроса

Ниже двух-трёх символов подсказки бесполезны: по «а» найдётся половина базы, а ранжировать их нечем. Плюс каждый однобуквенный запрос — это самая тяжёлая для сервера выборка.

Порог зависит от домена: для поиска по товарам разумно три символа, для поиска по коллегам в компании из ста человек хватит одного. Для языков с иероглифами порог в три символа абсурден — там один символ уже слово.

Важно: **при слишком коротком запросе показывать не пустоту, а что-то полезное** — недавние запросы, популярное, историю. Пустой выпадающий список выглядит как поломка.

### Чего дебаунс не делает

Частая ошибка на интервью: «дебаунс решает проблему гонок». Не решает. Дебаунс лишь уменьшает число запросов. Как только пользователь сделал паузу и запрос ушёл, а потом допечатал — в полёте два запроса, и порядок их возвращения дебаунс не контролирует.

```js
// Дебаунс с возможностью отмены — отмена нужна при размонтировании
function debounce(fn, delay) {
  let timer = null;
  const wrapped = (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
  wrapped.cancel = () => clearTimeout(timer);
  // Пользователь нажал Enter — ждать паузу бессмысленно, выполняем немедленно
  wrapped.flush = (...args) => { clearTimeout(timer); fn(...args); };
  return wrapped;
}
```

## Часть 3. Гонки запросов

Это главная тема задачи и самое частое место, где кандидат спотыкается.

**Гонка** (race condition) — ситуация, когда результат зависит от того, какая из параллельных операций закончится первой, а порядок не гарантирован. Корень тут в том, что промис не отменяется и не помнит, актуален ли он ещё; подробности про порядок выполнения — в статьях про [промисы](./promises) и [событийный цикл](./browser-rendering-event-loop).

Сценарий: пользователь печатает «аб», запрос уходит. Через 60 мс он допечатывает «в» — уходит второй запрос, за «абв». Первый запрос попал на холодный кеш и отвечает 400 мс, второй — 90 мс. Ответ на «абв» приходит первым, рисуется. Потом приходит ответ на «аб» и **затирает** его. В поле написано «абв», а в списке — подсказки для «аб».

Коварство в том, что баг **невоспроизводим на локальной машине**: там сервер отвечает за 5 мс и порядок почти всегда правильный. Ломается всё на медленной мобильной сети у пользователя.

Решений три, и знать надо все три — но выбирать первое.

### Решение 1. Отмена через AbortController

`AbortController` — объект с сигналом, который передаётся в `fetch`. Вызов `abort()` рвёт запрос: промис `fetch` отклоняется ошибкой с именем `AbortError`, а браузер закрывает соединение.

```js
let controller = null;

async function search(query) {
  controller?.abort();                    // старый запрос больше не нужен
  controller = new AbortController();
  try {
    const response = await fetch(url(query), { signal: controller.signal });
    if (!response.ok) throw new Error('HTTP ' + response.status);
    return await response.json();
  } catch (error) {
    if (error.name === 'AbortError') return null;   // это не ошибка, а наше решение
    throw error;
  }
}
```

Почему это лучший вариант:

- **Позднего ответа физически не будет.** Не «мы его проигнорируем», а «он не придёт». Ошибка невозможна по построению, а не по договорённости.
- **Экономится сеть.** На мобильной связи это заметно: неотменённые запросы качают тело ответа, которое никто не прочитает.
- **Освобождаются соединения.** По HTTP/1.1 браузер держит к одному домену около шести параллельных соединений. Быстрая печать легко забивает их мусорными запросами, и настоящий, нужный запрос ждёт очереди. С HTTP/2 лимит другой, но пропускная способность всё равно конечна.
- **Сервер может прекратить работу.** Хорошо написанный бэкенд увидит разрыв и не станет добивать тяжёлый поиск.

Чем платим: `AbortError` надо отличать от настоящей ошибки, иначе интерфейс покажет «что-то пошло не так» при каждом нажатии клавиши. И отмена **не гарантирует**, что сервер не выполнил работу — если запрос что-то меняет, отмена не отменяет изменение. Для поиска это неважно (запрос читающий), но привычку различать стоит завести.

### Решение 2. Проверка актуальности по последнему запросу

Запрос не отменяем, но перед отрисовкой сверяем, для того ли значения пришёл ответ.

```js
let latestQuery = '';

async function search(query) {
  latestQuery = query;
  const data = await fetchJson(url(query));
  if (query !== latestQuery) return;      // пока ходили, пользователь напечатал ещё
  render(data);
}
```

Просто и работает. Цена: сеть и сервер всё равно нагружены, соединения заняты, а сравнение по значению ломается в неочевидном случае — пользователь напечатал «абв», стёр до «аб», и старый ответ на «аб» внезапно снова стал «актуальным», хотя он мог быть уже устаревшим.

### Решение 3. Порядковый номер

Каждому запросу выдаём растущий номер и принимаем результат, только если его номер больше последнего принятого.

```js
let issued = 0;
let accepted = 0;

async function search(query) {
  const id = ++issued;
  const data = await fetchJson(url(query));
  if (id <= accepted) return;             // уже показали более свежий результат
  accepted = id;
  render(data);
}
```

Это самый строгий вариант: он корректен даже при повторяющихся значениях запроса и не путается, когда пользователь вернулся к прежнему тексту. Расход тот же, что у второго способа.

### Как делать на практике

Отмена плюс номер как страховка. Отмена решает 99% случаев, номер закрывает остаток: между `abort()` и реальным прекращением обработки есть окно, а в некоторых средах (собственный транспорт, WebSocket, кеш-слой перед `fetch`) отмены может не быть вовсе.

```js
export function createSearcher(fetchSuggestions) {
  let controller = null;
  let issued = 0;
  let accepted = 0;

  async function run(query) {
    controller?.abort();
    controller = new AbortController();
    const id = ++issued;

    try {
      const items = await fetchSuggestions(query, controller.signal);
      if (id <= accepted) return null;    // страховка: результат уже устарел
      accepted = id;
      return items;
    } catch (error) {
      if (error.name === 'AbortError') return null;
      throw error;
    }
  }

  run.cancel = () => controller?.abort();
  return run;
}
```

В React отмена естественно ложится на функцию очистки эффекта — она вызывается перед следующим запуском эффекта и при размонтировании:

```jsx
useEffect(() => {
  if (query.length < 2) { setItems([]); return; }
  const controller = new AbortController();
  setStatus('loading');

  fetchSuggestions(query, controller.signal)
    .then(items => { setItems(items); setStatus('ready'); })
    .catch(error => { if (error.name !== 'AbortError') setStatus('error'); });

  return () => controller.abort();       // ушли с запроса — рвём его
}, [query]);
```

Здесь `query` — уже задебаунсенное значение, а не то, что в поле прямо сейчас. Эти два состояния надо держать раздельно: в поле показываем сырое значение (иначе ввод будет тормозить), запрос делаем по отложенному.

## Часть 4. Кеш

Подсказки — почти идеальный кандидат на кеширование: один и тот же префикс запрашивается снова и снова, а ответ мал.

```js
const cache = new Map();                  // нормализованный запрос -> массив подсказок
const inFlight = new Map();               // нормализованный запрос -> промис

function suggest(query, signal) {
  const key = normalize(query);
  if (cache.has(key)) return Promise.resolve(cache.get(key));
  if (inFlight.has(key)) return inFlight.get(key);      // такой запрос уже летит

  const promise = fetchSuggestions(key, signal)
    .then(items => {
      cache.set(key, items);
      if (cache.size > 100) cache.delete(cache.keys().next().value);  // грубый LRU
      return items;
    })
    .finally(() => inFlight.delete(key));

  inFlight.set(key, promise);
  return promise;
}
```

Главный выигрыш не в экономии трафика, а в **ощущении мгновенности при возврате назад**. Пользователь напечатал «москва», стёр до «моск» — результат для «моск» уже лежит в памяти и рисуется в том же кадре, без единого запроса и без спиннера. Это самое заметное улучшение из всех, что здесь описаны.

Второй выигрыш — **дедупликация**: два компонента на странице просят одно и то же, а запрос уходит один.

`Map` сохраняет порядок вставки, поэтому «удалить самый старый ключ» — это одна строка. Настоящий LRU (least recently used, «вытесняем то, к чему дольше всего не обращались») требует переставлять ключ при каждом чтении: `cache.delete(key); cache.set(key, value)`.

**Когда кеш вреден:**

- **Персонализованная выдача.** Если подсказки зависят от пользователя, кеш переживёт смену аккаунта и покажет чужие данные. При выходе из аккаунта кеш обязан очищаться.
- **Быстро меняющиеся данные.** Поиск по списку заказов, который меняется каждую минуту: показывать удалённый заказ хуже, чем сходить в сеть.
- **Приватность.** История поиска по внутренней базе, лежащая в памяти вкладки, — обычно приемлемо; та же история в `localStorage` — уже вопрос к безопасности.
- **Память.** Без ограничения размера кеш подсказок по длинной сессии вырастает неограниченно.

Компромисс между свежестью и скоростью — **stale-while-revalidate**: сразу показываем содержимое кеша, параллельно идём за свежим и обновляем, если ответ отличается. Пользователь не ждёт, а данные не протухают. Цена — содержимое списка может измениться под курсором, поэтому при таком подходе нельзя терять выделенный элемент.

**Поле пустое, фокус есть.** Не показывать пустоту. Показать недавние запросы этого пользователя, популярные категории, подсказку «ищите по номеру заказа или фамилии». Это самое дешёвое место, где интерфейс объясняет, что он вообще умеет искать.

**Запрос короче порога.** Тот же экран, что и пустое поле, плюс, если нужно, мягкая подсказка «введите ещё один символ». Ошибкой это оформлять нельзя: пользователь не сделал ничего плохого.

**Идёт загрузка.** Две важные детали.

Во-первых, **не показывать индикатор мгновенно**. Если ответ приходит за 120 мс, спиннер успеет мигнуть и создать ощущение дёрганого интерфейса. Задержка перед показом индикатора в 200–300 мс убирает мигание на быстрых ответах.

Во-вторых, **не стирать старые результаты**. Список, который очищается на каждое нажатие и заполняется заново, мигает. Правильнее оставить прошлый список, приглушив его или наложив тонкий индикатор: содержимое обновится на месте.

**Ничего не найдено.** Пустой блок с надписью «ничего не найдено» — минимум. Лучше — сказать, что искали (`Ничего не найдено по запросу «абырвалг»`), и предложить выход: убрать фильтры, поискать по другому полю, создать новую запись прямо отсюда.

**Ошибка.** Тишина недопустима. Короткое сообщение и кнопка «повторить», которая перезапускает тот же запрос. Отличать `AbortError` от настоящей ошибки — обязательно, иначе поле будет краснеть на каждый второй символ.

Отдельно про **сброс**: крестик очистки должен возвращать поле в состояние «пустое с фокусом», а не просто стирать текст и оставлять открытым старый список. И фокус после очистки остаётся в поле — иначе пользователь вынужден целиться мышью второй раз.

## Часть 6. Клавиатура и доступность

Стандартный паттерн для «поле плюс список вариантов» называется **combobox**. Это не тег, а набор ролей и атрибутов, по которым вспомогательные технологии понимают конструкцию.

```html
<label for="q">Поиск по заказам</label>
<input
  id="q"
  role="combobox"
  aria-expanded="true"
  aria-controls="q-list"
  aria-autocomplete="list"
  aria-activedescendant="q-opt-2"
  autocomplete="off"
>
<ul id="q-list" role="listbox">
  <li id="q-opt-1" role="option" aria-selected="false">Заказ 1042</li>
  <li id="q-opt-2" role="option" aria-selected="true">Заказ 1043</li>
</ul>
<div aria-live="polite" class="visually-hidden">Найдено 2 варианта</div>
```

Что здесь важно:

- **`aria-expanded`** — открыт ли список прямо сейчас. Меняется вместе с реальной видимостью, иначе скринридер врёт.
- **`aria-controls`** указывает на список, **`aria-activedescendant`** — на выделенный вариант **по идентификатору**.
- **Реальный фокус остаётся в поле.** Это ключевая мысль паттерна: если перемещать настоящий фокус на элементы списка, из поля пропадёт каретка, а ввод перестанет работать. Поэтому выделение — «виртуальное»: фокус в поле, а `aria-activedescendant` сообщает, какой вариант считается активным.
- **`aria-live="polite"`** в скрытом блоке объявляет число найденных вариантов. Без него пользователь скринридера просто не узнает, что под полем что-то появилось.
- **`autocomplete="off"`** на поле не даёт браузеру наложить своё выпадающее меню на ваше.

### Клавиши

| Клавиша | Поведение |
| --- | --- |
| Стрелка вниз | открыть список, если закрыт; иначе сдвинуть выделение вниз |
| Стрелка вверх | сдвинуть выделение вверх |
| Enter | выбрать выделенный вариант; если ничего не выделено — искать по введённому тексту |
| Escape | первое нажатие закрывает список, второе очищает поле |
| Tab | закрыть список и уйти на следующий элемент, не выбирая вариант |
| Home, End | в начало и конец текста в поле, а не списка |

Три детали, которые обычно забывают.

**Зацикливание.** Со стрелкой вниз на последнем варианте: либо переход к первому, либо остановка — но обязательно одинаково в обе стороны. Отдельное состояние «ничего не выделено» полезно: с него начинается список, и в него можно вернуться, чтобы Enter искал по сырому тексту.

**Прокрутка выделенного в зону видимости.** Список подсказок обычно ограничен по высоте. Двигая выделение стрелками, надо звать `element.scrollIntoView({ block: 'nearest' })`, иначе оно уедет за границу.

**Escape в два шага** — общепринятое поведение: сначала закрыть список, потом очистить. Одно нажатие, стирающее текст, злит: пользователь хотел просто убрать список.

### Почему mousedown, а не click

Классическая ловушка. Пользователь кликает мышью по варианту в списке. Порядок событий такой:

1. `mousedown` на варианте;
2. **`blur` на поле ввода** — фокус уходит;
3. `mouseup`;
4. `click`.

Если список скрывается по `blur` — а он почти всегда так и делает, — то к моменту `click` элемента уже нет в DOM. Клик не срабатывает, выбор не происходит. Баг воспроизводится только мышью, поэтому на клавиатуре разработчик его не видит.

Два решения. Первое — вешать выбор на `mousedown`, который приходит до `blur`. Второе, аккуратнее, — гасить сам `blur`:

```jsx
<li
  role="option"
  // preventDefault на mousedown не даёт полю потерять фокус
  onMouseDown={event => event.preventDefault()}
  onClick={() => select(option)}
>
  {option.label}
</li>
```

Второй вариант лучше тем, что сохраняет привычную семантику: `click` не срабатывает, если пользователь нажал кнопку на варианте, увёл мышь и отпустил в стороне. При выборе по `mousedown` такой отмены не будет.

И общее правило: закрытие списка по `blur` лучше отложить на следующий тик или проверять, куда именно ушёл фокус (`event.relatedTarget`), — так конструкция переживает клики по собственным внутренним элементам вроде кнопки очистки.

### Подсветка совпадения

Совпавшую часть подсвечивают, чтобы было видно, почему вариант найден. Соблазн написать так:

```js
// Никогда так не делайте
item.innerHTML = label.replace(query, '<mark>' + query + '</mark>');
```

Здесь две дыры сразу. Во-первых, `innerHTML` с данными, пришедшими с сервера, — это XSS: в названии может оказаться разметка. Во-вторых, `replace` со строкой ищет только первое вхождение и не учитывает регистр, а если собирать из запроса регулярное выражение, символы вроде `.` или `(` его сломают.

Правильно — резать строку по индексам и отдавать каркасу массив узлов, где текст остаётся текстом:

```jsx
function Highlight({ text, query }) {
  const at = text.toLowerCase().indexOf(query.toLowerCase());
  if (!query || at === -1) return text;
  return (
    <>
      {text.slice(0, at)}
      <mark>{text.slice(at, at + query.length)}</mark>
      {text.slice(at + query.length)}
    </>
  );
}
```

Тег `mark` выбран не случайно: он несёт смысл «выделено как релевантное», а не только цвет.

### Сенсорные экраны

На телефоне экранная клавиатура занимает половину экрана, и список подсказок обязан помещаться в оставшуюся часть — иначе пользователь не увидит ни одного варианта. Практически это значит: список открывается вниз, если места хватает, и вверх, если нет; количество видимых вариантов ограничено; выбор одним касанием, без «наведения».

## Часть 7. Серверная сторона в двух словах

Знать это на фронтенде полезно: половина вопросов про подсказки на системном интервью — про то, почему они такие быстрые.

**Подсказки почти всегда одинаковы для всех.** По префиксу «моск» топ-10 вариантов не зависит от того, кто спрашивает. А раз ответ одинаковый, его можно закешировать один раз на всех — на CDN, то есть на сети серверов, стоящих ближе к пользователю, чем ваш бэкенд.

Дальше работает распределение запросов: коротких префиксов мало, а обращений к ним очень много. Первые три-четыре символа покрывают подавляющее большинство запросов, поэтому попадание в кеш по префиксу оказывается очень высоким, а до основного сервиса доходит небольшая доля трафика. Отсюда типичный набор решений:

- ответ кешируется по URL с коротким временем жизни (`Cache-Control: public, max-age=60`);
- запрос делается предсказуемым: нижний регистр, обрезка пробелов, фиксированный порядок параметров — иначе `MOSK` и `mosk` станут разными ключами кеша;
- **персонализация выносится из общего ответа.** Общие подсказки кешируются, личная история подмешивается на клиенте или отдельным лёгким запросом. Если подмешать личное в общий ответ, кеш перестаёт работать, а заголовок `Vary` по идентификатору пользователя делает его бессмысленным.

Внутри сервиса за подсказками обычно стоит структура, умеющая искать по префиксу: **префиксное дерево** (trie) — дерево, где путь от корня к узлу составляет префикс, а в узле лежат лучшие продолжения; или поисковый движок с индексом по n-граммам. Ранжирование — по частоте запроса, свежести и совпадению с начала слова.

И почти всегда есть **ограничение частоты** (rate limit): поле поиска — самая простая точка для случайной DDoS-атаки собственным клиентом с поломанным дебаунсом.

## Часть 8. Когда данные уже на клиенте

Отдельный, очень частый случай: список из двухсот проектов, тысячи сотрудников, справочник валют — данные уже загружены, ходить некуда. Тогда весь поиск локальный, и главное здесь — не скорость, а **совпадение ожиданий**.

### Нормализация

Пользователь печатает не то, что записано в базе. Минимальный набор приведений:

```js
function normalize(text) {
  return text
    .toLowerCase()
    .normalize('NFD')                     // разложить символы с диакритикой на базу и знак
    .replace(/\p{M}/gu, '')               // убрать знаки: é становится e
    .replace(/ё/g, 'е')                   // страховка: ё и е ищутся как одно

    .replace(/[^\p{L}\p{N}]+/gu, ' ')     // дефисы, кавычки, точки — в пробел
    .trim();
}
```

Каждая строчка — из реального бага. Разложение `NFD` разбивает «ü» на «u» и отдельный знак, а `\p{M}` этот знак выбрасывает — так «Müller» находится по «muller», а «Фёдоров» по «федоров» (в русском «ё» и «е» пользователи не различают). Без замены пунктуации «ООО «Ромашка»» не найдётся по «ромашка».

Порядок важен: `\p{M}` работает только после `normalize('NFD')`, потому что до разложения диакритика зашита внутрь символа и отдельным знаком не является.

### Простой индекс

Перебор массива с `includes` работает до нескольких тысяч элементов. Дальше строят **инвертированный индекс** — словарь «часть слова, где встречается».

```js
function buildIndex(items, getText) {
  const index = new Map();                // префикс -> Set идентификаторов
  for (const item of items) {
    for (const word of normalize(getText(item)).split(' ')) {
      // Префиксы от 2 символов: по ним ищем «начинается с»
      for (let length = 2; length <= Math.min(word.length, 12); length++) {
        const prefix = word.slice(0, length);
        if (!index.has(prefix)) index.set(prefix, new Set());
        index.get(prefix).add(item.id);
      }
    }
  }
  return index;
}

function search(index, query) {
  const words = normalize(query).split(' ').filter(w => w.length >= 2);
  if (!words.length) return null;
  // Пересечение множеств: подходят элементы, где встретились все слова запроса
  return words
    .map(word => index.get(word) ?? new Set())
    .reduce((a, b) => new Set([...a].filter(id => b.has(id))));
}
```

Цена: индекс занимает память (примерно десять записей на слово) и строится за один проход, зато поиск становится обращением к словарю вместо перебора. Строить его надо один раз при загрузке данных, а не на каждый ввод — типичная ошибка.

**Ранжирование** важнее полноты. Совпадение с начала строки должно быть выше совпадения в середине, совпадение в названии — выше совпадения в описании, точное совпадение — в самом верху. Список, где искомое лежит на седьмой позиции, воспринимается как «поиск не работает».

### Морфология русского языка

Русский язык флективный: одно слово имеет десятки форм («договор», «договора», «договору», «договорами»). Пользователь ищет «договоры», а в базе «договор» — и ничего не находится.

Полное решение — **лемматизация**, приведение слова к словарной форме через морфологический словарь. На клиенте это дорого: словарь весит мегабайты.

Дешёвое решение — **стемминг**, отсечение окончаний по правилам. Классический алгоритм Портера для русского отбрасывает типовые окончания и суффиксы; библиотека занимает несколько килобайт. Он грубоват (может склеить неродственные слова), но для поиска это чаще плюс, чем минус.

Самое дешёвое и на практике почти достаточное — **поиск по префиксу**. Если искать «начинается с» вместо «равно», то «договор» найдёт и «договоры», и «договорами». Проблема остаётся только с чередованиями в корне и с формами, где меняется начало слова, — таких немного.

Два соседних приёма, которые сильно повышают ощущение «умного поиска»:

- **Раскладка.** Пользователь забыл переключить язык и напечатал `ghbdtn` вместо «привет». Отображение раскладки — таблица на 66 символов, ищем по обоим вариантам.
- **Транслитерация.** «Ivanov» должен находить «Иванов».

А вот **исправление опечаток** (поиск по расстоянию Левенштейна) на клиенте обычно не окупается: сложность растёт, а выигрыш заметен только на больших коллекциях. Это работа для сервера.

## Что спросят на интервью

**Дебаунс или троттлинг для поля поиска?** Дебаунс: нужны не промежуточные значения, а последнее — то, на котором пользователь остановился. Троттлинг равномерно пропускает часть промежуточных запросов и для поиска бессмысленен; он уместен на скролле и ресайзе.

**Какую задержку взять?** 150–300 мс. Меньше — не склеивает соседние нажатия (интервал печати 100–150 мс), больше — интерфейс ощущается вялым, особенно с учётом времени ответа сервера.

**Решает ли дебаунс гонки?** Нет, только уменьшает число запросов. Как только два запроса оказались в полёте одновременно, порядок ответов не гарантирован.

**Как бороться с гонками?** Три способа: отмена через `AbortController`, проверка актуальности по последнему значению, порядковый номер запроса. Отмена лучше всех — позднего ответа физически не будет, экономится трафик, освобождаются соединения, сервер может прекратить работу. Номер полезен как страховка.

**Что делать с `AbortError`?** Отличать от настоящей ошибки и молча игнорировать: это наше собственное решение, а не сбой.

**Когда кеш подсказок вреден?** При персонализованной выдаче (переживёт смену аккаунта), при быстро меняющихся данных, при требованиях к приватности. И всегда нужен предел размера.

**Почему выбор мышью вешают на `mousedown`?** Потому что `blur` на поле приходит раньше `click`, а список закрывается по `blur` — к моменту клика элемента уже нет. Либо выбирать по `mousedown`, либо гасить `preventDefault` на нём, чтобы фокус не уходил.

**Как сделать список подсказок доступным?** Паттерн combobox: `role="combobox"` на поле, `aria-expanded`, `aria-controls`, `aria-activedescendant` на выделенный вариант, `role="listbox"` и `role="option"` на списке, объявление числа найденных через `aria-live`. Реальный фокус остаётся в поле — иначе пропадёт каретка.

**Почему подсказки такие быстрые?** Они одинаковы для всех, поэтому кешируются на CDN по префиксу, а короткие префиксы дают очень высокий процент попаданий. Персонализация выносится из общего ответа, иначе кеш перестаёт работать.

**Как искать по русскому тексту на клиенте?** Нормализовать (регистр, диакритика, «ё» в «е», пунктуация), искать по префиксу вместо точного совпадения — это дешёвая замена морфологии, — при необходимости добавить стемминг и учёт раскладки клавиатуры.

## Коротко, для повторения

1. Задача поля поиска — это дебаунс, гонки, кеш, машина состояний, клавиатура и доступность. Всё сразу.
2. Дебаунс, а не троттлинг: нужен последний ввод, а не равномерная выборка. 150–300 мс, минимальная длина запроса 2–3 символа.
3. Дебаунс не решает гонки. Как только в полёте два запроса, порядок ответов не определён.
4. Гонки лечатся отменой (`AbortController`), проверкой актуальности или порядковым номером. Отмена лучше: позднего ответа не будет вовсе, а сеть и соединения свободны.
5. `AbortError` — не ошибка. Отличать и игнорировать.
6. Кеш по нормализованному запросу плюс словарь запросов в полёте: мгновенный отклик на Backspace и никаких дублирующихся запросов.
7. Состояний шесть: пустое поле, короткий запрос, загрузка, результаты, ничего не найдено, ошибка. У каждого свой вид.
8. Индикатор загрузки показывать с задержкой 200–300 мс, старые результаты не стирать — иначе список мигает.
9. Combobox: `aria-expanded`, `aria-controls`, `aria-activedescendant`, `role="option"`, `aria-live` с числом найденных. Фокус остаётся в поле.
10. Выбор мышью — через `mousedown` или `preventDefault` на нём: `blur` приходит раньше `click`.
11. Подсветка совпадения — резать строку по индексам, а не `innerHTML`: иначе XSS и сломанные регулярные выражения.
12. Подсказки кешируются на CDN по префиксу, потому что одинаковы для всех; персонализацию выносят из общего ответа.
13. Локальный поиск: нормализация (регистр, диакритика, «ё», пунктуация), префиксный индекс, ранжирование по позиции совпадения. Морфологию русского дешевле всего заменить поиском по префиксу.
