# События DOM: всплытие, делегирование, отмена

Событие в браузере — это не «функция сработала на элементе». Это объект, который путешествует по дереву DOM сверху вниз и обратно, а обработчики — просто точки, где его можно перехватить. Пока в голове живёт первая модель, а не вторая, `stopPropagation` кажется магией, `event.target` путается с `this`, а делегирование выглядит хитрым трюком вместо очевидного следствия устройства.

Эта статья про механику: как событие движется, где его можно поймать, чем три способа «остановить» отличаются друг от друга и почему один слушатель на контейнере лучше сотни слушателей на элементах. Про то, что происходит с событиями внутри событийного цикла, есть отдельная статья — [как работает браузер](./browser-rendering-event-loop); здесь мы считаем, что обработчик уже вызван, и разбираем, почему именно этот.

## Часть 1. Три фазы и откуда их три

### Историческая развилка

В середине девяностых Netscape и Internet Explorer решили задачу «на каком элементе сработал клик» по-разному, и обе модели были логичны.

**Netscape** считал, что событие приходит в окно и идёт вниз по дереву к самому глубокому элементу, на котором произошло действие. Родитель узнаёт о событии первым и может его перехватить, не пустив дальше. Это называется **перехват** или **погружение** (capturing).

**Internet Explorer** считал наоборот: событие возникает на самом глубоком элементе и поднимается вверх, к предкам. Это **всплытие** (bubbling).

Комитет W3C, писавший стандарт DOM Level 2 Events, не стал выбирать. Он взял обе: событие сначала идёт вниз (фаза погружения), доходит до элемента-цели (фаза цели), потом идёт вверх (фаза всплытия). Разработчик сам решает, на какой фазе слушать.

Так что три фазы — не продуманная архитектура, а зафиксированный компромисс. Знать это полезно ровно потому, что вопрос «зачем три фазы» на интервью задают именно так, а честный ответ — «исторически».

Путь события называется **путь распространения** (propagation path). Он вычисляется **в момент возникновения события**, а не по ходу движения. Это важный нюанс: если обработчик на кнопке удалит её из DOM, событие всё равно продолжит всплывать по тому пути, который был построен изначально.

`event.composedPath()` возвращает этот путь массивом — от цели до `window`. Полезно и для отладки, и для работы с теневым DOM.

### Как подписаться на конкретную фазу

```js
// Всплытие — поведение по умолчанию
el.addEventListener('click', fn);
el.addEventListener('click', fn, false);          // то же самое

// Погружение
el.addEventListener('click', fn, true);           // старая форма
el.addEventListener('click', fn, { capture: true }); // современная
```

Третий аргумент исторически был булевым `useCapture`. Потом понадобились ещё флаги, и его превратили в объект настроек: `capture`, `once`, `passive`, `signal`. Булев вариант оставили для совместимости.

Тонкость, о которой забывают: **`capture` входит в «ключ» слушателя**. Слушатель на погружении и слушатель на всплытии с той же функцией — это два разных слушателя. И снимать надо тем же флагом, каким подписывался:

```js
el.addEventListener('click', fn, true);
el.removeEventListener('click', fn);        // не снимет — флаги не совпали
el.removeEventListener('click', fn, true);  // снимет
```

### Что происходит на самой цели

Формально у события есть фаза цели (`eventPhase === 2`), но практически она ведёт себя как «оба слушателя сразу». На самом целевом элементе обработчики, подписанные с `capture` и без него, вызываются **в порядке добавления**, а не «сначала capture». Различие фаз работает только для предков.

## Часть 2. target против currentTarget

Это первое место, где спотыкаются все.

- **`event.target`** — элемент, на котором событие **возникло**. Самый глубокий узел под курсором. Он один и тот же во всех обработчиках вдоль всего пути.
- **`event.currentTarget`** — элемент, на котором висит **сейчас выполняющийся** обработчик. Меняется по мере движения события.

```html
<div id="card">
  <button id="buy">Купить <span id="icon">🛒</span></button>
</div>
```

```js
document.getElementById('card').addEventListener('click', (e) => {
  console.log(e.target.id);        // 'icon' — кликнули по иконке внутри кнопки
  console.log(e.currentTarget.id); // 'card' — обработчик висит на карточке
});
```

Кликнули по иконке внутри кнопки — `target` будет `span`, а не `button`. Это ломает наивный код вида «если кликнули по кнопке, то…»: пользователь попал по вложенному элементу, и проверка `e.target === button` не сработала.

Ещё два факта, которые надо держать в голове:

1. **`this` внутри обычной функции-обработчика равен `currentTarget`.** Именно поэтому стрелочные функции в обработчиках иногда «ломают this» — у стрелки своего `this` нет, она берёт внешний. Про это подробнее в статье [this, контекст вызова и стрелочные функции](./this-and-context).

2. **`currentTarget` живёт только во время вызова обработчика.** После выхода из функции браузер обнуляет это поле. Код вида

```js
el.addEventListener('click', (e) => {
  setTimeout(() => console.log(e.currentTarget), 0); // null
});
```

выведет `null`. Нужен элемент позже — сохрани его в переменную сразу.

Есть ещё `relatedTarget` — у событий мыши указывает «второй» элемент: для `mouseover` это то, откуда курсор пришёл, для `mouseout` — куда ушёл.

## Часть 3. Три способа «остановить», и они разные

Их постоянно путают, потому что все три звучат как «отмени». На самом деле они отменяют три разные вещи.

### preventDefault: отменяет действие браузера

**Действие по умолчанию** — то, что браузер сделал бы сам: переход по ссылке, отправка формы, установка галочки в чекбоксе, прокрутка страницы при колесе мыши, показ контекстного меню по правой кнопке.

`event.preventDefault()` отменяет только это. **На движение события по дереву он не влияет вообще** — событие продолжит всплывать, все остальные обработчики отработают.

```js
form.addEventListener('submit', (e) => {
  e.preventDefault();   // страница не перезагрузится
  sendViaFetch();       // но событие всплывёт до document
});
```

Отменить можно не любое событие: у события есть флаг `cancelable`. У `scroll`, например, его нет — прокрутка уже произошла, отменять нечего. Проверить, отменили ли действие, можно через `event.defaultPrevented`.

Есть ещё старый способ: вернуть `false` из обработчика. В обработчиках, назначенных через `onclick=`, это работает как `preventDefault`. В `addEventListener` возврат значения игнорируется полностью. Использовать не стоит — источник путаницы.

### stopPropagation: останавливает движение по дереву

`event.stopPropagation()` говорит: «дальше по пути не иди». Событие доработает **всех оставшихся слушателей на текущем элементе**, но на следующий элемент пути не перейдёт. Действие по умолчанию при этом никуда не денется — ссылка всё равно откроется.

### stopImmediatePropagation: останавливает всё немедленно

`event.stopImmediatePropagation()` — то же самое, плюс не вызываются остальные обработчики **на этом же элементе**.

```js
btn.addEventListener('click', (e) => {
  e.stopPropagation();
  console.log('первый');
});
btn.addEventListener('click', () => console.log('второй')); // вызовется

// а с stopImmediatePropagation второй бы не вызвался
```

Сведём в таблицу:

| Метод | Обработчики на этом же элементе | Обработчики на предках | Действие браузера |
| --- | --- | --- | --- |
| `preventDefault()` | вызовутся | вызовутся | отменено |
| `stopPropagation()` | вызовутся | не вызовутся | останется |
| `stopImmediatePropagation()` | не вызовутся | не вызовутся | останется |

### Почему stopPropagation считают плохой практикой

`stopPropagation` — это скрытая поломка соседнего кода. Обработчик, который его вызвал, ничего не знает о том, кто ещё подписан выше. А выше почти наверняка кто-то есть: аналитика, закрытие выпадающего меню по клику вне его, глобальный обработчик модалки.

Классический баг: кнопка внутри дропдауна вызывает `stopPropagation`, чтобы «клик не закрыл меню». Через полгода добавляют аналитику кликов через один слушатель на `document` — и клики по этой кнопке не считаются. Причину ищут долго.

Правильнее решать вопрос **проверкой в верхнем обработчике**, а не глушением снизу:

```js
// Вместо stopPropagation внутри меню
document.addEventListener('click', (e) => {
  if (!menu.contains(e.target)) closeMenu();
});
```

## Часть 4. Какие события не всплывают

Не все события проходят полный путь. У события есть флаг `bubbles`; если он `false`, событие идёт вниз до цели и на этом заканчивается.

Не всплывают:

- **`focus` и `blur`** — фокус и потеря фокуса;
- **`load`, `unload`, `error`** на элементах (картинки, скрипты);
- **`mouseenter` и `mouseleave`** — их специально сделали невсплывающими, чтобы они не срабатывали при переходе на вложенные элементы;
- **`abort`** у медиа и запросов.

Практическая проблема: делегировать `focus` на контейнере нельзя — он до контейнера не долетит. Для этого добавили парные всплывающие события:

- `focusin` вместо `focus`,
- `focusout` вместо `blur`.

```js
// Не сработает: focus не всплывает
form.addEventListener('focus', highlight);

// Сработает
form.addEventListener('focusin', highlight);

// Или так: ловим на фазе погружения — она проходит через контейнер
form.addEventListener('focus', highlight, true);
```

Второй вариант — важное наблюдение: **невсплывающее событие всё равно проходит фазу погружения**. То есть предок может его поймать, если подпишется с `capture: true`. Именно так реализуют делегирование `load` и `error` для картинок:

```js
// Ловим ошибки загрузки любых картинок на странице
document.addEventListener('error', (e) => {
  if (e.target.tagName === 'IMG') e.target.src = '/placeholder.png';
}, true);   // без capture не поймает ничего
```

Ещё одна тонкость с `focusout`: он срабатывает **до** того, как фокус перешёл на новый элемент, поэтому `document.activeElement` в этот момент ещё старый. Новый элемент лежит в `event.relatedTarget`.

### Что это даёт на самом деле

**Память.** Каждый слушатель — запись во внутренней таблице браузера плюс живая ссылка на функцию и всё, что эта функция замкнула. Тысяча строк таблицы, каждая со своим обработчиком, замкнувшим объект строки — это тысяча объектов, которые не соберёт сборщик мусора. Подробнее о том, как это превращается в утечку, — в статье [память, сборка мусора и утечки](./memory-and-leaks).

**Динамика.** Слушатель, повешенный на элемент, исчезает вместе с элементом. Добавил новую строку — надо не забыть повесить обработчик и на неё. При делегировании новый элемент работает сразу: контейнер-то на месте.

**Время подключения.** Навесить тысячу слушателей — тысяча вызовов `addEventListener` в момент рендера. Это заметная работа на главном потоке при первой отрисовке большого списка.

### Как правильно находить цель

Наивная проверка ломается на вложенных элементах:

```js
// Плохо: не сработает, если кликнуть по иконке или тексту внутри кнопки
list.addEventListener('click', (e) => {
  if (e.target.matches('.remove')) remove(e.target);
});
```

Правильный инструмент — `closest`: он идёт от `target` вверх и возвращает первый подходящий элемент (включая сам `target`).

```js
list.addEventListener('click', (e) => {
  const btn = e.target.closest('.remove');

  // 1. Клик мимо интересных элементов
  if (!btn) return;

  // 2. Клик по элементу вне нашего контейнера — такое бывает
  //    при вложенных списках и порталах
  if (!list.contains(btn)) return;

  remove(btn.closest('li'));
});
```

Второй проверкой пренебрегают, а зря: `closest` идёт вверх по всему документу и может найти совпадение выше контейнера.

Данные удобно держать в атрибутах: `data-action="remove"`, `data-id="42"`. Тогда один обработчик разруливает целую панель:

```js
panel.addEventListener('click', (e) => {
  const el = e.target.closest('[data-action]');
  if (!el || !panel.contains(el)) return;

  const actions = {
    remove: () => removeItem(el.dataset.id),
    edit:   () => openEditor(el.dataset.id),
    copy:   () => copyItem(el.dataset.id),
  };
  actions[el.dataset.action]?.();
});
```

### Где делегирование не подходит

- События, которые не всплывают, — без `capture` не поймать.
- Если нужен `preventDefault` для узкого случая: к моменту всплытия до контейнера действие браузера ещё не произошло, так что технически можно, но легко случайно отменить лишнее.
- Очень «горячие» события (`mousemove`, `scroll`) на большом дереве: обработчик будет вызываться постоянно и на каждый вызов делать `closest`.

Кстати, React исторически делегирует все события: слушатели вешаются не на каждый элемент, а на корень приложения (до 17-й версии — на `document`). Отсюда классическая проблема смешивания React-обработчиков и «ручных» слушателей на `document`: порядок срабатывания оказывается неожиданным.

## Часть 6. Пассивные слушатели

Обработчики `touchstart`, `touchmove` и `wheel` могут вызвать `preventDefault` и отменить прокрутку. Значит, браузер обязан **дождаться завершения обработчика**, прежде чем прокручивать: вдруг тот отменит.

А обработчик выполняется на главном потоке. Пока он идёт, скролла нет. Отсюда классический «залипающий» скролл на мобильных.

Решение — сказать заранее, что отменять не будешь:

```js
el.addEventListener('touchmove', onMove, { passive: true });
```

С `passive: true` браузер прокручивает **немедленно**, не дожидаясь обработчика: он знает, что `preventDefault` не будет. Если вызвать его всё-таки — вызов проигнорируется, а в консоли появится предупреждение.

Важная деталь: для `touchstart`, `touchmove` и `wheel`, повешенных на `window`, `document` и `document.body`, браузеры **считают `passive: true` значением по умолчанию**. Если тебе там реально нужен `preventDefault` — придётся указать `{ passive: false }` явно.

## Часть 7. Мышь, касание, указатель

Исторически сложилось три семейства событий ввода.

**Мышь**: `mousedown`, `mouseup`, `click`, `dblclick`, `mousemove`, `mouseover`/`mouseout`, `mouseenter`/`mouseleave`, `contextmenu`.

**Касание**: `touchstart`, `touchmove`, `touchend`, `touchcancel`. У них есть `touches` — список всех касаний, что позволяет обрабатывать мультитач.

**Указатель**: `pointerdown`, `pointermove`, `pointerup`, `pointercancel` и другие. Это обобщение: одно событие для мыши, пальца, стилуса и чего угодно ещё. В `event.pointerType` лежит `'mouse'`, `'touch'` или `'pen'`, а также есть `pressure` (сила нажатия), `width`/`height` (площадь касания), `tiltX`/`tiltY` (наклон стилуса).

**Сегодня правильный выбор — `pointer`.** Причины:

1. Один код вместо двух веток. Не нужно писать обработку мыши и отдельно касаний.
2. Работает со стилусом, который в модели мыши описать нечем.
3. Есть `setPointerCapture(pointerId)` — привязка всех дальнейших событий этого указателя к элементу. Это решает главную боль перетаскивания: палец или курсор ушёл за границы элемента, а события всё равно приходят туда, куда надо. В мышиной модели это делали через слушатели на `document`.

```js
slider.addEventListener('pointerdown', (e) => {
  slider.setPointerCapture(e.pointerId);   // ловим все движения, даже вне элемента
  dragging = true;
});
slider.addEventListener('pointermove', (e) => {
  if (dragging) move(e.clientX);
});
slider.addEventListener('pointerup', (e) => {
  slider.releasePointerCapture(e.pointerId);
  dragging = false;
});
```

Мышиные события никуда не делись: для совместимости браузер **эмулирует** их после касаний. Это источник двойных срабатываний, если подписаться и на `touchstart`, и на `mousedown`.

### Порядок событий при клике

Порядок для обычного клика мышью по кнопке:

1. `pointerdown`
2. `mousedown`
3. события фокуса: `focus`, `focusin` (если элемент фокусируемый)
4. `pointerup`
5. `mouseup`
6. `click`
7. `dblclick` — только если это второй клик подряд

Практические следствия:

- **`click` наступает после `mouseup`.** Поэтому обработчик `blur` на поле ввода может уничтожить элемент раньше, чем по нему успеет пройти `click`. Классический баг с автодополнением: клик по подсказке «не работает», потому что `blur` на поле уже свернул список. Лечится обработкой на `mousedown`/`pointerdown` или вызовом `preventDefault` в `mousedown` (это не даёт полю потерять фокус).
- **`click` срабатывает не только от мыши.** Нажатие Enter или пробела на кнопке с клавиатуры порождает `click`. Поэтому вешать логику на `click`, а не на `mousedown`, — это ещё и доступность.
- `dblclick` не отменяет предыдущие `click`: они уже произошли, оба.

## Часть 8. Свои события

Событие можно создать и разослать самому. Это способ развязать модули: один сообщает «случилось вот это», другие подписываются, и они друг о друге не знают.

```js
const evt = new CustomEvent('cart:add', {
  detail: { id: 42, qty: 2 },   // произвольные данные
  bubbles: true,                // по умолчанию false!
  cancelable: true,
});

const notCancelled = button.dispatchEvent(evt);
if (!notCancelled) {
  // кто-то вызвал preventDefault в обработчике
}
```

Три вещи, о которых спотыкаются:

1. **`bubbles` по умолчанию `false`.** Своё событие без этого флага поймает только тот, кто подписан ровно на элемент, где его разослали. Делегировать не выйдет.
2. **`dispatchEvent` синхронный.** Он не ставит задачу в очередь: обработчики вызываются прямо внутри вызова `dispatchEvent`, и управление вернётся только когда они все отработают. Это отличает своё событие от настоящего пользовательского, которое приходит отдельной задачей событийного цикла — см. [как работает браузер](./browser-rendering-event-loop).
3. **Данные кладут в `detail`.** Не в произвольное свойство: `new CustomEvent('x', { id: 5 })` молча проигнорирует `id`.

Полезная деталь: `dispatchEvent` возвращает `false`, если хоть один обработчик вызвал `preventDefault` (и событие было `cancelable`). Так делают «событие с правом вето»: разослал `before-close`, кто-то отменил — не закрываем.

## Часть 9. Утечки и снятие слушателей

### Почему слушатель — это ссылка

Подписка связывает элемент DOM и функцию. Пока элемент жив, жива и функция. А функция замыкает всё, что видела в месте создания.

Обратная сторона тоже работает и опаснее: пока функция достижима из кода — например, лежит в массиве подписок — жив и элемент, на который она подписана. Даже если элемент давно удалён из документа. Это и есть **отсоединённый узел DOM** (detached node), главный источник утечек во фронтенде. Разбор в статье [память, сборка мусора и утечки](./memory-and-leaks).

### removeEventListener требует ту же функцию

```js
// Не снимется никогда: каждый вызов создаёт новую функцию
el.addEventListener('click', () => save());
el.removeEventListener('click', () => save());

// Правильно
const onClick = () => save();
el.addEventListener('click', onClick);
el.removeEventListener('click', onClick);
```

Та же ловушка с `bind`: `fn.bind(this)` каждый раз возвращает **новую** функцию. Привязанную версию надо сохранить — подробнее в статье [функции: приёмы, которые спрашивают на собеседовании](./functions-and-patterns).

### once

Если слушатель нужен ровно один раз, снимать вручную не обязательно:

```js
dialog.addEventListener('transitionend', cleanup, { once: true });
```

Браузер снимет его сам после первого срабатывания.

### AbortController: снять всё разом

Самый удобный современный способ. `AbortController` — объект с сигналом, который можно «дёрнуть» один раз; всё, что этот сигнал слушает, отменяется.

```js
const controller = new AbortController();
const { signal } = controller;

window.addEventListener('resize', onResize, { signal });
document.addEventListener('keydown', onKey, { signal });
el.addEventListener('pointermove', onMove, { signal });
fetch(url, { signal });   // тот же сигнал отменит и запрос

// Одна строка снимает всё сразу
controller.abort();
```

Это ровно то, что нужно в `useEffect` или в методе уничтожения компонента: не хранить список функций и не помнить про флаги `capture`, а завести один контроллер и оборвать всё одним вызовом.

```js
useEffect(() => {
  const c = new AbortController();
  window.addEventListener('scroll', onScroll, { signal: c.signal, passive: true });
  return () => c.abort();
}, []);
```

## Что спросят на интервью

**Какие фазы проходит событие и почему их три?** Погружение, цель, всплытие. Три — исторический компромисс: Netscape реализовал погружение, IE — всплытие, W3C взял обе модели и дал разработчику выбор через третий аргумент `addEventListener`.

**Чем `target` отличается от `currentTarget`?** `target` — где событие возникло, одинаков во всех обработчиках. `currentTarget` — где висит текущий обработчик, равен `this` в обычной функции, обнуляется после выхода из обработчика.

**`stopPropagation` против `preventDefault`?** Первый останавливает движение события по дереву, но не трогает действие браузера. Второй отменяет действие браузера (переход по ссылке, отправку формы), но событие продолжает всплывать. `stopImmediatePropagation` дополнительно глушит остальные обработчики на этом же элементе.

**Что такое делегирование и что оно даёт?** Один слушатель на контейнере вместо слушателя на каждом элементе. Экономит память и время подключения, автоматически работает для динамически добавленных элементов. Цель ищут через `e.target.closest(selector)` с дополнительной проверкой `container.contains(...)`.

**Почему нельзя делегировать `focus`?** Он не всплывает. Варианты: использовать `focusin`/`focusout` или подписаться на `focus` с `capture: true` — фаза погружения проходит через контейнер даже у невсплывающих событий.

**Что такое пассивный слушатель?** Обещание браузеру не вызывать `preventDefault`, чтобы он мог прокручивать страницу, не дожидаясь выполнения обработчика. Для `touchstart`/`touchmove`/`wheel` на `window`, `document` и `body` это уже поведение по умолчанию.

**Почему `pointer`, а не `mouse` и `touch`?** Один код для мыши, пальца и стилуса, есть `pointerType`, давление и наклон, а главное — `setPointerCapture` для корректного перетаскивания за пределы элемента.

**Как снять много слушателей разом?** `AbortController`: передать `signal` в опции всех `addEventListener` и вызвать `controller.abort()`. Тот же сигнал отменяет и `fetch`.

**Почему `removeEventListener` иногда не работает?** Передали другую функцию (новая стрелка или новый `bind`) либо не совпал флаг `capture` — он входит в идентичность слушателя.

## Коротко, для повторения

1. Событие идёт вниз (погружение), доходит до цели, идёт вверх (всплытие). Три фазы — компромисс между моделями Netscape и IE.
2. Путь распространения фиксируется в момент возникновения события; `composedPath()` его показывает.
3. `target` — где возникло, `currentTarget` — где обрабатывается сейчас, он же `this` в обычной функции и он же `null` после выхода из обработчика.
4. `preventDefault` отменяет действие браузера, `stopPropagation` — движение по дереву, `stopImmediatePropagation` — ещё и соседей на том же элементе.
5. `stopPropagation` ломает чужой код молча. Лучше проверка в верхнем обработчике.
6. Не всплывают `focus`, `blur`, `load`, `error`, `mouseenter`/`mouseleave`. Заменители — `focusin`/`focusout` или подписка с `capture: true`.
7. Делегирование: один слушатель на контейнере, цель через `closest`, плюс проверка `contains`. Работает для динамических элементов, экономит память.
8. `{ passive: true }` снимает блокировку скролла обработчиком; для тач- и wheel-событий на корневых узлах это уже по умолчанию.
9. `pointer` вместо `mouse` и `touch`; `setPointerCapture` — для перетаскивания.
10. Свои события: `CustomEvent` с `detail`, `bubbles: true` указывать явно, `dispatchEvent` синхронный.
11. Снимать слушатели — той же функцией и тем же `capture`; проще — `{ once: true }` или один `AbortController` на всё.
