# Массивы, объекты и иммутабельность

Список методов массива можно выучить за вечер. Толку от этого мало: на интервью спрашивают не «что делает `splice`», а «почему после сортировки пропал старый порядок», «почему компонент не перерисовался» и «когда `Map` лучше объекта».

Эта статья про механику: как массив устроен внутри, чем мутирующий метод отличается от копирующего и почему это разделение важнее самих методов, как работает `reduce`, в каком порядке движок отдаёт ключи объекта, зачем нужны `Map` и `WeakMap` и как обновлять вложенные структуры, не ломая сравнение по ссылке.

Предполагается, что ты уже понимаешь разницу между значением и ссылкой — если нет, начни со статьи про [типы и приведение](./types-and-coercion).

## Часть 1. Массив — это объект

### Числовые ключи и `length`

В JavaScript нет отдельного типа «массив». Массив — это объект с особым прототипом (`Array.prototype`), особым свойством `length` и ключами, которые выглядят как числа.

Ключи объекта всегда строки (или символы). Поэтому индекс тоже строка:

```js
const arr = ['a', 'b'];
Object.keys(arr);            // ['0', '1'] — строки, не числа
arr['0'] === arr[0];         // true — число молча превращается в строку
```

Свойство `length` не «считает элементы», а хранит **на единицу больше максимального целочисленного индекса**. Оно доступно на запись, и запись работает как обрезание:

```js
const a = [1, 2, 3, 4, 5];
a.length = 2;
console.log(a);        // [1, 2] — хвост удалён

a[100] = 'x';
console.log(a.length); // 101 — а элементов по-прежнему три
```

Никакой магии: движок держит специальный внутренний метод, который при записи числового ключа поднимает `length`, а при уменьшении `length` удаляет всё, что за границей.

Это ещё не значит, что массив хранится как хеш-таблица. Пока индексы идут подряд и типы элементов однородны, движок использует **плотное представление** — непрерывный блок памяти, как настоящий массив в C. Это быстро. Как только появляются дыры или ключи вроде `a.foo = 1`, представление может переключиться на **словарное** (хеш-таблица) — и всё резко замедлится.

### Разреженный массив

**Разреженный массив** (sparse array) — массив, у которого часть индексов не существует как свойство. Это не то же самое, что `undefined`: свойства просто нет.

Как получаются дыры:

```js
const a = [1, , 3];      // литерал с пропуском
const b = new Array(3);  // [ , , ] — три дыры
const c = [1, 2, 3];
delete c[1];             // [1, , 3] — length остался 3
```

Из-за дыр методы ведут себя по-разному, и это ровно та деталь, на которой ломается код:

```js
const a = [1, , 3];

a.forEach(x => console.log(x));  // 1, 3 — дыра пропущена
a.map(x => x * 2);               // [2, , 6] — дыра сохранена, колбэк не вызван
a.filter(() => true);            // [1, 3] — дыры удалены
a.includes(undefined);           // true  — includes видит дыру как undefined
a.indexOf(undefined);            // -1    — а indexOf пропускает
Object.keys(a);                  // ['0', '2']
a.length;                        // 3
```

Правило простое: **не создавай дыры**. Вместо `delete arr[i]` используй `splice` (сдвинет хвост) или `filter` (вернёт новый массив). Вместо `new Array(n)` — `Array.from({ length: n }, (_, i) => i)`, который даёт настоящие элементы.

```js
// Плохо: дыры, колбэк не вызовется ни разу
new Array(3).map((_, i) => i);        // [ , , ]

// Хорошо
Array.from({ length: 3 }, (_, i) => i);  // [0, 1, 2]
new Array(3).fill(0).map((_, i) => i);   // [0, 1, 2] — fill заполняет дыры
```

Мнемоника: **мутирующих ровно семь**, и все они «действия» — толкнуть, вытолкнуть, вырезать, отсортировать, перевернуть, залить, скопировать внутри. Всё, что «преобразует», копирует.

Пара, которую путают чаще всего:

```js
const a = [1, 2, 3, 4, 5];

a.slice(1, 3);       // [2, 3]     — a не изменился
a.splice(1, 3);      // [2, 3, 4]  — a стал [1, 5]
```

`slice` — «отрезать копию», `splice` — «вырезать из оригинала».

### Новые копирующие методы

В 2023 году в язык добавили четвёрку, которая закрыла давнюю дыру: раньше, чтобы отсортировать массив не мутируя, приходилось писать `[...arr].sort()`.

```js
const a = [3, 1, 2];

a.toSorted((x, y) => x - y);  // [1, 2, 3], a не тронут
a.toReversed();               // [2, 1, 3]
a.with(0, 99);                // [99, 1, 2]
a.toSpliced(1, 1);            // [3, 2]
a;                            // [3, 1, 2] — как было
```

Они же есть у типизированных массивов, а `toSorted`, `toReversed`, `with` — ещё и удобны в React, где мутировать состояние нельзя.

И `at`, который решает вечную боль с последним элементом:

```js
a.at(-1);         // последний
a[a.length - 1];  // то же, но длиннее
a.at(0);          // первый
```

Отрицательные индексы в квадратных скобках не работают: `a[-1]` — это обычное свойство с ключом `'-1'`, оно `undefined`.

### Почему `sort` мутирует и сравнивает как строки

`sort` появился в языке в 1995 году, когда идея «не мутировать» ещё не была нормой, и сортировал на месте ради экономии памяти. Изменить поведение задним числом нельзя, поэтому и добавили `toSorted`.

Вторая особенность — сравнение по умолчанию. Без компаратора `sort` **приводит элементы к строке** и сравнивает лексикографически, посимвольно по коду символа:

```js
[10, 9, 1, 100].sort();
// [1, 10, 100, 9]  — потому что '10' меньше '9' по первому символу
```

Логика авторов: массив может содержать что угодно, а строковое сравнение определено для любого значения. Практически это значит, что **компаратор нужен всегда**, когда сортируешь не строки.

```js
nums.sort((a, b) => a - b);                       // по возрастанию
nums.sort((a, b) => b - a);                       // по убыванию
strs.sort((a, b) => a.localeCompare(b));          // с учётом языка: ё, ä, é
objs.sort((a, b) => a.date - b.date);             // даты вычитаются как числа
```

Компаратор должен вернуть отрицательное число, если первый идёт раньше, положительное — если позже, ноль — если равны. Возвращать `true`/`false` нельзя: `true` превратится в `1`, `false` в `0`, и «раньше» станет неотличимо от «равны» — сортировка получится частичной и разной в разных браузерах.

```js
// Плохо: булев компаратор, результат непредсказуем
arr.sort((a, b) => a.age > b.age);

// Хорошо
arr.sort((a, b) => a.age - b.age);
```

`localeCompare` заслуживает отдельного упоминания: для кириллицы и умляутов обычное сравнение по коду символа даёт неверный алфавитный порядок, потому что расположение букв в Unicode не совпадает с алфавитом.

### Стабильность сортировки

**Стабильная сортировка** — та, что сохраняет взаимный порядок элементов, которые компаратор посчитал равными. С 2019 года спецификация требует стабильности от `sort`, и все актуальные движки её обеспечивают.

Почему это важно: стабильность позволяет сортировать по нескольким полям последовательно.

```js
// Сначала по имени, потом по отделу — внутри отдела имена останутся упорядоченными
users.sort((a, b) => a.name.localeCompare(b.name));
users.sort((a, b) => a.dept.localeCompare(b.dept));
```

Без стабильности такой приём не работал бы, и пришлось бы писать компаратор с несколькими уровнями:

```js
users.sort((a, b) =>
  a.dept.localeCompare(b.dept) || a.name.localeCompare(b.name)
);
```

Второй вариант всё равно надёжнее и быстрее: один проход вместо двух.

## Часть 3. Перебирающие методы

### Какой когда

- `forEach` — просто пройтись, ничего не собирая. Нельзя прервать (`break` не работает, `return` выходит только из колбэка). Если нужен выход — обычный `for...of`.
- `map` — на каждый элемент один новый элемент. Длина сохраняется. Если результат не используешь, это не `map`, а `forEach`.
- `filter` — оставить подходящие. Длина уменьшается или остаётся.
- `find` / `findIndex` / `findLast` / `findLastIndex` — первый (или последний) подходящий, останавливается сразу как нашёл.
- `some` / `every` — логический ответ, тоже с ранним выходом. `some` на пустом массиве — `false`, `every` — `true` (пустая истина, привыкнуть придётся).
- `flat(depth)` — разгладить вложенные массивы. `flat(Infinity)` — на любую глубину.
- `flatMap` — `map` плюс разглаживание на один уровень. Удобен, когда на элемент приходится ноль, один или несколько результатов:

```js
// Отфильтровать и преобразовать за один проход
const ids = users.flatMap(u => u.active ? [u.id] : []);
```

- `reduce` — свернуть массив в одно значение.

### `reduce` изнутри

`reduce` вызывает колбэк для каждого элемента, передавая **аккумулятор** — значение, накопленное к этому моменту. Что колбэк вернул, то и станет аккумулятором на следующем шаге.

```js
[1, 2, 3, 4].reduce((acc, x) => acc + x, 0);
// шаг 1: acc = 0, x = 1 → 1
// шаг 2: acc = 1, x = 2 → 3
// шаг 3: acc = 3, x = 3 → 6
// шаг 4: acc = 6, x = 4 → 10
```

Полная сигнатура колбэка — `(acc, item, index, array)`, второй аргумент `reduce` — начальное значение.

Начальное значение **лучше указывать всегда**. Без него аккумулятором становится первый элемент, а перебор начинается со второго — и на пустом массиве это `TypeError: Reduce of empty array with no initial value`.

```js
[].reduce((a, b) => a + b);       // TypeError
[].reduce((a, b) => a + b, 0);    // 0
```

Где `reduce` действительно на месте — там, где результат не массив:

```js
// Сгруппировать по ключу
const byRole = users.reduce((acc, u) => {
  (acc[u.role] ??= []).push(u);
  return acc;
}, {});

// Посчитать частоты
const counts = words.reduce((acc, w) => {
  acc[w] = (acc[w] || 0) + 1;
  return acc;
}, {});

// Собрать индекс по идентификатору
const byId = users.reduce((acc, u) => { acc[u.id] = u; return acc; }, {});
```

### Где `reduce` хуже цикла

Два случая.

**Первый — когда `reduce` просто маскирует цикл.** Если аккумулятор — массив, а внутри `push`, читаемость падает, а выигрыша нет: `map` и `filter` выражают то же намерение яснее.

```js
// Плохо: reduce ради reduce
const names = users.reduce((acc, u) => { acc.push(u.name); return acc; }, []);

// Хорошо
const names = users.map(u => u.name);
```

**Второй, серьёзнее — спред в аккумуляторе.** Это выглядит «иммутабельно», но превращает линейный алгоритм в квадратичный:

```js
// Плохо: на каждом шаге копируется весь накопленный объект
const byId = users.reduce((acc, u) => ({ ...acc, [u.id]: u }), {});
```

На каждом из `n` шагов копируются все уже добавленные ключи. Итого около `n²/2` операций: на тысяче элементов это полмиллиона копирований вместо тысячи. На десяти тысячах интерфейс встанет. Мутация локального аккумулятора здесь абсолютно законна — объект создан внутри `reduce` и наружу в промежуточном виде не выходит.

Ещё один аргумент за цикл: **из `reduce` нельзя выйти досрочно**. Если нужно остановиться на середине — бери `for...of` и не изобретай.

## Часть 4. Объекты: перебор и порядок ключей

### Способы перебрать

```js
const o = { b: 1, a: 2 };

Object.keys(o);      // ['b', 'a']         — собственные строковые перечислимые
Object.values(o);    // [1, 2]
Object.entries(o);   // [['b', 1], ['a', 2]]

for (const k in o) {}          // ключи, включая унаследованные от прототипа
Object.getOwnPropertyNames(o); // включая неперечислимые
Reflect.ownKeys(o);            // всё, включая символы
```

**Перечислимое** (enumerable) свойство — то, которое видно при переборе. Обычные свойства перечислимы; методы класса и многие встроенные — нет. Именно поэтому `Object.keys` экземпляра класса не показывает его методы.

`for...in` — единственный, кто лезет в прототип. Отсюда классическая защита `if (Object.hasOwn(o, k))` внутри цикла. На практике `for...in` почти не нужен: `Object.keys` короче и безопаснее.

Обратное преобразование — `Object.fromEntries`, парный к `entries`:

```js
// Преобразовать значения объекта, оставив ключи
const doubled = Object.fromEntries(
  Object.entries(prices).map(([k, v]) => [k, v * 2])
);

// Из URLSearchParams или FormData в обычный объект
Object.fromEntries(new URLSearchParams(location.search));
Object.fromEntries(new FormData(form));
```

И `Object.groupBy` — недавнее добавление, которое закрывает самый частый сценарий `reduce`:

```js
Object.groupBy(users, u => u.role);
// { admin: [...], user: [...] }

Map.groupBy(users, u => u.dept);   // то же, но ключами могут быть объекты
```

Результат `Object.groupBy` — объект с прототипом `null`, то есть без унаследованных свойств. Это защита: ключ `'toString'` в данных не сломает объект.

### Порядок ключей

Долго считалось, что порядок ключей не определён. С ES2015 он определён строго, и это спрашивают:

1. Сначала **целочисленные ключи** — те, что выглядят как неотрицательные целые числа, — по возрастанию **числового** значения.
2. Затем остальные строковые ключи — в порядке добавления.
3. Затем символы — в порядке добавления.

```js
const o = { b: 1, 2: 2, a: 3, 1: 4 };
Object.keys(o);   // ['1', '2', 'b', 'a']
```

Практический вывод: **если ключи — числовые идентификаторы, порядок вставки не сохранится**. Словарь `{ 100: ..., 5: ... }` перебирается как `5, 100`. Если порядок важен, используй `Map` или храни порядок отдельным массивом идентификаторов.

`JSON.stringify` следует тому же порядку, поэтому две «одинаковые» структуры с разным порядком добавления могут дать разные строки — сравнивать объекты через `JSON.stringify` ненадёжно.

## Часть 5. `Map`, `Set` и их слабые версии

### `Map` против объекта

| | Объект | `Map` |
| --- | --- | --- |
| Ключи | только строки и символы | **любые**, включая объекты и `NaN` |
| Порядок | целые числа вперёд | строго порядок вставки |
| Размер | `Object.keys(o).length` | `m.size` |
| Перебор | через `Object.keys/entries` | итерируемый напрямую |
| Прототип | наследует от `Object.prototype` | нет посторонних ключей |
| Частые вставки и удаления | медленнее | оптимизирован под это |
| Сериализация в JSON | из коробки | нужно вручную |

Ключевое отличие — **ключи по ссылке**:

```js
const m = new Map();
const user = { id: 1 };
m.set(user, { lastSeen: Date.now() });
m.get(user);          // работает
m.get({ id: 1 });     // undefined — другой объект, другой адрес
```

С объектом так нельзя: ключ приводится к строке, и любой объект станет `'[object Object]'`, затирая предыдущий.

Второе отличие, о котором вспоминают в проде, — **посторонние ключи**. Обычный объект наследует `toString`, `constructor`, `__proto__`. Если ключи приходят от пользователя, это дыра:

```js
const dict = {};
dict['toString'];             // унаследованная функция, а не undefined!
'toString' in dict;           // true, хотя мы ничего не клали

const safe = Object.create(null);   // объект без прототипа
const m = new Map();                // или просто Map
```

Когда что брать: **объект** — когда ключи известны заранее и это структура данных («у пользователя есть имя и роль»). **`Map`** — когда это словарь с динамическими ключами, особенно если ключи не строки или порядок важен.

### `Set`

`Set` хранит уникальные значения. Уникальность определяется по SameValueZero — тому же алгоритму, что у `includes`: `NaN` считается равным `NaN`, `+0` и `-0` — одно и то же, объекты сравниваются по ссылке.

```js
new Set([1, 2, 2, 3]);            // Set(3) {1, 2, 3}
[...new Set(arr)];                // дедупликация массива
new Set([NaN, NaN]).size;         // 1
new Set([{}, {}]).size;           // 2 — разные адреса
```

Главный практический выигрыш — скорость проверки принадлежности. `arr.includes(x)` перебирает массив линейно, `set.has(x)` работает за примерно постоянное время. На массиве в десять тысяч элементов внутри цикла разница между «мгновенно» и «секунды».

```js
// Плохо: n × m операций
const result = items.filter(i => banned.includes(i.id));

// Хорошо: n операций
const bannedSet = new Set(banned);
const result = items.filter(i => bannedSet.has(i.id));
```

В новых версиях у `Set` появились операции над множествами: `union`, `intersection`, `difference`, `symmetricDifference`, `isSubsetOf`.

### `WeakMap` и `WeakSet`

**Слабая ссылка** — ссылка, которая не мешает сборщику мусора удалить объект. Обычная (сильная) ссылка держит объект в памяти, пока существует.

`WeakMap` хранит ключи слабо: если на объект-ключ больше никто не ссылается, пара удаляется из карты автоматически.

```js
let el = document.querySelector('#widget');
const meta = new WeakMap();
meta.set(el, { clicks: 0 });

el.remove();
el = null;     // последняя сильная ссылка ушла
// запись в meta исчезнет сама при следующей сборке мусора
```

С обычным `Map` эта запись жила бы вечно — классическая утечка памяти в приложениях, которые вешают данные на DOM-узлы.

Ограничения, вытекающие из механики:

- **Ключи только объекты** (и незарегистрированные символы). Примитив нельзя: он не имеет идентичности, которую можно отследить.
- **Нельзя перебирать**: нет `keys`, `values`, `size`, `forEach`. Причина принципиальная — момент сборки мусора недетерминирован, и перебор давал бы разный результат в разных запусках, то есть выдавал бы информацию о работе сборщика.
- Есть только `get`, `set`, `has`, `delete` (у `WeakSet` — `add`, `has`, `delete`).

Типичные применения: приватные данные экземпляра, кеш вычислений по объекту, пометка «этот объект мы уже обработали» при обходе графа.

## Часть 6. Иммутабельность на практике

### Зачем вообще

Три причины, и все прикладные.

**Сравнение по ссылке становится осмысленным.** Если объект никогда не мутируется, то `prev === next` означает «ничего не изменилось». Именно на этом стоят `React.memo`, `useMemo`, селекторы Redux, `shouldComponentUpdate`. Сравнить два адреса — одна операция; сравнить два глубоких дерева — обход всей структуры.

**Отладка.** Мутация происходит «где-то», и найти, кто испортил объект, тяжело. Новое значение всегда создаётся в одном месте.

**Предсказуемость.** Функция, которая не трогает аргументы, ведёт себя одинаково независимо от того, кто ещё держит ссылку на те же данные.

### Спред копирует один уровень

Главная ловушка: спред и `Object.assign` **поверхностные**. Верхний уровень новый, всё вложенное — общее.

```js
const state = { user: { name: 'Аня', tags: ['a'] }, count: 1 };
const copy = { ...state };

copy.count = 2;
state.count;              // 1 — примитив скопировался

copy.user.name = 'Боря';
state.user.name;          // 'Боря' — ссылка общая, оригинал испорчен
```

Чтобы обновить вложенное поле честно, нужно **создать новый объект на каждом уровне пути** от корня до изменяемого поля. Всё, что в стороне от пути, переиспользуется как есть — это называется **структурным разделением** (structural sharing).

// Плохо: мутация
state.user.address.city = 'Питер';

  },

Для массивов внутри состояния — тот же принцип:

```js
// Добавить
[...items, newItem]

// Удалить по идентификатору
items.filter(i => i.id !== id)

// Обновить один элемент
items.map(i => i.id === id ? { ...i, done: true } : i)

// Заменить по индексу
items.with(index, newItem)

// Вставить в середину
items.toSpliced(index, 0, newItem)
```

Когда вложенность становится больно глубокой, берут библиотеку с «черновиками» (Immer): ты пишешь мутирующий код, а она под капотом строит новое дерево со структурным разделением. Redux Toolkit включает её по умолчанию — именно поэтому в редьюсерах RTK можно писать `state.value += 1` и это законно.

### `Object.freeze` тоже поверхностный

`Object.freeze` запрещает добавлять, удалять и менять свойства объекта. Но ровно на один уровень:

```js
const o = Object.freeze({ a: 1, nested: { b: 2 } });

o.a = 99;             // молча игнорируется (в strict mode — TypeError)
o.nested.b = 99;      // работает! вложенный объект не заморожен
o.nested;             // { b: 99 }
```

Глубокая заморозка пишется рекурсией:

```js
function deepFreeze(obj) {
  for (const v of Object.values(obj)) {
    if (v && typeof v === 'object') deepFreeze(v);
  }
  return Object.freeze(obj);
}
```

Родственники: `Object.seal` — менять можно, добавлять и удалять нельзя; `Object.preventExtensions` — только запрет на добавление. Проверки — `Object.isFrozen`, `Object.isSealed`.

На практике `freeze` включают в разработке (чтобы поймать случайную мутацию) и выключают в продакшене: проверка на каждую запись стоит производительности.

### Нормализация вместо вложенности

Самое надёжное лечение проблем с вложенными обновлениями — не иметь вложенности. **Нормализация** — хранение сущностей плоско, в словаре по идентификатору, а связей — массивами идентификаторов. Идея взята из реляционных баз.

```js
// Было: обновить комментарий — значит пройти три уровня спреда
const state = {
  posts: [
    { id: 1, author: { id: 7, name: 'Аня' }, comments: [{ id: 3, text: '...' }] },
  ],
};

// Стало: обновление любой сущности — один уровень
const state = {
  posts:    { byId: { 1: { id: 1, authorId: 7, commentIds: [3] } }, allIds: [1] },
  users:    { byId: { 7: { id: 7, name: 'Аня' } } },
  comments: { byId: { 3: { id: 3, text: '...' } } },
};

// Обновить комментарий
const next = {
  ...state,
  comments: {
    byId: { ...state.comments.byId, 3: { ...state.comments.byId[3], text: 'новый' } },
  },
};
```

Что это даёт помимо простых обновлений: сущность хранится в одном экземпляре, значит нет рассинхронизации копий; поиск по идентификатору мгновенный; список идентификаторов задаёт порядок явно, а не через порядок ключей объекта.

Цена — данные нужно нормализовать при получении и «собирать» обратно при отображении. Для этого и существуют селекторы.

## Что спросят на интервью

**Какие методы массива мутируют исходник?** Семь: `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse` (плюс `fill` и `copyWithin`). У всех есть копирующие аналоги: `toSorted`, `toReversed`, `toSpliced`, `with`, спред, `slice`.

**Чем `slice` отличается от `splice`?** `slice` возвращает копию куска и не трогает оригинал. `splice` вырезает из оригинала и возвращает удалённое.

**Почему `[10, 9, 1].sort()` даёт `[1, 10, 9]`?** Без компаратора элементы приводятся к строкам и сравниваются лексикографически.

**Что такое стабильная сортировка и зачем она?** Равные элементы сохраняют исходный взаимный порядок. Позволяет сортировать по нескольким критериям последовательными вызовами. С ES2019 обязательна.

**Когда `reduce` — плохой выбор?** Когда достаточно `map`/`filter`; когда нужен досрочный выход; и особенно когда в аккумуляторе спред — это превращает алгоритм в квадратичный.

**В каком порядке перебираются ключи объекта?** Сначала целочисленные по возрастанию, потом строковые в порядке добавления, потом символы.

**Чем `Map` лучше объекта?** Любые ключи (включая объекты), гарантированный порядок вставки, `size`, прямая итерация, отсутствие унаследованных ключей, лучшая производительность при частых вставках и удалениях.

**Зачем нужен `WeakMap`?** Хранить данные, привязанные к объекту, не мешая его сборке. Ключи только объекты, перебирать нельзя — иначе результат зависел бы от момента сборки мусора.

**Что такое разреженный массив и чем он опасен?** Массив с отсутствующими индексами. `forEach` и `map` дыры пропускают, `filter` удаляет, `includes` видит как `undefined`, `indexOf` — нет. Создаётся `delete arr[i]` и `new Array(n)`.

**Почему спред не решает проблему иммутабельности до конца?** Он копирует один уровень; вложенные объекты остаются общими. Нужно копировать каждый уровень пути или использовать `structuredClone`/Immer.

**Насколько глубоко работает `Object.freeze`?** На один уровень. Вложенные объекты остаются изменяемыми.

**Зачем нормализовать состояние?** Убирает глубокие обновления, исключает дубликаты сущности, даёт быстрый доступ по идентификатору и явный порядок через массив идентификаторов.

## Коротко, для повторения

1. Массив — объект с числовыми ключами-строками и особым `length`. Дыры переводят его в медленное представление, а методы обрабатывают дыры по-разному.
2. Мутирующих методов семь: `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`. Остальные преобразующие — копируют.
3. `toSorted`, `toReversed`, `toSpliced`, `with` — копирующие двойники. `at(-1)` — последний элемент.
4. `sort` без компаратора сравнивает строки. Компаратор возвращает число, не булево. Сортировка стабильна с ES2019.
5. `reduce`: аккумулятор — то, что вернул прошлый вызов. Начальное значение указывай всегда. Спред в аккумуляторе — квадратичная сложность.
6. Ключи объекта: целые по возрастанию, потом строки в порядке добавления, потом символы.
7. `Map` — любые ключи, порядок вставки, `size`, нет унаследованных ключей. `Set` — уникальность по SameValueZero и быстрый `has`.
8. `WeakMap` и `WeakSet` не держат объект в памяти, ключами берут только объекты и не перебираются.
9. Спред, `Object.assign` и `Object.freeze` работают на один уровень. Глубоко — рекурсия, `structuredClone` или Immer.
10. Обновление вложенного поля — новый объект на каждом уровне пути; соседние ветки переиспользуются по ссылке.
11. Нормализация состояния убирает глубокие обновления и дубликаты сущностей.
