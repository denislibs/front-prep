# async/await: что это на самом деле

`async/await` выглядит как способ писать асинхронный код синхронно. Это удобная ложь, и она работает до первой ошибки производительности: человек ставит пять `await` подряд, страница грузится пять секунд вместо одной, и объяснить причину он не может.

На самом деле `await` ничего не «ждёт». Он **разрезает функцию на части** и превращает остаток в колбэк промиса. Разберём, что это значит для стека, для порядка выполнения и для скорости.

Статья опирается на две соседние: [промисы изнутри](./promises) — про то, что `.then` возвращает новый промис, и [как работает браузер](./browser-rendering-event-loop) — про очередь микрозадач. Отдельно их пересказывать не будем; нужно помнить, что продолжение после `await` — это микрозадача, и она выполняется раньше любого `setTimeout`.

## Часть 1. `async` — это про возвращаемое значение

Слово `async` перед функцией делает ровно две вещи.

**Первая: функция всегда возвращает промис.** Всегда, без исключений.

```js
async function f() { return 1; }
console.log(f());          // Promise { 1 } — не число
f().then(v => console.log(v));   // 1
```

Если внутри `return 1`, движок оборачивает единицу в уже выполненный промис. Если внутри нет `return` вообще — вернётся промис со значением `undefined`. Если внутри `throw` — вернётся **отклонённый** промис, а не выброшенное наружу исключение.

```js
async function boom() { throw new Error('бум'); }

try {
  boom();                  // ошибки здесь НЕ будет
} catch (e) {
  console.log('не поймает');
}
boom().catch(e => console.log('вот так поймает'));
```

Это важная деталь: `async` **превращает исключение в отклонение промиса**. Обычный `try/catch` вокруг вызова без `await` бесполезен.

Если из `async`-функции вернуть промис, он развернётся — по тем же правилам, что и возврат промиса из `.then`. Промиса внутри промиса не бывает.

**Вторая: внутри разрешено слово `await`.** Больше `async` не делает ничего. Он не переносит выполнение в другой поток, не делает функцию параллельной, не ускоряет её. Код внутри `async`-функции до первого `await` выполняется **синхронно**, прямо сейчас, на том же стеке.

```js
async function f() {
  console.log('1');       // синхронно, прямо при вызове
  await null;
  console.log('3');       // а это уже микрозадача
}
f();
console.log('2');
// 1, 2, 3
```

## Часть 2. `await` разрезает функцию

Теперь главное. Прочитай определение и вернись к нему, когда будешь разбирать порядок вывода:

**`await X` означает: «заверши текущий вызов здесь, подпишись на `X`, а всё, что идёт ниже по функции, выполни как колбэк этой подписки».**

Функция с `await` физически не может выполняться «с паузой посередине» — главный поток один и стоять он не умеет. Вместо этого движок **снимает функцию со стека** на месте `await`, запоминает, где остановился и какие были локальные переменные, и возвращает управление наружу. Когда промис завершится, движок восстановит сохранённое состояние и продолжит с той же строки — но уже в новой микрозадаче, на новом стеке.

Строго говоря, `await X` эквивалентен подписке `.then` на `Promise.resolve(X)`, а тело функции ниже становится телом колбэка.

### Разбор по шагам

```js
async function f() {
  console.log('A');
  await null;
  console.log('C');
  await null;
  console.log('E');
}

console.log('start');
f();
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('then'));
console.log('end');
```

Вывод: **start, A, end, C, then, E, timeout**. По шагам, с указанием, что где лежит:

1. Печатается `start`. Стек: скрипт.
2. Вызвана `f`. Она легла на стек и выполняется синхронно: печатается `A`.
3. Встретился `await null`. Движок оборачивает `null` в готовый промис, ставит продолжение `f` в очередь микрозадач и **снимает `f` со стека**. Управление возвращается в скрипт. Очередь микрозадач: `[продолжение f]`.
4. `setTimeout` кладёт колбэк в очередь **задач** (не микрозадач). Очередь задач: `[timeout]`.
5. `.then` на готовом промисе ставит колбэк в очередь микрозадач: `[продолжение f, then]`.
6. Печатается `end`. Скрипт закончился, стек пуст.
7. Движок опустошает очередь микрозадач. Первое — продолжение `f`: печатается `C`, встречается второй `await`, `f` снова снимается со стека, её новое продолжение уходит **в конец** очереди: `[then, продолжение f #2]`.
8. Выполняется `then`.
9. Выполняется продолжение `f`: печатается `E`, функция доходит до конца и разрешает свой промис.
10. Очередь микрозадач пуста. Только теперь берётся задача `timeout`.

Формулировка, ради которой этот вопрос задают: **каждый `await` — это ещё один оборот очереди микрозадач, и на каждом обороте вперёд может пролезть чужой код**.

### Что при этом происходит со стеком

**Стек вызовов** — список функций, которые сейчас выполняются: вызвал функцию — её кадр лёг на стек, вернулась — кадр снялся. Проследим за ним на примере выше.

- **Пока идёт шаг 2**, стек выглядит так: снизу кадр скрипта, сверху кадр `f`. Обычная синхронная картина.
- **На `await` (шаг 3)** кадр `f` снимается со стека. Не «замораживается на стеке», а именно снимается — иначе главный поток был бы занят и не смог бы выполнять другой код. Локальные переменные и точка остановки сохраняются в объекте-состоянии в куче, к стеку он отношения не имеет.
- **Между шагами** стек пуст либо занят чужим кодом: скриптом, обработчиком, другой микрозадачей. `f` в этот момент на стеке отсутствует физически.
- **На шаге 7** движок берёт микрозадачу и создаёт для `f` **новый** кадр, восстанавливая сохранённое состояние. Снизу под ним — не скрипт, а служебный кадр движка, разбирающего очередь микрозадач.

Отсюда два практических вывода. Первый: `f` больше не «внутри» вызвавшего её кода, поэтому его `try/catch` до неё не дотянется — ловить надо внутри самой `f` или через `.catch` на её промисе. Второй: у ошибки, случившейся после `await`, в стеке трассировки не будет вызывающих функций — они давно снялись. Современные движки дорисовывают асинхронные кадры искусственно, но это реконструкция, а не настоящий стек; подробнее — в статье [ошибки и отладка](./errors-and-debugging).

### Что означает `await` на не-промисе

`await 5` тоже разрезает функцию. Значение оборачивается в готовый промис, продолжение всё равно уходит в микрозадачу. Ускорения от «await на числе» не бывает — только лишний оборот очереди.

### Между кусками мир меняется

Раз функция снимается со стека, между её кусками может выполниться что угодно: другой обработчик, другой запрос, размонтирование компонента. Значит, состояние, прочитанное до `await`, могло устареть после него.

```js
async function save() {
  const draft = store.draft;          // прочитали
  await api.validate(draft);          // здесь пользователь успел всё поменять
  store.saved = draft;                // записали устаревшее
}
```

Это тот же класс проблем, что и гонки в многопоточном коде, только без потоков. Правило: **всё, что может измениться, перечитывай после `await`**.

## Часть 3. Последовательно против параллельно

Самая частая ошибка производительности с `await` — и самый частый вопрос на интервью.

```js
// Плохо: три запроса по 300 мс подряд = 900 мс
const user = await fetchUser(id);
const orders = await fetchOrders(id);
const settings = await fetchSettings(id);
```

Каждый `await` останавливает **эту функцию** до готовности промиса. Второй `fetch` даже не начнётся, пока не завершится первый. При этом никакой зависимости между ними нет — все три можно было запустить сразу.

```js
// Хорошо: три запроса разом = 300 мс
const [user, orders, settings] = await Promise.all([
  fetchUser(id), fetchOrders(id), fetchSettings(id)
]);
```

### Разделяй запуск и ожидание

Ключ к параллельности — понять, что **промис стартует в момент создания, а не в момент `await`**. Значит, можно сначала запустить всё, а ждать потом:

```js
// Тоже параллельно, без Promise.all
const userPromise = fetchUser(id);        // пошёл запрос
const ordersPromise = fetchOrders(id);    // пошёл второй, не дожидаясь первого

const user = await userPromise;
const orders = await ordersPromise;       // к этому моменту уже готов
```

Такой вариант годится, когда после первого результата нужно что-то сделать до получения второго. Но у него есть **опасный угол**: если `ordersPromise` отклонится, пока мы стоим на `await userPromise`, отклонение окажется временно необработанным, и в консоли появится предупреждение. А если упадёт первый, до `await ordersPromise` мы вообще не доедем — и его ошибка останется без обработчика навсегда. `Promise.all` от этого избавлен: он подписывается на все промисы сразу.

Поэтому по умолчанию — `Promise.all`, а ручное разделение только там, где оно правда нужно, с `.catch` на каждом промисе.

### Когда последовательность обязательна

Не всякий `await` подряд — ошибка. Если второй запрос **зависит** от первого, иначе нельзя:

```js
const user = await fetchUser(id);
const orders = await fetchOrders(user.orgId);   // нужен результат первого
```

Проверяй по одному признаку: **использует ли следующая строка результат предыдущей**. Если нет — запросы должны идти параллельно.

### `await` в цикле

Тот же вопрос в самом коварном виде.

```js
// Плохо, если итерации независимы: N запросов по очереди
for (const id of ids) {
  results.push(await fetchItem(id));
}

// Хорошо: все разом
const results = await Promise.all(ids.map(id => fetchItem(id)));
```

Но и обратное верно: `await` в цикле бывает единственно правильным. Когда операции зависят друг от друга (постраничная загрузка, где следующий курсор приходит с предыдущей страницей) или когда параллельность нежелательна — сервер не выдержит тысячу одновременных запросов, а браузер всё равно ограничивает число соединений к одному домену.

Компромисс — ограниченная параллельность: резать массив на пачки по 5–10 и обрабатывать пачки последовательно, а внутри пачки — через `Promise.all`.

```js
async function inBatches(items, size, fn) {
  const out = [];
  for (let i = 0; i < items.length; i += size) {
    const batch = items.slice(i, i + size);
    out.push(...await Promise.all(batch.map(fn)));
  }
  return out;
}
```

## Часть 4. Ошибки

Главное удобство `await` — обычный `try/catch` снова работает.

```js
try {
  const res = await fetch(url);
  if (!res.ok) throw new Error('HTTP ' + res.status);
  return await res.json();
} catch (err) {
  showError(err);
} finally {
  hideSpinner();     // выполнится в любом случае
}
```

Механика: `await` на отклонённом промисе **бросает** его причину как обычное исключение — в той точке, где стоит `await`. Раз исключение бросается внутри `try`, обычный `catch` его видит.

### Чего `try/catch` не поймает

Всё, что не прошло через `await`. Это самая частая дыра.

```js
try {
  doAsyncThing();      // async-функция БЕЗ await
} catch (e) {
  // не поймает: функция вернула промис, который отклонится позже
}
```

Вызов без `await` возвращает промис и мгновенно завершается успешно. Отклонение произойдёт потом, когда `try` давно закончился. Ошибка станет необработанным отклонением.

То же самое с колбэками таймеров и обработчиками событий: код внутри них выполняется на своём стеке, снаружи его никто не оборачивает.

```js
try {
  setTimeout(() => { throw new Error('бум'); }, 0);
} catch (e) { /* не поймает никогда */ }
```

### `forEach` с асинхронным колбэком не ждёт

Классическая ловушка, на которую попадаются все.

```js
// Плохо: «Готово» напечатается раньше, чем сохранится хоть один элемент
items.forEach(async (item) => {
  await save(item);
});
console.log('Готово');
```

`forEach` не смотрит на возвращаемое значение колбэка. Он вызывает функцию, получает промис, выбрасывает его и идёт дальше. Ошибки внутри колбэков тоже никто не поймает.

```js
// Хорошо, если нужна параллельность
await Promise.all(items.map(item => save(item)));

// Хорошо, если нужна последовательность
for (const item of items) await save(item);
```

Правило: **встроенные методы массива не умеют ждать**. Это касается `forEach`, `map`, `filter`, `reduce`, `sort`. `map` хотя бы возвращает массив промисов, который можно отдать в `Promise.all`; `filter` с асинхронным предикатом просто сломается — промис всегда истинный, поэтому фильтр пропустит всё.

### Забытый `await` перед возвратом

```js
async function load() {
  try {
    return fetchData();        // без await
  } catch (e) {
    return fallback();         // сюда НЕ попадём
  }
}
```

Без `await` функция возвращает промис и выходит из `try` **до** того, как промис отклонится. Ловить уже нечего — `catch` бесполезен. С `await` перед `return` ошибка бросается внутри `try`, и всё работает.

Вне `try/catch` `return promise` и `return await promise` дают одинаковый результат, но `return await` тратит лишний оборот микрозадач. Внутри `try` — обязательно `await`. Ещё одна причина писать `return await`: без него сломанный промис не попадёт в стек трассировки этой функции, и в отчёте об ошибке её не будет видно.

## Часть 5. `for await...of` и асинхронные итераторы

**Итератор** — объект с методом `next()`, который выдаёт значения по одному. Обычный `for...of` работает с ним синхронно. **Асинхронный итератор** — тот же интерфейс, но `next()` возвращает промис.

`for await...of` — цикл, который на каждой итерации делает `await` над результатом `next()`.

```js
for await (const chunk of stream) {
  process(chunk);       // обрабатываем по мере поступления
}
```

Зачем: данные, которых заранее нет целиком. Чтение тела ответа кусками, постраничная выгрузка, поток событий. Вместо «дождись всего массива» получается «обрабатывай по мере готовности» — первый кусок можно показать сразу.

Свой асинхронный источник пишется через `async function*`:

```js
async function* pages(url) {
  let next = url;
  while (next) {
    const res = await fetch(next);
    const data = await res.json();
    yield data.items;         // отдаём страницу
    next = data.nextUrl;      // курсор следующей приходит с текущей
  }
}

for await (const items of pages('/api/items')) {
  render(items);              // рисуем каждую страницу, не дожидаясь последней
}
```

Обрати внимание: `for await...of` **строго последовательный**. Если источник — обычный массив промисов, он будет ждать их по одному, что почти всегда не то, что нужно. Для параллельности — `Promise.all`.

## Часть 6. Отмена и таймауты

Отменить `await` нельзя — как нельзя отменить и сам промис (см. [промисы изнутри](./promises)). Прерывается операция, а `await` при этом просто бросит ошибку.

```js
const controller = new AbortController();

async function load(signal) {
  try {
    const res = await fetch('/api/data', { signal });
    return await res.json();
  } catch (err) {
    if (err.name === 'AbortError') return null;   // отменили сами
    throw err;
  }
}
```

Таймаут проще всего сделать готовым сигналом, который прерывает запрос по-настоящему:

```js
const res = await fetch(url, { signal: AbortSignal.timeout(5000) });
```

Вариант через `Promise.race` с таймером тоже работает, но запрос при этом продолжает идти — гонка лишь перестаёт ждать его результат.

Отдельная неприятность: после `await` компонент мог размонтироваться. Проверять «жив ли я» флагом — обычная практика, но лучше прерывать саму операцию сигналом, иначе запрос доработает впустую.

## Часть 7. `await` на верхнем уровне модуля

В ES-модулях (`<script type="module">` или файл, собранный сборщиком) `await` разрешён вне функций.

```js
// config.js — модуль
const res = await fetch('/config.json');
export const config = await res.json();
```

Что происходит механически: модуль с верхнеуровневым `await` сам становится асинхронным, и **все модули, которые его импортируют, ждут его завершения** перед выполнением своего кода. Порядок импортов при этом сохраняется.

Ограничения, о которых стоит знать:

- Только в модулях. В обычном `<script>` и в CommonJS — синтаксическая ошибка.
- Задерживает старт всего дерева зависимостей. Медленный запрос в верхнеуровневом `await` откладывает выполнение всего приложения.
- Ошибка при таком `await` ломает загрузку модуля целиком.

Хорошее применение — выбор реализации на старте (`const db = await import(useMock ? './mock' : './real')`), инициализация WebAssembly. Плохое — грузить в нём данные, которые может подождать интерфейс.

## Часть 8. Распространённые ошибки, коротко

**`await` в цикле там, где итерации независимы.** Время растёт линейно вместо константы. Проверка: использует ли итерация результат предыдущей.

**Забытый `await`.** Функция вернёт промис вместо значения, а ошибка станет необработанным отклонением. Симптом — `[object Promise]` в интерфейсе или «Готово» раньше готовности. Линтер с правилами `no-floating-promises` и `require-await` находит это заранее.

**`forEach` с `async`-колбэком.** Не ждёт ничего и глотает ошибки.

**`try` без `await` внутри.** `catch` не сработает.

**`await` внутри конструктора класса.** Не разрешён: конструктор не может быть асинхронным. Обычное решение — статический фабричный метод.

```js
class Repo {
  static async create() {
    const conn = await connect();
    return new Repo(conn);
  }
}
```

**Лишний `async`.** Функция без `await` внутри не нуждается в `async` — он только оборачивает результат в промис и добавляет оборот очереди. Исключение: если функция обязана возвращать промис по контракту.

**`await` внутри синхронного колбэка.** `array.map(async x => ...)` вернёт массив промисов, а не значений — иногда это ровно то, что нужно (отдать в `Promise.all`), но чаще неожиданность.

## Что спросят на интервью

**Что возвращает `async`-функция, если внутри `return 1`?** Промис, разрешённый единицей. `async` всегда возвращает промис.

**Блокирует ли `await` поток?** Нет. Он снимает функцию со стека и превращает остаток в микрозадачу. Главный поток в это время выполняет другой код.

**Синхронно ли выполняется код в начале `async`-функции?** Да, всё до первого `await` идёт синхронно, на стеке вызывающего.

**Что выведет код с `await`, `setTimeout` и `.then`?** Продолжения после `await` — микрозадачи, они выполняются раньше любого таймера. Разбор по шагам — в части 2.

**В чём разница между тремя `await` подряд и `Promise.all`?** Последовательные `await` не дают следующему запросу стартовать. `Promise.all` запускает всё сразу и ждёт самый долгий.

**Почему `try/catch` не поймал ошибку?** Скорее всего, промис не дождались через `await`, или ошибка произошла в колбэке таймера или события — там свой стек.

**Почему `forEach` с `async`-колбэком не работает?** `forEach` игнорирует возвращаемое значение колбэка, ждать ему нечего. Нужен `for...of` или `Promise.all(map(...))`.

**В чём разница `return promise` и `return await promise`?** Вне `try/catch` — только в лишнем обороте микрозадач. Внутри `try` — принципиальная: без `await` ошибка не будет поймана. И без `await` вызов не попадёт в стек трассировки.

**Зачем `for await...of`?** Для источников, которые выдают данные порциями во времени. Обрабатывает по мере поступления, строго последовательно.

**Что даёт `await` на верхнем уровне модуля?** Модуль становится асинхронным, импортирующие его модули ждут завершения. Работает только в ES-модулях.

## Коротко, для повторения

1. `async` делает две вещи: функция всегда возвращает промис и внутри разрешён `await`. Ничего другого он не делает.
2. `throw` внутри `async`-функции превращается в отклонение возвращённого промиса, а не в исключение наружу.
3. Код до первого `await` выполняется синхронно, на стеке вызывающего.
4. `await` не ждёт — он снимает функцию со стека и делает остаток микрозадачей. Каждый `await` это ещё один оборот очереди.
5. Между кусками функции выполняется чужой код. Состояние, прочитанное до `await`, могло устареть после.
6. Промис стартует при создании, а не при `await`. Отсюда параллельность: сначала запусти всё, потом жди.
7. Последовательные `await` независимых операций — главная ошибка производительности. Проверка: нужен ли следующей строке результат предыдущей.
8. `try/catch` ловит только то, что прошло через `await`. Вызов без `await`, колбэк таймера и обработчик события — мимо.
9. `forEach` и другие методы массива не умеют ждать. Нужен `for...of` или `Promise.all(map(...))`.
10. Внутри `try` пиши `return await`, иначе `catch` бесполезен.
11. `for await...of` обрабатывает поток по мере поступления и всегда последовательно.
12. Отменяется не `await`, а операция — через `AbortController`; `await` при этом бросит `AbortError`.
