# Работа с данными: гонки, кеш, оптимистичность

Загрузка данных выглядит как самая простая часть фронтенда: позвал сервер, получил JSON, показал. На собеседовании эта тема — одна из самых злых именно потому, что кажется простой. Стандартный вопрос «напишите загрузку списка в компоненте» отделяет тех, кто помнит про отмену устаревшего ответа, от тех, кто не помнит.

Разберём по шагам: что именно ломается в наивном коде, какие проблемы решает кеш, как устроены оптимистичные обновления и где проходит граница, за которой библиотеку писать самому не надо.

Все примеры на React и `fetch`, но проблемы не про React: гонка запросов ломает и Vue, и код без фреймворка вообще.

## Часть 1. Что приходится написать самому

Начнём с кода, который пишет каждый и который почти правильный.

```jsx
// Было: обычный запрос в компоненте
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch(`/api/users/${userId}`)
      .then((r) => r.json())
      .then((data) => { setUser(data); setLoading(false); })
      .catch((e) => { setError(e); setLoading(false); });
  }, [userId]);

  if (loading) return <Spinner />;
  if (error) return <Error error={error} />;
  return <Profile user={user} />;
}
```

Перечислим, что здесь не так. Не придирки, а вещи, которые ломаются в проде.

**Ошибки HTTP не ловятся.** `fetch` отклоняет промис только при сетевом сбое. Ответ 500 или 404 — это успешный промис, и `r.json()` попытается разобрать HTML страницы ошибки. Ловится сетевой сбой, а не отказ сервера.

**Гонка запросов.** Быстро сменили `userId` — ответы могут прийти в обратном порядке, и на экране окажется чужой профиль. Разбираем в части 2.

**Обновление размонтированного компонента.** Ушли со страницы до ответа — `setUser` вызовется у мёртвого компонента. Утечки памяти это уже не вызывает, но лишняя работа и невидимые ошибки остаются. Про то, как такое течёт в других случаях, — в статье [память и утечки](./memory-and-leaks).

**Нет дедупликации.** Три компонента на экране просят одного пользователя — три одинаковых запроса.

**Нет кеша.** Ушли на соседнюю страницу и вернулись — грузим заново, показываем спиннер вместо мгновенных данных.

**Нет повтора.** Одна упавшая по таймауту сеть — и экран с ошибкой, хотя достаточно было попробовать ещё раз.

**Нет фонового обновления.** Вкладка провисела два часа — данные протухли, и никто их не обновил.

**Спиннер вместо данных при перезагрузке.** `setLoading(true)` на каждый заход означает, что даже при наличии старых данных пользователь видит пустой экран.

Восемь пунктов, из которых наивный код не решает ни одного. Именно это и есть ответ на вопрос «зачем нужна библиотека для запросов»: не потому что `fetch` неудобен, а потому что вокруг него нужно восемь механизмов.

## Часть 2. Гонки запросов

Самая частая и самая коварная проблема. Коварная — потому что на быстром интернете разработчика не воспроизводится.

Механика: пользователь набирает в поиске «а», потом «аб», потом «абв». Уходят три запроса. Ответ на «а» — это тяжёлая выборка (много совпадений), ответ на «абв» — лёгкая. Второй приходит раньше первого. Последним `setState` выигрывает ответ на «а», и в поле написано «абв», а в списке результаты по «а».

Три способа лечения, от простого к правильному.

### Способ 1. Флаг актуальности

```jsx
useEffect(() => {
  let actual = true;                 // замыкание живёт до следующего запуска эффекта

  fetch(`/api/search?q=${query}`)
    .then((r) => r.json())
    .then((data) => {
      if (actual) setResults(data);  // опоздавший ответ просто выбрасывается
    });

  return () => { actual = false; };  // очистка перед следующим запуском
}, [query]);
```

Работает так: React перед повторным запуском эффекта вызывает функцию очистки. Она переключает `actual` предыдущего запуска в `false`. Каждый запуск видит свою переменную — это обычное замыкание, подробнее в статье [область видимости и замыкания](./scope-and-closures).

Плюс: три строки, работает всегда. Минус: запрос продолжает выполняться и жрать сеть, результат просто игнорируется.

### Способ 2. Отмена через `AbortController`

```jsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${query}`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setResults)
    .catch((e) => {
      if (e.name === 'AbortError') return;   // штатная отмена, не ошибка
      setError(e);
    });

  return () => controller.abort();
}, [query]);
```

Здесь запрос действительно прерывается: браузер закрывает соединение, сервер может это заметить. Обязательный нюанс — отмена приходит в `catch` как исключение с именем `AbortError`, и её нельзя показывать пользователю как ошибку.

Это правильный способ по умолчанию. Он экономит и сеть, и слоты соединений: браузер держит ограниченное число одновременных запросов к одному домену, и висящие ненужные запросы задерживают нужные.

### Способ 3. Сверка ключа при записи

```jsx
const lastRequested = useRef(null);

async function search(query) {
  lastRequested.current = query;
  const data = await api.search(query);

  // пишем, только если за время ожидания запрос не сменился
  if (lastRequested.current === query) setResults(data);
}
```

Пригождается, когда запросы идут не из эффекта, а из обработчиков, и общего места для очистки нет. По сути тот же флаг, но привязанный к смыслу запроса, а не к запуску эффекта.

**Что выбирать.** Отмену — как основной механизм. Сверку ключа — как страховку в местах, где отмена невозможна (например, запрос уже ушёл в очередь на повтор). Библиотеки кеша делают обе вещи сами, привязывая ответ к ключу запроса.

Отдельно: гонка бывает не только при смене параметра, но и при повторяющемся действии. Пользователь дважды нажал «сохранить» — уходят два PUT, и порядок их применения на сервере не гарантирован. Здесь лечит не отмена, а блокировка кнопки на время отправки — то самое состояние `submitting` из статьи [где должно жить состояние](./state-management-patterns).

## Часть 3. Дедупликация в полёте

Экран заказа: шапка показывает имя клиента, боковая панель — его баланс, футер — ссылку на профиль. Три компонента, каждый честно вызывает свой хук `useUser(clientId)`. Уходит три одинаковых запроса.

Решение — реестр запросов «в полёте»: если такой запрос уже идёт, второй вызывающий получает **тот же промис**, а не новый запрос.

```js
// Стало: минимальный дедупликатор
const inFlight = new Map();

function dedupedFetch(key, fn) {
  if (inFlight.has(key)) return inFlight.get(key);   // подписываемся на существующий

  const promise = fn().finally(() => {
    inFlight.delete(key);          // чистим сразу, чтобы следующий вызов пошёл в сеть
  });

  inFlight.set(key, promise);
  return promise;
}

dedupedFetch(`user:${id}`, () => api.getUser(id));
```

Тонкость в `finally`: удалять запись надо и при успехе, и при ошибке. Если оставить упавший промис в реестре, все последующие вызовы будут получать ту же ошибку, и починиться приложение сможет только перезагрузкой.

Заметь, что дедупликация — не то же самое, что кеш. Дедупликация склеивает **одновременные** запросы, кеш переиспользует **уже полученный** результат. Библиотеки делают и то и другое, но это два разных механизма.

## Часть 4. Кеш: ключ, устаревание, инвалидация

Кеш серверных данных стоит на трёх понятиях.

### Ключ

Ключ — это то, что однозначно описывает запрос. Обычно массив: имя ресурса плюс все параметры, влияющие на ответ.

```js
['users']                                  // список
['users', userId]                          // один
['orders', { status: 'paid', page: 2 }]    // список с фильтрами
```

Правило простое и жёсткое: **всё, что попадает в URL запроса, должно быть в ключе**. Забыл параметр — получишь ответ на другой запрос под тем же ключом, и это баг, который выглядит как «иногда показываются данные из прошлого фильтра».

Обратное тоже верно: не клади в ключ то, что на ответ не влияет. Ключ с временной меткой означает промах кеша каждый раз, то есть кеша нет.

### Устаревание

Данные в кеше бывают трёх видов, и путать их — типичная ошибка на собеседовании.

**Свежие** (fresh) — с момента загрузки прошло меньше, чем время свежести. Новый вызов берёт из кеша и в сеть не идёт вообще.

**Устаревшие** (stale) — время свежести прошло. Данные всё ещё показываются, но новый вызов запустит фоновое обновление.

**Удалённые из кеша** (garbage collected) — данными долго никто не пользовался, запись выбросили, чтобы не росла память. Следующий вызов начнётся с нуля, со спиннером.

Разница между «устарело» и «выброшено» — ключевая. Устаревшие данные всё ещё показываются, и в этом смысл.

### Stale-while-revalidate

Идея, вокруг которой построены все современные библиотеки данных, а заодно и одноимённая директива HTTP-кеша: **покажи что есть, параллельно сходи за новым, замени когда придёт**.

```jsx
// Было: спиннер при каждом заходе
if (loading) return <Spinner />;
return <List items={items} />;

// Стало: спиннер только когда показывать нечего
if (!data && isPending) return <Spinner />;         // первая загрузка
return (
  <>
    {isFetching && <TopProgressBar />}              // фоновое обновление
    <List items={data} />
  </>
);
```

Разница для пользователя огромная: вместо мигания спиннером при каждой навигации он видит данные мгновенно, а обновление замечает только как короткую полоску сверху. Обрати внимание на два разных флага: «идёт первая загрузка, показывать нечего» и «идёт любая загрузка, включая фоновую».

### Инвалидация

После изменения данных кеш надо пометить неактуальным. Есть три стратегии, и выбирать между ними надо осознанно.

**Инвалидация по ключу.** Пометить записи устаревшими, и активные экраны сами перезапросят. Самый надёжный вариант: источник истины остаётся на сервере.

```js
await api.createOrder(payload);
queryClient.invalidateQueries({ queryKey: ['orders'] });
// префикс: инвалидируются и ['orders'], и ['orders', {page: 2}]
```

**Запись ответа в кеш.** Сервер вернул созданный объект — положить его сразу, не делая второй запрос.

```js
const created = await api.createOrder(payload);
queryClient.setQueryData(['orders', created.id], created);
```

**Оптимистичное обновление.** Изменить кеш до ответа сервера. Разбираем в следующей части.

Практический совет: **по умолчанию инвалидируй**. Ручное обновление кеша даёт минус один запрос, но появляется риск, что твоё представление о результате не совпадёт с серверным — сервер мог проставить статус, посчитать скидку, изменить порядок сортировки.

## Часть 5. Оптимистичные обновления

**Оптимистичное обновление** — показать результат до того, как сервер подтвердил. Пользователь жмёт «лайк», сердечко закрашивается мгновенно, запрос уходит фоном. Если сервер откажет — возвращаем как было.

Приём нужен там, где вероятность отказа мала, а задержка заметна: лайки, чекбоксы, drag-and-drop, добавление в избранное.

```jsx
// Было: ждём сервер, интерфейс подтормаживает
async function toggleLike(postId) {
  setPending(true);
  await api.toggleLike(postId);
  await refetchPost(postId);      // ещё один круг по сети
  setPending(false);
}
```

Пользователь нажал — ничего не произошло — через 400 мс сердечко закрасилось. Ощущается как тормоза, даже когда сеть быстрая.

```jsx
// Стало: применяем сразу, откатываем при ошибке
const mutation = useMutation({
  mutationFn: (postId) => api.toggleLike(postId),

  onMutate: async (postId) => {
    // 1. Отменяем текущие запросы этого ключа: иначе ответ старого
    //    запроса перезапишет наше оптимистичное значение
    await queryClient.cancelQueries({ queryKey: ['post', postId] });

    // 2. Запоминаем состояние до изменения — это и есть точка отката
    const previous = queryClient.getQueryData(['post', postId]);

    // 3. Применяем ожидаемое изменение
    queryClient.setQueryData(['post', postId], (old) => ({
      ...old,
      liked: !old.liked,
      likes: old.likes + (old.liked ? -1 : 1),
    }));

    return { previous };
  },

  onError: (err, postId, context) => {
    // 4. Не вышло — возвращаем ровно то, что было
    queryClient.setQueryData(['post', postId], context.previous);
    toast.error('Не удалось поставить лайк');
  },

  onSettled: (data, err, postId) => {
    // 5. В любом случае сверяемся с сервером
    queryClient.invalidateQueries({ queryKey: ['post', postId] });
  },
});
```

Пять шагов, и все пять обязательны. Разберём, почему.

**Отмена текущих запросов (шаг 1)** — самый пропускаемый. Если в этот момент уже летит фоновое обновление поста, его ответ придёт со старым значением `liked` и затрёт оптимистичное. Пользователь увидит, как сердечко закрасилось и тут же погасло.

**Снимок предыдущего значения (шаг 2)** — именно снимок, а не «вычислим обратную операцию». Обратная операция кажется проще (`likes - 1`), но она неверна, если за это время значение изменилось по другой причине.

**Сверка после (шаг 5)** нужна даже при успехе: сервер мог посчитать иначе. Например, лайк был уже поставлен с другого устройства, и счётчик отличается от нашего предсказания.

### Несколько быстрых действий подряд

Здесь простая схема ломается. Пользователь трижды подряд кликает по лайку.

Что происходит с наивным откатом: первая мутация сняла снимок «не лайкнут». Вторая мутация сняла снимок «лайкнут» (то есть оптимистичное значение первой, ещё не подтверждённое). Первая падает — откат вернёт «не лайкнут», перечеркнув вторую и третью.

Три рабочих подхода:

**Блокировать, пока идёт.** Самое простое: кнопка `disabled` во время мутации. Годится для «сохранить», не годится для лайка — быстрое переключение должно работать.

**Считать оптимистичное состояние от количества мутаций в полёте.** Не менять кеш напрямую, а накладывать все активные мутации поверх серверных данных при рендере. Тогда откат — это просто исчезновение мутации из списка, и порядок неважен.

```jsx
// Оптимистичное значение как наложение, а не как запись в кеш
const pending = useMutationState({
  filters: { mutationKey: ['like', postId], status: 'pending' },
  select: (m) => m.state.variables,
});

// сервер сказал одно, поверх накладываем все незавершённые действия
const liked = pending.length > 0 ? pending.at(-1).liked : post.liked;
```

**Схлопывать очередь.** Для переключателей осмысленно только последнее значение: отменить предыдущую мутацию и отправить актуальную. Это тот же приём, что и `debounce` у поиска, — про него подробно в статье [поиск и автодополнение](./search-and-autocomplete).

Практический совет: если действие идемпотентно и итоговое значение задаётся явно (`{ liked: true }`, а не «переключи»), гонка почти не страшна — последний ответ выигрывает и он же верный. Проблемы начинаются у операций-инкрементов.

## Часть 6. Водопад запросов

**Водопад** (waterfall) — ситуация, когда запросы идут последовательно, хотя могли бы идти параллельно. Каждый ждёт предыдущего, и общее время складывается.

```jsx
// Было: три уровня, три круга по сети
function Dashboard() {
  const { data: user } = useQuery({ queryKey: ['me'], queryFn: api.getMe });
  return user ? <Team teamId={user.teamId} /> : <Spinner />;
}

function Team({ teamId }) {
  const { data: team } = useQuery({ queryKey: ['team', teamId], queryFn: () => api.getTeam(teamId) });
  return team ? <Projects ids={team.projectIds} /> : <Spinner />;
}
```

Каждый следующий запрос не может начаться, пока не пришёл предыдущий: 200 мс плюс 200 мс плюс 200 мс — 600 мс до первого полезного пикселя. Причём часть зависимостей мнимая: список проектов, возможно, можно было запросить сразу, зная только идентификатор пользователя.

### Как увидеть

Открой панель Network в DevTools и посмотри на диаграмму справа. Водопад видно буквально: полоски идут лесенкой, каждая начинается там, где кончилась предыдущая. Параллельные запросы выглядят как полоски, начинающиеся на одной вертикали.

Второе место, где это видно, — панель Performance: запросы отображаются на общей шкале рядом с работой главного потока. Как её читать, разобрано в статье [как работает браузер](./browser-rendering-event-loop).

### Как чинить

**Убрать мнимые зависимости.** Если второй запрос не нуждается в ответе первого — запускай сразу.

```jsx
// Стало: запросы стартуют одновременно
const [user, projects] = useQueries({
  queries: [
    { queryKey: ['me'], queryFn: api.getMe },
    { queryKey: ['projects'], queryFn: api.getMyProjects },
  ],
});
```

**Поднять загрузку наверх.** Компоненты-дети, каждый со своим запросом, порождают водопад по уровням дерева. Загрузи всё нужное экрану на уровне маршрута.

**Предзагрузка по намерению.** Пользователь навёл курсор на ссылку — можно начать грузить данные заранее, не дожидаясь клика.

```js
<Link
  to={`/orders/${id}`}
  onMouseEnter={() => queryClient.prefetchQuery({
    queryKey: ['order', id],
    queryFn: () => api.getOrder(id),
  })}
/>
```

Между наведением и кликом обычно проходит 100–300 мс — этого часто хватает, чтобы страница открылась мгновенно.

**Попросить бэкенд.** Три круга по сети иногда чинятся одной ручкой, отдающей всё сразу. Это не хак, а нормальный разговор с командой бэкенда: сеть — самая дорогая часть.

## Часть 7. Список и детали

Типичный сценарий: список заказов, клик открывает подробности.

```jsx
// Было: клик — спиннер, хотя часть данных уже была
function OrderDetails({ id }) {
  const { data, isPending } = useQuery({
    queryKey: ['order', id],
    queryFn: () => api.getOrder(id),
  });
  if (isPending) return <Spinner />;
  return <Details order={data} />;
}
```

Список уже содержал номер, статус и сумму. Показать пустой экран, когда половина данных на руках, — расточительство.

```jsx
// Стало: начальные данные берём из списка
function OrderDetails({ id }) {
  const queryClient = useQueryClient();

  const { data, isPending, isFetching } = useQuery({
    queryKey: ['order', id],
    queryFn: () => api.getOrder(id),
    // подставляем то, что уже лежит в кеше списка
    placeholderData: () =>
      queryClient
        .getQueryData(['orders'])
        ?.find((o) => o.id === id),
  });

  if (isPending) return <Spinner />;    // сработает, только если в списке ничего не нашлось
  return <Details order={data} partial={isFetching} />;
}
```

Пользователь мгновенно видит шапку с номером и статусом, а подробности дорисовываются через мгновение. Ощущение скорости меняется радикально при том же времени ответа сервера.

Важное различие: `placeholderData` — это «показать вместо пустоты, но считать данные отсутствующими», а `initialData` — «считать это настоящими данными и положить в кеш». Второе применяй, только если данные действительно полные, иначе усечённая запись из списка попадёт в кеш как полноценная.

## Часть 8. Нормализация против вложенности

Лента постов, у каждого поста автор и счётчик лайков. Тот же пост открыт на отдельной странице. Пользователь лайкает в ленте — что должно произойти на странице поста?

При **вложенном** хранении (каждый ключ кеша держит свою копию) — ничего. Данные разъехались, и это тот же баг, что и дублирование состояния из статьи [где должно жить состояние](./state-management-patterns), только на уровне кеша.

```js
// Вложенно: пост существует в двух копиях
['feed']            // [{ id: 1, likes: 10, author: {...} }, ...]
['post', 1]         // { id: 1, likes: 10, author: {...} }
```

При **нормализованном** хранении сущность лежит в одном экземпляре, а списки хранят только идентификаторы:

```js
// Нормализованно: одна копия, ссылки по id
posts:   { 1: { id: 1, likes: 10, authorId: 7 } }
authors: { 7: { id: 7, name: 'Ася' } }
feed:    [1, 4, 9]
```

Обновили `posts[1].likes` — обновилось везде, потому что везде одна и та же запись.

Цена нормализации: нужен слой, который разбирает ответы на сущности и собирает обратно при чтении. Это делают клиенты GraphQL, где у объектов есть `__typename` и `id`, и делают нормализующие хранилища. В обычном REST-кеше типа TanStack Query нормализации нет по умолчанию — и это осознанное решение авторов.

Практичный средний путь без нормализации:

```js
// Инвалидировать всё, где может встречаться этот пост
onSettled: () => {
  queryClient.invalidateQueries({ queryKey: ['post', id] });
  queryClient.invalidateQueries({ queryKey: ['feed'] });
}
```

Минус — лишние запросы. Плюс — нет слоя нормализации, и данные точно не разъедутся, потому что источником истины остаётся сервер.

Когда нормализация окупается: одна сущность встречается во многих списках, обновления частые, приложение большое и живёт долго на одной вкладке. Когда нет: экраны независимы, пересечений мало.

## Часть 9. Пагинация и бесконечная лента

Обычная пагинация со страницами кладётся в кеш естественно: страница — часть ключа.

```js
queryKey: ['orders', { page, status }]
```

Проблема одна: при переходе на страницу 2 ключ меняется, данных под ним нет, показывается спиннер, таблица схлопывается в ноль высоты и страницу дёргает. Лечится тем, что предыдущие данные остаются на экране, пока грузятся новые:

```js
const { data, isPlaceholderData } = useQuery({
  queryKey: ['orders', { page }],
  queryFn: () => api.getOrders(page),
  placeholderData: keepPreviousData,   // показываем прошлую страницу, пока грузится новая
});
// таблицу можно приглушить, пока isPlaceholderData === true
```

Бесконечная лента устроена иначе: все загруженные страницы лежат под **одним** ключом как массив страниц. Это важно, потому что инвалидация должна перезагрузить все загруженные страницы разом — иначе лента станет несогласованной.

```js
const { data, fetchNextPage, hasNextPage } = useInfiniteQuery({
  queryKey: ['feed'],
  queryFn: ({ pageParam }) => api.getFeed({ cursor: pageParam }),
  initialPageParam: null,
  getNextPageParam: (last) => last.nextCursor ?? undefined,  // undefined = конец
});

const items = data?.pages.flatMap((p) => p.items) ?? [];
```

Отдельно про **курсорную** пагинацию против **страничной**. При страничной (`?page=2`) добавление нового элемента в начало сдвигает всё: элемент, бывший последним на первой странице, окажется первым на второй, и пользователь увидит его дважды. Курсорная (`?after=id`) от этого свободна: сервер отдаёт то, что идёт после конкретного элемента. Для лент, куда постоянно добавляют сверху, курсор обязателен.

Хранение всех страниц в памяти — это не бесплатно. Три тысячи элементов ленты живут в кеше и держатся в DOM, если не применена виртуализация. Про то, как показывать десять тысяч строк, не создавая десять тысяч узлов, — в статье [бесконечный список и виртуализация](./infinite-list-and-virtualization).

## Когда не надо

**Не тащи библиотеку кеша ради двух запросов.** Один экран с одной загрузкой — это `useEffect` с `AbortController` и три состояния. Сорок килобайт зависимости и новый набор понятий здесь не окупаются.

**Не делай оптимистичным то, что часто падает.** Оплата, отправка формы с серверной валидацией, любое действие с проверкой прав. Пользователь увидит успех, потом откат и сообщение об ошибке — это хуже, чем честное ожидание. Оптимистичность годится, когда отказ — редкость.

**Не оптимистичен и тот случай, где откат непонятен пользователю.** Перетащил карточку в другую колонку, ушёл читать соседнюю секцию, через две секунды карточка прыгнула обратно — он этого не увидит и решит, что данные потерялись.

**Не увеличивай время свежести бездумно.** Долгий `staleTime` убирает запросы, но приносит устаревшие данные. Для остатков на складе или курса валют это прямой ущерб. Для справочника городов — наоборот, разумно.

**Не нормализуй маленькое приложение.** Слой нормализации — это код, который надо писать и отлаживать. Пока пересечений между экранами мало, инвалидация по ключам проще и надёжнее.

**Не переноси всю фильтрацию на клиент, чтобы «избежать запросов».** Загрузить десять тысяч записей и фильтровать локально кажется быстрым решением, пока записей не стало сто тысяч. Фильтрация — работа сервера.

**Не глуши ошибки повторами.** Автоповтор осмыслен для сетевых сбоев и 5xx. Повторять 400 или 403 бессмысленно: ответ не изменится, а пользователь три раза подождёт таймаут. Про разделение ожидаемых и неожиданных ошибок — в статье [ошибки и отладка](./errors-and-debugging).

## Что спросят на интервью

**Напишите загрузку данных в компоненте. Что здесь не так?** Правильный ответ начинается с гонки запросов и отмены, продолжается проверкой `response.ok` и заканчивается перечислением того, чего нет: дедупликации, кеша, повтора, фонового обновления.

**Что такое гонка запросов и три способа её решить?** Ответы приходят не в том порядке, в котором ушли. Флаг актуальности в очистке эффекта, `AbortController`, сверка ключа при записи результата. Отмена предпочтительнее: экономит сеть.

**Чем отличается «устарело» от «удалено из кеша»?** Устаревшие данные показываются и обновляются в фоне. Удалённые из кеша отсутствуют, и следующий заход начнётся со спиннера. Это два разных таймера.

**Что такое stale-while-revalidate?** Показать имеющееся немедленно, параллельно запросить свежее, заменить по приходу. Спиннер остаётся только для случая, когда показывать нечего.

**Как сделать оптимистичное обновление правильно?** Отменить текущие запросы ключа, снять снимок, применить изменение, при ошибке вернуть снимок, в любом случае сверить с сервером. Пропуск отмены даёт мигание, пропуск снимка — неверный откат.

**Что будет при трёх быстрых кликах с оптимистичным обновлением?** Наивный откат первой мутации сотрёт результат второй и третьей. Лечится наложением активных мутаций поверх серверных данных, блокировкой на время отправки или схлопыванием очереди до последнего значения.

**Что такое водопад запросов и как его найти?** Последовательные запросы там, где могли быть параллельные. Видно в панели Network как лесенку. Чинится параллельным запуском, подъёмом загрузки на уровень маршрута, предзагрузкой и объединением ручек на бэкенде.

**Нормализовать кеш или нет?** Нормализация нужна, когда одна сущность встречается во многих списках и часто меняется: лайк в ленте должен отразиться на открытом посте. Иначе проще инвалидация по ключам — источник истины остаётся на сервере.

**Чем курсорная пагинация лучше страничной?** Она устойчива к вставкам: смещение по номеру страницы приводит к дублям и пропускам, когда список меняется во время просмотра.

## Коротко, для повторения

1. Наивная загрузка в компоненте не решает восемь задач: ошибки HTTP, гонку, отмену, дедупликацию, кеш, повтор, фоновое обновление, показ старых данных вместо спиннера.
2. `fetch` не отклоняет промис на 404 и 500. Проверяй `response.ok` руками.
3. Гонка лечится флагом актуальности, `AbortController` или сверкой ключа. Основной способ — отмена.
4. Дедупликация склеивает одновременные запросы, кеш переиспользует полученные. Это разные механизмы.
5. Ключ кеша содержит всё, что влияет на ответ, и ничего лишнего.
6. Свежее — из кеша молча. Устаревшее — показать и обновить в фоне. Отсутствующее — спиннер.
7. Оптимистичное обновление — пять шагов, и отмена текущих запросов среди них обязательна.
8. Откат делается к снимку, а не обратной операцией. При нескольких действиях подряд снимки нельзя брать наивно.
9. Водопад видно в панели Network лесенкой. Параллельный запуск, подъём загрузки, предзагрузка по наведению.
10. Данные для деталей часто уже лежат в кеше списка — подставляй их вместо спиннера.
11. Нормализация решает «лайк в ленте и открытый пост», но стоит отдельного слоя. Средний путь — инвалидация обоих ключей.
12. Бесконечная лента живёт под одним ключом массивом страниц; для лент с вставками нужен курсор, а не номер страницы.
