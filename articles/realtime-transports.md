# Реалтайм: polling, SSE и WebSocket

Обычный HTTP устроен так: клиент спросил — сервер ответил — соединение свободно. Сервер не может сам постучаться в браузер. А задач, где данные рождаются на сервере и нужны немедленно, полно: чат, уведомления, курс валют, статус заказа, кто сейчас редактирует документ.

Есть три способа обойти это ограничение, и выбор между ними — классический вопрос на senior-собеседовании. Но настоящая проверка начинается после выбора: живое соединение — это не «открыл сокет и радуйся». Оно рвётся, молча умирает за прокси, дублирует сообщения при переподключении и открывается по копии в каждой вкладке. Всё это надо написать самому, потому что браузер этого не делает.

Статья про то, как выбрать транспорт и что придётся дописать вокруг него.

### Таблица выбора

| Критерий | Polling | SSE | WebSocket |
|---|---|---|---|
| Направление | клиент спрашивает | сервер → клиент | в обе стороны |
| Задержка доставки | до интервала опроса | почти мгновенно | почти мгновенно |
| Накладные расходы | заголовки на каждый запрос | одни заголовки на всё соединение | рукопожатие один раз, дальше кадры по 2–14 байт |
| Нагрузка на сервер | всплески запросов | долгое соединение на клиента | долгое соединение на клиента |
| Сложность клиента | минимальная | низкая | высокая: всё пишешь сам |
| Прокси и корпоративные сети | проходит всегда | проходит почти всегда | ломается заметно чаще |
| Кеш, куки, коды ошибок | как обычно | как обычно | заново |
| Переподключение | не нужно | у `EventSource` бесплатно | пишешь сам |
| Бэкенд | любой | любой, умеющий долгий ответ | нужна поддержка сокетов и общая шина |

Как выбирать на практике:

- **Данные нужны раз в минуту, обновление не критично по секундам** — polling. Не стесняйся: это меньше кода, меньше инфраструктуры и меньше способов сломаться.
- **Данные идут только вниз, но нужны сразу** — SSE. Лента уведомлений, статус длинной операции, обновление дашборда, ответ модели.
- **Трафик в обе стороны и часто** — WebSocket. Чат, совместное редактирование, игры, набранный текст с индикатором «печатает».

Ошибка, которую делают чаще всего: берут WebSocket «на вырост», получают в нагрузку переподключение, heartbeat, очередь сообщений и проблемы с прокси — ради односторонней ленты, где хватило бы SSE.

## Часть 2. Polling

### Короткий polling

Просто спрашиваем по таймеру:

```js
async function poll(url, onData, intervalMs) {
  while (true) {
    try {
      const data = await fetch(url).then(r => r.json());
      onData(data);
    } catch {
      // сеть моргнула — просто подождём и попробуем снова
    }
    await new Promise(r => setTimeout(r, intervalMs));
  }
}
```

Обрати внимание: пауза **после** ответа, а не `setInterval`. С `setInterval` при медленном сервере запросы наложатся друг на друга — классический способ уронить свой же бэкенд.

Цена короткого опроса считается легко. Тысяча пользователей, интервал 5 секунд — 200 запросов в секунду, из которых 95% возвращают «ничего нового». Каждый несёт полный набор заголовков и куки: полезных данных ноль, трафика — килобайт.

Задержка тоже честная: событие произошло сразу после запроса — пользователь узнает через полный интервал.

Что улучшает картину малой кровью:

- **`ETag` и `If-None-Match`.** Сервер отвечает **304 Not Modified** без тела, если ничего не изменилось. Трафик падает в разы, число запросов — нет.
- **Курсор вместо полной выдачи.** Клиент шлёт идентификатор последнего известного события, сервер отдаёт только новое. Заодно это готовая механика восстановления, которая понадобится дальше.
- **Пауза, когда вкладка скрыта.** Обязательно — иначе десять открытых вкладок долбят сервер вхолостую.

```js
document.addEventListener('visibilitychange', () => {
  if (document.hidden) stopPolling();
  else { startPolling(); refreshNow(); }   // вернулись — сразу обновить, не ждать интервал
});
```

### Длинный polling

**Длинный polling** (long polling) — тот же запрос, но сервер не отвечает сразу. Он держит его открытым, пока не появится событие или не выйдет таймаут (обычно 30 секунд). Ответил — клиент немедленно шлёт следующий запрос.

Результат: задержка доставки почти нулевая, а пустых ответов почти нет.

```js
async function longPoll(url, onEvent) {
  let cursor = null;
  let attempt = 0;

  while (true) {
    try {
      const response = await fetch(url + (cursor ? '?after=' + cursor : ''));
      if (!response.ok) throw new Error('HTTP ' + response.status);

      const batch = await response.json();
      for (const event of batch.events) { onEvent(event); cursor = event.id; }
      attempt = 0;                                       // успех — сброс паузы
    } catch {
      attempt++;
      await new Promise(r => setTimeout(r, Math.min(2 ** attempt * 500, 30000)));
    }
  }
}
```

Цена: соединение держится долго, то есть по нагрузке это уже почти как SSE, но с повторным рукопожатием после каждого события. При частых событиях длинный polling вырождается в короткий с оверхедом.

**Когда polling — правильный выбор:** данные меняются редко; аудитория маленькая; бэкенд не готов к долгим соединениям; надёжность важнее задержки. Ещё один аргумент, о котором забывают: polling — единственный транспорт, который не ломается ни за одним прокси и не требует ничего писать про переподключение. Иногда это решающее.

## Часть 3. SSE как транспорт

Формат SSE и его разбор поверх `fetch` подробно разобраны в статье [про стриминг ответов](./streaming-responses). Здесь — про SSE именно как способ держать связь.

### Что даёт из коробки

`EventSource` делает три вещи, которые для WebSocket пришлось бы писать руками:

**Автоматическое переподключение.** Соединение оборвалось — браузер сам переподключится через паузу. Значение паузы сервер может задать полем `retry: 5000`.

**`Last-Event-ID`.** Если сервер присылал поле `id`, браузер запоминает последний и при переподключении отправляет заголовком `Last-Event-ID`. Сервер по нему отдаёт всё пропущенное. Это готовое восстановление без единой строки клиентского кода.

```
id: 4211
data: {"type":"message","text":"привет"}

id: 4212
data: {"type":"message","text":"как дела"}
```

Оборвалось после 4212 — при переподключении уйдёт `Last-Event-ID: 4212`, сервер начнёт с 4213. Единственное условие: сервер должен хранить историю событий хотя бы недолго.

**Типы событий.** Поле `event` разводит потоки по обработчикам, не заставляя изобретать своё поле внутри JSON.

### Ограничение на число соединений

В HTTP/1.1 браузер держит не больше **6 одновременных соединений на домен**. SSE занимает одно и не отпускает. Шесть вкладок одного сайта — и все шесть заняты: седьмая вкладка не подключится, а обычные запросы за данными встанут в очередь за живыми потоками.

Это не теория, а один из самых частых боевых сюрпризов: «у меня в седьмой вкладке приложение не грузится».

В **HTTP/2 ограничения нет**: все запросы к домену идут по одному TCP-соединению, мультиплексируются в потоки, и их лимит — сотни. Поэтому первое, что надо проверить, увидев проблему: работает ли сайт по HTTP/2 (в DevTools колонка Protocol покажет `h2`).

Если HTTP/2 недоступен, остаётся способ, который полезен и сам по себе, — держать **одно соединение на все вкладки**. К нему вернёмся в части 6.

### Чего SSE не умеет

- **Только текст.** Бинарные данные придётся кодировать, например в base64, с потерей трети объёма.
- **Только вниз.** Отправка наверх — обычным `fetch`, отдельным запросом. Для чата это нормально: сообщения отправляются нечасто.
- **`EventSource` только GET и без заголовков.** Обходится своим парсером поверх `fetch` — но тогда переподключение и `Last-Event-ID` тоже пишешь сам.

## Часть 4. WebSocket

### Рукопожатие

Сокет начинается как обычный HTTP-запрос со специальными заголовками:

```http
GET /socket HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

Код **101 Switching Protocols** означает: «этот TCP-канал больше не HTTP, дальше говорим кадрами WebSocket». `Sec-WebSocket-Accept` — хеш от ключа клиента: доказательство, что на том конце действительно WebSocket-сервер, а не случайно совпавший обработчик.

Практические следствия рукопожатия:

- **Схема `wss://`, а не `https://`.** Незашифрованный `ws://` со страницы на HTTPS браузер заблокирует. И `wss` заодно резко повышает шансы пройти через прокси, который не понимает Upgrade.
- **Заголовки задать нельзя.** Конструктор `WebSocket` не принимает заголовки — только URL и подпротоколы. Токен передают либо в query-строке (плохо: светится в логах), либо, что правильнее, отдельным сообщением сразу после соединения, либо коротким одноразовым тикетом в URL, полученным обычным HTTP-запросом.
- **Куки на тот же домен отправляются.** Это рабочий способ аутентификации, если фронт и сокет-сервер на одном домене.

### Кадры

После рукопожатия данные идут **кадрами** — короткими блоками со своим заголовком в 2–14 байт. Есть текстовые кадры, бинарные и служебные: ping, pong и close.

Важная деталь: браузерный API **не даёт отправлять ping**. Метод один — `send`. Служебные ping-кадры может слать сервер, и браузер ответит на них автоматически, но из JavaScript это невидимо и неуправляемо. Отсюда вывод, который дальше станет отдельным разделом: **прикладной heartbeat приходится делать своими сообщениями.**

### Голый API и чего в нём нет

```js
const socket = new WebSocket('wss://example.com/socket');

socket.addEventListener('open', () => socket.send(JSON.stringify({ type: 'hello' })));
socket.addEventListener('message', (e) => console.log(JSON.parse(e.data)));
socket.addEventListener('close', (e) => console.log('закрыт', e.code, e.reason, e.wasClean));
socket.addEventListener('error', () => console.log('что-то пошло не так'));
```

Чего здесь нет и что придётся дописать:

1. **Переподключения.** Закрылся — и всё, объект мёртв навсегда. Нужен новый.
2. **Определения «соединение живо».** `readyState` может показывать `OPEN`, когда физически связь уже потеряна.
3. **Очереди исходящих.** `send` при закрытом сокете бросает исключение, сообщение теряется.
4. **Гарантий доставки и порядка при переподключении.** Что не дошло — то не дошло.
5. **Внятных ошибок.** Событие `error` не несёт никакой информации: ни кода, ни причины. Всю диагностику приходится брать из `close`.

Коды закрытия, которые стоит различать: `1000` — нормальное закрытие; `1001` — уход со страницы; `1006` — **аварийный обрыв без кадра close** (самый частый в бою: сеть пропала, прокси убил соединение); `1008` и `1011` — отказ и ошибка сервера; `4000` и выше — коды приложения, ими сервер может сказать «токен протух, не переподключайся с этим».

## Часть 5. Что придётся написать самому

Это ядро статьи и то, ради чего вопрос задают на интервью. Собираем работающую обёртку по кускам.

### Переподключение с нарастающей паузой и джиттером

Наивное «оборвалось — подключаемся снова сразу» превращает упавший сервер в непрерывно обстреливаемый: как только он поднимется, вся аудитория ударит одновременно и уронит его снова. Это называется **громовое стадо** (thundering herd).

Два приёма против этого:

**Экспоненциальная задержка** (exponential backoff): пауза удваивается с каждой неудачей — 0.5 с, 1, 2, 4, 8, до потолка в 30 секунд.

**Джиттер** (jitter): случайная добавка. Без неё тысяча клиентов, оборвавшихся одновременно, и переподключаться будет одновременно — просто с общей паузой.

```js
function backoff(attempt, base = 500, cap = 30000) {
  const delay = Math.min(cap, base * 2 ** attempt);
  return delay / 2 + Math.random() * (delay / 2);   // «полный джиттер»: от половины до полной
}
```

Счётчик попыток обнуляется **не при открытии сокета, а после того, как соединение прожило разумное время** (скажем, 5 секунд). Иначе получится цикл: сервер принимает соединение и тут же рвёт, а клиент считает каждую попытку успешной и долбит без пауз.

### Heartbeat: зачем он нужен

Главная неочевидность живых соединений: **они умирают молча**. NAT на роутере, корпоративный прокси, балансировщик в облаке — все они выкидывают соединения, по которым долго не было трафика, обычно через 30–120 секунд. При этом уведомление о закрытии до клиента часто не доходит: с точки зрения браузера сокет по-прежнему `OPEN`, просто оттуда ничего не приходит. Клиент считает, что всё хорошо, и молча не получает данные.

Решение — **heartbeat**: клиент периодически шлёт короткое сообщение и ждёт ответа. Не пришёл ответ за отведённое время — считаем соединение мёртвым и переподключаемся, не дожидаясь события `close`, которого может не быть никогда.

Heartbeat решает две задачи разом: держит соединение «шумным», чтобы посредники его не убили, и даёт способ обнаружить обрыв.

```js
const PING_EVERY = 25000;   // чаще, чем типичный таймаут прокси в 30–60 секунд
const PONG_WITHIN = 10000;

startHeartbeat() {
  this.pingTimer = setInterval(() => {
    if (this.socket?.readyState !== WebSocket.OPEN) return;

    this.socket.send(JSON.stringify({ type: 'ping', t: Date.now() }));

    // Ответа нет — соединение мёртвое, каким бы ни был readyState
    this.pongTimer = setTimeout(() => this.socket?.close(4001, 'no pong'), PONG_WITHIN);
  }, PING_EVERY);
}

onPong() {
  clearTimeout(this.pongTimer);
}
```

Цена heartbeat: постоянный фоновый трафик и работа на клиенте даже когда ничего не происходит. На мобильном это будит радиомодуль и ест батарею, поэтому интервал не делают слишком коротким и heartbeat останавливают, когда вкладка скрыта.

### Очередь исходящих

Пока идёт переподключение, пользователь может нажать «отправить». Терять сообщение нельзя, бросать исключение — тем более.

Правильно: складывать в очередь и отправить, когда соединение вернётся. С двумя оговорками — очередь ограничена по размеру (иначе при долгом обрыве она съест память), и у сообщений есть срок годности (индикатор «печатает» через две минуты не нужен никому).

### Дедупликация и порядок

При переподключении почти неизбежны две беды.

**Дубли.** Клиент отправил сообщение, сеть оборвалась до подтверждения. Клиент не знает, дошло ли, и отправляет снова. Если дошли оба — в чате два одинаковых сообщения.

Лечится **ключом идемпотентности**: клиент генерирует `clientId` для каждого сообщения, сервер помнит уже виденные и второй раз не применяет. Тот же приём работает и во входящем направлении: клиент помнит идентификаторы последних полученных событий и повторы игнорирует.

**Порядок.** После переподключения может прийти вперемешку: часть событий из восстановленной истории, часть — свежие. Лечится тем же курсором: у событий сквозной возрастающий номер, клиент применяет только те, чей номер больше последнего применённого, а если обнаружил дырку — запрашивает пропущенное.

### Обёртка целиком

Собираем всё вместе. Этот класс можно переносить в проект.

```js
class ReliableSocket {
  constructor(url, { pingEvery = 25000, pongWithin = 10000, maxQueue = 100 } = {}) {
    this.url = url;
    this.options = { pingEvery, pongWithin, maxQueue };
    this.socket = null;
    this.attempt = 0;
    this.queue = [];              // исходящие, накопленные во время разрыва
    this.seen = new Set();        // идентификаторы применённых событий
    this.cursor = null;           // последний применённый номер
    this.closedByUs = false;
    this.listeners = new Set();
    this.timers = {};
  }

  connect() {
    this.closedByUs = false;
    const socket = new WebSocket(this.url + (this.cursor ? '?after=' + this.cursor : ''));
    this.socket = socket;

    socket.addEventListener('open', () => {
      // Счётчик сбрасываем не сразу, а когда соединение доказало живучесть
      this.timers.stable = setTimeout(() => { this.attempt = 0; }, 5000);
      this.flushQueue();
      this.startHeartbeat();
    });

    socket.addEventListener('message', (event) => this.handle(event.data));

    socket.addEventListener('close', (event) => {
      this.stopHeartbeat();
      clearTimeout(this.timers.stable);
      if (this.closedByUs) return;
      if (event.code === 4003) return;             // сервер сказал: не возвращайся
      this.scheduleReconnect();
    });

    // Событие error не несёт информации: реагируем на close, который придёт следом
    socket.addEventListener('error', () => {});
  }

  scheduleReconnect() {
    const delay = Math.min(30000, 500 * 2 ** this.attempt);
    const jittered = delay / 2 + Math.random() * (delay / 2);
    this.attempt++;
    this.timers.reconnect = setTimeout(() => this.connect(), jittered);
  }

  handle(raw) {
    let message;
    try { message = JSON.parse(raw); } catch { return; }

    if (message.type === 'pong') {
      clearTimeout(this.timers.pong);
      return;
    }

    // Дедупликация: повтор после переподключения игнорируем
    if (message.id != null) {
      if (this.seen.has(message.id)) return;
      this.seen.add(message.id);
      if (this.seen.size > 1000) {
        this.seen = new Set([...this.seen].slice(-500));   // не даём множеству расти вечно
      }
      this.cursor = message.id;
    }

    for (const listener of this.listeners) listener(message);
  }

  send(message) {
    if (this.socket?.readyState === WebSocket.OPEN) {
      this.socket.send(JSON.stringify(message));
      return;
    }
    // Соединения нет — в очередь, с ограничением и отметкой времени
    this.queue.push({ message, at: Date.now() });
    if (this.queue.length > this.options.maxQueue) this.queue.shift();
  }

  flushQueue() {
    const fresh = this.queue.filter(item => Date.now() - item.at < 60000);
    this.queue = [];
    for (const item of fresh) this.socket.send(JSON.stringify(item.message));
  }

  startHeartbeat() {
    this.timers.ping = setInterval(() => {
      if (this.socket?.readyState !== WebSocket.OPEN) return;
      this.socket.send(JSON.stringify({ type: 'ping' }));
      // Нет pong вовремя — рвём сами, не дожидаясь close, которого может не быть
      this.timers.pong = setTimeout(() => this.socket?.close(4001, 'no pong'), this.options.pongWithin);
    }, this.options.pingEvery);
  }

  stopHeartbeat() {
    clearInterval(this.timers.ping);
    clearTimeout(this.timers.pong);
  }

  on(listener) {
    this.listeners.add(listener);
    return () => this.listeners.delete(listener);
  }

  close() {
    this.closedByUs = true;                        // чтобы close не запустил переподключение
    this.stopHeartbeat();
    clearTimeout(this.timers.reconnect);
    this.socket?.close(1000, 'bye');
  }
}
```

Отдельно про `on`, возвращающий функцию отписки: без неё подписчики накапливаются, и размонтированные компоненты продолжают получать сообщения. Это классический источник утечек, разобранный в статье [про память и утечки](./memory-and-leaks).

Не забудь отключаться при уходе со страницы и приостанавливать heartbeat в скрытой вкладке:

```js
document.addEventListener('visibilitychange', () => {
  if (document.hidden) client.stopHeartbeat();
  else { client.startHeartbeat(); client.ensureConnected(); }
});
window.addEventListener('pagehide', () => client.close());
```

`pagehide` надёжнее `beforeunload`: на мобильных `beforeunload` часто не срабатывает вовсе.

## Часть 6. Несколько вкладок

Пользователь открыл приложение в пяти вкладках. По умолчанию это пять соединений: пятикратная нагрузка на сервер, пятикратный heartbeat, а в HTTP/1.1 — ещё и упор в лимит шести соединений на домен.

Правильно: **одно соединение на все вкладки, остальные получают данные от него.**

### Выбор владельца через Web Locks

**Web Locks API** даёт межвкладочную блокировку: `navigator.locks.request` захватывает именованный замок, и пока владелец жив, остальные ждут. Умерла вкладка-владелец — браузер отпускает замок сам, и следующий претендент немедленно его получает. Именно автоматическое освобождение делает этот способ лучше самодельных выборов через `localStorage`, где падение владельца оставляет замок навсегда.

```js
const channel = new BroadcastChannel('realtime');
let socket = null;

// Промис никогда не резолвится, поэтому замок держится всё время жизни вкладки
navigator.locks.request('realtime-owner', () => new Promise(() => {
  socket = new ReliableSocket(url);

  socket.on((message) => {
    handleLocally(message);
    channel.postMessage({ type: 'inbound', message });    // раздаём соседям
  });

  channel.addEventListener('message', (event) => {
    if (event.data.type === 'outbound') socket.send(event.data.message);
  });

  socket.connect();
}));

// Не-владелец: слушает соседей и отправляет через владельца
channel.addEventListener('message', (event) => {
  if (event.data.type === 'inbound') handleLocally(event.data.message);
});

function send(message) {
  if (socket) socket.send(message);
  else channel.postMessage({ type: 'outbound', message });
}
```

**`BroadcastChannel`** — шина сообщений между вкладками одного origin. Отправленное в канал приходит всем, кроме отправителя. Структурируемые данные передаются как есть, без ручной сериализации в строку.

Цена этой схемы: сложность заметно растёт. Появляются состояния, которых не было: вкладка-владелец закрылась в момент отправки; новый владелец переподключается, пока соседи ждут; сообщение ушло владельцу, а тот умер. Нужен курсор, общий для всех вкладок (обычно его кладут в `localStorage`), чтобы новый владелец знал, с какого места восстанавливаться.

Поэтому берут её не всегда: если пользователи почти не открывают несколько вкладок, а нагрузка невелика, проще жить с несколькими соединениями. Но знать про эту схему и уметь рассказать — стандартное ожидание от senior.

Альтернатива — держать соединение в **Shared Worker**: один воркер на все вкладки, соединение внутри него. Схема чище, но Shared Worker не поддерживается в Safari, из-за чего в продакшне чаще выбирают Web Locks. Про воркеры и их ограничения — в статье [про Web Workers](./web-workers).

## Часть 7. Что происходит на бэкенде

Фронтендера не просят проектировать бэкенд, но просят понимать ограничения — иначе предложенное решение оказывается нереализуемым.

**Соединения привязаны к процессу.** Открытый сокет живёт в памяти конкретного сервера. Если пользователь A подключён к серверу 1, а пользователь B — к серверу 2, то сообщение от A к B требует, чтобы серверы могли поговорить между собой.

**Отсюда шина.** Обычно Redis Pub/Sub, Kafka или очередь: сервер публикует событие в канал, все серверы, у которых есть подписчики на этот канал, разбирают и рассылают своим клиентам.

**Отсюда же липкие сессии.** Балансировщик должен направлять переподключение туда же или, что лучше, состояние вообще не должно храниться в процессе — тогда любой сервер может обслужить любого клиента.

**Отсюда история событий.** Восстановление по курсору требует, чтобы сервер помнил последние N событий, обычно недолго — минуты или часы. Без хранилища истории `Last-Event-ID` бесполезен.

**Отсюда лимит соединений.** Каждое открытое соединение — файловый дескриптор и память. Десятки тысяч на процесс — реально, миллионы — нет, отсюда горизонтальное масштабирование и стоимость.

Как это выглядит целиком на примере одного продукта — в статье [про проектирование чата](./chat-system-design).

Ответ, который хорошо звучит на интервью: «Соединения stateful, поэтому масштабирование упирается в маршрутизацию сообщений между узлами: нужна шина типа Redis Pub/Sub, отсутствие состояния в процессе и хранилище последних событий для восстановления по курсору».

## Часть 8. Отладка

**Панель Network, фильтр WS.** Кликнув на соединение, увидишь вкладку Messages: все кадры в обе стороны, со стрелкой направления и временем. Зелёные — исходящие, белые — входящие. Служебные ping и pong браузер по умолчанию прячет — их показ включается галочкой в контекстном меню.

Что смотреть первым делом:

- **Статус 101** — рукопожатие прошло. Не 101 — смотри код: 200 значит, что до сокет-обработчика не дошло, 403 — авторизация, 502 — прокси не понял Upgrade.
- **Время между кадрами.** Регулярные пропуски heartbeat — верный признак, что соединение убивает посредник.
- **Код в событии close.** `1006` — обрыв без прощания: почти всегда прокси, NAT или потеря сети.

Для SSE отдельной панели нет: соединение видно как обычный запрос типа `eventsource`, во вкладке EventStream — разобранные события с типом и данными.

Полезный приём в разработке — гонять клиента с искусственными обрывами: раз в 20 секунд принудительно закрывать сокет и проверять, что пользователь этого не замечает. Логика восстановления, которую никогда не проверяли, почти наверняка сломана.

## Что спросят на интервью

**Чем отличаются polling, long polling, SSE и WebSocket?** Короткий polling — периодические запросы, задержка до интервала, много пустых ответов. Длинный polling — сервер держит запрос до события. SSE — одно долгое соединение, поток событий вниз, поверх обычного HTTP. WebSocket — двусторонний канал после апгрейда протокола.

**Что выберешь для ленты уведомлений?** SSE: данные идут только вниз, работает поверх HTTP со всеми заголовками и куками, даёт бесплатное переподключение и восстановление через `Last-Event-ID`.

**Что выберешь для чата?** WebSocket: трафик в обе стороны и часто, нужны индикатор «печатает» и низкая задержка на отправку. И сразу оговори, что вокруг него нужны переподключение, heartbeat, очередь и дедупликация.

**Почему SSE иногда ломает приложение?** В HTTP/1.1 лимит — шесть соединений на домен, и каждое SSE занимает одно навсегда. Шесть вкладок исчерпают лимит. В HTTP/2 проблемы нет, либо надо держать одно соединение на все вкладки.

**Зачем нужен heartbeat, если есть событие `close`?** Потому что `close` может не прийти: прокси и NAT рвут «тихие» соединения молча, и сокет остаётся в состоянии `OPEN`, ничего не получая. Heartbeat и держит соединение шумным, и позволяет обнаружить смерть по отсутствию ответа.

**Как правильно переподключаться?** Экспоненциальная задержка с потолком плюс джиттер, чтобы клиенты не ударили одновременно. Счётчик попыток сбрасывать не при открытии, а когда соединение прожило несколько секунд.

**Что делать с сообщениями, отправленными во время разрыва?** Складывать в ограниченную очередь с отметкой времени, отправлять после восстановления, протухшие выбрасывать. У каждого сообщения — идемпотентный ключ, чтобы повтор не создал дубль.

**Как не потерять события, пока связи не было?** Хранить курсор последнего применённого события и при переподключении просить всё после него. У SSE это `Last-Event-ID` автоматически. Пришедшие повторно — отбрасывать по идентификатору.

**Пять вкладок — пять соединений. Что делать?** Выбрать одну вкладку владельцем через `navigator.locks` (замок освобождается сам при закрытии вкладки), держать соединение только в ней и раздавать сообщения остальным через `BroadcastChannel`. Альтернатива — Shared Worker, но его нет в Safari.

**Как масштабируется сокет-сервер?** Соединения stateful и живут в конкретном процессе, поэтому нужна шина между узлами (Redis Pub/Sub, Kafka), отсутствие состояния в памяти процесса и хранилище последних событий для восстановления по курсору.

## Коротко, для повторения

1. Три транспорта: polling (клиент спрашивает), SSE (сервер льёт вниз), WebSocket (обе стороны). Выбор — по направлению трафика и требуемой задержке.
2. Polling — не позор. Редкие обновления, маленькая аудитория, простой бэкенд — правильный выбор. Пауза после ответа, а не `setInterval`.
3. Длинный polling даёт почти нулевую задержку без сокетов, но при частых событиях вырождается в короткий с оверхедом.
4. SSE даёт бесплатно: разбор формата, автопереподключение и `Last-Event-ID` для восстановления пропущенного.
5. В HTTP/1.1 — шесть соединений на домен, и SSE занимает одно навсегда. В HTTP/2 ограничения нет.
6. WebSocket начинается с HTTP-рукопожатия и кода **101**. Заголовки задать нельзя, поэтому токен шлют отдельным сообщением или одноразовым тикетом.
7. Браузерный API не даёт слать ping-кадры: heartbeat делается своими сообщениями.
8. Соединения умирают молча. `readyState` показывает `OPEN`, данных нет. Обнаруживается только отсутствием ответа на heartbeat.
9. Переподключение: экспоненциальная пауза с потолком плюс джиттер, счётчик сбрасывается после нескольких секунд стабильной связи.
10. Очередь исходящих — ограниченная по размеру и с истечением срока. Идемпотентный ключ на каждое сообщение против дублей.
11. Восстановление — по курсору последнего применённого события, дубли отбрасываются по идентификатору.
12. Одно соединение на все вкладки: владелец через `navigator.locks`, раздача через `BroadcastChannel`. Замок освобождается сам при закрытии вкладки.
13. На бэкенде соединения stateful: нужна шина между узлами и хранилище последних событий.
