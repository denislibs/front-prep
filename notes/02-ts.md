# TypeScript

Narrowing, дженерики, utility types руками.

_Вопросов: 50_

## 1. interface или type — что выбрать и почему?

### Коротко

Для описания объекта они почти взаимозаменяемы. Ключевые отличия: `interface` умеет declaration merging и описывает только объектные формы; `type` умеет union, кортежи, примитивы, mapped и conditional типы. Практическое правило: `interface` для публичных объектных контрактов, `type` для всего остального.

### Как это работает

- **Declaration merging**: два `interface Window` в одной области сливаются в один. Это единственный способ расширить типы чужой библиотеки или глобальные объявления (`declare global`). Повторное объявление `type` — ошибка.
- **Расширение**: `interface B extends A` проверяется в момент объявления — конфликтующее поле даёт ошибку сразу. Пересечение `type B = A & { x: number }` конфликт не отвергает, а сводит поле к `never`, и ошибка вылезает позже и не там.
- **Производительность**: интерфейс компилятор кеширует по имени, длинные цепочки пересечений считаются заново. На больших проектах это заметно на времени `tsc`.
- **Тексты ошибок**: у интерфейса в сообщении остаётся имя, псевдоним типа компилятор часто разворачивает в полную структуру.

### Почему так

Интерфейсы пришли из мира номинальных языков как способ описать контракт, который могут дополнять несколько деклараций (важно для типизации DOM и глобалов). Псевдонимы типов — это выражения в системе типов, поэтому они умеют всё, что умеет система, но не могут быть «открытыми». Плата за merging: чужой код способен незаметно расширить твой интерфейс.

### Подводные камни

- **Индексные сигнатуры**: `interface` не совместим с `Record<string, unknown>`, потому что может быть дополнен позже; `type` — совместим. Это ломается на функциях-хелперах и при работе с JSON.
- Оба варианта **структурны**: смена ключевого слова не даёт номинальной типизации.
- Через `type` нельзя случайно расширить чужой тип — иногда это плюс, иногда мешает при аугментации модулей.
- Смешение стилей в одном проекте создаёт бесконечные споры на ревью. Зафиксируй правило линтером (`consistent-type-definitions`).

### Что спросят следом

«Как расширить типы библиотеки?» — только через `interface` и `declare module`. «Что выбрать для пропсов React-компонента?» — любое; `type` удобнее, если пропсы это union взаимоисключающих режимов. «Есть разница в рантайме?» — нет, оба стираются полностью.

```js
// merging: единственный способ дополнить чужие типы
declare global {
  interface Window { __APP_VERSION__: string; }
}

// конфликт полей: интерфейс ругается сразу
interface A { id: string }
// interface B extends A { id: number }   // Error прямо здесь

type C = A & { id: number };
// ошибки нет: C['id'] стало never — упадёт позже и не тут

// это умеет только type
type Status = 'idle' | 'loading';
type Pair = [string, number];
type Keys<T> = { [K in keyof T]: K };
```

> **Что добавит очков.** Не отвечай «дело вкуса» — назови три конкретных различия: merging, поведение при конфликте полей и совместимость с Record. И скажи, что правило команды важнее личного предпочтения, оно фиксируется линтером.

## 2. unknown против any — в чём принципиальная разница?

### Коротко

`any` выключает проверку типов и «заражает» всё, чего касается: любое обращение считается валидным, ошибка уезжает в рантайм. `unknown` — честное «тип неизвестен»: значение можно хранить и передавать, но нельзя ничего с ним делать, пока не сузишь проверкой. Это верхний тип системы, а `any` — дыра в ней.

### Как это работает

- Присваивать **в** `unknown` можно что угодно; присваивать `unknown` **во что-то другое** — нельзя без сужения. `any` присваивается в обе стороны свободно.
- Сужение делается через `typeof`, `instanceof`, проверку `in`, `Array.isArray` или пользовательский type guard с сигнатурой `v is User`.
- В union `unknown` поглощает всё: `unknown | string` это `unknown`. В пересечении наоборот исчезает: `unknown & string` это `string`.
- С `useUnknownInCatchVariables` (входит в `strict`) переменная в `catch` получает тип `unknown`, а не `any` — обращение к `e.message` перестаёт компилироваться без проверки.

### Почему так

`any` оставили для постепенной миграции с JavaScript: без него нельзя было бы типизировать проект по частям. `unknown` добавили в 3.0, когда выяснилось, что «неизвестно» и «не проверяй» — это разные намерения, а разработчики использовали `any` для обоих. Плата за `unknown` — придётся писать валидацию там, где раньше молча верили на слово.

### Подводные камни

- **Заражение**: одно поле `any` в типе ответа выключает проверки во всей цепочке обращений к нему, и падает это далеко от источника.
- `JSON.parse` возвращает `any` — типовая точка проникновения. Оборачивай в функцию, возвращающую `unknown`, и валидируй.
- Аннотация ответа как `Promise<User>` — это обещание, а не проверка: рантайм ничего не гарантирует.
- `{}` и `object` — не замена `unknown`: `{}` принимает всё, кроме `null` и `undefined`, и разрешает обращение к методам `Object`.
- Запрет `any` линтером без альтернативы приводит к массовым `as` — это та же дыра, только заметнее.

### Что спросят следом

«Где `any` всё-таки уместен?» — в миграции легаси, в редких обобщённых утилитах и в тестовых моках; в остальном ставь `unknown`. «Как валидировать ответ API?» — schema-first через zod, valibot или io-ts: схема даёт и рантайм-проверку, и выведенный тип из одного источника. «Что такое never в этом ряду?» — нижний тип, значение которого не существует.

```js
// any — ошибка доедет до рантайма
function bad(data: any) {
  return data.user.name.toUpperCase();  // компилируется, падает в проде
}

// unknown — компилятор требует доказательства
function good(data: unknown) {
  if (typeof data === 'object' && data !== null && 'user' in data) { /* ... */ }
}

// type guard: сужение, которое можно переиспользовать
function isUser(v: unknown): v is { name: string } {
  return typeof v === 'object' && v !== null
    && typeof (v as Record<string, unknown>).name === 'string';
}

// schema-first: одна схема даёт и проверку, и тип
const User = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof User>;
const user = User.parse(await res.json());   // бросит на несоответствии

// catch при strict
try { risky(); } catch (e) {            // e: unknown
  if (e instanceof Error) log(e.message);
}
```

> **Что добавит очков.** Сформулируй границу доверия: «всё, что пересекает границу процесса — ответ API, localStorage, postMessage, URL-параметры — приходит как unknown и проходит валидацию». Это ответ уровня архитектуры, а не синтаксиса.

## 3. Что такое never и как сделать exhaustive check?

### Коротко

`never` — тип, у которого нет ни одного значения: нижний тип системы. Он возвращается функцией, которая никогда не завершается нормально (всегда бросает или зацикливается), и получается при сужении, исчерпавшем все варианты. Главное практическое применение — exhaustive check: заставить компилятор падать, когда в union добавили вариант и забыли его обработать.

### Как это работает

1. В `switch` по дискриминанту после всех `case` компилятор сужает переменную до `never` — вариантов не осталось.
2. В `default` присваиваем её в переменную типа `never`. Пока union исчерпан, присваивание валидно.
3. Добавили в union `{ kind: 'triangle' }` — в `default` тип станет этим вариантом, и присваивание в `never` перестанет компилироваться. Ошибка появляется **во всех** местах, где обрабатывается union: компилятор сам находит все точки, которые надо обновить.

`never` — подтип любого типа, поэтому присваивается куда угодно, а вот в него не присваивается ничего. Отсюда же нейтральность в union: `string | never` это `string`.

### Почему так

Это перенос ошибки со стадии «прод» на стадию «сборка» ценой четырёх строк. Особенно ценно в редьюсерах, обработке событий сокета и роутинге по типу сообщения — местах, где вариантов много и они добавляются со временем. Плата: работает только с честными discriminated union, а не с `string`-полем без литеральных типов.

### Подводные камни

- **default с фолбэком** вместо `never`-проверки убивает всю пользу: код скомпилируется и молча вернёт заглушку.
- Функция, возвращающая `never`, помогает сужению только если объявлена как `function assertNever(x: never): never` или как **стрелка с явной аннотацией** — выведенный тип у неё будет `void`.
- Данные из сети типизированы верой: exhaustive check не защитит, если бэкенд прислал неизвестный `kind`. В рантайме всё равно нужен throw или логирование.
- В conditional types `never` дистрибутивен и исчезает: `T extends U ? never : T` — так работает `Exclude`, и это же ломает наивные обходы union.
- `Record<string, never>` и `{}` — не то же самое, что «пустой объект»; на этом часто путаются.

### Что спросят следом

«Чем `never` отличается от `void`?» — `void` значит «возвращает, но значение не важно», `never` — «не возвращает вовсе». «Как сделать то же для if-цепочки?» — тот же `assertNever` в последнем `else`. «Где ещё встречается `never`?» — в результате несовместимого пересечения, например `string & number`.

```js
type Shape =
  | { kind: 'circle'; r: number }
  | { kind: 'square'; side: number };

function assertNever(x: never): never {
  throw new Error('Необработанный вариант: ' + JSON.stringify(x));
}

function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle': return Math.PI * shape.r ** 2;
    case 'square': return shape.side ** 2;
    default: return assertNever(shape);   // добавили kind — ошибка сборки здесь
  }
}

// неправильно: фолбэк прячет незакрытый вариант
default: return 0;

// never нейтрален в union и дистрибутивен в conditional
type A = string | never;              // string
type Exclude2<T, U> = T extends U ? never : T;
```

> **Что добавит очков.** Скажи, зачем это нужно на языке продукта: добавили новый тип события — компилятор сам показал все места, где его забыли обработать. И добавь, что от неизвестного kind с бэкенда это не спасает, нужен рантайм-throw.

## 4. Напиши типобезопасную функцию pick.

### Коротко

Нужны два параметра типа: `T` — сам объект, `K extends keyof T` — ключи, ограниченные ключами этого объекта. Возвращаемый тип собирается как `Pick<T, K>`. Ограничение `extends keyof T` — вся суть задачи: без него опечатка в имени ключа пройдёт молча.

### Как это работает

1. `keyof T` даёт union ключей: для `{id: number; name: string}` это `'id' | 'name'`.
2. `K extends keyof T` ограничивает второй параметр этим union. Компилятор **выводит** `K` из фактического аргумента: передали `['id', 'name']` — вывелся `'id' | 'name'`, а не просто `string`.
3. `Pick<T, K>` — mapped type `{ [P in K]: T[P] }`: перебирает выбранные ключи и берёт для каждого его исходный тип. Результат — точный объект с двумя полями, а не `Partial`.
4. Аккумулятор приходится объявлять как `{} as Pick<T, K>`: компилятор не умеет доказать, что цикл заполнит все ключи. Это одно из немногих оправданных применений `as`.

### Почему так

Дженерик здесь не украшение: он сохраняет связь между входом и выходом. Наивная сигнатура `(obj: object, keys: string[]) => object` компилируется, но теряет всю информацию — дальше по коду придётся приводить типы руками. Плата за точность — читаемость сигнатуры и то, что в редких случаях приходится подсказывать вывод явно.

### Подводные камни

- `keys: K[]` позволяет передать один и тот же ключ дважды. Строже — `readonly K[]` плюс вызов с `as const`.
- Ключ, которого нет в объекте, отсеивается на этапе компиляции, но **не в рантайме**: при данных из JSON проверяй `Object.hasOwn`.
- Функция копирует значения поверхностно — вложенные объекты остаются общими с исходным.
- С `noUncheckedIndexedAccess` обращение `obj[key]` даёт `T[K] | undefined`; на присваивание внутрь `Pick` это не влияет, но в других утилитах ломает вывод.
- Символьные и унаследованные ключи `keyof` учитывает, а `Object.keys` — нет: сигнатура и реализация расходятся.

### Что спросят следом

«Напиши `omit`» — `K extends keyof T` и возврат `Omit<T, K>`, то есть `Pick<T, Exclude<keyof T, K>>`. «Почему `Omit` не проверяет лишние ключи?» — он объявлен через `keyof any`, поэтому опечатка проходит; в своей версии ставь `K extends keyof T`. «Как типизировать `get(obj, path)` с вложенным путём?» — рекурсивным conditional type по шаблонному литералу.

```js
function pick<T extends object, K extends keyof T>(
  obj: T,
  keys: readonly K[],
): Pick<T, K> {
  const result = {} as Pick<T, K>;   // оправданный as: цикл заполнит все ключи
  for (const key of keys) result[key] = obj[key];
  return result;
}

const user = { id: 1, name: 'D', age: 30 };
pick(user, ['id', 'name']);   // { id: number; name: string }
pick(user, ['nope']);         // Error: 'nope' не входит в keyof

// зеркальный omit — со строгим ограничением, в отличие от встроенного Omit
function omit<T extends object, K extends keyof T>(obj: T, keys: readonly K[]): Omit<T, K> {
  const result = { ...obj };
  for (const key of keys) delete result[key];
  return result;
}
```

> **Что добавит очков.** Проговори вслух, зачем ограничение extends keyof T — это и есть проверяемый навык. Отдельные очки: объяснить, почему {} as Pick<T,K> здесь допустим, и назвать известную дыру во встроенном Omit.

## 5. Что такое структурная типизация и как сделать номинальную?

### Коротко

TypeScript сравнивает типы по **форме**, а не по имени: если у значения есть все нужные поля подходящих типов, оно подходит — независимо от того, как объявлено. Отсюда и главная практическая дыра: `UserId` и `PostId`, оба `string`, свободно подставляются друг вместо друга. Номинальность эмулируют branded types.

### Как это работает

При проверке присваиваемости компилятор сопоставляет члены: у источника должны быть все члены цели совместимых типов. Лишние члены допустимы — кроме случая **object literal freshness**, когда литерал присваивается напрямую и лишние свойства считаются ошибкой (эту проверку легко обойти через промежуточную переменную).

Branded type — пересечение примитива с невидимым «клеймом»: `string & { readonly __brand: 'UserId' }`. Такого значения в рантайме не существует, поэтому создать его можно только через явную функцию с `as`, которая и становится единственной точкой валидации. Обычная строка в позицию `UserId` уже не пройдёт, а `UserId` в позицию `string` — пройдёт, что и нужно.

### Почему так

Структурность выбрана намеренно: TypeScript надстраивается над JavaScript, где объекты создаются литералами и никаких деклараций классов может не быть вовсе. Номинальность потребовала бы «регистрации» типов и сломала бы совместимость с существующим кодом. Плата — компилятор не различает сущности с одинаковой формой: деньги и проценты, идентификаторы разных сущностей, «сырую» и «санитизированную» строку.

### Подводные камни

- Брендирование **не бесплатно**: нужна функция-конструктор, и весь код должен ходить через неё, иначе смысла нет.
- Бренд стирается при сериализации: после `JSON.parse` это снова обычная строка, проверять надо заново.
- Классы тоже структурны: класс с приватным полем (`private` или `#field`) — редкое исключение, там сравнение становится по сути номинальным.
- Функции сравниваются **бивариантно** для методов и контравариантно по параметрам для свойств-функций при `strictFunctionTypes` — источник неожиданных «совместимых» колбэков.
- Опциональное поле не спасает от путаницы: тип с лишним необязательным полем всё равно совместим.

### Что спросят следом

«Где брендирование реально окупается?» — деньги в копейках против рублей, id разных сущностей, санитизированный HTML, валидированный email. «Есть ли номинальность из коробки?» — нет, только приватные поля класса как побочный эффект. «Чем это лучше отдельного класса-обёртки?» — нулевая цена в рантайме: бренд полностью стирается.

```js
// структурность: разные имена, одна форма — взаимозаменяемы
interface Point { x: number; y: number }
interface Vector { x: number; y: number }
const p: Point = { x: 1, y: 2 };
const v: Vector = p;              // ok, никакой ошибки

// проблема: два string перепутать нечем
function getPost(userId: string, postId: string) {}
getPost(postId, userId);          // компилируется, баг в проде

// branded types: номинальность за ноль байт рантайма
type Brand<T, B extends string> = T & { readonly __brand: B };
type UserId = Brand<string, 'UserId'>;
type PostId = Brand<string, 'PostId'>;

const toUserId = (v: string): UserId => {
  if (!/^u_/.test(v)) throw new Error('не UserId: ' + v);  // единственная точка проверки
  return v as UserId;
};

declare function getPost2(userId: UserId, postId: PostId): void;
getPost2('abc' as PostId, 'abc' as UserId);   // Error — типы не перепутать
```

> **Что добавит очков.** Не ограничивайся определением структурной типизации — покажи, какую реальную ошибку она пропускает и как бренд её закрывает. Упомяни, что приватное поле класса — единственная номинальность из коробки.

## 6. Почему as опасен?

### Коротко

`as` — это **утверждение** типа, а не приведение. Он ничего не проверяет и не меняет данные в рантайме: он только сообщает компилятору «поверь мне». Если реальность не совпала, ошибка не исчезает, а переезжает в прод и всплывает далеко от места, где ты соврал.

### Как это работает

Компилятор разрешает `x as T`, если `T` и тип `x` хоть как-то пересекаются — то есть одно присваиваемо другому. При полной несовместимости он потребует двойного приведения `x as unknown as T`; именно это и есть индикатор, что происходит что-то не то. После утверждения всё дальнейшее выводится из объявленного типа, поэтому автодополнение показывает поля, которых может не быть.

Побочный эффект — обход проверки лишних свойств: `{ id: 1, typo: 2 } as User` не выдаст ошибку об опечатке, а обычное присваивание выдаст.

### Почему так

Утверждения нужны там, где разработчик знает больше компилятора: результат `querySelector`, ключи `Object.keys`, поэтапное построение объекта. Отказаться от них полностью нельзя. Плата — каждое `as` это непроверяемое допущение, и в отличие от `any` оно выглядит аккуратно, поэтому проходит ревью.

### Подводные камни

- **Ответ API как `as User`** — самый частый и самый дорогой случай: типизация есть, гарантии нет. Нужен разбор схемой (zod, valibot) или type guard.
- `as unknown as T` — маркер, что типы спроектированы неверно, а не приём.
- `as` скрывает `null`: `document.querySelector('.x') as HTMLElement` уберёт `| null`, и упадёт на `.style`.
- `Object.keys(obj) as (keyof T)[]` — распространённая, но не всегда честная ложь: у объекта могут быть лишние ключи из-за структурности.
- `as const` — **другая конструкция**: она не утверждение, а указание вывести литеральные и readonly-типы. Путать их не стоит.
- Тесты часто становятся кладбищем `as`: `{} as User` в моке скрывает изменение контракта.

### Что спросят следом

«Когда `as` уместен?» — сужение после проверки, которую компилятор не понимает; поэтапная сборка объекта (`{} as T` с последующим заполнением всех полей); работа с DOM после явной проверки на `null`; фабрика branded type. «Чем заменить?» — type guard с `v is T`, функция-assert с `asserts v is T`, схема с рантайм-валидацией. «Что безопаснее для DOM?» — `instanceof HTMLInputElement`: это и проверка, и сужение.

```js
// опасно: типизация без гарантии
const user = await res.json() as User;
user.profile.name;                 // TypeError в проде, если поля нет

// безопасно: схема даёт и проверку, и тип
const user2 = UserSchema.parse(await res.json());

// опасно: null молча исчез
const el = document.querySelector('.btn') as HTMLElement;
el.style.color = 'red';            // упадёт, если элемента нет

// безопасно: проверка вместо утверждения
const el2 = document.querySelector('.btn');
if (el2 instanceof HTMLElement) el2.style.color = 'red';

// type guard вместо as
function isUser(v: unknown): v is User {
  return typeof v === 'object' && v !== null && 'id' in v;
}

// assert-функция: сужает после вызова
function assertDefined<T>(v: T): asserts v is NonNullable<T> {
  if (v == null) throw new Error('ожидалось значение');
}
```

> **Что добавит очков.** Формулировка, которая работает: «as — это не приведение, а обещание компилятору, и оно ничем не подкреплено». Дальше сразу назови три легальных случая — иначе прозвучит как догма «as всегда плохо», а это красный флаг.

## 7. Что такое user-defined type guard и чем он опасен?

```js
function isUser(v: unknown): v is User {
  return true; // компилируется без единой жалобы
}

declare const raw: unknown;
if (isUser(raw)) raw.name.trim();
```

### Коротко

Type guard — функция, у которой возвращаемый тип объявлен как предикат `x is T`. Компилятор верит предикату на слово и не проверяет, доказывает ли его тело хоть что-нибудь. По надёжности это тот же `as`, только собранный в одну функцию, которую можно покрыть тестами.

### Как это работает

Сигнатура `function isUser(v: unknown): v is User` связывает результат вызова с конкретным параметром. На месте вызова control flow analysis видит `if (isUser(v))` и в true-ветке сужает `v` до `User`, в false-ветке применяет `Exclude` к объявленному типу (для `unknown` вычесть нечего, остаётся `unknown`). От тела функции компилятор требует ровно одного: чтобы оно возвращало `boolean`. Безусловный `return true` из сниппета проходит проверку, и вызов `raw.name.trim()` компилируется, а падает уже в браузере.

В рантайме от предиката не остаётся ничего: в JS уезжает обычная функция, возвращающая булево. Сужение существует только в модели компилятора.

С TS 5.5 работает **вывод предикатов**: если у функции нет явной аннотации возвращаемого типа, она состоит из одного `return` с булевым выражением над параметром и параметр нигде не переприсваивается — компилятор сам выводит `x is T`. Поэтому `['a', null].filter((x) => x !== null)` с 5.5 даёт `string[]`, а до 5.5 давало `(string | null)[]`.

### Почему так

Доказать, что произвольный JS действительно устанавливает принадлежность типу, — работа верификатора, а не тайпчекера: пришлось бы понимать семантику всех операций и всех вызовов внутри. TS выбрал дешёвый обмен: разработчик берёт на себя ответственность, компилятор взамен получает право сужать. Цена — предикат молча расходится с моделью при рефакторинге.

### Подводные камни

- Добавили в `User` обязательное поле — предикат, проверяющий только `'id' in v`, продолжает врать, и ошибка вылезет далеко от места проверки.
- `typeof v === 'object'` не исключает `null` и не исключает массивы — самый частый дефект самописных предикатов.
- Явная аннотация `: boolean` глушит вывод предиката из 5.5: чтобы он сработал, тип возврата писать нельзя.
- Предикат сужает конкретный параметр, а не выражение: `isUser(a.b)` сужает путь `a.b`, но сужение слетит после любого вызова, который компилятор не может проанализировать.

### Что спросят следом

**Чем заменить на границе с сетью?** Схемой валидации: у zod и valibot предикат порождается из той же декларации, что и тип (`z.infer`), поэтому разойтись они не могут. **Есть ли форма для методов?** Да, `this is T` — им типизируют такие проверки, как `isLoaded()` у модели.

```js
// предикат, который не врёт: проверяем ровно то, что обещаем
function isUser(v: unknown): v is User {
  return typeof v === 'object' && v !== null
    && 'id' in v && typeof (v as { id: unknown }).id === 'string';
}

// TS 5.5: аннотации нет — предикат выводится сам
const notNull = (x: string | null) => x !== null; // (x) => x is string
const clean = ['a', null].filter(notNull);        // string[]

const typed = (x: string | null): boolean => x !== null;
const dirty = ['a', null].filter(typed);          // (string | null)[] — вывод заглушен
```

> **Что добавит очков.** Формулировка «предикат — это as с человеческим лицом» плюс уточнение, что с 5.5 явная аннотация : boolean ломает автовывод предиката.

## 8. Какими встроенными способами сужается тип и где у каждого ловушки?

```js
function f(x: string | number | null | undefined) {
  if (typeof x === 'object') { /* какой тип у x? */ }
  if (x) { /* а здесь? */ }
}
```

### Коротко

Сужение — это control flow analysis: компилятор строит граф потока и на каждом узле держит текущий тип переменной. Источники сужения — `typeof`, `instanceof`, `in`, сравнение с литералом, `Array.isArray`, truthiness, дискриминант union и пользовательские предикаты. Ловушки у каждого свои и повторяют кривизну самого JS.

### Как это работает

В сниппете первый `if` сузит `x` до `null`: `typeof null === 'object'`, а других объектных членов в union нет. Второй сузит до `string | number`, но **не** исключит пустую строку и ноль — они просто проходят по falsy-ветке вместе с `null` и `undefined`.

Механически чекер для каждого условия вычисляет пару «тип в true-ветке / тип в false-ветке», раскладывая union на члены и оставляя те, что совместимы с проверкой. На слиянии ветвей (после `if`, в `catch`, на входе в цикл) типы объединяются обратно в union. Всё это существует только при компиляции: в JS уезжают ровно те `typeof`, что вы написали.

### Почему так

TS обязан описывать существующий JS, а не идеальный язык: `typeof null` — баг первой реализации 1995 года, зафиксированный спецификацией навсегда. Поэтому сужение честно моделирует рантайм со всеми его странностями, а не то, что кажется логичным.

### Подводные камни

- `typeof x === 'object'` не исключает `null` и не исключает массивы — нужна пара `x !== null && !Array.isArray(x)`.
- Truthiness съедает `''`, `0`, `0n`, `NaN`: `if (count)` и `if (count !== undefined)` — разные проверки, и на нуле поведение расходится.
- `instanceof` ломается через границу realm (iframe, worker, vm): объект из другого окна не пройдёт `instanceof Array`. Спасает `Array.isArray`, у которого проверка кросс-realm.
- `in` сужает по наличию ключа и не отличает «ключа нет» от «ключ равен `undefined`». С TS 4.9 `in` ещё и добавляет ключ в тип для `unknown`-подобных значений, что делает его пригодным для валидации.
- Сужение слетает после любого вызова функции, если переменная — `let` или свойство объекта: компилятор не делает escape-анализ.
- При `useUnknownInCatchVariables` (входит в `strict`) `catch (e)` даёт `unknown`, и `e.message` требует сужения через `instanceof Error`.

### Что спросят следом

**Что надёжнее для внешних данных?** Дискриминированный union со строковым полем-тегом: сужение по литералу — единственный способ, который компилятор проверяет строго и который не ломается при добавлении полей. **Почему `Array.isArray` на `readonly T[]` иногда даёт `any[]`?** Из-за сигнатуры в старых lib.d.ts; в свежих версиях перегрузка для `ReadonlyArray` добавлена.

```js
declare const x: unknown;

if (typeof x === 'object' && x !== null && !Array.isArray(x)) {
  // x: object — null и массивы отсечены
}

type Res = { ok: true; data: string } | { ok: false; error: string };
function show(r: Res) {
  if (r.ok) r.data;   // сужение по дискриминанту — самый надёжный вариант
  else r.error;
}
```

> **Что добавит очков.** Сильная формулировка: сужение — статическая модель потока управления, она консервативна везде, где не может доказать неизменность значения.

## 9. Как работают ограничения дженериков и вывод типов? Где обычно теряется точность?

```js
declare function a<T>(v: T): T;
declare function b<T extends string>(v: T): T;

const r1 = a('x'); // какой тип?
const r2 = b('x'); // а какой здесь?
```

### Коротко

`T extends C` — одновременно ограничение (что можно передать) и подсказка выводу (насколько узко выводить). Компилятор собирает кандидатов из всех позиций вывода, выбирает среди них общий супертип и только потом сверяет результат с ограничением. Точность теряется на расширении литералов, на приоритете позиций и на дефолтах.

### Как это работает

В сниппете `r1` получит тип `string`, а `r2` — литерал `'x'`. Причина в правиле literal widening: литеральный тип аргумента расширяется до базового примитива, если у параметра типа нет ограничения, включающего литералы. `T extends string` сигнализирует, что литеральность значима, и компилятор её сохраняет. То же с `T extends readonly unknown[]` для кортежей.

Сам вывод идёт так: чекер обходит пары «параметр — аргумент», для каждого вхождения `T` кладёт кандидата в набор, помечая приоритет позиции. Позиции с более низким приоритетом (например, вывод из возвращаемого типа контекстно типизированной стрелки) учитываются только если высокоприоритетных кандидатов нет. Затем берётся общий супертип набора; если ни один кандидат не является супертипом остальных, вывод падает в union или в ошибку. Проверка `extends` выполняется в конце — она не сужает вывод, а бракует результат.

Дефолт `T = X` вступает в игру только когда кандидатов нет вообще (аргумент не передан, позиция не выводима), а не когда вывод получился «плохим».

### Почему так

Widening существует, чтобы `let s = 'a'` не залипал на литерале и переменную можно было переприсвоить. Ограничение — способ автора API сказать «мне литерал нужен», не заставляя вызывающего писать `as const`. С TS 5.0 у этой задачи есть более прямое решение — `const`-параметры типа.

### Подводные камни

- **Дженерик ради дженерика**: если `T` встречается в сигнатуре один раз, он ничего не связывает и работает как замаскированный `any`. Правило: параметр типа должен появляться минимум дважды.
- `T extends {}` и `T extends unknown` ведут себя по-разному: первое исключает `null`/`undefined` и подавляет widening, второе нет.
- Возвращаемый тип — не источник вывода: contextual typing идёт снаружи внутрь, поэтому `const x: Foo = make()` не «дожмёт» `T` до `Foo`, если параметр уже дал кандидата.
- Несколько кандидатов из разных аргументов дают супертип, а не пересечение: `pair(1, 'a')` при `<T>(a: T, b: T)` выведет `1 | 'a'` в новых версиях и ошибку в старых.

### Что спросят следом

**Как заставить вывести только из одного аргумента?** `NoInfer<T>` в остальных позициях (TS 5.4). **Когда ограничение вредно?** Когда оно шире реальной потребности: `T extends object` у функции, которой достаточно `keyof`, зря запрещает передать примитив с брендом.

```js
declare function pick<T extends string>(v: T): T;
pick('a');            // 'a' — литерал сохранён

declare function loose<T>(v: T): T;
loose('a');           // string — расширился

declare function tuple<const T extends readonly unknown[]>(v: T): T;
tuple([1, 'a']);      // readonly [1, "a"] — TS 5.0

declare function bad<T>(v: T): void;   // T встречается один раз — это any
```

> **Что добавит очков.** Правило «параметр типа должен появляться в сигнатуре минимум дважды, иначе это замаскированный any» — короткий и сильный ответ про плохие сигнатуры.

## 10. Как связаны keyof, typeof и indexed access types? Приведите нетривиальный пример.

```js
const ROLES = ['admin', 'user'];
type Role = typeof ROLES[number];   // какой тип получится?

const cfg: Record<string, number> = { port: 1 };
type Key = keyof typeof cfg;        // а здесь?
```

### Коротко

`typeof x` в type-позиции поднимает значение в тип, `keyof T` даёт union ключей, `T[K]` — тип значения по ключу. Вместе это мост из мира значений в мир типов: одна константа порождает и рантайм-данные, и типы, вместо того чтобы дублировать список в двух местах.

### Как это работает

В сниппете обе строки дают широкий результат. `ROLES` объявлен без `as const`, поэтому его тип — `string[]`, и `typeof ROLES[number]` даёт `string`, а не `'admin' | 'user'`. У `cfg` тип объявлен как `Record<string, number>`, то есть с индексной сигнатурой, и `keyof` от неё — `string`, а не `'port'`. Оба случая — самая частая причина жалобы «мой Record ничего не проверяет».

`typeof` в type-позиции и `typeof` в выражении — два разных оператора с одинаковым написанием: первый существует только при компиляции и работает с идентификаторами, второй — рантайм-оператор, возвращающий строку. Компилятор различает их по контексту.

`T[number]` на кортеже даёт union элементов, потому что кортеж — это объект с числовыми ключами `0`, `1`, … плюс `length`: индексирование по `number` собирает union по всем числовым ключам. Отсюда идиома «union из массива»: `as const` превращает массив в кортеж литералов, `[number]` сплющивает его в union.

### Почему так

Дублировать список в константе и в union — гарантированный источник рассинхрона: добавили роль в массив, забыли в тип, и валидация молча пропускает. Приём «значение — источник истины, тип выводится» решает это структурно. Обратное направление (тип как источник, а массив вручную) невозможно: типы стираются, породить из них рантайм-массив нельзя.

### Подводные камни

- Забытый `as const` обесценивает всю конструкцию и не даёт ошибки — тип просто становится `string`.
- Индексная сигнатура делает `keyof T` равным `string | number`, что рушит точность любого маппера поверх такого типа.
- `keyof` объекта с числовыми ключами вернёт `number`; `keyof any` — это `string | number | symbol`, а `keyof unknown` — `never`.
- Оптиональные свойства попадают в `keyof`, а их тип в `T[K]` включает `undefined`; для «только обязательные ключи» нужен отдельный маппер.
- `typeof` берёт объявленный тип, а не сужённый в текущей точке: `typeof x` после `if (x !== null)` всё равно даст union с `null`.

### Что спросят следом

**Чем это лучше enum?** Численный `enum` оставляет объект в рантайме и допускает присваивание произвольного числа; `as const`-массив даёт и итерируемый список, и точный union без рантайм-накладных расходов. **Как получить только ключи с определённым типом значения?** Через перемаппинг: `{ [K in keyof T as T[K] extends string ? K : never]: T[K] }` и затем `keyof`.

```js
const ROLES = ['admin', 'user'] as const;
type Role = typeof ROLES[number];      // "admin" | "user"

const cfg = { host: 'x', port: 1 } as const;
type Key  = keyof typeof cfg;          // "host" | "port"
type Port = typeof cfg['port'];        // 1
type Any  = typeof cfg[Key];           // "x" | 1

// индексная сигнатура убивает точность
type Wide = keyof Record<string, number>;  // string | number
```

> **Что добавит очков.** Формулировка «константа рантайма порождает тип, а не наоборот» плюс уточнение, что забытый as const не даёт ошибки, а тихо расширяет тип до string.

## 11. Что такое discriminated union и почему это главный паттерн для стейта?

### Коротко

Discriminated union — union объектов с общим полем-**дискриминантом**, у которого в каждом варианте свой литеральный тип. Проверка этого поля автоматически сужает весь объект. Смысл приёма шире синтаксиса: невозможные состояния перестают быть представимыми, и проверять их в коде больше не нужно.

### Как это работает

Компилятор распознаёт union как discriminated, если в каждом члене есть общее свойство с литеральным типом (строка, число, булево). Тогда `if (s.status === 'success')` или `switch` по нему сужают тип в ветке до конкретного члена, и доступны становятся именно его поля. Вне ветки поле `data` не существует в типе вовсе — обращение к нему не скомпилируется.

Альтернатива, которую делают по привычке, — плоский объект с четырьмя необязательными полями. Он допускает `{ isLoading: true, error: 'oops', data: [...] }`: состояние, которого не бывает, но которое придётся обрабатывать в JSX.

### Почему так

Это перенос инварианта из головы разработчика в тип. Выигрыш заметен на редьюсерах, состоянии запроса, сообщениях сокета, результатах парсинга (`{ ok: true, value } | { ok: false, error }`) и на пропсах компонентов со взаимоисключающими режимами. Плата — многословность и то, что структуру придётся расширять честно: добавил вариант — компилятор потребует обработать его везде.

### Подводные камни

- **Дискриминант должен быть литеральным типом.** Поле `status: string` сужения не даёт. Для объектов вне контекста нужен `as const`.
- Сужение **теряется** при деструктуризации по частям (`const { status, data } = state`) и после `await` или колбэка внутри ветки: компилятор считает, что значение могло измениться.
- Сужение по полю **объекта** (`if (props.state.kind === ...)`) до TS 5.5 не сохранялось при вынесении в переменную; используй присваивание всего объекта в локальную константу.
- Дискриминант по `undefined` (наличие поля) хрупок: `in` работает, но по опциональному полю сужение неполное.
- Без `assertNever` в `default` польза наполовину теряется: забытый вариант не будет пойман.

### Что спросят следом

«Как это выглядит в React?» — состояние запроса одним `useReducer` с таким union, а не четырьмя `useState`. «Как типизировать взаимоисключающие пропсы?» — union пропсов с дискриминантом; TS не даст передать `href` вместе с `onClick`. «А если дискриминанта нет?» — пользовательский type guard либо ввести искусственное поле.

```js
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: User[] }
  | { status: 'error'; error: string };

// невозможные комбинации просто не выражаются
if (state.status === 'success') state.data.length;  // ok
// state.data — ошибка вне этой ветки

// взаимоисключающие пропсы компонента
type ButtonProps =
  | { as: 'link'; href: string }
  | { as: 'button'; onClick: () => void };
// <Button as="link" onClick={...} /> — ошибка сборки

// сужение теряется при частичной деструктуризации
const { status, data } = state;      // data: User[] | undefined

// дискриминант обязан быть литералом
const bad = { status: 'success', data: [] };          // status: string
const ok  = { status: 'success', data: [] } as const; // status: 'success'
```

> **Что добавит очков.** Ключевая формулировка — «make illegal states unrepresentable». Приведи контраст с четырьмя булевыми флагами: это сразу показывает, что ты понимаешь пользу, а не синтаксис.

## 12. Как устроены Partial, Pick и ReturnType изнутри?

### Коротко

На двух механизмах. **Mapped types** перебирают ключи (`[K in keyof T]`) и позволяют навешивать или снимать модификаторы `?` и `readonly`. **Conditional types** (`T extends U ? X : Y`) вместе с `infer` вытаскивают тип из позиции — например тип возврата из сигнатуры функции. Написать их руками — стандартная проверка на интервью.

### Как это работает

- `Partial<T>` — `{ [K in keyof T]?: T[K] }`. Модификатор `?` добавляется, `-?` снимает его (`Required`), то же с `readonly` и `-readonly` (`Mutable`).
- `Pick<T, K>` — `{ [P in K]: T[P] }`: перебор идёт не по всем ключам, а по переданному union.
- `ReturnType<T>` — `T extends (...a: any) => infer R ? R : never`. `infer R` объявляет переменную типа, которую компилятор связывает при сопоставлении.
- **Дистрибутивность**: если проверяемый тип — голый параметр, conditional применяется к каждому члену union по отдельности. `Exclude<'a'|'b', 'a'>` раскладывается в `('a' extends 'a' ? never : 'a') | ('b' extends 'a' ? never : 'b')` и даёт `'b'`. Отключается обёрткой в кортеж: `[T] extends [U]`.
- `as` внутри mapped type переименовывает ключи, а возврат `never` — отфильтровывает их. На этом строят `Getters` и выборку по типу значения.

### Почему так

Утилиты не встроены в компилятор магически — они объявлены в `lib.es5.d.ts` теми же средствами, что доступны тебе. Это значит, что под свою доменную задачу можно написать точную утилиту вместо приведения через `as`. Плата: сложные рекурсивные типы заметно замедляют `tsc` и дают нечитаемые сообщения об ошибках.

### Подводные камни

- `Partial` заразителен: он **не рекурсивен**, вложенные объекты остаются обязательными. `DeepPartial` пишут руками.
- Дистрибутивность по `never`: `Exclude<never, 'a'>` это `never`, потому что union пуст и раскладывать нечего. Регулярный источник «пустых» типов.
- Mapped type над union распределяется не так, как ожидают: `Partial<A | B>` станет `Partial<A> | Partial<B>`, дискриминант при этом станет опциональным и сужение сломается.
- Рекурсия глубже примерно 50 уровней упирается в лимит инстанцирования типов.
- `keyof` над union даёт только **общие** ключи — частая причина «поле пропало».

### Что спросят следом

«Как отключить дистрибутивность?» — обернуть обе стороны в кортеж. «Напиши `DeepReadonly`» — рекурсивный mapped type с проверкой на объект. «Зачем `as` в mapped type?» — переименование ключей и фильтрация через `never`.

```js
type MyPartial<T>  = { [K in keyof T]?: T[K] };
type MyRequired<T> = { [K in keyof T]-?: T[K] };
type MyMutable<T>  = { -readonly [K in keyof T]: T[K] };
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
type MyExclude<T, U> = T extends U ? never : T;
type MyOmit<T, K extends keyof T> = MyPick<T, MyExclude<keyof T, K>>;

// рекурсия: Partial вглубь
type DeepPartial<T> = T extends object ? { [K in keyof T]?: DeepPartial<T[K]> } : T;

// переименование ключей и фильтрация через never
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };
type OnlyStrings<T> = { [K in keyof T as T[K] extends string ? K : never]: T[K] };

// отключение дистрибутивности
type IsUnion<T> = [T] extends [infer U] ? false : true;
```

> **Что добавит очков.** Обязательно проговори дистрибутивность — именно на ней ловят: почему Exclude работает, а NonNullable<never> даёт never. И назови цену: рекурсивные типы тормозят tsc и дают нечитаемые ошибки.

## 13. Зачем нужен satisfies и чем он отличается от аннотации и as?

### Коротко

Три операции с разной силой. **Аннотация** `const c: Config = {...}` проверяет соответствие, но **расширяет** тип переменной до объявленного — конкретные литералы теряются. **`as`** ничего не проверяет и просто переопределяет тип. **`satisfies`** (TS 4.9) проверяет соответствие и при этом сохраняет точный выведенный тип.

### Как это работает

`satisfies` — оператор проверки без изменения типа выражения. Компилятор сначала выводит тип литерала как обычно (со всеми литеральными значениями и точным набором ключей), затем проверяет, что этот тип присваиваем указанному. Если да — переменная получает **выведенный** тип, а не указанный.

Разница видна сразу: с аннотацией `Record<string, string>` тип `routes.home` станет `string`, а `keyof typeof routes` — просто `string`, и автодополнение пропадёт. С `satisfies` тип `routes.home` останется `'/'`, а `keyof` даст union реальных ключей.

При этом `satisfies` ловит и опечатки, и лишние ключи, и неверные значения — то есть даёт ровно ту проверку, ради которой обычно и ставят аннотацию.

### Почему так

До 4.9 приходилось выбирать: либо проверка (аннотация), либо точность (`as const` без проверки). Типовые жертвы — конфиги маршрутов, палитры темы, словари обработчиков, мапы «ключ → компонент». `satisfies` закрывает разрыв. Плата: это чисто компиляторная конструкция, в рантайме её нет, и от невалидных данных извне она не защищает.

### Подводные камни

- `satisfies` сам по себе **не делает значения readonly** и не сужает до литералов там, где вывод по умолчанию широкий. Для массивов и вложенных объектов часто нужна связка `as const satisfies T`.
- Порядок важен: `as const satisfies T`, а не наоборот.
- `as` с несовместимым типом требует двойного приведения через `unknown` — это сигнал, что типы неверны, а не повод так писать.
- Аннотация всё ещё нужна там, где надо намеренно **расширить** тип: например, переменная-состояние, которой позже присвоят другое значение из union.
- В параметре функции `satisfies` не поможет — там тип задаёт сигнатура.

### Что спросят следом

«Чем отличается от `as const`?» — `as const` делает всё `readonly` и литеральным, но ничего не проверяет; `satisfies` проверяет, но не замораживает. «Когда всё-таки аннотация?» — когда переменная должна принимать более широкий набор значений в дальнейшем. «Влияет ли на бандл?» — нет, стирается полностью.

```js
// аннотация: проверяет, но теряет литералы
const a: Record<string, string> = { home: '/', user: '/users/:id' };
// a.home: string; keyof typeof a: string — автодополнения нет

// satisfies: проверяет и сохраняет точность
const routes = {
  home: '/',
  user: '/users/:id',
} satisfies Record<string, string>;
// routes.home: '/'; keyof typeof routes: 'home' | 'user'

// ошибку в значении ловит так же, как аннотация
const bad = { home: 42 } satisfies Record<string, string>;  // Error

// связка для конфигов: заморозить и проверить
const theme = {
  colors: ['red', 'blue'],
  spacing: 8,
} as const satisfies { colors: readonly string[]; spacing: number };

// as ничего не проверяет
const lie = {} as { id: number };   // упадёт в рантайме
```

> **Что добавит очков.** Покажи выигрыш на конкретике: с satisfies keyof typeof конфига даёт union реальных ключей, и роутер с автодополнением получается бесплатно. Добавь про порядок «as const satisfies T» — на нём часто спотыкаются.

## 14. enum или union литералов? Какие настройки строгости включать?

### Коротко

По умолчанию — union строковых литералов, при необходимости в паре с `as const`-объектом. Он не генерирует рантайм-код, полностью стирается, естественно совместим с данными извне и не тянет за собой особенностей `enum`. Из настроек обязателен `strict: true`, дальше — `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`.

### Как это работает

Обычный `enum` компилируется в объект-IIFE, то есть остаётся в бандле, даже если использовался только как тип. `const enum` инлайнится, но не работает с `isolatedModules` и потому несовместим с esbuild, SWC и Babel — а на них собирается почти всё современное. С TypeScript 5.8 и флагом `erasableSyntaxOnly` (нужным для нативного выполнения TS в Node) `enum` запрещён вовсе.

Числовой `enum` вдобавок двунаправлен (`E[0] === 'Active'`) и до 5.0 принимал **любое число** в позиции своего типа — дыра в типобезопасности. Строковый `enum` номинален: строка `'active'` не подойдёт туда, где ждут `Status.Active`, что мешает работать с JSON.

### Почему так

Связка `as const`-объект плюс `typeof X[keyof typeof X]` даёт и рантайм-значения для итерации, и точный union для типов, ничего не добавляя в бандл сверх обычного объекта. Плата — синтаксис многословнее, и надо помнить про два имени (значение и тип), которые обычно объявляют одинаковыми.

### Подводные камни

- `const enum` в библиотеке ломает потребителей, собирающих транспайлером без типов.
- Без `strict` включённым остаётся почти всё важное: `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes`, `useUnknownInCatchVariables`.
- `noUncheckedIndexedAccess` даёт `T | undefined` при доступе по индексу и по строковому ключу — честно, но шумно: включать лучше сразу, а не на зрелом проекте.
- `exactOptionalPropertyTypes` различает «поля нет» и «поле есть со значением `undefined`» — ломает привычный спред с явным `undefined`.
- `skipLibCheck: true` обычно нужен для скорости, но прячет конфликты типов в зависимостях.
- `strict` не проверяет рантайм: без валидации внешних данных `strictNullChecks` — иллюзия безопасности.

### Что спросят следом

«Когда enum всё-таки норм?» — в закрытом приложении без библиотечных границ, если команда привыкла и сборщик его поддерживает. «Как перебрать варианты union?» — через `Object.values` исходного `as const`-объекта. «Что ещё включить?» — `noImplicitOverride`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax`.

```js
// вариант по умолчанию: значения и тип из одного источника
const Status = { Active: 'active', Blocked: 'blocked' } as const;
type Status = typeof Status[keyof typeof Status];   // 'active' | 'blocked'
Object.values(Status);                              // перебор вариантов

// если значения не нужны — достаточно union
type Role = 'admin' | 'editor' | 'viewer';

// проблема числового enum
enum Level { Low, High }
const l: Level = 42;      // до TS 5.0 компилировалось

// проблема строкового enum: номинальность мешает JSON
enum S { Active = 'active' }
const fromApi: S = 'active';   // Error — строка не подходит

// tsconfig
{ "strict": true,
  "noUncheckedIndexedAccess": true,
  "exactOptionalPropertyTypes": true,
  "noFallthroughCasesInSwitch": true,
  "verbatimModuleSyntax": true }
```

> **Что добавит очков.** Назови конкретную причину, а не моду: enum остаётся в бандле, const enum несовместим с isolatedModules, а с erasableSyntaxOnly в TS 5.8 enum вообще запрещён. По настройкам добавь, что noUncheckedIndexedAccess дешевле включить в первый день проекта.

## 15. Что такое assertion function и чем она отличается от type guard?

```js
const assertDefined = <T,>(v: T): asserts v is NonNullable<T> => {
  if (v == null) throw new Error('expected value');
};

const el = document.querySelector('#root');
assertDefined(el); // почему здесь ошибка компиляции?
```

### Коротко

Assertion function объявляется как `asserts x is T` или `asserts x`, ничего не возвращает и либо бросает исключение, либо сужает переменную **для всего кода ниже вызова**. Type guard сужает только внутри ветки `if`, assertion — до конца области видимости.

### Как это работает

Компилятор трактует вызов как узел control flow с двумя исходами: либо функция выбросила и поток прервался, либо утверждение истинно. Второй исход и записывается в таблицу сужений. Тип возврата `asserts …` означает «возврата в нормальном смысле нет» — это близкий родственник `never`, и функция обязана быть объявлена без явного `return` значения.

Сниппет не компилируется, и это специально: TS требует, чтобы у цели вызова было **явно объявленное имя с явным типом**. Стрелка, присвоенная в `const` без аннотации, этого условия не выполняет — тип выведен, а не написан, и появляется ошибка «Assertions require every name in the call target to have an explicit type annotation». Лечится двумя способами: переписать в `function`-декларацию или проставить `const assertDefined: <T>(v: T) => asserts v is NonNullable<T>` руками.

В рантайме от `asserts` не остаётся ничего, кроме самой функции с её `throw`. Ни один байт проверки не генерируется компилятором — работает только то, что вы написали в теле.

### Почему так

Требование явной аннотации существует потому, что вывод типов в TS ленивый и в общем случае циклический: чтобы понять, влияет ли вызов на поток управления, чекеру нужен тип вызываемого **до** анализа потока, а вывод типа мог бы, наоборот, зависеть от результата анализа. Явная аннотация разрывает этот цикл. Плата — эргономика: `invariant`, написанный как стрелка, внезапно не работает.

### Подводные камни

- Импорт через namespace (`utils.assertDefined(x)`) требует явного типа у каждого имени в пути вызова, включая сам `utils`.
- Сужение не переживает деструктуризацию: `assertDefined(obj.a)` сужает `obj.a`, но не ранее вытащенную `const { a }`.
- Как и предикат, тело не верифицируется: `asserts v is string` с пустым телом молча пропустит что угодно.
- В продовой сборке соблазн вырезать `invariant` терсером: тогда типы обещают то, чего в рантайме больше не проверяется.

### Что спросят следом

**Чем отличается `asserts x` без `is`?** Это утверждение истинности: сужает `x` по truthiness, годится для `invariant(cond)`. **Как типизировать exhaustive switch?** Через `function assertNever(x: never): never` в `default`: добавили вариант в union — получили ошибку компиляции в этой строке.

```js
// function-декларация — требование про explicit type выполняется само
function assertDefined<T>(v: T, msg?: string): asserts v is NonNullable<T> {
  if (v == null) throw new Error(msg ?? 'expected value');
}

const el = document.querySelector('#root'); // Element | null
assertDefined(el);
el.classList.add('ok');                     // Element — сужение живёт до конца блока

function assertNever(x: never): never { throw new Error('unhandled: ' + String(x)); }
```

> **Что добавит очков.** Назовите ошибку «Assertions require every name in the call target to have an explicit type annotation» и её причину — циклическую зависимость вывода типа и анализа потока.

## 16. Почему тип «разсуживается» внутри колбэка и как с этим жить?

```js
let v: string | null = get();
if (v !== null) {
  setTimeout(() => v.length, 0);   // Object is possibly 'null'
}

const c: string | null = get();
if (c !== null) {
  setTimeout(() => c.length, 0);   // ошибки нет
}
```

### Коротко

Сужение держится на допущении «значение не изменилось с момента проверки». Для `let` и для свойств объекта компилятор доказать это через границу функции не может: колбэк выполнится когда угодно, а переприсвоить переменную может любой код. Поэтому внутри стрелки тип откатывается к объявленному.

### Как это работает

При анализе тела функции-выражения чекер смотрит на **вид объявления** захваченной переменной. Если это `const` (или `readonly`-поле, или параметр, который нигде не переприсваивается), значение неизменно по построению — сужение из внешней области переносится внутрь. Если это `let` или `var`, чекер должен был бы доказать, что между проверкой и вызовом колбэка присваивания не произошло. Это требует межпроцедурного анализа, которого в TS нет, поэтому применяется консервативное правило: внутри функции берём объявленный тип.

Отсюда рецепт из сниппета: та же проверка над `const c` работает, потому что `c` нельзя переприсвоить в принципе. Со свойствами хуже — `obj.value` разсуживается уже после **любого вызова функции** в том же блоке, потому что чекер не отслеживает алиасинг: другая ссылка на тот же объект могла записать туда что угодно.

С TS 4.4 работает **aliased condition**: результат проверки, сохранённый в `const`, сам становится источником сужения — `const isOk = v !== null; if (isOk) { … }` сузит `v`, но только если `v` тоже неизменяема.

### Почему так

Альтернатива — escape-анализ: доказать, что колбэк вызовется синхронно и до него нет присваиваний. Это дорого и всё равно неполно, потому что колбэк можно сохранить и вызвать из другого модуля. TS выбрал предсказуемость: правило простое, объяснимое и не зависит от того, как далеко утекла функция. Платим лишними промежуточными переменными.

### Подводные камни

- Синхронный колбэк (`arr.forEach`) страдает так же, как асинхронный — компилятор не различает их и не знает про `Array.prototype`.
- `await` внутри блока сбрасывает сужение свойств: между `if` и продолжением мог выполниться чужой код.
- Массовое лечение через `!` прячет реальные гонки: значение действительно могло стать `null`, пока таймер ждал.
- Деструктуризация в `const { value }` лечит сужение, но делает снимок: последующая запись в `obj.value` в этой копии не видна.

### Что спросят следом

**А если переменная — параметр?** Параметр ведёт себя как `let`: сужение внутри колбэка слетит, если в теле есть хоть одно присваивание этому параметру. **Почему не помогает `as` внутри колбэка?** Помогает подавить ошибку, но не решает задачу: значение к моменту вызова действительно может быть другим, и `as` просто отключает предупреждение о реальном риске.

```js
// плохо: ! маскирует настоящую гонку
let v: string | null = get();
if (v !== null) setTimeout(() => v!.length, 0);

// хорошо: снимок значения, неизменность доказуема
const snapshot = v;
if (snapshot !== null) setTimeout(() => snapshot.length, 0); // string

// TS 4.4 aliased condition
const hasValue = snapshot !== null;
if (hasValue) snapshot.length; // string
```

> **Что добавит очков.** Ключевая фраза: TS не делает escape-анализ и не отслеживает алиасинг, поэтому сбрасывает сужение везде, где не может доказать неизменность.

## 17. Расскажите про вариантность в TypeScript и что меняет strictFunctionTypes.

```js
declare let handleDog: (a: Dog) => void;
declare let handleAnimal: (a: Animal) => void;

handleAnimal = handleDog;  // ошибка или нет при strictFunctionTypes?

interface Bi { on(a: Dog): void }
const bi: Bi = { on(a: Animal) {} };  // а здесь?
```

### Коротко

Вариантность описывает, как отношение подтипов у `T` переносится на обёртку `F<T>`. В TS она нигде не объявляется — компилятор **выводит её структурно** из позиций, в которых параметр типа встречается. Возвращаемые значения и свойства дают ковариантность, параметры функций — контравариантность, оба сразу — инвариантность.

### Как это работает

В сниппете первая строка — ошибка при `strictFunctionTypes`: `handleDog` умеет только собак, а через переменную типа `(a: Animal) => void` ему передадут кошку. Вторая строка ошибки не даёт: `on` объявлен методом, а параметры методов проверяются **бивариантно** даже в strict-режиме.

Правило подтипирования функций: `(a: A) => R1` присваивается `(b: B) => R2`, если `B` присваивается `A` (параметры наоборот) и `R1` присваивается `R2` (возврат прямо). Это и есть контравариантность параметров, и она единственно безопасна.

Для дженериков чекер вычисляет вариантность один раз при первом сравнении: обходит определение, отмечает, в каких позициях появляется параметр, и кеширует маркер (`Covariant`, `Contravariant`, `Invariant`, `Bivariant`, `Independent`). Дальше сравнение `F<A>` с `F<B>` идёт по маркеру, а не по структуре — это и есть та оптимизация, которую подкручивают аннотации `in`/`out`.

### Почему так

Массивы в TS ковариантны сознательно: `Dog[]` присваивается `Animal[]`, хотя запись через вторую ссылку может положить туда кошку. Строго правильная инвариантность массивов сломала бы гигантское количество существующего JS-кода, где «список собак» естественно передают в функцию «посчитай животных». Ровно та же логика за бивариантностью методов: типы DOM, `Array.prototype`, `EventTarget` и React написаны так, что строгая проверка сделала бы их непригодными.

### Подводные камни

- `strictFunctionTypes` входит в `strict`, но **не действует на методы** — это не баг конфигурации, а явное исключение в чекере.
- Разница «метод против свойства-функции» невидима глазом, поэтому строгость обработчиков включается переписыванием `on(e: E): void` в `on: (e: E) => void`.
- Ковариантность массивов даёт runtime-ошибку без единого предупреждения компилятора — классический пример unsound-места в TS.
- Функция с меньшим числом параметров присваивается функции с большим: `() => void` подходит везде, где ждут `(e: Event) => void`. Отсюда баг `arr.map(parseInt)`.
- Возврат `void` особенный: любая функция с любым возвратом присваивается типу с `=> void`, поэтому `arr.forEach(x => set.add(x))` не ругается.

### Что спросят следом

**Что такое «unsound» в этом контексте?** Система типов unsound, если существует программа без ошибок компиляции, падающая на несоответствии типов в рантайме — TS unsound намеренно. **Как получить инвариантность руками?** Использовать параметр типа и в позиции параметра, и в позиции возврата, либо явно написать `in out`.

```js
type Handler = (a: Animal) => void;
let onDog: (a: Dog) => void = (d) => d.bark();
const h: Handler = onDog;      // ошибка при strictFunctionTypes

interface Loose  { on(a: Dog): void }        // бивариантно — проверки нет
interface Strict { on: (a: Dog) => void }    // контравариантно — проверка есть

const dogs: Dog[] = [new Dog()];
const animals: Animal[] = dogs;  // ковариантность массивов: ок для компилятора
animals.push(new Cat());         // и вот здесь в dogs лежит кошка
```

> **Что добавит очков.** Скажите прямо: ковариантность массивов и бивариантность методов — осознанный unsound-компромисс ради совместимости с существующим JS, а не недосмотр компилятора.

## 18. Что такое template literal types и где они реально полезны?

```js
type Size  = 'sm' | 'md' | 'lg';
type Color = 'red' | 'blue';

type Token = `--btn-${Size}-${Color}`;
// сколько членов в этом union и какие?
```

### Коротко

Template literal types — строковые типы, собранные из литеральных кусков и плейсхолдеров `${…}`. При подстановке union они **дистрибутивно разворачиваются в декартово произведение**. К ним прилагаются четыре интринзика компилятора: `Uppercase`, `Lowercase`, `Capitalize`, `Uncapitalize`.

### Как это работает

В сниппете `Token` — это union из шести литералов: `'--btn-sm-red' | '--btn-sm-blue' | '--btn-md-red' | …`. Компилятор перемножает все позиции: 3 × 2. Это ключевая механика и одновременно главная опасность — размер результата мультипликативен по числу плейсхолдеров.

В обратную сторону работает сопоставление: тип ``get${infer K}`` в условном типе разбирает строку по образцу, отдавая в `K` хвост. Разбор жадный слева направо: ``${infer A}-${infer B}`` на строке `'a-b-c'` даст `A = 'a'`, `B = 'b-c'`. На этом строится парсинг роутов, разбор CSS-значений и типизация путей к вложенным полям.

Интринзики `Uppercase` и компания реализованы прямо в чекере (в файле `checker.ts` есть таблица `intrinsicTypeKinds`), а не через типы из lib.d.ts — выразить их средствами языка невозможно.

В рантайме, как обычно, ноль следа: `Token` исчезает при компиляции, а строки в коде остаются обычными строками.

### Почему так

До 4.1 «ключ вида on + имя события» приходилось выписывать руками или отдавать `string`. Шаблонные типы позволили выразить строковые протоколы (CSS-переменные, ключи i18n, имена событий, пути к полям) в системе типов и получить автодополнение вместо документации. Плата — компилятор считает произведения, и большие union стоят памяти и времени.

### Подводные камни

- **Комбинаторный взрыв**: два union по 50 членов дают 2500 литералов, три — 125 000, и компилятор упирается в жёсткий лимит в 100 000 членов union с ошибкой «Expression produces a union type that is too complex to represent».
- Рекурсивные пути к вложенным полям на большой модели порождают десятки тысяч литералов и в одиночку прибивают отзывчивость IDE.
- `${number}` и `${bigint}` сопоставляются с числовыми литералами, но обратно тип не считает: `'01'` и `'1'` — разные строки, а `'1e3'` тоже проходит как число.
- `keyof T` включает `symbol`, а символ в шаблон не подставляется — нужен `K & string`.
- Порядок членов в получившемся union не специфицирован и менялся между версиями; полагаться на него в type-тестах нельзя.

### Что спросят следом

**Как ограничить взрыв?** Не разворачивать всё сразу: держать тип как проверку (`T extends `--btn-${string}` ? T : never`) вместо перечисления, ограничивать глубину рекурсии и отсекать ветки на первом же несоответствии. **Где это применяют в проде?** Tailwind-подобные типы классов, tRPC-роуты, ключи i18n с проверкой плейсхолдеров, типизированные CSS-переменные дизайн-системы.

```js
type Ev<T extends string> = `on${Capitalize<T>}`;
type A = Ev<'click' | 'focus'>;   // "onClick" | "onFocus"

// разбор роута на уровне типов: жадно слева направо
type Params<S extends string> =
  S extends `${string}:${infer P}/${infer R}` ? P | Params<R>
  : S extends `${string}:${infer P}` ? P
  : never;
type P = Params<'/users/:id/posts/:postId'>;  // "id" | "postId"

// проверка вместо перечисления — не взрывается
type CssVar<T extends string> = T extends `--${string}` ? T : never;
```

> **Что добавит очков.** Назовите жёсткий лимит в 100 000 членов union и приём «проверять шаблоном, а не перечислять произведение» — это сразу отличает практика от читателя статей.

## 19. Что такое дистрибутивность conditional types и когда она мешает?

```js
type IsString<T> = T extends string ? true : false;

type A = IsString<string | number>;  // ?
type B = IsString<never>;            // ?
type C = IsString<any>;              // ?
```

### Коротко

Если проверяемый тип — **голый параметр** (`T extends X ? A : B`, где `T` ничем не обёрнут), то при подстановке union условие применяется к каждому члену по отдельности, а результаты объединяются. На этом построены `Exclude`, `Extract`, `NonNullable`. Отключается обёрткой в кортеж: `[T] extends [X]`.

### Как это работает

Ответы на сниппет: `A = boolean` (то есть `true | false` — условие применилось к `string` и к `number` отдельно), `B = never` (не `false`!), `C = boolean`.

Случай с `never` — прямое следствие определения: `never` это union из нуля членов, дистрибуция по нулю членов даёт union из нуля результатов, то есть снова `never`. Ветка условия не выполняется ни разу. Это ломает любую наивную проверку вида «пустой ли тип» и все хелперы, которые пишут `T extends never ? …`.

`any` обрабатывается особым правилом: условный тип над `any` сразу возвращает union обеих веток, потому что `any` одновременно совместим и несовместим с чем угодно. `unknown`, наоборот, просто уходит в false-ветку.

Отключение через кортеж работает потому, что `[T]` — уже не голый параметр, а тип-обёртка: чекер сравнивает `[string | number]` с `[string]` целиком, и получает `false`. Тот же приём применяют к правой части, когда нужно сравнить union как единое целое.

### Почему так

Дистрибутивность введена ради утилит фильтрации: без неё `Exclude<'a' | 'b', 'a'>` пришлось бы писать через рекурсию по членам union, а такой рекурсии в языке не было. Правило «голый параметр — дистрибутивно» синтаксическое и потому предсказуемое, но оно бьёт по всем, кто пишет условный тип, не думая про union на входе.

### Подводные камни

- `T = never` даёт `never`, а не false-ветку — самая частая ловушка на интервью и в реальных хелперах.
- `boolean` — это `true | false`, поэтому он тоже дистрибутируется: `T extends true ? …` на `boolean` даст обе ветки.
- Дистрибутивность мешает при `UnionToIntersection`, при проверке «является ли T объединением» и при точном сравнении типов.
- Обёртка в кортеж выключает и полезную дистрибуцию: если внутри маппер, он теперь получит union целиком.
- Проверка на `any` должна идти первой: любое условие после неё уже даст обе ветки и результат станет бессмысленным.

### Что спросят следом

**Как проверить, что тип — `never`?** Только через невывернутую форму: `[T] extends [never] ? true : false`. **Как определить, что `T` — union?** Сравнить дистрибутивную версию с недистрибутивной: `T extends any ? ([U] extends [T] ? false : true) : never` с `U = T`, зафиксированным до дистрибуции.

```js
type IsString<T> = T extends string ? true : false;
type A = IsString<string | number>;        // boolean
type C = IsString<never>;                  // never — ветки не выполнялись
type D = IsString<any>;                    // boolean — особое правило для any

type IsStringStrict<T> = [T] extends [string] ? true : false;
type B = IsStringStrict<string | number>;  // false

type IsNever<T> = [T] extends [never] ? true : false;
type E = IsNever<never>;                   // true
```

> **Что добавит очков.** Назовите случай T = never сами и объясните причину: never — union из нуля членов, поэтому дистрибуция не выполняет ни одной ветки.

## 20. Где может стоять infer и что даёт infer extends?

```js
type Co<T> = T extends { a: infer U; b: infer U } ? U : never;
type Contra<T> = T extends { f: (x: infer U) => void; g: (x: infer U) => void } ? U : never;

type A = Co<{ a: string; b: number }>;                              // ?
type B = Contra<{ f: (x: string) => void; g: (x: number) => void }>; // ?
```

### Коротко

`infer` объявляет переменную типа прямо в правой части `extends` внутри условного типа. Позиций несколько, и от позиции зависит, как компилятор соединяет несколько кандидатов: в ковариантных — через union, в контравариантных — через пересечение.

### Как это работает

Ответы на сниппет: `A = string | number`, `B = string & number`, то есть `never`. Это не курьёз, а прямое следствие вариантности. Свойство — ковариантная позиция: чтобы тип подошёл обоим кандидатам «сверху», нужен супертип, то есть union. Параметр функции — контравариантная: чтобы функция приняла и `string`, и `number`, нужен подтип обоих, то есть пересечение. На этом построен классический `UnionToIntersection`.

Полный список позиций: возвращаемое значение (`T extends () => infer R`), параметры, элементы кортежа с rest (`[infer H, ...infer R]` — база всей рекурсии по кортежам), аргументы дженерика (`Promise<infer U>`), плейсхолдеры template literal.

`infer R extends C` (TS 4.8) добавляет ограничение прямо в вывод. Это делает две вещи: отсекает ветку, если вывод не удовлетворяет ограничению, и — для строковых литералов — **приводит тип**. `S extends `${infer N extends number}`` на строке `'42'` даёт числовой литерал `42`, а не строку `'42'`.

### Почему так

Правило «ковариантно — union, контравариантно — intersection» не выбрано произвольно: это единственный способ получить тип, безопасный во всех местах, где параметр встречается. Компилятор здесь просто честно применяет теорию подтипов, а не эвристику.

### Подводные камни

- Несколько `infer U` с одним именем — не ошибка, а сознательное объединение кандидатов; если вы этого не планировали, результат будет неожиданным.
- Пересечение примитивов (`string & number`) схлопывается в `never` без предупреждения — типичный «почему у меня never» в самописных утилитах.
- `infer` в rest-позиции кортежа жаден: `[...infer A, infer B]` и `[infer A, ...infer B]` дают разный разбор, и первый заметно дороже по времени проверки.
- Без `extends`-ограничения выведенный из шаблона тип всегда строковый — ``${infer N}`` на `'42'` даст `'42'`, а не `42`.
- При выводе из перегруженной функции берётся **последняя** сигнатура, а не «подходящая» — из-за этого `ReturnType` на перегрузках часто врёт.

### Что спросят следом

**Как устроен `UnionToIntersection`?** Дистрибуция раскладывает union на члены, каждый попадает в контравариантную позицию `(x: T) => void`, затем `infer` оттуда собирает кандидатов через пересечение. **Почему `ReturnType` на перегрузках даёт не то?** Потому что вывод берёт последнюю сигнатуру; лечится явным списком перегрузок или условным типом с несколькими ветками.

```js
type Ret<T> = T extends (...a: any[]) => infer R ? R : never;
type Head<T> = T extends [infer H, ...unknown[]] ? H : never;

// контравариантная позиция даёт пересечение
type UnionToIntersection<U> =
  (U extends any ? (x: U) => void : never) extends (x: infer I) => void ? I : never;
type X = UnionToIntersection<{ a: 1 } | { b: 2 }>;  // { a: 1 } & { b: 2 }

// infer extends приводит строковый литерал к числовому
type ToNum<S> = S extends `${infer N extends number}` ? N : never;
type N = ToNum<'42'>;   // 42 (число), без extends было бы "42"
```

> **Что добавит очков.** Пример с двумя одноимёнными infer в свойстве и в параметре — самая короткая демонстрация того, что вы понимаете вариантность, а не заучили список позиций.

## 21. Когда использовать overloads, а когда union или дженерик?

```js
function get(k: 'a'): number;
function get(k: 'b'): string;
function get(k: string): unknown { return null as never; }

declare const key: 'a' | 'b';
get(key);   // почему ошибка?
```

### Коротко

Перегрузки описывают набор допустимых пар «аргументы — результат», когда связь между ними нельзя выразить одной сигнатурой. Реализационная сигнатура снаружи невидима и против перегрузок почти не проверяется — по надёжности это дыра уровня `as`. Разрешение идёт **первым совпадением сверху вниз**.

### Как это работает

Сниппет не компилируется, и это не баг. Чекер перебирает перегрузки по порядку и ищет **первую**, к которой список аргументов присваивается целиком. `'a' | 'b'` не присваивается ни `'a'`, ни `'b'` по отдельности; идеи «разложить union и объединить результаты» в разрешении перегрузок нет. Ошибка: «No overload matches this call».

Реализационная сигнатура проверяется слабо: она обязана быть «совместимой» с каждой перегрузкой, но компилятор проверяет это очень мягко — тело `get` может вернуть строку там, где перегрузка обещала число, и ошибки не будет. Возврат `unknown` из реализации приемлем, потому что снаружи её никто не видит.

В рантайме перегрузки не существуют вовсе: в JS уезжает одна функция. Все ветвления по числу и типу аргументов вы пишете руками.

### Почему так

Механизм появился для описания существующих JS-API вроде `document.createElement`, где связь «аргумент → результат» задана таблицей. Правило «первое совпадение» проще и предсказуемее выбора «наиболее подходящей», как в C++, но требует ручного упорядочивания: узкие сигнатуры ставим первыми, иначе широкая перехватит вызов и вернёт слишком общий тип.

### Подводные камни

- Union на входе не подходит ни к одной перегрузке — самая частая боль; лечится дженериком с `keyof` или отдельной перегрузкой для union.
- Порядок значим: широкая сигнатура сверху делает все нижние недостижимыми, и компилятор об этом не предупреждает.
- Плохо работают со spread: `get(...args)` не разрешается, если `args` — не кортеж.
- Сообщения об ошибках нечитаемы: чекер печатает последнюю попытку, а не самую близкую.
- Опциональные параметры в разных перегрузках порождают комбинации, которые легко забыть покрыть в теле.

### Что спросят следом

**Что вместо?** Дженерик с индексированным доступом (`<K extends keyof M>(k: K) => M[K]`) — он дружит с union и даёт `M['a'] | M['b']` без ошибок. Второй вариант — дискриминированный union параметров-объектов: `f({ kind: 'a' })`, где результат зависит от дискриминанта. **Чем платим за условный возвращаемый тип?** Внутри реализации он почти не проверяется, и тело обычно требует `as any` — компромисс осознанный, но его надо назвать вслух.

```js
interface M { a: number; b: string }

// дженерик вместо перегрузок: union на входе работает
declare function get<K extends keyof M>(k: K): M[K];
declare const key: 'a' | 'b';
get(key);          // number | string — ошибки нет

// перегрузки: узкие сигнатуры первыми
function el(tag: 'input'): HTMLInputElement;
function el(tag: string): HTMLElement;
function el(tag: string): HTMLElement { return document.createElement(tag); }

el('input');       // HTMLInputElement — если поменять порядок, будет HTMLElement
```

> **Что добавит очков.** Фраза «перегрузки не разлагают union на входе, потому что разрешение ищет первое целиком подходящее совпадение» — конкретная боль плюс объяснение причины.

## 22. Что реально даёт readonly и as const, и чего они не дают?

```js
type Frozen = { readonly x: number };
declare const f: Frozen;

const mutable: { x: number } = f;   // ошибка?
mutable.x = 42;                     // а что с f.x?
```

### Коротко

`readonly` — **исключительно compile-time** модификатор. Объект не заморожен, в рантайме от него не остаётся ничего, и — что важнее — `readonly`-свойства **игнорируются при проверке присваиваемости объектов**. Защита протекает по построению.

### Как это работает

В сниппете ошибки нет: тип `{ readonly x: number }` спокойно присваивается `{ x: number }`. После этого `mutable.x = 42` меняет **тот же самый объект**, на который смотрит `f`, — компилятор ничего не заметил, рантайм ничего не запретил. Это известный unsound-компромисс: сделать `readonly` значимым для присваиваемости означало бы сломать огромное количество кода, где readonly-тип передают в функцию, которая ничего не мутирует, но объявила параметр обычным.

С массивами строже: `readonly T[]` и `T[]` — разные типы, и присваивание идёт только в одну сторону. `number[]` присваивается `readonly number[]`, обратно — ошибка. Причина в том, что `ReadonlyArray` просто не имеет мутирующих методов, и структурная проверка честно это ловит.

`as const` делает три вещи разом: не расширяет литералы (`'a'` остаётся `'a'`), помечает все свойства `readonly` рекурсивно, превращает массивные литералы в кортежи. Это чисто типовая операция — `Object.freeze` она не вызывает и в JS-выводе исчезает бесследно.

### Почему так

Настоящая иммутабельность в рантайме стоит денег: `Object.freeze` в V8 переводит объект в медленный режим доступа и стоит обхода всех свойств. TS предлагает бесплатную дисциплину «не мутировать» с проверкой в 90% мест — и честно не претендует на гарантию. Понимание этой границы важнее заученных правил.

### Подводные камни

- Присваивание readonly-объекта изменяемому типу — молчаливая дыра, о которой почти никто не помнит.
- `as const` не работает на выражениях с вычислениями: `{ x: a + b } as const` даст `number`, а не литерал.
- `readonly` поверхностный: `readonly items: Item[]` запрещает переприсвоить массив, но не запрещает `items.push`.
- `Readonly<T>` тоже поверхностный — глубокая версия требует рекурсивного маппера с отсечением `Date` и функций.
- `Object.freeze` в нестрогом режиме молча игнорирует запись; ошибка бросается только в `'use strict'`, то есть в модулях.

### Что спросят следом

**Как получить реальную неизменяемость?** Библиотекой персистентных структур (Immer с `freeze`, Immutable.js) либо `Object.freeze` в dev-сборке и полагаться на типы в prod. **Зачем `as const` в реальном коде?** Связка `as const` + `typeof` + `[number]` — стандартный способ иметь одно определение и для рантайма (итерируемый список), и для типов (точный union).

```js
const a: readonly number[] = [1, 2];
const b: number[] = a;                 // ошибка — массивы строже

type P = { readonly x: number };
const p: { x: number } = { x: 1 } as P; // ошибки нет — дыра в объектах

const ROLES = ['admin', 'user'] as const;  // readonly ["admin", "user"]
type Role = typeof ROLES[number];          // "admin" | "user"

const n = 1, m = 2;
const bad = { x: n + m } as const;         // { readonly x: number } — не литерал
```

> **Что добавит очков.** Назовите то, что readonly-модификаторы свойств не влияют на присваиваемость объектов (в отличие от массивов) — этот факт почти никто не помнит.

## 23. Что делает Awaited и почему он оказался нетривиальным?

```js
type Naive<T> = T extends Promise<infer U> ? U : T;

type A = Naive<Promise<Promise<string>>>;   // ?
type B = Awaited<Promise<Promise<string>>>; // ?
```

### Коротко

`Awaited<T>` (TS 4.5) моделирует то, что делает `await`: рекурсивно разворачивает вложенные промисы, понимает произвольные thenable, дистрибутируется по union и оставляет не-промисы как есть. Наивная однократная распаковка через `infer` всё это ломает.

### Как это работает

В сниппете `A = Promise<string>` — наивный тип снял ровно один слой. `B = string` — `Awaited` раскрутил рекурсивно, ровно как рантайм: `await` разрешает промис промиса до значения, потому что `Promise.resolve` ассимилирует thenable.

Реализация в lib.es5.d.ts выглядит так: если `T` — `null`/`undefined`, вернуть как есть; если у `T` есть метод `then`, принимающий колбэк, — вывести аргумент этого колбэка и применить `Awaited` к нему рекурсивно; иначе вернуть `T`. Проверка идёт именно по форме `{ then(onfulfilled: (value: infer V) => any): any }`, а не по имени `Promise` — поэтому работают и пользовательские thenable, и `PromiseLike`.

Через `Awaited` типизирован `Promise.all`: он применяется к каждому элементу кортежа, поэтому позиции сохраняются и `Promise.all([a(), b()])` даёт `[A, B]`, а не `(A | B)[]`. У `Promise.allSettled` результат — union `PromiseFulfilledResult<T> | PromiseRejectedResult`, и до `value` надо сужаться по полю `status`.

### Почему так

Рекурсивная распаковка отражает решение ES2015: `Promise<Promise<T>>` в рантайме не существует как наблюдаемое состояние — цепочка резолвится до конца. Тип, который этого не учитывает, обещает то, чего никогда не будет. Отсюда и `Awaited` появился в lib: слишком многие писали наивную версию и получали неверные типы у `Promise.all`.

### Подводные камни

- `Awaited<any>` даёт `any`, и вся цепочка типов после этого молча теряет проверку.
- `filter((r) => r.status === 'fulfilled')` до TS 5.5 не сужал тип массива — нужен был явный предикат. С 5.5 предикат выводится, и `value` доступен без каста.
- Тип не отражает тайминг: `await` на не-промисе всё равно откладывает продолжение на микротаск, но `Awaited<string>` — это просто `string`.
- `Promise.all` на массиве (а не кортеже) даёт `T[]` и теряет позиции — нужен `as const` или кортежный литерал.
- Тип отклонения нигде не выражен: `Promise<T>` не параметризован ошибкой, поэтому `catch` всегда даёт `unknown` (при `useUnknownInCatchVariables`).

### Что спросят следом

**Как достать тип данных загрузчика?** `Awaited<ReturnType<typeof loadUser>>` — стандартная идиома для типов из API-слоя. **Почему нельзя типизировать ошибку промиса?** Потому что бросить можно что угодно, включая не-`Error`; поэтому библиотеки вроде neverthrow возвращают `Result`-объект вместо исключения.

```js
type Data = Awaited<ReturnType<typeof loadUser>>;

// кортеж сохраняет позиции
const [user, posts] = await Promise.all([loadUser(), loadPosts()]);
// user: User, posts: Post[]

// allSettled требует сужения по status
const rs = await Promise.allSettled([loadUser(), loadPosts()]);
const ok = rs.filter((r) => r.status === 'fulfilled');
// TS 5.5: PromiseFulfilledResult<...>[] — .value доступен без каста

type Weird = Awaited<{ then(cb: (v: number) => void): void }>;  // number
```

> **Что добавит очков.** Пример с allSettled и тем, что сужение фильтром по status заработало только с выводом предикатов в TS 5.5, показывает работу с этим в проде.

## 24. Что такое declaration merging и какие правила слияния важно помнить?

```js
interface Box { a: string }
interface Box { b: number }
interface Box { a: number }

type T = { a: string };
type T = { b: number };
// где ошибка и какая?
```

### Коротко

Declaration merging — объединение нескольких объявлений с одним именем в одной области видимости. Сливаются `interface` с `interface`, `namespace` с `namespace`, а также `namespace` с `class`, `function` или `enum`. `type` не сливается никогда.

### Как это работает

В сниппете две ошибки. Третье объявление `Box` конфликтует: свойство `a` уже объявлено как `string`, повторное объявление с другим типом даёт «Subsequent property declarations must have the same type». Второе объявление `type T` даёт «Duplicate identifier 'T'» — алиасы типов принципиально не мержатся. Первые два `interface Box` сливаются нормально в `{ a: string; b: number }`.

Механика: компилятор строит таблицу символов; у символа может быть несколько деклараций, и при разрешении типа он собирает члены со всех. Одноимённые **свойства** должны совпадать по типу, а одноимённые **методы** превращаются в перегрузки — и порядок здесь неочевиден: объявления из позже обработанных файлов идут **раньше** в списке перегрузок, а внутри одного файла порядок сохраняется.

Слияние namespace с функцией даёт «функция со статическими свойствами» — так типизируют jQuery-подобные API и React-компоненты с `Component.displayName`. Внутри namespace сливаются только `export`-члены; неэкспортированные остаются локальными для своего блока.

### Почему так

Merging существует ради двух задач: описывать JS-библиотеки, которые дописывают свойства в существующие объекты, и давать точку расширения плагинам. Именно поэтому `Window`, `ProcessEnv`, `JSX.IntrinsicElements` — интерфейсы: любой пакет может добавить в них члены из своего `.d.ts`. Алиасы типов задумывались как обычные вычисляемые выражения над типами (они могут быть union, кортежем, условным типом), а «дописать член» в union бессмысленно — отсюда запрет.

### Подводные камни

- Публичный API библиотеки на `type` лишает пользователей возможности расширить его аугментацией — необратимое решение после релиза.
- Слияние срабатывает **молча**: опечатка в имени интерфейса не создаст новый тип, а незаметно дополнит существующий.
- Порядок перегрузок при слиянии зависит от порядка файлов, а он зависит от порядка импортов — источник плавающих ошибок в монорепе.
- Класс и интерфейс с одним именем сливаются: интерфейс дописывает члены в тип экземпляра, но реализацию за вас никто не напишет — получите ложное обещание.
- Слияние работает только в одной области видимости: интерфейс в модуле и интерфейс в global — разные символы.

### Что спросят следом

**Так `interface` или `type`?** Для публичных API и объектных форм — `interface` (расширяемость плюс кеширование по имени, что дешевле для чекера). Для union, кортежей, условных и мапнутых типов — `type`, потому что интерфейс их выразить не может. **Где merging используется каждый день?** `declare global { interface Window {…} }`, поля в `Express.Request`, темы в styled-components.

```js
interface Box { a: string }
interface Box { b: number }        // Box = { a: string; b: number }

// методы становятся перегрузками
interface Api { call(x: string): void }
interface Api { call(x: number): void }

// функция + namespace = функция со статикой
function greet(n: string) {}
namespace greet { export const version = '1.0' }
greet('x'); greet.version;

// type не сливается
type T = { a: string };
// type T = { b: number };         // Duplicate identifier 'T'
```

> **Что добавит очков.** Сильный вывод: расширяемость через merging — причина, по которой библиотеки выставляют публичные объектные типы интерфейсами; заменить interface на type в мажорном релизе значит отобрать у пользователей аугментацию.

## 25. Как типизировать внешнюю библиотеку без типов? Что важно в .d.ts?

### Коротко

Порядок такой: проверить типы в самом пакете (поля `types`/`typings`/`exports` в его package.json), затем `@types/*` из DefinitelyTyped, и только потом писать своё. Свои типы — это `.d.ts` в `src/types`, включённый в `include`, с описанием ровно того, чем вы пользуетесь.

### Как это работает

Разрешение типов идёт параллельно разрешению кода и обязано давать тот же файл. Для `moduleResolution: node10` компилятор смотрит `types` в package.json и `index.d.ts` рядом с точкой входа. Для `node16`/`nodenext` и `bundler` — читает поле `exports` и идёт по условиям: `types` внутри нужной ветки (`import` или `require`), затем сам файл. Если пакет описал `exports`, но не положил в него `types`, вы получите классику: «работает в рантайме, не резолвится в типах».

Быстрая заглушка `declare module 'legacy-lib';` объявляет модуль с типом `any` — компилятор перестаёт ругаться, но и проверять перестаёт. Более полезная форма — описать только используемые экспорты: остальное просто не будет доступно, и это хорошо.

В `.d.ts` не должно быть исполняемого кода: только `declare`-объявления, интерфейсы, типы и `export`. `export =` описывает CommonJS-модуль, экспортирующий одно значение, и требует у потребителя `esModuleInterop` или `allowSyntheticDefaultImports`, иначе `import x from` не соберётся.

### Почему так

Раздельные `@types` появились, когда библиотеки писались на JS и типов не поставляли; DefinitelyTyped решил это через сообщество. Сегодня большинство пакетов везёт типы с собой, и проблема сместилась в другую плоскость — согласование `exports`, ESM/CJS и условий разрешения. Отсюда и инструмент `arethetypeswrong`, который проверяет пакет по всем комбинациям резолюции сразу.

### Подводные камни

- Заглушку кладут в `typeRoots` вместо `include` — и она не подхватывается, потому что `typeRoots` ищет папки вида `@types/name`.
- **Dual-package hazard**: пакет поставляет CJS и ESM сборки с разными `.d.ts`, типы расходятся, и `instanceof` между ними ломается в рантайме.
- Типы, которые тянут `devDependencies` в публичные сигнатуры, ломают сборку у потребителя: он этих пакетов не ставил.
- `skipLibCheck: false` на большом дереве зависимостей превращает любую ошибку в чужом `.d.ts` в вашу — почти всегда включают `true`.
- Версия `@types/*` должна соответствовать мажору библиотеки; рассинхрон даёт типы, которых в рантайме нет.

### Что спросят следом

**Как проверить свой пакет перед публикацией?** `attw --pack` (arethetypeswrong) плюс `publint`: они ловят отсутствующие `types`-условия, неверные расширения и dual-package проблемы. **Что такое `isolatedDeclarations` (TS 5.5)?** Режим, требующий явных аннотаций у всего экспортируемого, чтобы `.d.ts` можно было сгенерировать пофайлово и параллельно — заметно ускоряет сборку монорепы.

```js
// src/types/legacy-lib.d.ts — включён через include, не через typeRoots
declare module 'legacy-lib' {
  export interface Options { retries?: number }
  export default function run(o?: Options): Promise<void>;
}

// CommonJS-библиотека
declare module 'old-cjs' {
  function run(): void;
  export = run;      // требует esModuleInterop у потребителя
}

// быстрая, но слепая заглушка: всё становится any
declare module 'no-types-at-all';
```

> **Что добавит очков.** Упоминание attw (arethetypeswrong), publint и dual-package hazard сразу выдаёт человека, который сам публиковал пакеты, а не только их ставил.

## 26. Как правильно типизировать переменные окружения и глобальные объекты?

```js
declare global {
  namespace NodeJS { interface ProcessEnv { API_URL: string } }
}

const url = process.env.API_URL;   // тип string
fetch(url + '/users');             // что произойдёт, если переменной нет?
```

### Коротко

По умолчанию `process.env.X` — это `string | undefined`, и это честно. Объявить его как `string` через аугментацию можно, но тип ничего не проверяет: переменной может не быть, и вы получите `undefined/users` в запросе. Правильный подход — один `parse` схемой на старте.

### Как это работает

В сниппете компилятор доволен, а рантайм — нет: `process.env.API_URL` вернёт `undefined`, конкатенация даст строку `'undefined/users'`, и запрос уйдёт на несуществующий адрес. Ошибка проявится не в момент старта, а в момент первого запроса — возможно, у пользователя. Аугментация здесь работает как `as string`, только на весь проект сразу.

Второй слой — **подстановка на этапе сборки**. Vite и webpack через DefinePlugin делают текстовую замену: строка `process.env.API_URL` в исходнике заменяется на литерал `"https://…"`. Замена именно текстовая, по точному совпадению выражения. Поэтому `process.env[key]` с вычисляемым ключом не заменяется, и в браузере падает с «process is not defined» — самая частая ошибка при переносе кода с Node на фронт.

Схема даёт третий, правильный слой: `Env.parse(import.meta.env)` при старте либо возвращает типизированный объект, либо кидает с внятным сообщением, какой переменной не хватает. Дальше весь код читает `env.API_URL`, где `string` — не обещание, а факт.

### Почему так

Переменные окружения — это внешние данные ровно в том же смысле, что и ответ сервера: их состав зависит от того, как запустили процесс, и статически он неизвестен. Все проблемы с ними — частный случай общего правила «типы стираются, доверять внешним данным нельзя». Fail fast на старте дешевле, чем отладка `undefined` в URL через три часа после деплоя.

### Подводные камни

- Аугментация `ProcessEnv` с типом `string` маскирует отсутствие переменной и даёт ложное чувство безопасности.
- Vite подставляет только переменные с префиксом `VITE_` — остальные молча становятся `undefined` в браузерном бандле.
- Всё, что попало в клиентский бандл, публично: секрет в `VITE_API_KEY` уедет в исходник страницы.
- `process.env[key]` с вычисляемым ключом не подставляется, и в браузере обращение к `process` падает.
- Пустая строка — валидное значение переменной, и `z.string()` её пропустит: нужен `.min(1)` или `.url()`.
- SSR-состояние `window.__STATE__` надо объявлять как `unknown`, а не готовой моделью: оно пришло из HTML и по сути недоверенное.

### Что спросят следом

**Где вызывать parse?** В отдельном модуле `env.ts`, импортируемом первым из точки входа, — так падение произойдёт до старта приложения. **А как быть в тестах?** Отдельная схема с дефолтами или фабрика `createEnv(source)`, чтобы не тянуть реальный `process.env` и не заводить `.env.test` с секретами.

```js
// env.ts — импортируется первым
const Env = z.object({
  VITE_API_URL: z.string().url(),
  VITE_SENTRY_DSN: z.string().min(1).optional(),
});
export const env = Env.parse(import.meta.env);  // упадёт на старте, а не в проде

// аугментация — дополнение к валидации, не замена
declare global {
  interface ImportMetaEnv { readonly VITE_API_URL: string }
}

// это не будет подставлено бандлером и упадёт в браузере
const key = 'VITE_API_URL';
const broken = import.meta.env[key];
```

> **Что добавит очков.** Мысль, которую хотят услышать: типы не проверяют наличие переменной в рантайме, поэтому нужен parse на старте — падение при запуске дешевле, чем строка «undefined/users» в URL у пользователя.

## 27. Как типизировать дженерик-компонент в React, включая forwardRef и полиморфный as?

```js
const List = forwardRef(<T,>(props: { items: T[] }, ref: Ref<HTMLUListElement>) => {
  return <ul ref={ref}>{props.items.map(String)}</ul>;
});

<List items={[1, 2, 3]} />   // почему T здесь не выводится?
```

### Коротко

Обычный дженерик-компонент работает без хитростей: `function List<T>(p: Props<T>)` выводит `T` из пропсов, как обычная функция. Проблемы начинаются с обёрток — `forwardRef` и `memo` «схлопывают» дженерик, потому что их собственные сигнатуры возвращают конкретный тип.

### Как это работает

В сниппете `T` теряется на границе `forwardRef`. Её сигнатура — `forwardRef<T, P>(render: …) => ForwardRefExoticComponent<…>`: параметры типа принадлежат самому `forwardRef`, а не результату. Компилятор вынужден зафиксировать `T` в момент вызова, кандидатов нет — и он подставляет `unknown`. Результат: компонент есть, дженерик исчез, `items` имеет тип `unknown[]`.

Обходов два. Классический — привести результат: `const List = forwardRef(inner) as <T>(p: Props<T> & { ref?: Ref<HTMLUListElement> }) => ReactElement`. Это осознанный `as`: рантайм не меняется, меняется только заявленная сигнатура. Современный — **React 19**, где `ref` стал обычным пропом функционального компонента, и `forwardRef` просто не нужен. Дженерик остаётся дженериком, потому что обёртки нет.

С `memo` ровно та же история и то же лекарство: `const M = memo(C) as typeof C`.

Отдельная тема — полиморфный `as`. Он требует `ElementType`, `ComponentPropsWithoutRef<E>` и вычитания собственных пропсов через `Omit`. Это работает, но дорого: каждый вызов инстанцирует большой union пропсов всех HTML-элементов, и IDE начинает подтормаживать на автодополнении.

### Почему так

JS не умеет возвращать «дженерик-значение»: параметр типа существует только у функции, а не у объекта, который она вернула. `forwardRef` возвращает объект (`ForwardRefExoticComponent`), поэтому нести `T` ему негде. React 19 убрал обёртку не ради типов, а ради упрощения API — но побочный эффект для TypeScript оказался решающим.

### Подводные камни

- В `.tsx` стрелочный дженерик требует запятой — `<T,>(…)`, иначе парсер видит JSX-тег. С `extends` (`<T extends unknown>`) тоже работает.
- Приведение через `as` убивает проверку: если сигнатура разойдётся с реализацией, никто не заметит. Пишите его один раз в утилите, а не в каждом компоненте.
- Полиморфный `as` ломает `displayName` и React DevTools, а сообщения об ошибках в нём читать невозможно.
- `memo` с дженериком и кастомным `areEqual` теряет типизацию сравнителя — его аргументы становятся `unknown`.
- Дефолт параметра типа (`<T = unknown>`) молча съедает ошибки вывода: вместо «не смог вывести» получите `unknown` без предупреждения.

### Что спросят следом

**Как ограничить полиморфизм и не убить компилятор?** Ограничить `as` союзом из 5–7 реально нужных тегов вместо всего `ElementType` — в дизайн-системах это стандартная практика. **Что изменилось в типах React 19?** `ref` — обычный проп, `ReactNode` больше не включает `{}`, а `JSX` переехал из глобального пространства в неймспейс `React.JSX`.

```js
type Props<T> = { items: T[]; render: (i: T) => React.ReactNode };

// React 19: ref — обычный проп, дженерик не теряется
export function List<T>({ items, render, ref }: Props<T> & { ref?: React.Ref<HTMLUListElement> }) {
  return <ul ref={ref}>{items.map(render)}</ul>;
}

// React 18: приведение возвращает дженерик руками
const Inner = <T,>(p: Props<T>, ref: React.Ref<HTMLUListElement>) => null;
const List18 = React.forwardRef(Inner) as <T>(
  p: Props<T> & { ref?: React.Ref<HTMLUListElement> }
) => React.ReactElement;
```

> **Что добавит очков.** Скажите, что forwardRef теряет дженерик из-за возврата ForwardRefExoticComponent, и что React 19 снимает проблему целиком, сделав ref обычным пропом.

## 28. Зачем zod, если есть типы? Где граница между статикой и рантаймом?

```js
const res = await fetch('/api/user');
const user = await res.json() as User;

user.profile.name.trim();   // что здесь гарантирует TypeScript?
```

### Коротко

Ничего не гарантирует. `res.json()` возвращает `any` (в свежих типах — `Promise<any>`), `as User` — просто утверждение разработчика, а типы стираются при компиляции. Любая точка входа извне — сеть, localStorage, URL, postMessage, конфиг, форма — статически не защищена. Схема даёт **одну** декларацию, из которой берутся и рантайм-проверка, и тип.

### Как это работает

В сниппете компилятор проверяет только то, что `User` имеет поле `profile` с полем `name`. Если бэкенд переименовал поле, вернул `null` или отдал 500 с HTML-страницей, то `user.profile` будет `undefined`, и вы получите «Cannot read properties of undefined» в компоненте — далеко от места, где данные пришли.

Схема разворачивает это в обратную сторону: `const User = z.object({…})` — это **значение**, живущее в рантайме. `User.parse(data)` обходит объект, проверяет каждое поле и либо возвращает типизированные данные, либо кидает `ZodError` с путём до проблемного поля. Тип берётся оттуда же: `type User = z.infer<typeof User>` — компилятор выводит его из схемы, поэтому разойтись они не могут физически.

Разница в том, где падает программа: с `as` — в случайном месте UI через несколько тиков; со схемой — на границе, с сообщением «expected string at profile.name, received null».

### Почему так

TS сознательно не генерирует рантайм-проверок: это увеличило бы размер бандла для всех и сделало бы стоимость типов непредсказуемой. Позиция команды — «типы описывают то, что уже верно», а обеспечение истинности на границе — задача кода. Отсюда и всплеск schema-first библиотек: они закрывают ровно эту дыру.

### Подводные камни и цена

- Размер бандла: zod v3 добавляет заметные килобайты и плохо шейкается; valibot и zod v4 mini дают модульный API и в разы меньший вес.
- Стоимость валидации на больших списках реальна: `parse` тысячи объектов — это тысячи проходов; для горячих путей лучше `safeParse` выборочно или быстрые кодеки.
- Сложные схемы нагружают **компилятор**: `z.infer` над глубоко вложенной схемой считается на каждом hover.
- `z.object` по умолчанию отбрасывает лишние поля — это тихая потеря данных, если вы прокидываете объект дальше.
- Схема не спасает от логических ошибок бэка: она подтвердит, что `price` — число, но не что оно в тех же копейках.

### Что спросят следом

**Всё ли валидировать?** Нет. Полностью — критичные данные и всё, что попадает в деньги, права и хранилище. Не валидировать то, что пришло из собственного типизированного RPC (tRPC) с проверкой на своей стороне. **Чем заменить, если бандл дорог?** Генерацией типов из OpenAPI/GraphQL: рантайм-стоимость нулевая, но защиты от того, что бэк нарушил свою же схему, нет — это осознанный размен.

```js
const User = z.object({
  id: z.string().uuid(),
  age: z.number().int().nonnegative(),
  profile: z.object({ name: z.string().min(1) }),
});
type User = z.infer<typeof User>;   // тип выведен из схемы — разойтись не могут

const res = await fetch('/api/user');
if (!res.ok) throw new Error('HTTP ' + res.status);

const parsed = User.safeParse(await res.json());
if (!parsed.success) {
  report(parsed.error.issues);      // путь до поля, а не «undefined is not an object»
  return null;
}
parsed.data.profile.name.trim();    // здесь string — уже по факту, а не по обещанию
```

> **Что добавит очков.** Формулировка «типы — про рефакторинг, схемы — про доверие к данным» плюс уточнение границы: RPC со своей проверкой валидировать повторно не нужно.

## 29. Какие флаги tsconfig вы включаете и почему strict — это не один флаг?

### Коротко

`strict: true` — зонтик над восемью отдельными флагами, а не один переключатель. Самый ценный из них — `strictNullChecks`: без него `null` и `undefined` входят в каждый тип, и вся система типов теряет смысл.

### Как это работает

Сам по себе `strict` ничего не проверяет: при чтении tsconfig компилятор разворачивает его в восемь независимых флагов, каждый из которых можно переопределить рядом (`"strict": true, "strictPropertyInitialization": false` — валидная комбинация). Вот что входит в набор.

- `strictNullChecks` — `null`/`undefined` перестают быть членами всех типов.
- `noImplicitAny` — параметр без аннотации и без выводимого типа становится ошибкой.
- `strictFunctionTypes` — контравариантная проверка параметров функциональных типов (но не методов).
- `strictBindCallApply` — точные сигнатуры `bind`/`call`/`apply` вместо `any[]`.
- `strictPropertyInitialization` — поле класса должно быть инициализировано или помечено `!`.
- `noImplicitThis` — `this` в свободной функции больше не `any`.
- `useUnknownInCatchVariables` — `catch (e)` даёт `unknown`, а не `any`.
- `alwaysStrict` — `'use strict'` в выводе и парсинг в strict-режиме.

### Что включают сверх strict

- `noUncheckedIndexedAccess` — `arr[i]` и `rec[key]` дают `T | undefined`.
- `exactOptionalPropertyTypes` — различает «ключа нет» и «ключ равен `undefined`».
- `noImplicitOverride` — `override` обязателен при переопределении метода; ловит опечатки в именах.
- `noFallthroughCasesInSwitch`, `noPropertyAccessFromIndexSignature` (доступ через точку только к объявленным полям).
- `isolatedModules` и `verbatimModuleSyntax` — обязательны, если собираете не через `tsc`.
- `skipLibCheck: true` — почти всегда, ради скорости: чужие `.d.ts` не ваша забота.

### Почему так

Флаги вводились в разные версии и по-разному ломают существующий код. `strictNullChecks` в большом легаси даёт тысячи ошибок, `noImplicitThis` — десятки. Разделение позволяет мигрировать поэтапно и держать промежуточные состояния зелёными. Зонтик `strict: true` добавлен позже, чтобы новые проекты не собирали конфиг по кусочкам — и чтобы новые флаги включались автоматически при апгрейде.

### Подводные камни

- `strict: true` включает и будущие флаги: апгрейд минорной версии TS может сломать сборку. В CI это лечится пиннингом версии, а не отключением strict.
- `strictPropertyInitialization` конфликтует с DI-фреймворками и ORM — там поля заполняются извне; спасает `declare` или `!`, но `!` надо ставить осознанно.
- `noUnusedLocals`/`noUnusedParameters` лучше отдать ESLint: у компилятора нет автофикса, и он мешает при отладке, когда переменную временно закомментировали.
- `skipLibCheck: false` на большом дереве превращает баг в чужом `.d.ts` в вашу красную сборку.
- Отдельный `tsconfig` для тестов часто забывают, и в тестах strict оказывается выключен.

### Что спросят следом

**Как включить strict в легаси?** Включить глобально, а старые папки вынести в отдельный проект с ослабленным конфигом через project references — так новый код сразу пишется строго, а долг виден и конечен. Откладывать «пока не почистим» значит не включить никогда. **Что даёт `useUnknownInCatchVariables` на практике?** Заставляет писать `e instanceof Error ? e.message : String(e)` — и ловит случаи, когда бросили строку или объект.

```js
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "moduleResolution": "bundler",
    "noEmit": true
  }
}
```

> **Что добавит очков.** Стратегия миграции: включить strict глобально сразу и вынести легаси в отдельный проект с ослабленным конфигом через project references — долг становится видимым и конечным вместо «включим, когда почистим».

## 30. Что делают noUncheckedIndexedAccess и exactOptionalPropertyTypes и почему их часто выключают?

```js
const list: string[] = [];
const first = list[0];
first.trim();            // ошибка при каком флаге?

type O = { a?: number };
const o: O = { a: undefined };   // а здесь при каком?
```

### Коротко

`noUncheckedIndexedAccess` добавляет `| undefined` к результату доступа по индексу — `arr[i]`, `record[key]`. `exactOptionalPropertyTypes` различает «ключа нет» и «ключ равен `undefined`». Оба ловят реальные баги и оба шумят, поэтому в существующих проектах их чаще всего выключают.

### Как это работает

В сниппете первая ошибка — от `noUncheckedIndexedAccess`: `list[0]` получает тип `string | undefined`, потому что массив может быть пуст, и `.trim()` на нём запрещён. Вторая — от `exactOptionalPropertyTypes`: тип `{ a?: number }` при этом флаге означает «поля может не быть, но если есть — это число», и явное `a: undefined` ему не соответствует. Без флага `?` раскрывается в `a?: number | undefined`, и присваивание проходит.

Оба флага меняют не рантайм, а модель типов: они делают её ближе к реальному JS. До них `arr[999]` имел тип `T` — очевидная ложь, из-за которой `arr[0].id` на пустом списке падал в проде без единого предупреждения.

### Почему их не включают по умолчанию

`noUncheckedIndexedAccess` нельзя сделать умным: компилятор не доказывает, что `i < arr.length`, поэтому шумит даже в цикле `for (let i = 0; i < arr.length; i++)`, где индекс заведомо валиден. Включение его в `strict` сломало бы почти каждый существующий проект. `exactOptionalPropertyTypes` упирается в экосистему: React-пропсы и повсеместный паттерн `{...props, a: undefined}` с ним не собираются.

### Подводные камни

- Шум в индексных циклах лечится сменой стиля: `for...of`, `entries()`, `at()`, деструктуризация — они дают корректные типы без проверок.
- Кортежи: `noUncheckedIndexedAccess` не трогает доступ по литеральному индексу в пределах длины кортежа, но срабатывает на `rest`-элементах.
- Соблазн заглушить всё через `!` сводит выигрыш от флага к нулю — и делает код хуже, чем без него.
- `exactOptionalPropertyTypes` ломает spread-паттерны в React и в билдерах опций; иногда приходится писать `...(v !== undefined && { a: v })`.
- Флаг важен там, где `undefined` в PATCH-запросе означает «не трогать поле», а `null` — «сбросить»: без него эти два случая неотличимы в типах.

### Что спросят следом

**Стоит ли включать в существующем проекте?** Оба дешевле включать на новом коде: ретроспективное включение даёт сотни ошибок, большинство из которых ложные. Практичный путь — включить в новом пакете монорепы и не тащить в старые. **Что делать с `Object.keys` при этих флагах?** Итерироваться по явному `as const`-списку ключей: тогда индексный доступ типизирован точно, а `undefined` не появляется.

```js
// noUncheckedIndexedAccess
const first = list[0];              // string | undefined
if (first !== undefined) first.trim();

for (const item of list) item.trim();   // for...of — undefined не появляется
const [head] = list;                    // string | undefined — тоже честно

// exactOptionalPropertyTypes
type Patch = { name?: string; avatar?: string | null };
const p1: Patch = {};                    // «не трогать»
const p2: Patch = { avatar: null };      // «сбросить»
const p3: Patch = { name: undefined };   // ошибка — намерение неясно
```

> **Что добавит очков.** Честный ответ: оба флага дешевле включать на новом коде, а ретроспективно они дают сотни ложных срабатываний — и заглушённые ! делают результат хуже, чем без флага.

## 31. Проект собирается медленно, tsc ест минуты. Как диагностировать и что чинить?

### Коротко

Сначала измерить, потом чинить. `tsc --extendedDiagnostics` даёт разбивку по фазам (parse, bind, check, emit) и счётчики инстанцирований; `tsc --generateTrace ./trace` плюс `@typescript/analyze-trace` показывают конкретные файлы и типы, съевшие время. Без этого любая оптимизация — гадание.

### Как это работает

В `--extendedDiagnostics` смотрят на три числа. **Check time** против **Parse time**: если парсинг доминирует, проблема в количестве файлов и `include`; если проверка — в сложности типов. **Instantiations** — сколько раз компилятор создавал экземпляры дженериков; счёт в десятках миллионов означает, что где-то развёрнут тяжёлый условный или мапнутый тип. **Memory used** под пару гигабайт — признак того же.

`analyze-trace` выдаёт список «hot spots» с путями до конкретных строк: чаще всего это одна утилита-тип, инстанцируемая в сотнях мест, или один `.d.ts` из зависимости.

### Типовые причины и лечение

- **Гигантские union и рекурсивные условные типы** — самый частый источник. Ограничить глубину, заменить вычисляемый тип явным перечислением, разорвать цепочку промежуточным `interface`.
- **`interface` вместо пересечений `type`**: интерфейс получает имя и кешируется, а `A & B & C` перепроверяется структурно при каждом сравнении. На больших пропсах разница измеримая.
- **Явные аннотации возвращаемых типов** у экспортируемых функций: без них компилятор выводит тип заново на каждом использовании и тянет за собой всё, от чего зависит тело. Это же требование `isolatedDeclarations` (TS 5.5), который позволяет генерировать `.d.ts` пофайлово и параллельно.
- **Инфраструктура**: `skipLibCheck: true`, `incremental: true` с `tsBuildInfoFile`, project references для монорепы, узкий `include` вместо всего дерева.
- **Аннотации вариантности** `in`/`out` в тяжёлых библиотечных дженериках — снимают структурный вывод вариантности.
- **Зависимости**: один пакет с гигантским `.d.ts` (иконки, i18n-ключи, GraphQL-схема) способен в одиночку удвоить время; лечится сужением импорта или генерацией более узкого типа.

### Почему так

Чекер ленив: он вычисляет тип только когда его спросили, но результат кеширует не всегда — отложенные условные типы и структурные пересечения пересчитываются при каждом новом сравнении. Отсюда и правило: всё, что имеет **имя** (интерфейс, аннотированный возврат), дешевле того, что вычисляется на месте.

### Подводные камни

- «Медленно» бывает разным: медленный CI лечится `incremental` и references, а медленная IDE — конкретным типом в конкретном файле. Это разные задачи.
- tsserver в редакторе и `tsc` в CI имеют разные профили: hover пересчитывает типы, которых при полной сборке никто не спрашивает.
- `skipLibCheck: false` заставляет проверять тысячи чужих `.d.ts` — это самая дешёвая победа, если он был выключен.
- Оптимизация типов ради скорости легко ухудшает читаемость ошибок; сначала докажите профилем, что этот тип действительно горячий.

### Что спросят следом

**Что дают project references?** Инкрементальную сборку по проектам: изменение в одном пакете не заставляет перепроверять остальные, и `.d.ts` зависимостей берутся с диска. **Как сократить работу до нуля в CI?** Кешировать `.tsbuildinfo` между запусками и запускать `tsc --build`, а не полную проверку.

```js
# измерение
tsc --noEmit --extendedDiagnostics
tsc --noEmit --generateTrace ./trace
npx @typescript/analyze-trace ./trace

# дорогое: пересечение пересчитывается структурно
type Props = Base & Theme & Handlers & A11y;

# дешевле: имя кешируется
interface Props extends Base, Theme, Handlers, A11y {}

# дорогое: возврат выводится заново на каждом использовании
export const build = (o: Options) => ({ /* ... */ });

# дешевле и требуется isolatedDeclarations
export const build = (o: Options): Result => ({ /* ... */ });
```

> **Что добавит очков.** Назовите --generateTrace и @typescript/analyze-trace, а также счётчик Instantiations из --extendedDiagnostics: это конкретные инструменты вместо общих слов про «упростить типы».

## 32. Что такое excess property check и почему он иногда не срабатывает?

```js
type P = { a: number };

const x: P = { a: 1, b: 2 };   // ошибка
const t = { a: 1, b: 2 };
const y: P = t;                // ошибки нет — почему?
```

### Коротко

Excess property check — дополнительная проверка при присваивании **свежего объектного литерала**: TS ругается на свойства, которых нет в целевом типе. Структурная типизация этого не требует, это эвристика против опечаток. Как только литерал теряет «свежесть», проверка исчезает.

### Как это работает

В сниппете `{ a: 1, b: 2 }` в первой строке — свежий литерал, присваиваемый напрямую типу `P`: срабатывает проверка. Во второй строке тот же объект сначала получает собственный тип `{ a: number; b: number }` через переменную `t`. Дальше идёт обычная проверка присваиваемости: `{ a: number; b: number }` структурно подходит под `{ a: number }`, потому что имеет всё требуемое. Лишнее поле по правилам структурной типизации не мешает.

Внутри чекера у типа литерала есть флаг `FreshLiteral`. Он выставляется при создании и **сбрасывается** при первом же widening — присваивании в переменную, возврате из функции, приведении через `as`. При сравнении со свежим типом чекер дополнительно проверяет, что каждое свойство источника есть в цели.

Особый случай — union в цели. Свойство считается допустимым, если оно есть **хотя бы в одном** члене union. Поэтому `{ kind: 'a', extra: 1 }` пройдёт, если `extra` объявлено в другом варианте дискриминированного union. Это ровно та причина, по которой лишние пропсы компонента иногда проскакивают.

### Почему так

Строгая структурная типизация не может запретить лишние поля: объект с большим числом свойств — законный подтип. Но на практике лишнее поле в литерале почти всегда опечатка (`onClik` вместо `onClick`), и молча проглатывать её плохо. Команда TS выбрала компромисс: ловить очевидный случай литерала, не трогая систему типов. Отсюда и «дырявость» — она встроена в замысел.

### Где проверка не срабатывает

- Через промежуточную переменную — самый частый обход, часто случайный.
- При `as`: приведение сбрасывает свежесть вместе со всей проверкой.
- При spread: `{ ...obj, a: 1 }` в ряде позиций не считается свежим целиком.
- Если целевой тип — union и свойство есть хотя бы в одном члене.
- Если у цели есть индексная сигнатура — тогда любое свойство допустимо по определению.
- При возврате из функции с выводимым (не аннотированным) типом возврата.

### Что спросят следом

**Как запретить лишние поля по-настоящему?** Тип-«exact» через перемаппинг: `T & { [K in Exclude<keyof U, keyof T>]?: never }`. Работает, но сообщения об ошибках становятся заметно хуже — размен обычно не в пользу строгости. **Почему это важно знать про пропсы?** На union-пропсах (компонент с вариантами) опечатки в именах пропсов не ловятся, и единственная защита — линтер или дискриминант, сужающий union до одного члена.

```js
type P = { a: number };
const x: P = { a: 1, b: 2 };     // ошибка: Object literal may only specify known properties
const t = { a: 1, b: 2 };
const y: P = t;                  // ошибки нет — свежесть потеряна

// union: свойство из соседнего члена проходит
type Btn = { kind: 'icon'; icon: string } | { kind: 'text'; label: string };
const b: Btn = { kind: 'icon', icon: 'x', label: 'oops' };  // не ловится

// индексная сигнатура отключает проверку целиком
type Bag = { a: number; [k: string]: unknown };
const g: Bag = { a: 1, whatever: true };   // ок
```

> **Что добавит очков.** Кейс с union — самый показательный: он объясняет, почему на пропсах компонента с вариантами опечатки в именах пропсов иногда проходят молча.

## 33. В чём разница между ts-ignore и ts-expect-error и что выбрать?

```js
// @ts-ignore
const a: number = 1;

// @ts-expect-error
const b: number = 1;

// одна из этих двух строк даёт ошибку — какая?
```

### Коротко

`@ts-ignore` подавляет ошибку на следующей строке и молчит, даже если ошибки там нет. `@ts-expect-error` подавляет ошибку, но **сам становится ошибкой**, когда строка стала валидной. Выбирать надо второе: оно самоочищается, первое превращается в вечный долг.

### Как это работает

В сниппете ошибку даст `@ts-expect-error`: строка `const b: number = 1` совершенно корректна, значит комментарий обещал ошибку, которой нет — «Unused '@ts-expect-error' directive». `@ts-ignore` над валидной строкой не даёт ничего и остаётся в коде навсегда.

Механически оба директивы работают одинаково: чекер собирает диагностики, а затем фильтрует те, что начинаются на следующей после комментария строке. Разница только в том, что для `expect-error` ведётся счётчик подавленных диагностик, и нулевое значение само порождает новую.

Практическое следствие: после апгрейда библиотеки, которая наконец починила типы, `@ts-expect-error` подсветит все места, где костыль больше не нужен, — и вы удалите их одной пачкой. С `@ts-ignore` вы об этом не узнаете никогда.

### Почему так

`@ts-ignore` появился раньше и решал задачу «дайте собраться». Опыт показал, что подавления накапливаются и переживают причину: код рефакторят, библиотеку обновляют, а комментарий остаётся и глушит уже совсем другую, настоящую ошибку. `@ts-expect-error` (TS 3.9) добавили именно чтобы у подавления был срок годности.

### Подводные камни

- Оба глушат **все** ошибки строки, а не конкретную. Если на строке два вызова, вторая ошибка исчезнет вместе с первой — сужайте строку до минимума.
- `@ts-expect-error` над строкой, где ошибка появляется **иногда** (зависит от версии библиотеки или флага), делает сборку нестабильной: то ошибка, то «unused directive».
- `@ts-nocheck` в начале файла отключает проверку целиком — крайняя мера при миграции, а не рабочий инструмент.
- В `.tsx` внутри JSX нужен другой синтаксис: `{/* @ts-expect-error */}`, обычный комментарий там не сработает.
- Подавление часто маскирует настоящий баг: тип не соответствует реальности не потому, что типы плохие, а потому что данные другие.

### Что вместо

Точечный `as unknown as T` с комментарием часто честнее: он не глушит соседние ошибки, локализован в выражении и виден при чтении. Ещё лучше — локальная аугментация типов библиотеки: она чинит причину, а не симптом, и работает во всех местах сразу.

### Что спросят следом

**Как это регулируется в проекте?** ESLint-правило `@typescript-eslint/ban-ts-comment`: `'ts-ignore': true` (запрещён), `'ts-expect-error': 'allow-with-description'` плюс `descriptionFormat` с требованием ссылки на issue. **Как найти накопленные подавления?** Грепом по репозиторию плюс метрика в CI: их число не должно расти между релизами.

```js
// @ts-expect-error TODO: обновить типы после релиза lib@3 (issue #421)
legacy.call();

// плохо: глушит обе ошибки строки
// @ts-expect-error
foo(bad1(), bad2());

// лучше: подавление локализовано в одном выражении
const value = raw as unknown as User;   // API отдаёт snake_case, см. #421

// правило в .eslintrc
// "@typescript-eslint/ban-ts-comment": ["error", {
//   "ts-ignore": true,
//   "ts-expect-error": "allow-with-description",
//   "minimumDescriptionLength": 10
// }]
```

> **Что добавит очков.** Готовый ответ про процессы: ts-ignore запрещён линтером, разрешён только ts-expect-error с описанием и ссылкой на issue — тогда подавления самоочищаются при апгрейде и их число можно мерить в CI.

## 34. Почему Object.keys возвращает string[], а не keyof T, и как с этим быть?

```js
type P = { a: number };
const wide = { a: 1, b: 'oops' };
const p: P = wide;                 // структурно допустимо

Object.keys(p).forEach((k) => {
  // если бы k имел тип keyof P, что случилось бы на ключе 'b'?
});
```

### Коротко

Потому что в рантайме объект может быть **шире** объявленного типа. Структурная типизация это прямо разрешает: переменная типа `{ a: number }` законно ссылается на объект с полями `a`, `b`, `c`. Вернуть `(keyof T)[]` значило бы дать гарантию, которая нарушается в первом же реальном коде.

### Как это работает

В сниппете `p` имеет тип `{ a: number }`, но в рантайме это тот же объект `wide` с полем `b`. `Object.keys(p)` вернёт `['a', 'b']`. Если бы тип был `'a'[]`, то `p[k]` считался бы `number`, а на итерации по `'b'` там оказалась бы строка — и последующая арифметика молча дала бы `NaN`.

Та же причина у `for...in` и `Object.entries`: их сигнатуры в lib.d.ts возвращают `string[]` и `[string, T][]`. Это не недосмотр, а единственный корректный вариант при структурной типизации без exact-типов.

Обходов два. Безопасный — итерироваться по **явному списку** ключей: `const KEYS = ['a', 'b'] as const`, затем `for (const k of KEYS)`. Здесь `k` имеет точный литеральный тип, и `obj[k]` типизирован верно, а лишние поля просто не посещаются. Осознанно небезопасный — локальный хелпер `objectKeys` с `as (keyof T)[]` и комментарием: он допустим, когда объект создан здесь же и точно не шире.

### Почему так

Это следствие фундаментального выбора: TS структурно типизирован и не имеет exact-типов (в отличие от Flow с его `{| |}`). Структурность даёт огромную гибкость — не нужны объявления «реализует интерфейс», подходит любой совместимый объект. Плата — невозможность знать полный набор ключей. Excess property check прикрывает только литералы; всё остальное открыто.

### Подводные камни

- `for...in` дополнительно перебирает **унаследованные** перечислимые свойства — отсюда классический `hasOwnProperty`, а лучше `Object.hasOwn` (ES2022).
- `Object.entries` теряет связь ключа и значения: получите `[string, A | B][]` вместо пар. Для точных пар нужен маппер по `keyof T`.
- `Object.fromEntries` возвращает `{ [k: string]: T }` и почти всегда требует ручной аннотации результата.
- Хелпер `objectKeys` с приведением ломается ровно там, где объект пришёл извне, — то есть там, где он опаснее всего.
- При `noUncheckedIndexedAccess` доступ по ключу из `Object.keys` даёт `| undefined`, что справедливо, но неудобно.

### Что спросят следом

**Есть ли способ получить exact-тип?** Штатного нет; имитируется через `T & { [K in Exclude<string, keyof T>]?: never }`, но сообщения об ошибках портятся. **А `Map`?** `Map<K, V>` типизирует ключи точно, потому что это структура данных, а не структурный тип: `map.keys()` честно даёт `IterableIterator<K>`.

```js
const KEYS = ['a', 'b'] as const;
for (const k of KEYS) use(obj[k]);          // k: "a" | "b" — типобезопасно

// осознанное допущение, только для локально созданных объектов
function objectKeys<T extends object>(o: T) {
  return Object.keys(o) as (keyof T)[];     // объект может быть шире — знаем и принимаем
}

// точные пары вместо Object.entries
type Entries<T> = { [K in keyof T]: [K, T[K]] }[keyof T][];
const entries = Object.entries(obj) as Entries<typeof obj>;

for (const k in obj) if (Object.hasOwn(obj, k)) use(k);   // без унаследованных
```

> **Что добавит очков.** Точная формулировка причины: объект в рантайме может быть шире объявленного типа, и структурная типизация это разрешает — а не «так решили в TS».

## 35. Что такое NoInfer и зачем управлять источниками вывода?

```js
declare function createSet<T extends string>(items: T[], initial: T): Set<T>;

createSet(['a', 'b'], 'c'); // почему это компилируется?
```

### Коротко

`NoInfer<T>` (TS 5.4) помечает позицию как **не источник вывода**: кандидат оттуда не берётся, а проверка присваиваемости остаётся. Нужен там, где один аргумент задаёт множество, а другой обязан быть его элементом.

### Как это работает

В сниппете ошибки нет, и это логично с точки зрения алгоритма: `T` собирает кандидатов из обоих аргументов — `'a' | 'b'` из массива и `'c'` из второго параметра. Общий супертип набора — `'a' | 'b' | 'c'`, ограничение `extends string` выполнено, значит вывод успешен и проверять нечего. Второй аргумент не нарушил ограничение, он его **расширил**.

`NoInfer<T>` в этой позиции исключает её из сбора кандидатов. Тогда `T = 'a' | 'b'` выводится только из массива, и уже **после** вывода компилятор проверяет, присваивается ли `'c'` типу `'a' | 'b'`. Не присваивается — ошибка ровно там, где её ждёшь.

Внутри это интринзик компилятора, а не обычный условный тип: в лице чекера `NoInfer<T>` — это `T` с выставленным флагом «блокировать вывод». Никакого рантайм-следа, никакого влияния на итоговый тип. До 5.4 тот же эффект имитировали хаком `T & {}`, дополнительным параметром типа с дефолтом или обёрткой в `[T][0]` — все они работали через побочные эффекты алгоритма и ломались между версиями.

### Почему так

Вывод в TS оптимистичен: он ищет тип, при котором вызов валиден, а не самый узкий. Это удобно в 95% случаев (не приходится писать аргументы типа руками), но ровно там, где API хочет сказать «этот параметр подчинён тому», оптимизм даёт ложноотрицательные ошибки. `NoInfer` — точечный способ отключить оптимизм в одной позиции, не выключая вывод целиком.

### Подводные камни

- `NoInfer` не сужает и не проверяет ничего сам: если из остальных позиций `T` вывелся широко, ошибки не будет всё равно.
- Обернуть нужно позицию целиком: `NoInfer<T>[]` и `NoInfer<T[]>` — разные вещи по глубине блокировки.
- При наличии дефолта `T = X` блокировка всех позиций приводит к молчаливому применению дефолта вместо ошибки.
- Полифиллы `type NoInfer<T> = [T][T extends any ? 0 : never]` из npm ведут себя иначе на дистрибутивных типах — на 5.4+ их надо убирать.

### Что спросят следом

**Где это встречается в реальном коде?** Типобезопасные роутеры (путь задаёт множество параметров, объект params обязан ему соответствовать), i18n (ключ задаёт набор плейсхолдеров), дизайн-система (список вариантов и дефолтный вариант), `useState`-подобные фабрики с initial value. **Чем отличается от `const`-параметра?** `const T` управляет **насколько узко** выводить, `NoInfer` — **откуда** выводить; их часто используют вместе.

```js
declare function createSet<T extends string>(
  items: T[], initial: NoInfer<T>
): Set<T>;

createSet(['a', 'b'], 'c');   // Argument of type '"c"' is not assignable to '"a" | "b"'
createSet(['a', 'b'], 'a');   // Set<"a" | "b">

// роутер: params подчинён пути
declare function go<P extends string>(
  path: P, params: Record<NoInfer<P> extends `${string}:${infer K}` ? K : never, string>
): void;
```

> **Что добавит очков.** Разделите роли: const-параметр решает, насколько узко выводить, NoInfer — из каких позиций выводить вообще. Назвать оба и их связку — сильный ответ.

## 36. Что делают const type parameters и когда они лучше as const на месте вызова?

```js
declare function route<const T extends readonly string[]>(p: T): T;

const r = route(['users', 'id']);   // какой тип у r?

const arr = ['users', 'id'];
const r2 = route(arr);              // а у r2?
```

### Коротко

`<const T>` (TS 5.0) заставляет выводить аргумент так, будто на месте вызова написан `as const`: литералы не расширяются, массивные литералы становятся readonly-кортежами, объектные — readonly-объектами. Ответственность за «заморозку» переезжает с потребителя API на его автора.

### Как это работает

В сниппете `r` получит `readonly ['users', 'id']`, а `r2` — `string[]`. Разница принципиальная: модификатор `const` влияет на то, как выводится тип **литерального выражения в позиции аргумента**. К моменту вызова `route(arr)` переменная `arr` уже имеет тип `string[]` — вывод не может задним числом «дозаморозить» то, что было объявлено раньше.

Механически чекер при выводе кандидата из литерала обычно применяет widening: `'users'` → `string`, массивный литерал → массив, свойства объекта → изменяемые. Флаг `const` на параметре типа отключает эти три преобразования для данной позиции вывода. Результат идентичен `as const` на месте вызова, включая рекурсивность — вложенные литералы тоже застывают.

Раз тип получается `readonly`, ограничение обязано его принимать: `const T extends string[]` сломает все вызовы, потому что `readonly ['a']` не присваивается `string[]`. Писать нужно `readonly unknown[]` или `readonly string[]`.

### Почему так

До 5.0 автору типобезопасного API оставалось только просить пользователей писать `as const` — а они забывали, и типы молча деградировали до `string[]`, теряя всю точность роутов и токенов. Перенос модификатора в сигнатуру делает поведение частью контракта, а не документацией. Цена — раздувание типов: большой конфиг, замороженный целиком, увеличивает объём работы чекера на каждом сравнении.

### Подводные камни

- Переменная, объявленная заранее, не замораживается — самый частый вопрос «почему у коллеги работает, а у меня нет».
- Ограничение без `readonly` ломает вызовы; сообщение об ошибке при этом невнятное и указывает на аргумент, а не на сигнатуру.
- Внутри реализации `T` readonly, поэтому привычные `push`/`sort` по нему не работают — придётся копировать через spread.
- На больших объектах (тема дизайн-системы, схема таблицы на сотни полей) заметно растёт время проверки и размер подсказок в IDE.
- Не действует, если аргумент проходит через spread или через промежуточный вызов.

### Что спросят следом

**Чем отличается от `as const`?** Местом объявления и охватом: `as const` — решение вызывающего для одного выражения, `const T` — решение автора API для всех вызовов. **Что делать, если нужны и заморозка, и изменяемость внутри?** Оставить `const T extends readonly unknown[]` в публичной сигнатуре и внутри работать с копией `[...items]`.

```js
declare function route<const T extends readonly string[]>(p: T): T;
const r = route(['users', 'id']);        // readonly ["users", "id"]

// ограничение без readonly — вызовы перестают проходить
declare function bad<const T extends string[]>(p: T): T;
bad(['a']);   // readonly ["a"] не присваивается string[]

// объектный литерал тоже застывает рекурсивно
declare function conf<const T>(c: T): T;
const c = conf({ mode: 'dark', sizes: [1, 2] });
// { readonly mode: "dark"; readonly sizes: readonly [1, 2] }
```

> **Что добавит очков.** Ключевая пара фраз: const-параметр убирает as const из пользовательского кода, но не действует на переменную, объявленную до вызова.

## 37. Зачем нужны аннотации вариантности in/out и когда их писать?

```js
interface Producer<out T> { get(): T; set(v: T): void }
// что скажет компилятор на это объявление?
```

### Коротко

С TS 4.7 у параметра типа можно писать `in` (контравариантный), `out` (ковариантный), `in out` (инвариантный). Это **не новая семантика**, а способ сказать компилятору то, что он и так вычислил бы сам. Главный мотив — производительность проверки, вторичный — документация и защита от ошибок в объявлении.

### Как это работает

Сниппет не скомпилируется: `T` объявлен как `out`, но встречается в позиции параметра метода `set`, то есть реально инвариантен. Компилятор выдаст ошибку прямо на объявлении интерфейса — «Type 'Producer<T>' is not assignable to type 'Producer<…>' as implied by variance annotation». Без аннотации он молча вывел бы инвариантность, и странное поведение всплыло бы где-нибудь через десять файлов.

Обычный порядок такой: при первом сравнении `F<A>` с `F<B>` чекер обходит определение `F`, определяет вариантность каждого параметра и кеширует её. На взаимно-рекурсивных и глубоко вложенных дженериках этот обход дорог: он раскрывает типы, порождает инстанциации и тянет за собой соседние определения. Аннотация даёт маркер сразу — обход не нужен, и чекер сразу применяет быструю проверку по маркеру. Для проверки самой аннотации выполняется одно сравнение с «отмеченными» типами-маркерами, а не полный структурный обход.

В рантайме, как и у всей системы типов, следа нет: аннотации стираются вместе с объявлением интерфейса.

### Почему так

TS структурно типизирован, и вариантность в нём — производная от структуры, а не декларация автора (в отличие от C# и Kotlin, где `in`/`out` задают правило). Делать её обязательной было бы ломающим изменением для всей экосистемы. Поэтому аннотация — необязательная подсказка: если она совпадает с выведенной, ничего не меняется; если противоречит — ошибка.

### Подводные камни

- Аннотация не «включает» ковариантность там, где её нет: она только фиксирует и проверяет, а не переопределяет правило.
- Выигрыш в скорости заметен на библиотечных типах уровня RxJS, Redux-Toolkit, tRPC. В прикладном коде это преждевременная оптимизация, добавляющая шум в сигнатуры.
- Ошибка при несовпадении указывает на объявление, но её текст про «implied by variance annotation» читается плохо и часто вводит в заблуждение новичков.
- Бивариантные позиции (параметры методов) под аннотацию не подпадают так, как ожидается: метод даёт бивариантность, а `out` требует ковариантности — сочетание ведёт себя неочевидно.

### Что спросят следом

**Как понять, что тормозит именно вариантность?** Через `tsc --generateTrace` и `analyze-trace`: в трейсе видны долгие `structuredTypeRelatedTo` на одних и тех же дженериках. **Где это писать в первую очередь?** В `.d.ts` публичных пакетов и в типах стора, которые сравниваются тысячи раз за проверку.

```js
interface Producer<out T> { get(): T }            // только читаем
interface Consumer<in T>  { set(v: T): void }     // только пишем
interface State<in out T> { get(): T; set(v: T): void }  // и то и другое

declare let pDog: Producer<Dog>;
declare let pAnimal: Producer<Animal>;
pAnimal = pDog;   // ок: ковариантность

declare let sDog: State<Dog>;
declare let sAnimal: State<Animal>;
sAnimal = sDog;   // ошибка: инвариантность
```

> **Что добавит очков.** Правильный акцент: главный мотив фичи — время проверки (компилятор пропускает структурный вывод вариантности), а строгость идёт бонусом.

## 38. Чем тип метода отличается от свойства-функции и что такое bivariance hack?

```js
interface A { handle(e: MouseEvent): void }
interface B { handle: (e: MouseEvent) => void }

const a: A = { handle(e: Event) {} };  // одна из этих строк — ошибка
const b: B = { handle: (e: Event) => {} };
```

### Коротко

Синтаксис почти одинаков, проверка разная. Сокращённая форма `handle(e: E): void` — **метод**, его параметры сравниваются бивариантно даже при `strictFunctionTypes`. Форма `handle: (e: E) => void` — **свойство функционального типа**, параметры контравариантны, проверка строгая.

### Как это работает

В сниппете ошибки не будет ни там, ни там — потому что `Event` шире `MouseEvent`, а это как раз безопасное (контравариантное) направление. Разница проявится на обратном: `{ handle(e: MouseEvent & { custom: 1 }) {} }` пройдёт для `A` и упадёт для `B`.

Внутри чекера у сигнатуры есть флаг `MethodDeclaration`. При сравнении двух сигнатур, если обе объявлены методами и включён `strictFunctionTypes`, чекер сперва пробует строгое (контравариантное) сравнение параметров, и если оно не прошло — пробует ковариантное. Успех любого из двух означает совместимость. Для свойств второй попытки нет. Это единственное место, где строгий режим сознательно оставляет дыру.

Так называемый **bivariance hack** — объявление члена методом именно ради этой поблажки. Он используется в типах `Array` (`push`, `filter`, `sort`), в `EventTarget`, в `React.Component` и в старых типах событий React. Обратный приём — переписать метод в свойство, чтобы точечно включить строгость там, где она нужна.

### Почему так

Если бы параметры методов проверялись строго, `Dog[]` перестал бы присваиваться `Animal[]` (у `Array<T>` есть `push(v: T)`), и вместе с ним развалилась бы половина lib.d.ts и почти любая коллекция. Команда TS выбрала оставить бивариантность для методов и включить строгость только для явных функциональных типов, где автор может сознательно выбрать форму записи.

### Подводные камни

- Разницу невозможно заметить на ревью: две записи отличаются двоеточием и стрелкой, а поведение проверки — противоположное.
- `declare function` и перегрузки интерфейса ведут себя как методы; отдельная стрелочная запись перегрузок невозможна.
- ESLint-правило `@typescript-eslint/method-signature-style` умеет форсировать стиль `property` — это дешёвый способ включить строгость по всему проекту разом.
- Переезд на свойства ломает declaration merging: перегрузки через несколько объявлений возможны только для методов.
- Классы: метод в классе — тоже метод, поэтому строгость обработчиков в классовых компонентах достигается только полями-стрелками.

### Что спросят следом

**Почему `arr.map(parseInt)` компилируется?** Отдельный механизм: функция с меньшим числом параметров присваивается типу с большим, поэтому `parseInt(s, radix)` спокойно встаёт на место `(v, i, arr) => …` — и получает индекс в качестве системы счисления. **Как показать разницу за 10 секунд?** Присвоить объект с более узким параметром: метод пропустит, свойство — нет.

```js
interface Loose  { handle(e: MouseEvent): void }        // бивариантно
interface Strict { handle: (e: MouseEvent) => void }    // контравариантно

// сужение параметра — небезопасно, но метод его пропускает
const l: Loose  = { handle(e: MouseEvent & { custom: 1 }) {} };  // ок
const s: Strict = { handle: (e: MouseEvent & { custom: 1 }) => {} }; // ошибка
```

> **Что добавит очков.** Готовый рецепт для ревью: правило method-signature-style в ESLint переводит интерфейсы на свойства-функции и включает строгую проверку колбэков по всему проекту.

## 39. Что такое перемаппинг ключей через as в mapped types и какие задачи он решает?

```js
type Src = { a?: string; readonly b: number };

type Same   = { [K in keyof Src]: Src[K] };
type Renamed = { [K in keyof Src as `get_${K & string}`]: Src[K] };
// что стало с ? и readonly в каждом из них?
```

### Коротко

Синтаксис `{ [K in keyof T as NewKey]: … }` (TS 4.1) позволяет **переименовывать** ключи и **фильтровать** их: если выражение ключа даёт `never`, свойство исчезает из результата. Это идиоматический способ отобрать члены по типу значения или по имени.

### Как это работает

В сниппете `Same` сохранит и `?`, и `readonly`, а `Renamed` потеряет оба: получится `{ get_a: string | undefined; get_b: number }`. Причина в **гомоморфности**. Маппер вида `{ [K in keyof T]: … }` компилятор распознаёт как гомоморфный и копирует модификаторы каждого исходного свойства один к одному. Добавление `as` с изменением ключа разрывает связь «новый ключ ↔ исходное свойство», гомоморфность теряется, и модификаторы не переносятся.

Фильтрация работает так: выражение после `as` вычисляется для каждого `K` отдельно, результаты собираются, и члены, давшие `never`, просто не попадают в итоговый тип — ключа `never` не существует. Отсюда шаблон `as T[K] extends Function ? K : never`.

Модификаторы задаются здесь же: `-?` убирает опциональность (так устроен `Required`), `+?` добавляет (`Partial`), `-readonly` снимает (`Mutable`). Ключ может быть union — тогда одно исходное свойство порождает несколько (пара get/set из одного поля).

### Почему так

Гомоморфное копирование модификаторов — специальная логика в чекере, введённая ради `Partial`, `Readonly`, `Pick`: без неё `Partial<T>` терял бы `readonly`. Распознавание идёт по синтаксической форме, а не по семантике, поэтому любое отклонение (в том числе `as`) выключает механизм. Это цена простоты правила: оно предсказуемо, но нарушается неожиданно.

### Подводные камни

- Частое заблуждение: будто переименование съедает `?` и `readonly`. Это не так — при переборе по `keyof T` оба модификатора сохраняются, проверяется одной строкой в компиляторе. Терять их приходится осознанно, через `-?` и `-readonly`, и вот тогда вернуть поштучно (только тем полям, у которых они были) уже нельзя.
- Потерянный `?` превращается в обязательное поле типа `T | undefined`: при `exactOptionalPropertyTypes` это разные вещи, и код перестанет собираться.
- Два исходных ключа могут схлопнуться в один новый (например, после `Lowercase`) — компилятор не предупредит, свойство просто исчезнет.
- Шаблонные ключи требуют `K & string`: `keyof T` включает `symbol`, а символ в template literal не подставляется.
- Тяжёлые мапперы поверх больших типов заметно тормозят IDE: каждый hover пересчитывает весь результат.

### Что спросят следом

**Как сохранить опциональность при переименовании?** Двухшаговый маппер: сперва гомоморфно построить промежуточный тип, потом переименовать — или собрать результат как пересечение двух мапперов (обязательные и опциональные ключи отдельно). **Как реализован `Omit`?** Через `Pick<T, Exclude<keyof T, K>>` — он негомоморфен по историческим причинам и потому не проверяет, что `K` вообще есть в `T`.

```js
type Getters<T> = {
  [K in keyof T & string as `get${Capitalize<K>}`]: () => T[K]
};
// { getHost: () => string; getPort: () => number }

type OnlyFns<T> = {
  [K in keyof T as T[K] extends Function ? K : never]: T[K]
};

type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Required2<T> = { [K in keyof T]-?: T[K] };
```

> **Что добавит очков.** Нюанс, отличающий практика: as-переименование выключает гомоморфность, поэтому маппер молча теряет ? и readonly, а при exactOptionalPropertyTypes это ещё и ломает сборку.

## 40. Как писать рекурсивные типы и где у них предел?

```js
type Join<T extends string[], Acc extends string = ''> =
  T extends [infer H extends string, ...infer R extends string[]]
    ? Join<R, `${Acc}${H}`>
    : Acc;

type A = Join<['a', 'b', 'c']>;   // почему это работает на тысяче элементов,
                                  // а вариант с конкатенацией снаружи — нет?
```

### Коротко

Рекурсивный тип — условный тип, ссылающийся сам на себя. Типичные задачи: `DeepPartial`, `DeepReadonly`, пути к вложенным ключам, разбор строк, кортежная арифметика. Предел один — глубина инстанцирования, и он резко разный для хвостовой и не-хвостовой рекурсии.

### Как это работает

Компилятор ведёт стек инстанцирований. Для обычной рекурсии лимит — **около 50 уровней**, дальше выдаётся «Type instantiation is excessively deep and possibly infinite». С TS 4.5 работает **tail-recursion elimination**: если рекурсивная ссылка стоит непосредственно в ветке условного типа и её результат ничем не оборачивается, чекер разворачивает рекурсию в цикл, и предел поднимается до **1000 шагов** (жёсткая константа `maxTailRecursionDepth`).

Именно поэтому сниппет работает: `Join<R, …>` — последнее, что вычисляется в ветке, накопленный результат передаётся аккумулятором. Вариант ``${H}${Join<R>}`` хвостовым не является: результат рекурсии нужно подставить в шаблон, значит кадр стека приходится сохранять — и на пятидесятом элементе всё падает.

Второй важный механизм — **отложенное вычисление**. Условный тип с невыведенным параметром не раскрывается сразу, а откладывается. Поэтому `type X<T> = T extends … ? X<…> : …` может ссылаться на себя, а простой алиас `type Y<T> = Y<T>` даёт ошибку «circularly references itself».

### Почему так

Система типов TS полна по Тьюрингу, поэтому единственная защита от зависания компилятора — жёсткие лимиты. Они намеренно консервативны: лучше отказать на пятидесятом уровне, чем повесить IDE. Tail-recursion elimination — компромисс, который снимает лимит там, где кадр стека доказуемо не нужен.

### Подводные камни

- Рекурсия по объектам обязана отсекать `Date`, `Map`, `Set`, `RegExp`, функции и массивы: наивный `DeepPartial` превращает `Date` в `{ getTime?: … }`.
- Рекурсия по union без обёртки в кортеж дистрибутивна — тип раскрывается по каждому члену и стоимость умножается.
- Ошибка «excessively deep» появляется не всегда детерминированно: она зависит от порядка проверки файлов, поэтому падает в CI и не падает локально.
- Хвостовая форма ломается от невинного вида изменений — обернули результат в `Exclude`, и оптимизация выключилась без предупреждения.
- Даже в пределах лимита глубокая рекурсия дорога: подсказки IDE начинают тормозить задолго до ошибки компиляции.

### Что спросят следом

**Как обойти лимит совсем?** Разбить задачу: обрабатывать кортеж чанками по 10 через вложенный маппер, либо перенести вычисление в кодогенерацию. **Как проверить, что рекурсия хвостовая?** Эмпирически — прогнать тип на кортеже из 200 элементов: не-хвостовая упадёт, хвостовая пройдёт.

```js
// хвостовая форма с аккумулятором: до 1000 шагов
type Join<T extends readonly string[], Acc extends string = ''> =
  T extends readonly [infer H extends string, ...infer R extends string[]]
    ? Join<R, `${Acc}${H}`> : Acc;

// не хвостовая: результат оборачивается — предел ~50
type JoinBad<T extends readonly string[]> =
  T extends readonly [infer H extends string, ...infer R extends string[]]
    ? `${H}${JoinBad<R>}` : '';

// отсечение встроенных объектов обязательно
type DeepReadonly<T> =
  T extends Function | Date | RegExp ? T
  : T extends (infer U)[] ? readonly DeepReadonly<U>[]
  : T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;
```

> **Что добавит очков.** Конкретика, которую редко называют: обычный предел рекурсии — около 50 уровней, хвостовой (TS 4.5) — 1000, и оптимизация выключается от любой обёртки вокруг рекурсивного вызова.

## 41. Как написать корректный тип «равны ли два типа» и почему это сложно?

```js
type Naive<X, Y> = [X] extends [Y] ? ([Y] extends [X] ? true : false) : false;

type A = Naive<any, string>;   // почему здесь true?
type B = Naive<{a: 1}, {a: 1}>;
```

### Коротко

Наивное «взаимное `extends`» проверяет взаимную присваиваемость, а не идентичность. Оно ломается на `any` (совместим со всем в обе стороны) и на дистрибутивности union. Каноническое решение опирается на **внутреннее сравнение отложенных условных типов** и является деталью реализации компилятора, а не частью языка.

### Как это работает

В сниппете `A = true`: `any` присваивается `string`, и `string` присваивается `any`. Взаимная присваиваемость выполнена, хотя типы очевидно разные. Это принципиальный дефект подхода: присваиваемость — не отношение эквивалентности в нужном смысле.

Рабочий приём выглядит так: сравниваются два обобщённых функциональных типа `<T>() => T extends X ? 1 : 2` и `<T>() => T extends Y ? 1 : 2`. Внутри них `T` не подставлен, поэтому условные типы **откладываются**. При сравнении двух отложенных условных типов чекер не может их вычислить и вместо этого сверяет их структурно: одинаковы ли `checkType`, `extendsType` и обе ветки. Идентичными они окажутся только если `X` и `Y` — буквально один и тот же тип, включая различие `any`/`unknown`/`never` и порядок в пересечениях.

Именно поэтому такой `Equals` различает `any` и `unknown`, `{a: 1}` и `{a: number}`, но при этом даёт `false` на семантически равных, но по-разному записанных типах — например, на интерфейсе и структурно совпадающем type-алиасе в некоторых версиях.

### Почему так

В TS нет оператора «типы идентичны»: система структурная, и вопрос «один ли это тип» для неё нестандартный. Функция `isTypeIdenticalTo` внутри чекера есть, но наружу не выведена. Трюк с отложенными условными типами — способ дотянуться до неё окольным путём. Отсюда и главный риск: поведение неспецифицировано и уже менялось между версиями компилятора.

### Подводные камни

- Обёртка в кортеж `[T] extends [U]` убирает дистрибутивность, но не решает проблему `any` — это два разных дефекта.
- Результат зависит от версии TS: тесты на `Equals` ломаются при апгрейде без изменений в коде.
- Различает то, что различать обычно не хотят: `{a: 1} & {b: 2}` и `{a: 1; b: 2}` для него разные типы.
- Опциональные свойства и `readonly` учитываются, поэтому `Equals` строже, чем ожидает автор теста.
- В проде такой тип почти всегда не нужен: если он появился в бизнес-коде, скорее всего задача решается иначе.

### Что спросят следом

**Где это применяют?** В type-тестах: `expectTypeOf` из vitest, `tsd`, `@ts-expect-error`-фикстуры библиотек — там нужно убедиться, что утилита вывела ровно ожидаемый тип. **Как проверить на `any` отдельно?** `type IsAny<T> = 0 extends (1 & T) ? true : false` — пересечение с `any` схлопывается в `any`, и `0 extends any` проходит.

```js
type Equals<X, Y> =
  (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;

type A = Equals<any, unknown>;        // false
type B = Equals<{ a: 1 }, { a: 1 }>;  // true
type C = Equals<{ a: 1 } & { b: 2 }, { a: 1; b: 2 }>;  // false — строже, чем ждут

type IsAny<T> = 0 extends (1 & T) ? true : false;
type D = IsAny<any>;    // true
```

> **Что добавит очков.** Честно скажите, что трюк опирается на неспецифицированную деталь реализации чекера и ломается при апгрейде TS — такой ответ ценится выше, чем заученная формула.

## 42. Как типизировать this в TypeScript?

```js
class Q { where(): this { return this } }
class Sub extends Q { limit(): this { return this } }

new Sub().where().limit();   // какой тип у where() и почему это компилируется?
```

### Коротко

Механизмов четыре, и их путают: параметр `this` в сигнатуре, polymorphic `this` как тип, маркер `ThisType<T>` и флаг `noImplicitThis`. Все они compile-time; в рантайме `this` остаётся обычным динамическим `this` из JS.

### Как это работает

В сниппете `where()` возвращает `this` — не `Q`, а «тип текущего получателя». Для экземпляра `Sub` это `Sub`, поэтому `.limit()` доступен. Это **polymorphic this**, база для fluent-API: query-билдеры, чейнинг в тест-хелперах, наследуемые модели. Если бы `where()` возвращал `Q`, цепочка обрывалась бы на первом же вызове базового метода.

**Параметр `this`** — фиктивный первый параметр в сигнатуре: `function f(this: HTMLElement, e: Event)`. Он не входит в число аргументов, не существует в рантайме и полностью стирается при компиляции. Зато при вызове и при присваивании обработчика компилятор проверяет, что контекст подходит; `strictBindCallApply` распространяет проверку на `bind`, `call`, `apply`.

**`ThisType<T>`** — маркер без членов, распознаваемый чекером: если он попал в тип объектного литерала, `this` внутри методов этого литерала получает тип `T`. Работает только при `noImplicitThis` и придуман под Vue Options API, где `this` в методах собирается из data, computed и props.

**`noImplicitThis`** — флаг из `strict`: без него `this` в свободной функции молча становится `any`.

### Почему так

В JS `this` определяется способом вызова, а не местом объявления. Статически вывести его нельзя, поэтому TS даёт способ **задекларировать ожидание** и проверить его в местах вызова, которые видит. Всё, что уходит в динамику (`fn.call(x)` из чужого кода, обработчик, повешенный строкой в HTML), остаётся непроверенным.

### Подводные камни

- Параметр `this` стирается — соблазн подумать, что он что-то гарантирует в рантайме, ошибочен.
- Стрелочные функции не имеют своего `this`, и объявить им параметр `this` нельзя: это и есть штатный способ избежать темы целиком.
- Polymorphic `this` ломает присваиваемость: класс с методом `(): this` нельзя подставить туда, где ждут конкретный тип, если наследник добавил члены.
- Метод, вырванный из объекта (`const m = obj.method`), теряет контекст, и параметр `this` это как раз ловит — типичная причина «почему у меня undefined».
- `ThisType` не работает в классах и не работает без `noImplicitThis` — молча.

### Что спросят следом

**Что делает `strictBindCallApply`?** Типизирует `bind`/`call`/`apply` точно, вместо старых сигнатур с `any[]`: неправильный контекст или лишний аргумент становятся ошибкой. **Как типизировать обработчик DOM?** `(this: HTMLButtonElement, e: MouseEvent) => void` — тогда внутри `this.disabled` проверяется, а стрелка на этом месте вызовет ошибку по контексту.

```js
class Q { where(): this { return this } }
class Sub extends Q { limit(): this { return this } }
new Sub().where().limit();   // Sub — polymorphic this

// параметр this: не аргумент, стирается при компиляции
function onClick(this: HTMLButtonElement, e: MouseEvent) {
  this.disabled = true;
}
btn.addEventListener('click', onClick);       // ок
const detached = onClick;
detached(new MouseEvent('click'));            // ошибка: нет контекста

// ThisType: контекст внутри литерала
declare function make<D, M>(o: { data: D; methods: M & ThisType<D & M> }): void;
```

> **Что добавит очков.** Первый вопрос-подвох после ответа: параметр this полностью стирается при компиляции и не занимает позицию в аргументах — назовите это сами.

## 43. Как работает module augmentation и когда он необходим?

```js
// types.d.ts — в файле больше ничего нет
declare module 'express-serve-static-core' {
  interface Request { user?: { id: string } }
}

// почему после этого пропали ВСЕ типы express?
```

### Коротко

Module augmentation — расширение типов чужого модуля из своего кода. `declare module 'lib' { … }` внутри **файла-модуля** дописывает члены в существующее объявление. Тот же синтаксис в файле-скрипте создаёт **новый** ambient-модуль и полностью перекрывает типы библиотеки.

### Как это работает

В сниппете произошло ровно это. Файл не содержит ни одного `import` или `export`, значит для компилятора это скрипт, а не модуль. В скрипте `declare module 'x'` — объявление ambient-модуля: «вот полное описание пакета x». Компилятор берёт его вместо типов из `node_modules`, и `Request` с одним полем `user` — всё, что теперь известно про express.

Починка — сделать файл модулем: добавить `import 'express';` сверху или `export {};` снизу. Тогда `declare module` трактуется как аугментация, находит существующий символ модуля и мержит объявления по правилам declaration merging.

Отдельная форма — `declare global { … }`: она допустима только внутри модуля и дописывает члены в глобальную область (`Window`, `globalThis`, `NodeJS.ProcessEnv`). В скрипте она не нужна и запрещена: там всё и так глобально.

Важное ограничение: аугментация не создаёт новые экспорты в модуле и не может изменить существующие. Она только дополняет интерфейсы и namespace внутри него.

### Почему так

Разделение «скрипт против модуля» идёт от самого ES: файл без импортов и экспортов имеет глобальную область видимости. TS наследует это правило и вешает на него разную семантику `declare module`. Правило логичное, но диагностика ужасная: вместо ошибки вы получаете тихую потерю типов, которая выглядит как баг библиотеки.

### Подводные камни

- Забытый `export {}` перезатирает типы пакета молча — самая частая ошибка в теме.
- Расширять можно только то, что объявлено `interface` или `namespace`. Добавить поле в `type` из библиотеки невозможно в принципе.
- Имя модуля должно совпадать с тем, под которым типы объявлены внутри пакета: для express это `'express-serve-static-core'`, а не `'express'`.
- Аугментация глобальна для всей программы: в монорепе она создаёт неявную связанность между пакетами и «работает» только если файл попал в `include`.
- Файл с аугментацией должен быть включён в компиляцию явно; если на него никто не ссылается и он не в `include`/`types`, эффекта не будет.
- Две аугментации одного интерфейса из разных пакетов конфликтуют, если объявляют одно поле с разными типами — и ошибка вылезает в чужом коде.

### Что спросят следом

**Где это реально нужно?** Поле `user` в `Express.Request` после auth-middleware, кастомная тема в styled-components/MUI, свои `ImportMetaEnv`, `window.__APP_STATE__` из SSR, расширение `JSX.IntrinsicElements` для веб-компонентов. **Чем плоха аугментация как архитектурное решение?** Она делает глобальное утверждение о типе, которое верно только там, где middleware отработал; безопаснее локальный тип `AuthedRequest`, проверяемый явно.

```js
// правильно: файл — модуль благодаря import
import 'express';
declare module 'express-serve-static-core' {
  interface Request { user?: { id: string } }
}

// глобальная аугментация допустима только в модуле
declare global {
  interface Window { __APP_STATE__?: unknown }
  namespace NodeJS { interface ProcessEnv { API_URL?: string } }
}
export {};   // без этой строки файл стал бы скриптом
```

> **Что добавит очков.** Назовите export {} и объясните механизм: без импорта или экспорта файл — скрипт, и declare module в нём объявляет новый ambient-модуль, перекрывая типы пакета целиком.

## 44. Нужны ли namespace в 2025 году и где они всё ещё оправданы?

### Коротко

Для организации кода — нет: ES-модули их полностью вытеснили. Но `namespace` не мёртв: в `.d.ts` он остаётся штатным инструментом описания глобальных сущностей и UMD-библиотек. Правильная формулировка — «namespace в `.d.ts` нормально, namespace в `.ts` легаси».

### Как это работает

Не-`declare` namespace **генерирует код**: компилятор превращает его в IIFE, присваивающую свойства объекту-контейнеру. Отсюда все проблемы. Такой объект непрозрачен для бандлера: доступ идёт через `MyNs.helper`, статический анализ не может доказать, что остальные члены не нужны, и tree-shaking не срабатывает. Второе — конфликт с `isolatedModules`: однофайловый транспилятор не знает, объявляет namespace только типы (тогда его надо стереть) или ещё и значения (тогда оставить), потому что для этого нужны типы из других файлов.

`declare namespace` кода не генерирует — это чистое описание. Именно так устроены `NodeJS.ProcessEnv`, `JSX.IntrinsicElements`, `Intl`-типы в lib.d.ts. Слияние namespace с функцией или классом даёт «значение с типами рядом»: `MyLib(o)` вызывается, а `MyLib.Options` — тип из того же имени.

### Почему так

Namespace появился в 2012 году, когда модульной системы в JS не было и код склеивали конкатенацией файлов. С приходом ES-модулей задача «избежать глобальных коллизий» решается самой модульной системой, а namespace добавляет второй, параллельный механизм областей видимости — лишнюю сложность без выгоды. Официальный TS Handbook прямо не рекомендует их в новом коде.

### Где всё ещё оправданы

- В `.d.ts` для глобальных сущностей: `declare namespace NodeJS { interface ProcessEnv {…} }`.
- Для слияния с функцией или классом, чтобы дать типам пространство имён рядом со значением: `Foo.Props`, `Foo.Ref`.
- Для описания UMD-библиотек, которые доступны и как модуль, и как глобальная переменная (`export as namespace jQuery`).
- Для группировки типов в одном публичном объявлении, когда десяток плоских экспортов загрязняет API пакета.

### Подводные камни

- Namespace внутри модуля не становится глобальным — это частая иллюзия; он просто вложенная область в этом файле.
- `namespace` с кодом ломает сборку через esbuild/SWC при `isolatedModules` и даёт невнятную ошибку.
- `/// <reference path>`-стиль с namespace несовместим с `moduleResolution: bundler` и современными пакетами.
- Слияние namespace с классом требует, чтобы namespace шёл **после** объявления класса — иначе ошибка о порядке.

### Что спросят следом

**Чем заменить в модульном коде?** Именованными экспортами плюс `import * as X from './x'` на стороне потребителя — тот же синтаксис доступа, но с полноценным tree-shaking. **А `enum`?** Тот же класс проблем: генерирует объект, конфликтует с `isolatedModules` в форме `const enum`; в новом коде предпочтительнее `as const`-объект или union строковых литералов.

```js
// .d.ts — namespace уместен
declare namespace MyLib {
  interface Options { debug?: boolean }
}
declare function MyLib(o?: MyLib.Options): void;
export = MyLib;

// .ts — так больше не пишем
namespace Utils { export const f = () => {} }   // генерирует IIFE, не шейкается

// современная замена
export const f = () => {};
// у потребителя: import * as Utils from './utils'
```

> **Что добавит очков.** Формулировка «namespace в .d.ts нормально, namespace в .ts легаси» плюс причина: не-declare namespace генерирует IIFE, не шейкается и ломает isolatedModules.

## 45. Что такое isolatedModules и какие конструкции он запрещает?

```js
// types.ts
export interface User { id: string }

// index.ts
export { User } from './types';   // почему это ошибка при isolatedModules?
```

### Коротко

`isolatedModules` гарантирует, что каждый файл можно транспилировать **независимо**, не зная типов из других файлов. Это жёсткое требование любого однофайлового транспилятора: esbuild, SWC, Babel, Vite. Флаг ничего не меняет в выводе `tsc` — он лишь запрещает конструкции, которые такой транспилятор не смог бы обработать корректно.

### Как это работает

В сниппете esbuild видит только `index.ts`. Строка `export { User } from './types'` для него — реэкспорт значения, и он оставит в выводе `export { User } from './types'`. В рантайме модуль `./types` не экспортирует ничего (интерфейс стёрся), и импорт упадёт с «does not provide an export named 'User'». Чтобы транспилятор знал, что это тип, нужно написать это явно: `export type { User } from './types'`.

Ровно та же логика за остальными запретами. `const enum` требует, чтобы транспилятор подставил значение из другого файла — а он туда не заглядывает. Файл без импортов и экспортов для TS может быть модулем или скриптом в зависимости от конфигурации — нужен явный `export {}`. `export =` и часть форм declaration merging тоже требуют межфайлового контекста.

С TS 5.0 есть родственный флаг `verbatimModuleSyntax`, который делает правило ещё жёстче и заодно точнее: импорты без `type` сохраняются дословно, с `type` — вырезаются целиком.

### Почему так

Проверка типов принципиально требует всей программы, а транспиляция — нет. Разделив их, экосистема получила сборку в десятки раз быстрее: esbuild выкидывает аннотации по синтаксису, не строя граф типов. Цена — небольшой набор конструкций, где синтаксис неоднозначен без знания типов. `isolatedModules` просто делает эту цену явной ошибкой компиляции вместо тихого бага в сборке.

### Подводные камни

- Ошибка проявляется только в рантайме продовой сборки, если флаг не включён, — `tsc` её не покажет.
- `const enum` в библиотеке, которую вы потребляете, тоже проблема: с `isolatedModules` её значения не инлайнятся и обращение падает.
- Смешивание `export type` и `export` в одной строке (`export { type User, createUser }`) поддерживается только с TS 5.0.
- Декораторы и `emitDecoratorMetadata` с однофайловыми транспиляторами работают частично — метаданные требуют типов.
- Флаг не проверяет типы: `tsc --noEmit` в CI всё равно нужен, иначе ошибки типов вообще никто не увидит.

### Что спросят следом

**Как выглядит правильный пайплайн?** Сборка через Vite/esbuild с `isolatedModules`, отдельный шаг `tsc --noEmit` в CI и в pre-commit как чекер типов. **Чем `verbatimModuleSyntax` отличается?** `isolatedModules` запрещает неоднозначное, `verbatimModuleSyntax` задаёт детерминированное правило стирания — второй строже и заменяет старые `importsNotUsedAsValues` и `preserveValueImports`.

```js
import type { User } from './types';
export type { User };                    // корректно
// export { User } from './types';       // ошибка при isolatedModules

// TS 5.0: смешанный импорт
import { type Options, run } from './lib';

// файл без импортов и экспортов — нужен явный маркер модуля
export {};

// const enum вместо этого:
const Level = { Low: 0, High: 1 } as const;
type Level = typeof Level[keyof typeof Level];
```

> **Что добавит очков.** Суть в одном предложении: isolatedModules нужен, потому что esbuild и SWC не видят типы других файлов и не могут отличить реэкспорт типа от реэкспорта значения.

## 46. Чем moduleResolution bundler отличается от node16 и classic?

### Коротко

`moduleResolution` описывает, как TS ищет файл по спецификатору импорта. Настройка должна **совпадать с тем, что делает ваш рантайм или сборщик** — иначе типы разрешатся из одного файла, а код возьмёт другой. Это не шкала «старое → новое», а выбор модели среды.

### Четыре режима

- `classic` — доисторический алгоритм без `node_modules`. Существует только для обратной совместимости; с TS 5.0 его нельзя использовать с современными значениями `module`.
- `node10` (раньше назывался `node`) — легаси CommonJS-алгоритм Node: подъём по `node_modules`, поле `main`, импорт без расширения. **Не понимает `exports`** — отсюда большинство проблем с современными пакетами, которые публикуют типы только через условия.
- `node16`/`nodenext` — реальные правила Node ESM: читает `exports` и `imports`, требует расширение `.js` в относительных ESM-импортах, различает CJS и ESM по полю `type` в package.json и по расширениям `.mts`/`.cts`. Самый строгий и единственно верный для кода, который запускает Node напрямую.
- `bundler` (TS 5.0) — гибрид: понимает `exports`, но не требует расширений и разрешает ESM-синтаксис там, где Node потребовал бы CJS. Ровно та модель, по которой работают Vite, webpack и esbuild. Требует `module` не ниже `es2015`.

### Как это работает

Ключевая разница — **условные экспорты**. Пакет объявляет `"exports": { ".": { "types": "./d.ts", "import": "./esm.js", "require": "./cjs.js" } }`. Режимы `node16` и `bundler` идут по этой карте и берут ветку в зависимости от того, как импортируют. `node10` карту игнорирует и падает на `main`, которого в современных пакетах может не быть вовсе — отсюда «Cannot find module or its corresponding type declarations» при работающем рантайме.

Требование расширения `.js` в `node16` удивляет: в `.ts`-файле надо писать `import './a.js'`, хотя файл называется `a.ts`. Причина — TS не переписывает спецификаторы: что написано, то и уедет в вывод, а Node ESM расширение требует. С TS 5.7 есть `rewriteRelativeImportExtensions`, позволяющий писать `.ts`.

`module: preserve` (TS 5.4) подразумевает `moduleResolution: bundler` и сохраняет синтаксис импортов дословно — рекомендуемая связка для фронтенда со сборщиком.

### Почему так

Единого «правильного» алгоритма нет: Node, webpack и Vite ищут файлы по-разному, и TS обязан лишь **предсказать** результат чужого поиска. Поэтому режимов несколько, и выбор — это описание среды, а не уровень строгости.

### Подводные камни

- Тип-ошибки, которых нет в рантайме, и наоборот — почти всегда следствие рассинхрона резолюции со сборщиком.
- `bundler` в проекте, который реально запускает Node (скрипты, SSR-сервер), скроет отсутствующие расширения — и упадёт при запуске.
- `paths` в tsconfig влияет только на типы: сборщику нужен свой alias, иначе рантайм не найдёт модуль.
- Монорепа с миксом CJS и ESM пакетов требует `node16` и аккуратных `exports`; `bundler` замаскирует проблему до продакшена.
- Смена режима резолюции — ломающее изменение для потребителей библиотеки, если меняется и то, как публикуются типы.

### Что спросят следом

**Что выбрать в приложении на Vite?** `module: preserve` (или `esnext`) плюс `moduleResolution: bundler`, `noEmit: true`, сборка через Vite. **А в библиотеке?** `nodenext`: он строже всех и покажет проблемы, с которыми столкнутся ваши потребители, ещё до публикации. Проверять результат — через `attw`.

```js
// tsconfig приложения со сборщиком
{ "compilerOptions": {
  "module": "preserve", "moduleResolution": "bundler",
  "noEmit": true, "verbatimModuleSyntax": true
}}

// tsconfig библиотеки / Node-кода
{ "compilerOptions": {
  "module": "nodenext", "moduleResolution": "nodenext",
  "declaration": true
}}

// при nodenext расширение обязательно — TS не переписывает спецификатор
import { helper } from './helper.js';   // файл на диске helper.ts
```

> **Что добавит очков.** Ключевой тезис: резолюция должна описывать вашу среду выполнения, а не «включить самое новое». bundler в проекте, который запускает Node, скрывает ошибки до продакшена.

## 47. Что делает verbatimModuleSyntax и какую проблему он решает?

```js
import { Reflector } from './reflect-metadata-setup';

let r: Reflector;   // единственное использование — типовое

// что окажется в JS-выводе без verbatimModuleSyntax?
```

### Коротко

Правило детерминированное: импорты и экспорты **без** модификатора `type` сохраняются в выводе дословно, с модификатором — удаляются целиком. Флаг убирает историческое «умное» стирание, которое смотрело на фактическое использование и порождало два зеркальных класса багов.

### Как это работает

В сниппете без флага строка импорта исчезнет из вывода: `Reflector` использован только в типовой позиции, значит компилятор счёл импорт ненужным и вырезал его. Вместе с ним исчез и **сайд-эффект модуля** — регистрация `reflect-metadata`, установка полифилла, подписка на глобальное событие. Приложение падает в рантайме с ошибкой, не имеющей никакого отношения к типам.

Зеркальный баг — в однофайловых транспиляторах: esbuild не знает, тип это или значение, и оставляет импорт. В рантайме модуль не экспортирует такого имени, и сборка ломается на этапе линковки.

С `verbatimModuleSyntax` обе ситуации исключены по построению: что написано без `type`, то остаётся; что написано с `type`, того нет. Компилятор больше не принимает решений, а значит его вывод совпадает с выводом esbuild и SWC.

Флаг заменяет два старых: `importsNotUsedAsValues` и `preserveValueImports`. Он же запрещает CJS-синтаксис `export =` и `import x = require()` в файлах, которые компилируются в ESM: дословное сохранение таких конструкций в ESM-выводе бессмысленно.

### Почему так

«Умное» стирание было разумным в мире, где единственным транспилятором был `tsc`, видевший всю программу. С переходом на пофайловую сборку это стало источником расхождений между тем, что видит чекер, и тем, что собирает бандлер. Явность дороже в написании (приходится ставить `type` руками), но убирает целый класс несводимых багов.

### Подводные камни

- Требует дисциплины: каждый типовой импорт надо помечать. Спасает ESLint-правило `consistent-type-imports` с автофиксом.
- Смешанная форма `import { type X, y }` идиоматична, но поддерживается только с TS 5.0.
- Импорт ради сайд-эффекта надо писать явно: `import './polyfill'` без имён — это единственная надёжная запись.
- В проектах с декораторами и `emitDecoratorMetadata` флаг ломает генерацию метаданных: они требуют, чтобы тип был доступен как значение.
- Апгрейд существующего проекта даёт много ошибок сразу — но все они механические и чинятся автофиксом.

### Что спросят следом

**Чем отличается от `isolatedModules`?** `isolatedModules` запрещает конструкции, неоднозначные без типов; `verbatimModuleSyntax` задаёт правило стирания. Второй строже и покрывает первый по большинству случаев, но их обычно включают вместе. **Зачем помечать `export type`?** По той же причине с другой стороны: реэкспорт типа без модификатора превратится в рантайм-реэкспорт несуществующего значения.

```js
import { type User, createUser } from './user';
// в выводе: import { createUser } from './user';

import type { Config } from './config';
// в выводе: строки нет вообще

import './polyfill';
// в выводе: import './polyfill'; — сайд-эффект сохранён явно

export type { User };          // корректно
// export { User };            // ошибка: реэкспорт типа как значения
```

> **Что добавит очков.** Пример с исчезающим полифиллом (импорт использован только в типовой позиции — и сайд-эффект пропал из сборки) — самая понятная иллюстрация проблемы, которую решает флаг.

## 48. Type-level программирование: где польза, а где вред?

### Коротко

Сложный тип оправдан, когда он написан **один раз** и защищает контракт, используемый сотнями мест. Внутри одной фичи — почти никогда. Главный критерий не «получилось ли выразить», а «сможет ли джун прочитать ошибку и починить её сам».

### Как это работает

Механика простая и в этом ловушка: условные типы, рекурсия и `infer` дают полный по Тьюрингу вычислитель, работающий на этапе проверки. Всё, что он посчитал, стирается — в рантайм не уезжает ни байта, зато каждая инстанциация оплачивается временем чекера и памятью tsserver. То есть выразительность бесплатна для бандла и платна для команды: за неё платят скоростью IDE и читаемостью ошибок.

### Где польза реальна

- Типобезопасные роуты: путь `/users/:id` порождает тип параметров, и опечатка в имени становится ошибкой компиляции, а не 404 в проде.
- Ключи i18n с проверкой плейсхолдеров: перевод требует `{count}`, а вызов его не передал — ловится статически.
- Схемы таблиц и ORM-запросы: `select` возвращает ровно выбранные колонки, а не весь тип строки.
- Токены дизайн-системы: автодополнение вместо документации, невозможность опечататься в `--color-primry`.
- Невозможные состояния в редьюсерах: дискриминированный union вместо трёх независимых булевых флагов, из которых половина комбинаций бессмысленна.

### Где начинается вред

- **Нечитаемые ошибки.** Сообщение на сорок строк с раскрытыми условными типами останавливает работу человека, который не писал этот тип. Это прямой урон скорости команды, и он не виден в метриках.
- **Время проверки.** IDE начинает тормозить на автодополнении задолго до того, как упадёт CI. Разработчики замечают это как «редактор тупит», не связывая с типами.
- **Дублирование рантайма.** Тип, проверяющий то, что дешевле проверить схемой на границе, — работа впустую: данные всё равно приходят извне.
- **Опора на неспецифицированное поведение.** Трюки вроде `Equals` держатся на деталях реализации чекера и ломаются при апгрейде минорной версии.
- **Тип вместо теста.** Инварианты, зависящие от данных, статически невыразимы; попытка приводит к монстру, который всё равно не гарантирует нужного.

### Почему так

Система типов TS полна по Тьюрингу, поэтому вопрос «можно ли это выразить» почти всегда имеет ответ «да». Отсюда искушение: сложный тип ощущается как инженерное достижение. Но у типа есть аудитория — вся команда, включая тех, кто увидит ошибку через год. Стоимость чтения платится многократно, стоимость написания — один раз.

### Как принимать решение

- Считать отношение «мест использования» к «строкам типа». Один к ста — пишем, один к трём — не пишем.
- Проверить сообщение об ошибке заранее: сломать вызов специально и прочитать, что выдал компилятор.
- Спрятать сложность за именем: `type RoutePath` вместо инлайн-выражения на пять строк в сигнатуре.
- Оставить путь отхода: `as` с комментарием в одном месте лучше, чем тип, который никто не решается тронуть.

### Что спросят следом

**Приведите пример, где вы отказались.** Хороший ответ — конкретный: «сделали типизированный билдер SQL, ошибки стали нечитаемы, откатились на генерацию типов из схемы». **Как улучшить сообщение об ошибке?** Ветка с «понятным» типом-маркером: `T extends X ? Ok : { error: 'expected X, got:'; got: T }` — компилятор напечатает эту структуру, и она читается.

```js
// хорошо: тип один, применений сотни
type Params<S extends string> =
  S extends `${string}:${infer P}/${infer R}` ? P | Params<R>
  : S extends `${string}:${infer P}` ? P : never;

// невозможные состояния вместо трёх флагов
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'done'; data: User };

// приём для читаемых ошибок
type Expect<T, Shape> =
  T extends Shape ? T : { error: 'shape mismatch'; expected: Shape; got: T };
```

> **Что добавит очков.** Критерий «сможет ли джун прочитать ошибку и починить сам» — самый убедительный аргумент в этой теме, и его почти никогда не называют.

## 49. Что такое typeof import и зачем он нужен?

```js
declare global {
  interface Window { api: Api }   // Api объявлен в './api'
}
// почему сюда нельзя просто написать import { Api } from './api'?
```

### Коротко

`typeof import('./m')` в type-позиции даёт тип пространства имён модуля целиком — все его экспорты как один объектный тип — **не внося рантайм-импорта**. Работает в `.ts`, в `.d.ts` и в JSDoc-комментариях в `.js`.

### Как это работает

В сниппете проблема в том, что обычный `import` на верхнем уровне превращает файл в модуль, а `declare global` внутри модуля работает, но **внутри самого блока** `global` импортированные имена доступны не всегда, и добавление импорта меняет семантику файла целиком. `typeof import('./api')` решает это точечно: он выражается прямо в типовой позиции, ничего не добавляет в область видимости файла и не порождает `require` в выводе.

Компилятор при встрече такого выражения разрешает спецификатор по обычным правилам резолюции, берёт символ модуля и строит из его экспортов анонимный объектный тип. Индексировать его можно как обычно: `typeof import('./api')['getUser']` — тип конкретного экспорта.

С динамическим импортом это работает автоматически: `await import('./heavy')` имеет тип `typeof import('./heavy')`, поэтому `(await import('./heavy')).default` типизирован без единой аннотации.

### Почему так

До появления этой формы «взять тип из модуля, не импортируя его» было невозможно, и в `.d.ts` приходилось дублировать определения или тащить импорт, ломающий глобальность файла. Форма `typeof import()` отделяет разрешение модуля от его загрузки: типы существуют только при компиляции, значит и импортировать ради них ничего не нужно.

### Где это применяют

- Глобальные объявления: `declare global { interface Window { api: typeof import('./api') } }` без превращения файла в лишнюю зависимость.
- Разрыв циклических импортов: тип берётся «по требованию», рантайм-ребро в графе модулей не появляется.
- Ленивая загрузка: `const mod: typeof import('./heavy') = await import('./heavy')`.
- Моки в тестах: `vi.mock('./api', (): typeof import('./api') => ({ … }))` — компилятор проверит, что мок покрывает все экспорты с правильными сигнатурами. Забыли функцию после рефакторинга — ошибка компиляции, а не падение теста.
- JSDoc в JS-файлах: `@type {import('./api').User}` — так типизируют конфиги вебпака и eslint без перехода на TS.

### Подводные камни

- Путь в строке не проверяется рефакторингом так же надёжно, как импорт: переименование файла в IDE иногда его не обновляет.
- Тип включает **все** экспорты, включая внутренние — это делает мок обязанным реализовать и их.
- С `moduleResolution: node16` строка обязана содержать расширение `.js`, как и обычный импорт.
- Для CJS-модуля с `export =` результат — тип самого значения, а не объекта с ключом `default`: поведение зависит от `esModuleInterop`.

### Что спросят следом

**Чем отличается от `import type`?** `import type { X }` берёт один именованный тип и требует места в шапке файла; `typeof import()` берёт весь модуль и пишется прямо в типовом выражении, в том числе там, где импорт невозможен. **Останется ли что-то в бандле?** Нет: конструкция целиком типовая и стирается — рантайм-импорта не возникает даже при `verbatimModuleSyntax`.

```js
type Api = typeof import('./api');
declare global { interface Window { api: Api } }
export {};

// тип конкретного экспорта
type GetUser = typeof import('./api')['getUser'];

// динамический импорт типизирован сам
const mod = await import('./heavy');   // typeof import('./heavy')

// мок обязан совпасть с реальным модулем по сигнатурам
vi.mock('./api', (): typeof import('./api') => ({
  getUser: async () => ({ id: '1' }),
}));
```

> **Что добавит очков.** Кейс с моками — самый практичный: типизировать фабрику мока как typeof import(...) значит получать ошибку компиляции, когда в модуль добавили экспорт, а мок не обновили.

## 50. Как типизировать миксины и абстрактные конструкторы?

```js
type Ctor<T = {}> = new (...a: any[]) => T;
abstract class Base { abstract render(): void }

function Mixin<B extends Ctor>(B_: B) { return class extends B_ {} }
Mixin(Base);   // почему ошибка и что её чинит?
```

### Коротко

Миксин — функция, принимающая конструктор и возвращающая расширенный класс. Ключевых элементов два: тип конструктора `new (...args: any[]) => T` и то, что возвращаемый тип **выводится компилятором** — аннотировать его вручную почти невозможно без потери деталей.

### Как это работает

В сниппете ошибка потому, что абстрактный класс не присваивается обычной конструкторной сигнатуре: его нельзя инстанцировать через `new`, а тип `Ctor` именно это и обещает. Чинится **abstract construct signature** из TS 4.2: `type Ctor<T = {}> = abstract new (...a: any[]) => T`. Такая сигнатура описывает «конструктор, возможно абстрактный» и принимает оба вида классов.

Вывод результата устроен так: `class extends B_ {}` порождает анонимный класс, а тип его экземпляра — `InstanceType<B>` плюс добавленные члены. Компилятор это выводит, но **назвать** получившийся тип нельзя: у анонимного класса нет имени, на которое можно сослаться в `.d.ts`. Отсюда главная практическая проблема.

`extends` от произвольного выражения (а не от идентификатора) поддерживается языком специально ради этого паттерна — `class X extends Mixin(Base) {}` валидно и в TS, и в JS.

### Почему так

JS не имеет множественного наследования, но имеет динамическое `extends` от выражения — миксины эксплуатируют именно это. TS вынужден типизировать паттерн через вывод, потому что выписать «класс со всеми членами базы плюс мои» заранее, без пересечений и `InstanceType`, невозможно.

### Подводные камни

- **`declaration: true` ломается**: компилятор не может выписать в `.d.ts` имя анонимного класса и выдаёт «has or is using private name». Лечится явным интерфейсом и слиянием — ценой дублирования.
- `isolatedDeclarations` (TS 5.5) с миксинами несовместим по той же причине: тип возврата невыразим явно.
- **Приватные поля**: `private` и `#x` проверяются номинально, поэтому классы из двух разных вызовов миксина несовместимы, даже будучи структурно идентичными.
- Порядок применения значим, но невыразим в типах: `A(B(Base))` и `B(A(Base))` ведут себя по-разному, а типы совпадают.
- `constructor.name` у анонимного класса пуст — ломаются DI-контейнеры, логи и React DevTools.
- Цепочка из трёх-четырёх миксинов даёт нечитаемые ошибки с полностью раскрытыми пересечениями.

### Что спросят следом

**Чем заменить в прикладном коде?** Композицией: объект с зависимостями, хуки, отдельные сервисы. Миксины оправданы в библиотечном коде, где наследование — часть публичного API (Lit, старый Angular, часть ORM). **Зачем нужен `InstanceType`?** Достаёт тип экземпляра из конструктора: `InstanceType<typeof MyClass>` — нужен и в сигнатурах миксинов, и везде, где класс передают как значение.

```js
// abstract new принимает и обычные, и абстрактные классы (TS 4.2)
type Ctor<T = {}> = abstract new (...a: any[]) => T;

function Timestamped<B extends Ctor>(Base: B) {
  abstract class T extends Base { created = Date.now() }
  return T;
}

class Doc {}
class TimedDoc extends Timestamped(Doc) {}
new TimedDoc().created;     // number

// для declaration: true нужен явный именованный интерфейс
interface Timestamps { created: number }
export function withTs<B extends Ctor>(Base: B): B & Ctor<Timestamps> {
  return class extends Base { created = Date.now() };
}
```

> **Что добавит очков.** Нюанс, который убеждает: у миксинов ломается declaration: true (анонимный класс нельзя назвать в .d.ts), и та же причина делает их несовместимыми с isolatedDeclarations.
