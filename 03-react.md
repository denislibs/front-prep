# React + Next.js: вопросы уровня сеньора

## Рендеринг и реконсиляция

**Вопрос: что происходит при setState? Как React решает, что обновить в DOM?**

Рендер в React — вызов функции компонента, дающий новое дерево React-элементов (легковесных объектов-описаний). **Реконсиляция** — сравнение нового дерева со старым (diffing) по эвристикам: разные типы элементов → поддерево пересоздаётся; одинаковые → обновляются только изменённые пропсы; списки сравниваются по `key`. Затем **коммит** — минимальные мутации реального DOM.

**Fiber** — внутренняя архитектура: рендер-фаза разбита на прерываемые единицы работы, что позволяет конкурентный рендеринг — React может прервать низкоприоритетный рендер ради срочного (ввод пользователя). Отсюда `useTransition`/`useDeferredValue`: помечаем обновление как несрочное, UI остаётся отзывчивым.

**Батчинг**: с React 18 все setState батчатся автоматически (в т.ч. в промисах и таймаутах) — один ререндер на синхронный блок.

**Почему key и почему не index**: key — идентичность элемента между рендерами. Index при вставке/удалении/сортировке приводит к неправильному переиспользованию стейта и DOM (классический баг с инпутами в списке).

## Ререндеры и оптимизация

**Когда компонент ререндерится**: изменился его стейт; отрендерился родитель (пропсы сравнивать никто не обязан!); изменился используемый контекст.

Инструменты:
- `React.memo` — пропускает рендер при поверхностно равных пропсах.
- `useMemo` / `useCallback` — стабильные ссылки, чтобы memo/зависимости работали. Мемоизировать всё подряд — вредно (память + сложность); мемоизировать по результатам профилирования (React DevTools Profiler).
- Композиция вместо мемоизации: поднять тяжёлое поддерево в `children` — при ререндере родителя `children` ссылочно тот же и не ререндерится; state colocation — держать стейт максимально близко к месту использования.
- React Compiler (React 19) автоматизирует мемоизацию — знать, что он существует.

## Хуки

**Правила**: вызывать только на верхнем уровне (React сопоставляет хуки по порядку вызова между рендерами) и только из React-функций.

**useEffect** — синхронизация с внешними системами (подписки, таймеры, ручной DOM), а не «lifecycle-метод». Cleanup выполняется перед следующим эффектом и при размонтировании. Классические ошибки: гонки запросов (лечится AbortController или флагом в cleanup), лишние зависимости-объекты, использование эффекта там, где нужно вычисление при рендере или обработчик события.

**useLayoutEffect** — синхронно после мутаций DOM до отрисовки: измерения, позиционирование (тултипы) — иначе мигание.

**useRef** — мутабельный контейнер, не вызывающий ререндер: DOM-узлы, таймеры, «предыдущее значение», обход stale closure.

**useState: функциональный апдейт** `setCount(c => c + 1)` — когда новое значение зависит от старого (батчинг, замыкания).

**Кастомные хуки** — переиспользование логики со стейтом; каждый вызов — изолированный стейт. Уметь написать `useDebounce`, `useLocalStorage`, `useIntersectionObserver` (см. лайвкодинг).

**useSyncExternalStore** — подписка на внешние сторы без tearing в конкурентном режиме (так внутри устроены Redux/Zustand).

## Контекст и стейт-менеджмент

Context — механизм прокидывания без пропс-дриллинга, не стейт-менеджер: при изменении value ререндерятся **все** потребители. Оптимизации: разделять контексты (data vs api), мемоизировать value.

Сеньорский ответ про выбор стейт-менеджера — сначала классификация стейта:
- **Серверный стейт** (данные с API) → TanStack Query / SWR / RSC: кеширование, инвалидация, дедупликация, refetch. Хранить его в Redux — антипаттерн.
- **Клиентский глобальный** (тема, корзина, авторизация) → Zustand (просто, селекторы, мало бойлерплейта) / Redux Toolkit (большие команды, строгие конвенции, DevTools).
- **Локальный** → useState/useReducer. **URL — тоже стейт** (фильтры, пагинация — в query params).

## Формы, ошибки, порталы

- Controlled vs uncontrolled: контролируемые — значение в стейте (валидация на лету); неконтролируемые — DOM + ref (меньше ререндеров). React Hook Form — производительность через неконтролируемость.
- Error Boundary — классовый компонент (`componentDidCatch`/`getDerivedStateFromError`) или react-error-boundary; не ловит ошибки в обработчиках событий и асинхронном коде.
- `createPortal` — рендер вне DOM-иерархии родителя (модалки, тултипы); события всплывают по React-дереву.

## Server Components и Next.js

**RSC (React Server Components)**: компоненты, выполняющиеся только на сервере — их код не попадает в бандл, могут напрямую ходить в БД/API, async/await прямо в компоненте. Не имеют стейта и эффектов. `'use client'` — граница: этот модуль и его импорты попадают в клиентский бандл. Серверные могут рендерить клиентские (и передавать RSC в children клиентских), сериализуемые пропсы через границу.

**SSR vs SSG vs ISR vs CSR** (уметь выбирать):
- CSR — рендер в браузере: дешёво, но пустой HTML (SEO, медленный первый экран).
- SSR — HTML на каждый запрос: свежие данные, SEO; дороже, TTFB зависит от бэка.
- SSG — HTML на билде: максимально быстро/дёшево; для статики.
- ISR — SSG + фоновая регенерация по таймауту/по требованию (revalidate): компромисс для каталогов, блогов.

**Гидратация** — навешивание обработчиков и восстановление стейта на серверный HTML. Проблемы: hydration mismatch (Date.now, random, локаль — рендерить такое после маунта), TTI позже FCP. **Streaming SSR + Suspense** — отдавать HTML по частям, селективная гидратация по приоритету взаимодействия.

**App Router**: файловая маршрутизация (`layout.tsx` — сохраняется между навигациями, `page.tsx`, `loading.tsx` — автоматический Suspense, `error.tsx` — error boundary). Кеширование в Next 14/15 — многоуровневое: Request Memoization (дедупликация fetch в одном рендере), Data Cache (`fetch` с `revalidate`/тегами, `revalidateTag`), Full Route Cache, Router Cache на клиенте. **Server Actions** — мутации без ручных API-роутов (`'use server'`), прогрессивное улучшение форм.
